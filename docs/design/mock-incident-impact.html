Grammar of the line. It starts with the impact phrase — "Major impact", "Impact not specified" — the spec's <impact>, so the line reads as a sentence and never prints a bare "None" (D-10). The service name is the snapshot name; it is a link only while service_id is set (§4.6), and when it is not, "(deleted)" says why the one name that is not a link is not one (D-12) — the header has no subject chip for such an incident, so this line is the only place that still names the service. The frozen mapping is printed on the service form as a second, mono line, because the owner's condition on D7 is that the frozen mapping be visible on the incident page; the §4.6 line alone names only the current state (D-11). "project default" links to Settings → Incidents (D-13). "basis unavailable" wears the dashed border of the page's existing "impact links unavailable" chip, so a failed read does not look like a fact (D-14). The basis is never on the public page, in the list, in mail, feeds or webhooks (D15, I11).

Two strings, one rule. Where impact stands alone as a label (pill, badge, option), it is Not specified. Where impact is named as a phrase (headings, the past-row tail, the selected badge, the basis line, the page headline that already does this), it is Impact not specified. Both come from lib/incident.ts, so no view composes "<label> impact" by hand any more — the composition is exactly what produced "None impact". Not covered here, on purpose: the words none → minor inside the server's own note (§3a; D-18) and the stored word in mail and feeds (§6).

6 · What does not change, though impact is visible there

named, so the absence reads as a decision.
  • Incident list, right-hand panel (IncidentsView.vue) — shows the impact badge (§4, row 6) but no basis line: it is fed by the list, which does not carry the basis (D15, D19). "Manage →" leads to the incident page, where the line is.
  • No impact control anywhere on an existing incident — not on the incident page, not in the list's quick status buttons, not in "Post an update", for any role (D3, D17). The impact badge stays a badge.
  • Subscriber mail prints the stored word (Impact: none) and keeps today's subject [<status>] <title>; only a rise to critical is mailed, with the §4.5 template. Mail is not SPA; I13 does not apply (§4.6).
  • Feeds (RSS / Atom / JSON) print status: investigating · impact: none — read by programs, unchanged.
  • Webhooks — the incident object carries the new impact; a rise adds impact_raised; never the basis.
  • Public page headline and band — already say "Impact not specified" and already rank none below minor; no code change.
  • Service page, monitor page, dashboard — show no incident impact today and gain none. The service page's open-incident link stays a link.
  • Instance Settings → Monitor defaults — gains nothing: the default is per project (D4), in the project's Incidents tab.
  • The impact-link chips (🕸 probable root / affected) on the incident page — a different "impact" (the dependency graph), untouched; the basis line sits above them.

7 · Decisions for the owner — all eighteen approved as drawn, 2026-11-16

every place where this mock chose between options. One decision per item, with the alternative not taken. Items D-15 and D-18 are not wording choices but things the mock ran into.
  1. The eight none strings (§4): Not specified where impact is a standalone label (count pill, both badges, the selector option); Impact not specified where it is a phrase (group heading, selected-incident badge, basis line); impact not specified in the past-row tail. one word everywhere, "Unspecified" — shorter in the operator list, but it reads like a missing value rather than a statement, and the headline already says "Impact not specified".
  2. Selector order in Service → Alerting: down · degraded · unknown, the order of the "Pages for" row above it. degraded · down · unknown, the key order of the spec, the API and the audit segment.
  3. The hint under the selectors (always shown): "The impact this service's incident opens with, by the state that opened it. While the incident is open it rises to the value of any worse state the service reaches, and never falls. A change applies from the next incident; an open incident keeps the values it opened with." a shorter hint behind an ⓘ tooltip — less text on a busy card, but the rule "only rises, and an edit does not touch an open incident" is the one an operator most needs to see before saving.
  4. Inert presentation: the state name struck through, the select's border dashed, the select still enabled, plus one sentence under the row naming every inert state ("… do not page, so they never open or raise an incident. Their values are kept, and apply once they page."). It follows the draft, not the saved row. a hint under each selector — repeats itself twice in the default configuration, where two of three are inert; or follow only the saved row, which would contradict the toggles the operator just clicked.
  5. The default case is mostly inert: a service on today's paging (page_on = {down}) shows two of three selectors inert (§1b). Kept as is — that is the truth of the default. hide inert selectors until their state pages — tidier, but the operator could no longer prepare a value before turning paging on, which §4.1 allows.
  6. Selector option words: Not specified · Minor · Major · Critical in the service editor and the project tab, the same words as the badges. the enum words none · minor · major · critical in mono, matching the MaC key — but then the editor alone would print "none" (I13).
  7. The degraded > down warning: an amber notice under the row (the forms' existing degraded notice), the degraded select's border tinted, shown whenever the draft has it — even when degraded is inert — and never blocking Save. Text: "Degraded is rated above down (Critical against Major). That is allowed, but an incident that opens on down will be published as less severe than one that opens on degraded." a red border with a refusal-style message (it is not a refusal, §4.1), or showing it only when both states page.
  8. Tab name and field label: tab Incidents, card title Incidents, field Impact of monitor incidents — leaves room for later incident settings in the same tab. tab Incident impact — more exact today, but a tab per field is how the nav grew to ten entries.
  9. The project tab's explanation and read-only form: "The impact a monitor's automatic incident opens with. It is shown on status pages and in incident lists, and it does not change while the incident is open. Changing it here does not touch incidents that are already open — it applies from the next one. Incidents a service opens take their impact from that service's alerting settings instead." Read-only shows the value as the impact badge and "Only a project admin can change this." a disabled select for readers, as the instance Monitor-defaults card would; and no sentence about services (shorter, but the commonest question will be "why is my service incident not using this?").
  10. Where the basis line goes: its own row under the header's meta row, starting with the impact phrase ("Major impact — declared by …"). a span inside the meta row (wraps unpredictably beside "acknowledged by …"), or a tooltip on the impact badge (hidden; the owner's D7 condition is that the basis be visible).
  11. The frozen mapping is printed on the service form, as a second mono line: "mapping frozen at open: down → major · degraded → minor · unknown → not specified". the §4.6 line alone, the mapping only in the API — but D7's condition says the frozen mapping must be visible on the incident page (see the report: §4.6's table does not include it).
  12. A deleted service: the snapshot name as text, followed by a muted "(deleted)". the name alone — exactly the §4.6 text; the reader is left to guess why the one service name that is not a link is not one.
  13. "project default" is a link to Settings → Incidents. plain text — the spec's string, no navigation; the reader has to know where the setting lives.
  14. "basis unavailable" in a dashed outline, the "impact links unavailable" chip's grammar, text unchanged. plain ink-3 like the other forms — a failed read then looks like one more fact.
  15. Found, not chosen: ServiceAlerting.vue uses colour classes that no token defines (text-ok, bg-ok/10, border-ok, text-warn, text-bad) — absent from the compiled CSS, so a selected "Pages for" toggle differs from an unselected one only by ink against ink-3, and the "pages for no state" warning and save errors are uncoloured. The new inert state reads off those toggles. Proposed: fix them to up / degraded / down in the FR-042 change to this file. leave them for a separate fix; the mock then shows the toggles exactly as in §1.
  16. The operator list's badge row wraps (flex-wrap on that row), so "NOT SPECIFIED" and a subject chip fit the 320 px card (§4 row 5). shorten the badge in this one place ("N/S", "UNSPEC.") — saves the wrap, costs a word nobody can read; or drop the subject chip when it would not fit.
  17. The "Impact raised" note uses the status dot like the other system notes, no new gutter glyph. an ⬆ glyph in the gutter, as the changes note has its own — but that glyph exists because it links to a deploy, and this note links to nothing.
  18. The note's enum words on the public page: found, not chosen. §4.3 fixes the body as "⬆ Impact raised: <from> → <to> …" with the stored words, and the note is public, so a visitor reads "none → minor" — the only place the SPA would still print the bare word after FR-042. Shown here as specified. change §4.3 to the display words ("Impact raised: not specified → minor …"), which changes the server string, its idempotency-free rise test and the subscriber mail body — a spec change, not a mock change, and not made here.
