Design mock · monitor description · draft for the owner's eyes · 2026-09-03

A monitor says what it is for, not only what it is called

Someone who did not create payments-callback cannot tell from the name whether it guards a customer-facing flow or a nightly reconciliation. One optional sentence, written once, shown wherever the monitor is listed. Nothing about existing monitors changes: the field is empty for every one of them and every surface renders exactly as today when it is empty.

Fielddescriptionoptional · plain text · one string, no markup
Limit200 characterscounted as characters, the same way on the form and on the server; a longer value is refused at the field, never truncated silently
Defaultemptystored NOT NULL DEFAULT ''; an API body or a bundle that omits it means "no description" — old clients and old bundles stay valid unchanged

Rules on this surface. The refusal is met at the field, as every refusal in this form is: the count turns --down, the message says what to do, and Create/Save stays disabled until it fits. The server enforces the same 200 and the same counting, so a client that bypasses the form gets a 400 that names the field. Long-form operational text (what to do when it is down) belongs in a runbook link or an incident template, not here — the limit is what keeps a description a description.

5 · Monitoring-as-Code new

the monitor block in a bundle — one optional key; a bundle without it is unchanged and still applies cleanly.
monitors:
  - slug: payments-callback
    name: payments-callback
    description: Confirms the payment provider can reach our callback URL; a DOWN here means paid orders stay "pending".
    type: http
    target: https://api.example.internal/callbacks/ps
    interval_seconds: 60
Compatibility. A bundle that omits description declares "no description" — the same as today. Re-applying such a bundle over a monitor whose description was set in the UI clears it, exactly as every other bundle-owned field behaves: the bundle is the source of truth for the monitors it declares. That is the existing rule, stated here so it is not a surprise.

6 · Where it deliberately does NOT appear

named, so the absence reads as a decision and not an oversight.
  • Public status pages. A description is written for the team ("reports read from this replica") and may name internal hosts or partners. Status-page components keep their own public wording.
  • Alerts, notifications, incident text. Payloads and templates are unchanged in this release; adding the description to a DOWN notification is a reasonable follow-up, but it changes what every channel sends and deserves its own look.
  • Search results. Search keeps matching on the name. Matching on the description too is cheap and can be switched on later; not included unless you want it now.
  • Service pages and incident subject chips. They show the monitor name as a link; the description is one click away on the monitor page.
