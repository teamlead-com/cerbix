What this mock decides, so the implementation invents nothing.
  • An objective is per WINDOW, and only the window that has one shows numbers. A window with no objective shows a dash, never a borrowed one from 30d — a budget is meaningless without the promise it was measured against.
  • The Burn column stays a dash at project scope, always, and there is NO burn switch and no disabled control. A disabled control says "not yet"; an absent one says "not here". Paging at project scope needs an arming rule, a routing answer and close semantics, and until those exist the database itself refuses the row (sla_targets_project_no_burn_chk).
  • The existing mean card is kept and labelled — "mean across SLO monitors" beside "Project objective". Two numbers that could be confused for each other must each say which question it answers.
  • Rejection happens before the request, with the server's own rule mirrored client-side (lib/objective.ts, D-0165): the open interval (0,100), four decimals, half-up. The operator sees why, not a 400.
  • Clear is explicit. Removing the objective removes the budget with it, and the row goes back to dashes rather than to 100%.
  • Not shown, on purpose: a project-level burn history, and any per-monitor breakdown of the project budget. The first cannot exist without paging semantics; the second is the table below this panel, which already exists.
