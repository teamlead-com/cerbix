Design mock · recovery threshold · FR-043 / NFR-036 · APPROVED by the owner 2026-11-16

A monitor leaves DOWN only after a confirmed run of successes

Mock for docs/specs/func-recovery-threshold.md §8 (revision 5, approved 2026-11-15). One new number on the form, one warning, one hint, one label for a monitor that is down but has started answering, and one row on the monitor page. Every monitor that exists today has recovery_threshold = 1 and renders exactly as it does now. Two placement questions the spec leaves to the mock were drawn as variants; the owner chose on 2026-11-16 (§4: the chip, variant 2; §5: both labels, variant 1) and the rejected variants are kept, dimmed and marked, as the record of what was compared. The owner also narrowed the dependency hint (§3) — recorded in the spec, §8 and §11.

Fieldrecovery_thresholdinteger · consecutive successful checks a down monitor needs before it is declared up
Range · default1 … 10 · 11 is today's behaviour exactly: the first success recovers
Typesall but push, compositepush and composite must be 1 (D8); the form neither shows nor sends the field for them
Read modelconsecutive_successesnon-zero only while down; drives "recovering N/M", as fresh as the last page load (D13)

1 · Monitor form, Schedule card new field

routes /monitors/new, /monitors/:id/edit · frontend/src/views/NewMonitorView.vue, the schedTitle card. Today it is two rows of three: Interval · Timeout · Retries, then Confirmations · Confirm interval · Re-notify. The new field opens a third row, directly under Confirmations.

Schedule

http form the field is present for every type with an active check
push form "Heartbeat" card — unchanged, no field
composite form "Re-evaluate every" only — unchanged, no field
Why under Confirmations and not beside it. Confirmations and Confirm interval are already coupled (the interval is dimmed until Confirmations > 1); wedging a field between them would split that pair. Under it, the two hysteresis counts share a column — the way down above, the way up below — and the units read as a pair: fail / ok. Name. The form calls the down-side count "Confirmations" while the monitor page calls it "Failure threshold"; the new field uses the spec's name, "Recovery threshold", on both surfaces, because "Confirmations" for the way up would collide with the confirm phase, which only ever accelerates the way down (D4). What is sent. For push and composite the form sends no recovery_threshold at all, whatever the field held before the type was switched (a hidden 3 would be a 400 under D8). In a multi-region set the regional children receive the form's value and the composite parent receives none.

2 · Long-soak warning new

shown under the field when interval_seconds × (recovery_threshold − 1) ≥ 600. It states the delay, not a refusal: the value is valid and saves. Checks are not accelerated during a run (D4), so the delay is exactly that product.
below the boundary 60 s × (3 − 1) = 120 s — no warning
at the boundary 300 s × (3 − 1) = 600 s — warning
IntervalThresholdInterval × (M − 1)What the field shows
Every row above is derived, not typed. One function in the script builds the warning text and every cell of the table from the two inputs, the way the form will: soak = interval × (M − 1), warn when soak ≥ 600, durations written in the largest whole units (h, min, s). The highlighted rows sit on the boundary. Note the second row: a 60 s monitor can never reach the warning, because the threshold stops at 10 (9 × 60 s = 9 min). "About" is honest: the first success lands somewhere in its own interval and the result still has to be ingested.

3 · Dependency hint new

shown under the field when the monitor has a parent (depends_on non-empty and recovery_threshold > 1 — owner's decision 2026-11-16, spec §8; the "Depends on" picker in the alerting card further down the same form). It explains spec §4.4: a parent at a lower threshold leaves down first, and with it the suppression of this monitor's alerts.
schedule card threshold 3, one parent
This monitor depends on other monitors. A parent with a lower recovery threshold recovers first — and from that moment stops suppressing this monitor's alerts, even while this monitor is still down.
alerting card · existing where the parent is chosen
Depends on 1
orders-db ✕
Rules (approved 2026-11-16). Shown when depends_on is non-empty and the field is above 1. At 1 no parent can have a lower threshold, so the sentence could never apply and would only be noise on every dependent monitor that exists today; it appears as the field goes from 1 to 2 and disappears when it goes back. The hint does not compare thresholds per parent: the form's dependency picker lists names and statuses only, and the rule is one sentence that holds for every parent. Both the warning and the hint can be shown together; the warning comes first because it is about this monitor alone. Neither appears for push or composite, where the field is absent.

Approved by the owner 2026-11-16: variant 2, the chip. (1) The monitor is down — notifications, the auto-incident, composites and dependency suppression all still treat it as down — and the pill is the one word on the row that says so. Today's "Confirming" may replace its pill's word because it changes the colour too: amber says "not settled", and the word it hides ("Operational") would over-claim. A red pill reading "Recovering" hides the right word and carries two opposite messages; anyone scanning the column for "Down" misses it. (2) The Status cell already has a chip row for qualifiers of a down monitor — "⏸ suppressed by …", "quorum M/N" — in this exact shape; the run is one more qualifier and composes with them (row 3). (3) The monitor page already follows the same rule in code: "a delegated monitor keeps its real pill — DOWN reads as DOWN — and gains a chip" (FR-021 §16.1). Wording: lower case, "recovering 2/3", like its neighbours "suppressed by …" and "quorum 2/3"; no ellipsis (the run waits on the next scheduled check, not on something in progress on screen); no green and no "OK", which would announce a recovery that has not been confirmed. Cost: the cell then uses two mechanisms — confirming overrides the pill, recovering adds a chip. That asymmetry is real, not accidental: one sits on an up monitor whose pill word would over-claim, the other on a down monitor whose pill word is exactly right.

7 · How fresh the label is (D13)

the same limit "Confirming N/M…" has today, stated so it is not mistaken for a live counter.
  • As of the last load. The run advances without a status change, and nothing is published without a status change, so neither the list nor the page header moves the count by itself. The tooltip ends "As of page load." — the only place the mock spends words on it; a visible timestamp would imply a freshness the page does not have.
  • A live transition clears it (owner's decision 2026-11-16, stage 2, covered by a frontend unit test: applying a live status event sets consecutive_successes to 0, and a move into up sets consecutive_failures to 0 as well). The monitor page applies live status events to the loaded monitor. Every transition resets the run (into up on confirmation, into down with the counter at 0), so the page must zero consecutive_successes — and consecutive_failures on a move into up — when it applies one. Otherwise a monitor loaded mid-run that then goes up and down again would show the stale "recovering 2/3" from the first run.
  • What the label never does. It never turns green, never appears on an up or pending monitor, and never hides the Down pill. When the run completes the monitor is up and the label is gone with the pill change.

8 · What this mock does not change

named, so the absence reads as a decision.
  • Dashboard panels (MonitorCard.vue) do not show "Confirming" today and do not gain "recovering". §8 names the list and the monitor page only.
  • Status pages. A monitor component stays major_outage until the recovery is confirmed; its 90-day bar already shows the successes, because it is computed from checks (§4.4). No public wording changes.
  • Service pages. A service is measured from checks and can be green while its member monitor is still red — by design (§4.4). No label is added there.
  • Test connection. The probe-only test body refuses recovery_threshold as an unknown field (§4.5); the form's "Test" action never sends it.
  • Instance defaults (Settings → Monitor defaults) gain no recovery threshold (D12).
