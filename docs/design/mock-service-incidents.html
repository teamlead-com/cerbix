FR-022 — only what changes in the SPA

Four surfaces gain something; nothing else moves. Each panel below shows the DELTA and says where it lives, so the implementation has no room to invent a fifth. A monitor incident renders exactly as it does today — that is NFR-017, and it is the reason these panels are deltas rather than redesigns.

1 · The incident says what it is an incident OF

IncidentDetailView

🕸 probable root · payments affected · storefront

Unchanged for a monitor incident: the same header, the same timeline, the same acknowledge and resolve controls. The only new element is the SUBJECT chip — a monitor incident keeps its monitor chip, a project-level one keeps none.

What this mock decides.
  • The subject is a CHIP, not a column or a title prefix. Chips are how phases 4 and 5 already say "this row is a different KIND of thing"; a new column would reshape every existing row, and a prefix would put the discriminator inside text people search.
  • A monitor incident is untouched, visibly. Every panel shows the monitor case beside the service case for exactly that reason — NFR-017 is a promise the UI has to keep too.
  • "opened automatically" is stated, with what confirmed it. An operator who finds an incident nobody typed must be able to see the machine that opened it and why: "service DOWN confirmed over 2 evaluations", the same number that governs paging.
  • Impact chips appear only on the authenticated detail — they already do for monitors (§14), and this keeps that boundary rather than adding a public one.
  • The service page links, it does not embed. One timeline, one owner.
  • Not shown, and not built: a resolve-all control, per-member severity, or any escalation progress on a service incident (D5 defers the ladder). A control for a feature that does not exist is a promise the backend refuses.
