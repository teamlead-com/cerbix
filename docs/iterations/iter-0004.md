# iter-0004 — Monitors and the checking pipeline

## 1. Summary

cerbix now performs monitoring. Added monitor and heartbeat domain/store, HTTP and TCP
probers with a declarative condition engine, the dispatcher seam (in-process
implementation), a leader-elected scheduler, a worker pool, and result ingestion — plus a
monitor REST API with authz/isolation. Verified end-to-end with the real binary: a
`--role=all` process drove a seeded monitor to `up`, recording heartbeats and
`cerbix_checks_total`. Closes FR-007 and FR-008. Also added FR-015/NFR-010 (default local
login) to the spec per request, scheduled for a later iteration (D-0013).

## Role-rule / self-healing / dedup checklist

- Rule residence: monitor invariants → `domain`; check policy (timeout/retries/conditions)
  → `prober` (`application`-ish); scheduling/ingestion → `application`; persistence + lock
  → `infra`; request shape → `transport` (`api`).
- Duplicate checks: monitor type/status validity in `domain` + SQL `CHECK` (defensive) —
  domain is the source.
- Runtime self-healing: **no** — probes fail to `down` heartbeats; scheduler standby retries
  without duplicating leadership; no config fallback.
- Regression coverage: condition engine, prober outcomes, leader mutual-exclusion, and the
  full pipeline are covered.
- Conclusions transferred to canonical docs before artifact removal: yes.
