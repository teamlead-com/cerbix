# iter-0011 — FR-012 phase 1: incidents, timeline updates, postmortems (GUI + API)

## 1. Summary

Started FR-012 with the **incidents core**: a project-scoped incident with a lifecycle
(`investigating → identified → monitoring → resolved`, resolved terminal), a chronological
timeline of updates that advance the status, and a postmortem gated on resolution. Everything
is postable through the GUI **and** direct API calls, tenant-isolated, and enforced by the
existing editor+/viewer role matrix. Verified with hermetic handler/domain tests, a DB-gated
store test, and a real-binary API lifecycle e2e. Status pages, subscribers, feeds, webhooks,
api-tokens, and auto-incident-from-monitor are deferred to phase 2 (iter-0012).

- `docs/project-description.md` FR-012, plan §"Status pages and incident communication".
- Conventions from iter-0002/0004/0006 (domain → store → api → e2e), incidents mockup `d5baac16`.

## 3. What changed (by role)

### Agent A — Implementation
- **Domain** (`internal/domain/incident.go`): `Incident`, `IncidentUpdate`, `Postmortem`;
  enums `IncidentStatus` (with `Terminal()`), `IncidentImpact`, `IncidentSource`, each with
  `Valid()`; `Validate()` invariants. `ResolvedAt *time.Time` (nullable).
- **Migration** `00006_incidents.sql`: `incidents`, `incident_updates`, `postmortems` with
  CHECK-constrained status/impact/source enums, FKs `ON DELETE CASCADE`, indexes; `postmortems`
  unique per incident. `TruncateAll` extended.
- **Store** (`internal/store/incidents.go`): `CreateIncident` (incident + opening update in one
  tx), `GetIncident`, `ListIncidentsByProject`, `AddIncidentUpdate` (insert + status sync +
  first-resolve `resolved_at` stamp in one tx), `ListIncidentUpdates`, `UpsertPostmortem`,
  `GetPostmortem`.
- **API** (`internal/api/handlers_incidents.go` + routes): list/create incidents, get incident,
  list/add updates, get/put postmortem. `incidentAccess` mirrors `monitorAccess`
  (→ `projectAccess`), so isolation and role checks are reused. Writes require
  `ActionProjectWrite`, reads `ActionProjectRead`. Source server-set `manual`; resolved
  incidents reject updates (400); postmortem requires resolved (400).
- **Metrics**: `cerbix_incidents_opened_total`, via a nil-safe `api.Metrics` recorder
  (`Handler.WithMetrics`, wired in `cli.go`).
- **Contract** (`openapi.yaml`, → 0.7.0): `incidents` tag, 7 paths, `Incident`/`IncidentUpdate`/
  `Postmortem`/`CreateIncident`/`AddIncidentUpdate`/`PutPostmortem` schemas. Frontend types
  regenerated from it (`schema.d.ts`), `vue-tsc` still green.

### Agent B — Tests / verification
- **Hermetic**: `domain/incident_test.go` (enums/terminal/validate), `api/api_incidents_test.go`
  (list, isolation 404, create authz 404/403/201 + 400s, update lifecycle incl. terminal-400,
  list updates, postmortem-requires-resolved + 404-when-absent). fakeStore extended.
- **DB-gated**: `store_integration_test.go::TestIncidentLifecyclePersistence` — create (opening
  update present), advance, resolve (status synced + `resolved_at` stamped, timeline = 3),
  postmortem upsert-replace + read-back, project isolation, `ErrNotFound`.
- **Suite**: `go build`, `go vet`, `gofmt` clean; `go test -cover ./...` green with a real
  Postgres — `internal/api` 75.3%, `internal/store` 79.5%, `internal/domain` 89.3%,
  `internal/metrics` 86.2% (all ≥70% gate).
- **Real-binary e2e** (compiled image + Postgres, local login): create incident (`manual`,
  `resolved_at` null) → update `identified` → `resolved` (`resolved_at` stamped) → timeline of
  3 in order → update-after-resolve `400` → `PUT` postmortem `200` (author set) → list = 1 →
  `cerbix_incidents_opened_total 1` → no-cookie create `401`.
