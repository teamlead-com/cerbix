# iter-0012 — FR-012 phase 2a: status pages, components, public rendering

## 1. Summary

Added **status pages + components + rendering**. Org-scoped pages (optionally project-narrowed)
at three visibilities (`public` / `internal` / `unlisted`); components bound to a monitor (status
derived) or driven manually; and a **public, unauthenticated render** endpoint that assembles a
worst-of summary, per-component status + 90-day uptime, and active incidents — gated by
visibility (public served, unlisted requires a token, internal hidden). Verified with hermetic
domain/handler tests, a DB-gated store test, and a real-binary e2e. FR-012 stays IN_PROGRESS
(phase 2a); subscribers/webhooks/feeds, api-tokens, and auto-incident remain phase 2b (iter-0013).

## Role-rule / self-healing / dedup checklist

- Rule residence: page/component invariants and status derivation in `domain`; persistence in
  `store`; management authz + visibility gate in `api`. Contract single-sourced in `openapi.yaml`
  (frontend types generated).
- Runtime self-healing: none — invalid visibility/manual-status → 400; hidden pages → 404; render
  propagates DB errors (only a monitor removed via `SET NULL` is tolerated as manual/unknown).
- Duplicate checks: `statusPageAccess` centralises page load + membership; component status is
  derived at render time (not duplicated onto the row); monitor-in-org guard reuses
  `GetMonitor`+`GetProject`.
- Conclusions transferred to canonical docs before artifact removal: yes.
