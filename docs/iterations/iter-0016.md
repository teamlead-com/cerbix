# iter-0016 — FR-012 phase 2b-iv: outbound webhooks (signed, async, incident lifecycle)

## 1. Summary

Incidents now notify the outside world. A single incident-event sink fans every lifecycle change
(`opened` / `updated` / `resolved`) — from both the API handlers and the auto-incident pipeline —
out to matching webhook subscriptions as an HMAC-signed JSON POST, delivered asynchronously and
best-effort. Webhooks are org/project-scoped and managed by org admins. Verified with hermetic
domain/dispatcher/api/ingest tests, a DB-gated store test, and a real-binary e2e that signs and
delivers to a live receiver. FR-012 stays IN_PROGRESS; KC client-credentials and the Vue views remain.

## 2. Input artifacts

- iter-0011 incidents, iter-0014 auto-incidents; plan §"outbound webhooks", verification
  §"a webhook fires on every incident change".

## 3. What changed (by role)

### Agent A — Implementation
- **Domain**: `Webhook` (org/project scope, url, secret, enabled) + `Validate` (http(s) url);
  `IncidentEvent` + event-type constants (`incident.opened|updated|resolved`).
- **Migration** `00010_webhooks.sql`: `webhooks` (org/project cascade, enabled); `TruncateAll` extended.
- **Store**: webhook CRUD + `ListEnabledWebhooksForProject` (a project's own hooks + org-wide hooks).
- **`internal/webhook`**: `Sign` (HMAC-SHA256 → `sha256=<hex>`); `Dispatcher` — non-blocking
  `IncidentEvent` enqueue (drops with a log when full), a `Run` worker that loads applicable webhooks
  and POSTs the signed body (`X-Cerbix-Signature`, `X-Cerbix-Event`) with a per-request timeout;
  failures/non-2xx logged, never propagated.
- **API**: a nil-safe `IncidentSink` (`WithIncidentSink`), emitted on incident create (`opened`) and
  update (`updated`/`resolved`); webhook management handlers (create returns the secret once, list
  strips secrets, delete) — all org-admin, with a project-in-org guard.
- **Ingest**: `SetIncidentSink`; the auto-incident path emits `opened`/`resolved`.
- **Wiring** (`cli.go`): one `webhook.Dispatcher` built when a DB is present, `Run` in a goroutine,
  attached to both the API handler and the ingest consumer.
- **Contract** (`openapi.yaml` → 0.11.0): `webhooks` tag, paths, `Webhook`/`CreateWebhook` schemas.
  Frontend types regenerated, `vue-tsc` green.

### Agent B — Tests / verification
- **Hermetic**: `domain/webhook_test.go` (validate); `webhook/webhook_test.go` (deterministic sign;
  delivery via httptest asserts signature + event header + body; failure tolerance for store error,
  non-2xx, malformed URL; queue-full drop is non-blocking); `api/api_webhooks_test.go` (mgmt authz,
  secret-once, secret-stripped listing, bad-url 400, delete authz; **incident create/resolve emit the
  right events** via a fake sink); `ingest/ingest_test.go` (auto-incident emits opened + resolved).
- **DB-gated**: `store_integration_test.go::TestWebhookScopeSelection` — a project sees its own +
  org-wide enabled hooks, not another project's nor disabled ones; delete.
- **Suite**: `go build`, `go vet`, `gofmt` clean; `go test -cover ./...` green with real Postgres —
  `internal/webhook` 90.0%, `internal/api` 73.1%, `internal/ingest` 76.3%, `internal/store` 76.7%,
  `internal/domain` 91.0% (all ≥70%); every package OK.
- **Real-binary e2e** (image + Postgres + a Python receiver, `--role=all`): register an org-wide
  webhook (secret returned once) → open a manual incident, resolve it, and trigger an auto-incident
  (a monitor to a dead target) → the receiver logs **three signed deliveries**: `incident.opened`
  (source manual), `incident.resolved` (manual), `incident.opened` (**source auto**); the first
  delivery's `X-Cerbix-Signature` verifies (HMAC-SHA256 of the body under the returned secret).

## Role-rule / self-healing / dedup checklist

- Rule residence: webhook invariants and the event shape in `domain`; persistence + scope query in
  `store`; signing + async delivery in `internal/webhook`; management authz in `api`. One sink
  interface serves both producers (API + ingest); no duplicated delivery path.
- Runtime self-healing: none masking correctness — enqueue is non-blocking by design (drops logged),
  delivery failures/non-2xx are logged and not retried this iteration (a retry/backoff log is future
  work), and a webhook failure never affects the incident write.
- Duplicate checks: signing lives once (`webhook.Sign`); applicable-hook selection lives once
  (`ListEnabledWebhooksForProject`); the emit helper is shared shape across API and ingest.
- Conclusions transferred to canonical docs before artifact removal: yes.
