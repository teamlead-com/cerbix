# iter-0019 — RabbitMQ dispatcher: distributed scheduler / worker / api roles

## 1. Summary

Delivered the founding distributed architecture: the check pipeline can now run as separate
processes coordinating through RabbitMQ, not only in one `--role=all` process. Added a
`dispatch.AMQP` implementation of the existing `Dispatcher` interface (durable job/result queues,
lazy role-natural consumers, prefetch backpressure) and wired role-aware startup in `cli`. Verified
with a real-binary three-process e2e (scheduler + worker + api over the broker) plus a second worker
scaling out; the hermetic suite stays green (the AMQP round-trip test is opt-in). No interface change.

## 2. Input artifacts

- iter-0004 `dispatch.Dispatcher` seam + `inproc`; the plan's architecture (scheduler → RabbitMQ →
  workers → RabbitMQ → ingest), the user's founding "distributed from the start" requirement.

## 3. What changed (by role)

### Agent A — Implementation
- **`dispatch/amqp.go`** (`NewAMQP`): implements `Dispatcher`. Durable `checks.jobs`/`checks.results`;
  `PublishJob`/`PublishResult` publish persistent JSON on a mutex-guarded channel; `Jobs()`/`Results()`
  lazily start a manual-ack consumer (`Qos` prefetch) forwarding onto a buffered Go channel
  (ack-on-enqueue); `Close` cancels consumers and closes the connection. A **bounded startup dial
  retry** (30×1s) tolerates a lagging/booting broker.
- **`cli`**: role-aware pipeline — `--role=all` → in-process dispatcher (dev/tests); `api`/`scheduler`/
  `worker` → AMQP, each running only its part (scheduler publishes jobs, needs a DB; worker
  consumes+probes+publishes, stateless; api ingests results + serves HTTP). Distributed roles
  fail-fast without `rabbitmq.url`; scheduler/api fail-fast without a DB. Replaced the old
  "distributed_role_pipeline_pending" stub.
- **Dependency**: `github.com/rabbitmq/amqp091-go` (`go.mod`/`go.sum`).

### Agent B — Tests / verification
- **Opt-in**: `dispatch/amqp_test.go::TestAMQPRoundTrip` (gated by `CERBIX_TEST_RABBITMQ_URL`) —
  publish job → `Jobs()` receives it; publish result → `Results()` receives it. Skipped in CI, which
  keeps covering the seam via the in-process dispatcher.
- **Suite**: `go build`, `go vet`, `gofmt` clean; `go test ./...` green with real Postgres (20
  packages OK) after the dependency change.
- **Real-binary e2e** (Postgres + RabbitMQ + three cerbix processes on one network): start
  `--role=api` (migrates, serves), `--role=scheduler` (acquires the advisory-lock leader), and
  `--role=worker`; create a monitor via the API → its status goes **up** — the check flowed
  `scheduler →[checks.jobs]→ worker →[checks.results]→ api-ingest` across three processes (heartbeats
  code 200, 30d SLA 4/4). A **second worker** joined the broker and throughput continued (SLA 6/6),
  demonstrating horizontal scale with prefetch sharing.

### Agent C — Docs
- `docs/decisions.md` (D-0026), `docs/traceability.md` (distributed-dispatch row), `docs/status.md`,
  this report.

### Agent D — Ops
- Config already carried `rabbitmq.url`; `deploy/docker-compose.yml` already runs RabbitMQ. Startup
  retries make role boot order forgiving. Ops note: in some sandboxes the RabbitMQ container needs a
  writable `HOME` for its Erlang cookie (`-e HOME=/tmp`). All build/test/e2e in Docker.

## Role-rule / self-healing / dedup checklist

- Rule residence: transport in `dispatch` (AMQP alongside inproc, one interface); role orchestration
  in `cli`; no business logic moved. The scheduler/worker/ingest components are unchanged — they
  depend only on the `Dispatcher` seam.
- Runtime self-healing: distributed roles fail-fast on missing broker URL / DB; the only retry is a
  bounded startup dial (connection establishment for a booting dependency), which is not config
  self-healing. Ack-on-enqueue is a documented at-most-once tradeoff, not silent masking.
- Duplicate checks: one `Dispatcher` interface, two implementations; publish path shared across
  job/result; role wiring centralised in one `switch`.
- Conclusions transferred to canonical docs before artifact removal: yes.
