# iter-0020 — FR-010 notifications: per-monitor channels fired on transition

## 1. Summary

Monitors now alert on status change. A project can define notification channels (webhook / Slack /
Telegram) and link them to monitors; when a monitor transitions down (or recovers) the ingest
pipeline sends a formatted message to each linked enabled channel via an async best-effort
dispatcher. Verified with hermetic domain/notify/api/ingest tests, a DB-gated store test, and a
real-binary e2e (a monitor to a toggleable target fires 🔴 DOWN then 🟢 recovered to a webhook
receiver). FR-010 IN_PROGRESS — the three HTTP channel types ship; email/SMTP is deferred.

## 2. Input artifacts

- iter-0014 auto-incident transition seam (`reconcileTransition`), iter-0016 webhook async pattern;
  plan §"Notifications: pluggable Notifier (Telegram/Slack/Email/webhook)".

## 3. What changed (by role)

### Agent A — Implementation
- **Domain**: `NotificationChannel` (project-scoped, `type` webhook/slack/telegram, JSONB `config`,
  enabled) + type-specific `Validate` (webhook/slack need `config.url`; telegram needs
  `bot_token`+`chat_id`).
- **Migration** `00011_notifications.sql`: `notification_channels` (+ CHECK type) and a
  `monitor_notifications` join; `TruncateAll` extended.
- **Store**: channel CRUD, `Link`/`UnlinkMonitorChannel`, `ListChannelsByProject`,
  `ListMonitorChannels`, `ListEnabledChannelsForMonitor` (the delivery targets).
- **`internal/notify`**: a pure `render(channel, monitor, up)` → (url, body, content-type) per type
  (webhook structured JSON, Slack `{text}`, Telegram `sendMessage`) and an async `Dispatcher`
  (non-blocking `MonitorTransition` enqueue → worker loads enabled channels → POST with timeout,
  best-effort). `Message` centralises the 🔴/🟢 text.
- **Ingest**: `reconcileTransition` (renamed from `reconcileAutoIncident`) fetches the monitor once
  and fires **both** the auto-incident and the notifier on `→down`/`down→up`; `SetNotifier` (nil-safe).
- **API**: channel CRUD under a project (create/delete editor+, list viewer+) and monitor↔channel
  link/list/unlink (editor+, channel must be in the monitor's project).
- **Wiring** (`cli.go`): a `notify.Dispatcher` built when a DB is present, `Run` in a goroutine,
  attached to the ingest consumer (all + api roles).
- **Contract** (`openapi.yaml` → 0.12.0): `notifications` tag, channel + link paths,
  `NotificationChannel`/`CreateNotificationChannel` schemas. Frontend types regenerated, `vue-tsc` green.

- **Real-binary e2e** (image + Postgres + a Python receiver + a toggleable nginx target,

## Role-rule / self-healing / dedup checklist

- Rule residence: channel invariants in `domain`; persistence + scope queries in `store`; transport
  (`render` + async POST) in `internal/notify`; transition→notify orchestration in `ingest`;
  management authz in `api`. The transition seam fetches the monitor once for both auto-incident and
  notification.
- Runtime self-healing: none masking correctness — enqueue is non-blocking (drops logged), delivery
  failures/non-2xx are logged and not retried this iteration, and a notification failure never blocks
  ingestion. `pending→up` intentionally does not notify.
- Duplicate checks: one `render` for all three types; enabled-channel selection lives once
  (`ListEnabledChannelsForMonitor`); the async dispatcher shape mirrors `internal/webhook` but with
  its own payloads (no forced shared abstraction).
- Conclusions transferred to canonical docs before artifact removal: yes.
