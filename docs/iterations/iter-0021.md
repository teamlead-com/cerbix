# iter-0021 — Push monitors (dead-man's-switch): token heartbeat + scheduler liveness

## 1. Summary

Added **Push monitors** — the passive dead-man's-switch for cron/batch/backup jobs. A push monitor
gets a secret token and an unauthenticated heartbeat endpoint; the watched service POSTs every
interval, and the scheduler marks the monitor down when a heartbeat is missed. Heartbeats flow
through the same ingest pipeline as active checks, so status, notifications, and auto-incidents all
apply. Verified with hermetic domain/scheduler/api tests, a DB-gated store test, and a real-binary
e2e (push → up → timeout-down → push → up). **ICMP is deferred** (needs privileged raw sockets,
unreliable to test in the sandbox).

## 3. What changed (by role)

### Agent A — Implementation
- **Domain**: `Monitor.PushToken`; `Validate` now requires `interval_seconds > 0` for push monitors
  (the interval is the expected heartbeat window).
- **Migration** `00012_push_token.sql`: `monitors.push_token` (unique where set).
- **Store**: `push_token` in scan/insert; `GetMonitorByPushToken`.
- **Scheduler**: `evaluatePush` — for each enabled push monitor, if it hasn't reported within its
  interval and isn't already down, publish a **down result** (ingest then marks it down and fires
  notifications/incidents); a `nextRun` throttle prevents re-publishing while silent. Push monitors
  are never turned into `CheckJob`s.
- **API**: `createMonitor` issues a `push_token` for push type; an optional `ResultSink`
  (`WithResultSink`) and an **unauthenticated** `POST /api/v1/public/push/{token}` on the
  `PublicRouter` that publishes an up (or `?status=down`) heartbeat into the pipeline.
- **Wiring** (`cli.go`): the API handler is hoisted and given the dispatcher as its `ResultSink` for
  the api/all roles, so the push endpoint feeds the ingest pipeline.
- **Contract** (`openapi.yaml` → 0.13.0): the push path + `Monitor.push_token`. Frontend types
  regenerated, `vue-tsc` green.

### Agent B — Tests / verification
- **Hermetic**: `domain/monitor_test.go` (push requires interval); `scheduler/scheduler_test.go`
  (`TestSchedulerPushLiveness` — a stale push monitor is marked down via a published result, a fresh
  one and an already-down one are not); `api/api_push_test.go` (push records up/down, unknown token
  404, push monitor gets a token). Fakes extended (`GetMonitorByPushToken`, `LatestHeartbeat`,
  `fakeResultSink`).
- **DB-gated**: `store_integration_test.go::TestPushMonitorToken` — token persisted, lookup, unknown
  → ErrNotFound.
- **Suite**: `go build`, `go vet`, `gofmt` clean; `go test -cover ./...` green with real Postgres —
  `internal/domain` 92.2%, `internal/scheduler` 71.2%, `internal/api` 73.1%, `internal/store` 76.9%
  (the AMQP-heavy `dispatch` stays opt-in-tested per D-0026).
- **Real-binary e2e** (image + Postgres, `--role=all`): create a push monitor (interval 5s) → it's
  issued a `push_token`; `POST /api/v1/public/push/{token}` → status **up**; stop pushing → after the
  interval the scheduler marks it **down** (heartbeat "push timeout"); push again → **up**; an unknown
  token → 404.

## Role-rule / self-healing / dedup checklist

- Rule residence: push-token issuance in `api`, liveness policy in `scheduler`, persistence in
  `store`, validation in `domain`. Push heartbeats reuse the single ingest write path (no parallel
  writer) via the `ResultSink`.
- Runtime self-healing: none masking correctness — a missed heartbeat is a real down state, published
  once (throttled), not a silent retry; an unknown token is 404; the push handler is nil-safe on the
  result sink.
- Duplicate checks: liveness lives once (`evaluatePush`); the push endpoint reuses `PublishResult`
  and the ingest transition logic rather than re-implementing status/notify.
- Conclusions transferred to canonical docs before artifact removal: yes.
