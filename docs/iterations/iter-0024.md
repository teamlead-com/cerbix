# iter-0024 — Add member by email + local-login rate limit (NFR-010)

## 1. Summary

Two hardening improvements in one iteration: org members can now be added by **email** (resolved to
an existing user) instead of a raw user id, and local login is **rate-limited per client IP**
(NFR-010). Verified with hermetic auth/api tests, a DB-gated store test, and a real-binary e2e
(add-by-email 201 / unknown 400; 10 attempts then 429 for one IP, a fresh IP unaffected). NFR-010 is
now DONE.

## 2. Input artifacts

- iter-0010 note ("invite by email is a separate feature"); D-0016 (rate-limit deferred); the JIT
  provisioning model.

## 3. What changed (by role)

### Agent A — Implementation
- **invite-by-email**: `store.GetUserByEmail`; `api.addMember` accepts `email` as an alternative to
  `user_id`, resolving it to an existing user (400 "must sign in once first" if none). `openapi`
  `AddMember` gains `email` (user_id or email).
- **rate-limit (NFR-010)**: `config.Local.LoginRateLimitPerMinute` (default 10);
  `internal/auth/ratelimit.go` — a per-key sliding-window `loginLimiter` + `clientIP` helper (XFF
  first hop, else RemoteAddr); `Authenticator` builds it in `New`; `LocalLoginHandler` returns **429**
  when over the limit, before any credential work. 0 disables it.

### Agent B — Tests / verification
- **Hermetic**: `auth/ratelimit_test.go` (allow within window, deny over, per-key independence,
  disabled always-allow, `clientIP` incl. XFF); `api/api_members_test.go` (add by email 201, unknown
  400, user_id still works, viewer 403). Fakes extended (`GetUserByEmail`).
- **DB-gated**: `store_integration_test.go::TestGetUserByEmail`.
- **Suite**: `go build`, `go vet`, `gofmt` clean; `go test ./...` green with real Postgres
  (`internal/auth` 73.5%, `internal/api` 73.3%, `internal/config` 82.4%).
- **Real-binary e2e** (`--role=all`): add a member by the bootstrap admin's **email** → 201 (role +
  resolved user_id); an unknown email → 400; hammering `/auth/local/login` from one IP (XFF 9.9.9.9)
  → 10× 401 then **429** (first 429 at attempt 11 = default 10/min); a different IP → 401 (independent).

### Agent C — Docs
- `docs/decisions.md` (D-0031), `docs/status.md` (NFR-010 → DONE), `docs/traceability.md`, this report.

### Agent D — Ops
- One optional config field with a default; no migration. The limiter is in-memory (single-process);
  a distributed limiter would need shared state (noted). All build/test/e2e in Docker.

## Role-rule / self-healing / dedup checklist

- Rule residence: user lookup in `store`; email-resolve + limiter check in `auth`/`api` transport;
  membership invariants unchanged in `domain`. The limiter is one component keyed once by client IP.
- Runtime self-healing: none masking correctness — an unknown email is a 400 (not a silent skip); over
  the rate limit is a hard 429; the limiter fail-open only when explicitly disabled (limit 0).
- Duplicate checks: `addMember` reuses `CreateMembership`/`Validate`; the limiter and `clientIP` live
  once; add-by-email and add-by-user_id converge on the same membership path.
- Conclusions transferred to canonical docs before artifact removal: yes.
