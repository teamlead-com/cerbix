# iter-0027 — Keycloak client-credentials: a second machine-auth path

## 1. Summary

Added the second API-auth method the PRD calls for: a Keycloak machine client (OAuth2
client-credentials) can now call `/api/v1/*` with its realm-issued JWT, alongside cerbix
service-account tokens (iter-0013). The token's issuer and signature are verified (audience relaxed,
since a machine token's `aud` is the client, not cerbix); the subject is JIT-provisioned as a user
and resolved to a **membership-gated** principal — a client with no cerbix grants gets no access.
This completes **FR-013**. Verified with a hermetic mock-OIDC test; a live-Keycloak realm e2e stays
out of scope (realm/client naming is an open deployment question, per the plan).

## 2. Input artifacts

- The PRD "API auth — both ways" (service tokens **and** Keycloak client-credentials) and FR-013;
  D-0034 (this iteration); the existing OIDC login + JIT path (FR-004) and its mock-OIDC test harness
  (`auth_test.go`, RS256 JWKS); the service-account bearer path (iter-0013, FR-012 phase 2b-i).

## 3. What changed (by role)

### Agent A — Implementation
- **`auth/auth.go`**: a second verifier `ccVerifier = provider.Verifier(&oidc.Config{
  SkipClientIDCheck: true})`, built only when OIDC is enabled. Issuer + JWKS signature are checked;
  the per-client audience check is relaxed (documented as safe because authorization is
  membership-driven, not audience-driven).
- **`auth/middleware.go`**: the bearer block now tries `principalFromToken` (service token) first and,
  **only on `store.ErrNotFound`**, falls through to the new `principalFromJWT`: verify via
  `ccVerifier`; on failure return `ok=false` so the caller emits **401** (not 500);
  `UpsertUserByKeycloakSub(sub, email-or-"<sub>@clients", display)` JIT-provisions the identity;
  `loadPrincipal` builds the principal from its memberships; `ViaToken=true`. A cookie still wins over
  a bearer; a valid service token still short-circuits before any JWT work.

### Agent B — Tests / verification
- **`auth/clientcreds_test.go`** (hermetic, mock-OIDC): a minted client-credentials JWT (service-account
  `sub`, no email) → `RequireAuth` returns **204**, the principal is `ViaToken` with a non-empty
  `UserID`, the subject is **JIT-provisioned** (`usersBySub["service-account-ci"]`,
  email `service-account-ci@clients`), and it has **no memberships** (authorization is membership-gated
  until an admin grants access). An **invalid bearer** (`not.a.valid.jwt`) → **401**.
- **Suite**: `go build`, `go vet`, `gofmt` clean; `go test ./...` green. Hermetic packages all pass;
  DB-gated re-run against a throwaway Postgres green — `internal/store` 76.9%, `internal/api` 73.4%,
  `internal/scheduler` 72.2%, `internal/auth` **74.1%** (all over the 70% gate).

### Agent C — Docs
- `docs/decisions.md` (**D-0034**); `docs/status.md` (**FR-013 → DONE**, **NFR-007 → DONE** — service
  tokens hashed at rest / never logged; FR-012 phase-2b-v note updated); `docs/traceability.md`
  (FR-013/NFR-007 row + summary note); this report.

### Agent D — Ops
- No migration, no new dependency (`go-oidc` already present). `ccVerifier` is nil when OIDC is
  disabled, so `principalFromJWT` is a no-op and local-only deployments are unaffected. A machine
  client is granted access exactly like a human — an org/project admin adds the JIT-provisioned
  identity to a project with a role — so no new authorization surface. All build/test in Docker.

## 6. Decisions

**D-0034** — a second verifier (`SkipClientIDCheck`) trusts the realm issuer's signature but relaxes
audience; the bearer path falls through service-token → client-credentials JWT; the JWT subject is
JIT-provisioned and resolved to a membership-gated principal (`ViaToken`). One authorization model for
cookie, service token, and JWT.

## Role-rule / self-healing / dedup checklist

- Rule residence: JWT verification + JIT + principal assembly live in `auth` (transport/identity);
  authorization stays in `authz.Can` (unchanged) — the JWT path adds an identity source, not a
  permission path.
- Runtime self-healing: none. A JWT that fails verification is **not** downgraded or retried — it
  yields 401; `ccVerifier` nil (OIDC off) short-circuits cleanly rather than guessing.
- Duplicate checks: `principalFromJWT` reuses `UpsertUserByKeycloakSub` (the OIDC-login JIT path) and
  `loadPrincipal` (the cookie path) — no parallel provisioning or principal-building logic; the bearer
  block tries the service token first and only then the JWT, so the two machine-auth methods share one
  entry point.
- Conclusions transferred to canonical docs before artifact removal: yes.
