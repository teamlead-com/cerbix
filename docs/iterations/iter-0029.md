# iter-0029 — Transactional outbox for reliable webhook/notification delivery

## 1. Summary

Replaced the best-effort in-memory queues behind incident webhooks and monitor-transition
notifications with a **transactional outbox**: events are written to `outbox_events` in the *same*
database transaction as the state change that produced them (incident create/update; monitor status
transition), then delivered by a background worker with exponential backoff, a dead-letter state, and
`FOR UPDATE SKIP LOCKED` claiming so it is safe on every role/replica. Outbound events now survive
restarts and transient endpoint failures — the reviewer's P1. Hardens FR-010 and FR-012.

## 2. Input artifacts

- The reviewer prompt's P1 (guaranteed delivery via a transactional outbox) and my note that
  multi-replica delivery needs `SKIP LOCKED` / single-active; the existing best-effort dispatchers
  (`notify`, `webhook`), the ingest auto-incident pipeline, and the incident API handlers (both were
  emit sites); the tx-based `CreateIncident`/`AddIncidentUpdate` store methods.

## 3. What changed (by role)

### Agent A — Implementation
- **Migration `00016_outbox_events.sql`**: `outbox_events(topic, payload jsonb, status
  pending|delivered|dead, attempts, next_attempt_at, last_error)` + a partial due-index.
- **Store** (`outbox.go`): `enqueueOutboxTx` (in-tx insert); `ClaimDueOutbox` (atomic claim of due
  rows via `FOR UPDATE SKIP LOCKED`, incrementing attempts and pushing `next_attempt_at` by an
  exponential backoff that doubles as a lease); `MarkOutboxDelivered`; `FailOutbox` (dead at
  `maxAttempts`). **In-tx enqueue** added to `CreateIncident`/`AddIncidentUpdate` (`incident_event`)
  and `SetMonitorStatus` (now transactional; `monitor_transition` only on a real change).
- **Domain** (`outbox.go`): `OutboxEvent`, topic constants, `MonitorTransition{monitor_id,prev,cur}`
  with `ShouldNotify()` (the notification policy — moved here from ingest so the store records only
  the raw fact and the enqueue stays atomic).
- **Worker** (`internal/outbox`): polls, dispatches by topic (`incident_event` → webhook deliver;
  `monitor_transition` → policy → notification deliver, loading the monitor; a deleted monitor or a
  non-notified transition is a clean no-op), retries/dead-letters, records metrics.
- **`notify`/`webhook`**: in-memory queue + `Run` removed; each exposes `Deliver(...) error` reusing
  its rendering / HMAC / SMTP logic. **`ingest`** and the **incident API handler** lose their
  sink/notifier seams (delivery is now the store-enqueue + worker path). **`cli`** starts the outbox
  worker wherever a database is configured. **`metrics`**: `cerbix_outbox_delivered_total` /
  `cerbix_outbox_dead_total`.

### Agent B — Tests / verification
- **DB-gated** (`store/outbox_internal_test.go`): incident create + resolve leave exactly the expected
  pending `incident_event` rows (proving in-tx enqueue); `SetMonitorStatus` enqueues a
  `monitor_transition` only on a real change; `ClaimDueOutbox` increments attempts and leases
  `next_attempt_at` (an immediate re-claim is empty); delivered/dead terminal states.
- **Hermetic** (`outbox/outbox_test.go`): dispatch of both topics; policy-skip (pending→up not
  notified); deleted-monitor drop; retry-then-dead at `maxAttempts`; unknown-topic and nil-deliverer
  failures; `Run` returns on context cancel. Coverage `internal/outbox` **81.8%**.
- **Suite**: `go build`, `go vet`, `gofmt` clean; `go test ./...` green over Postgres (store 76.5%,
  api 73.0%, ingest 75.0%, notify 82.8%, webhook 93.8%, metrics 80.6% — all over the 70% gate).
- **Real-binary e2e** (`--role=all`): migration `00016` applied on boot, `/readyz` ready; a seeded
  pending outbox event was drained by the **wired** worker **pending→delivered in ~3 s** and
  `cerbix_outbox_delivered_total` incremented to 1.

### Agent C — Docs
- `docs/decisions.md` (**D-0036**); `docs/status.md` (FR-010 + FR-012 reliability notes);
  `docs/traceability.md` (outbox row + summary note); this report.

### Agent D — Ops
- Migration additive/reversible; `TruncateAll` includes the table. The worker is multi-replica-safe
  (`SKIP LOCKED`); a crashed worker's in-flight rows auto-recover at their lease. Dead events are
  retained for inspection and surfaced via `cerbix_outbox_dead_total`. No new config. All build/test
  in Docker.

## 4. Requirements advanced

FR-010 (notifications) and FR-012 (webhooks) are hardened from best-effort to **durable, retried,
at-least-once** delivery that survives restarts and transient failures.

## 5. Tests run + results

See §3 Agent B — DB-gated in-tx-enqueue + claim/lease test, hermetic worker test (81.8%), full suite
green over Postgres, and the real-binary wired-worker e2e (pending→delivered + metric).

## 6. Decisions

**D-0036** — enqueue in the state-change transaction; deliver from a `SKIP LOCKED` claim-with-lease
worker with exponential backoff and a dead-letter state; notification policy in the worker; at-least-
once (duplicates on partial failure preferred over loss).

## Role-rule / self-healing / dedup checklist

- Rule residence: in-tx enqueue is infra (store); the notification policy (`ShouldNotify`) is domain/
  application (worker), not the store; delivery mechanics stay in `notify`/`webhook`. One enqueue
  helper, one claim query.
- Runtime self-healing: none masking correctness — the backoff/lease is the intended recovery for a
  crashed worker (not a silent patch), and a failed delivery is retried a bounded number of times then
  **surfaced** as `dead` (+metric), never dropped silently.
- Duplicate checks: a single `outbox_events` path replaces two in-memory queues; both incident emit
  sites (API + auto) now funnel through the same in-tx enqueue in `CreateIncident`/`AddIncidentUpdate`;
  no parallel emit logic remains in ingest or the API handler.
- Conclusions transferred to canonical docs before artifact removal: yes.
