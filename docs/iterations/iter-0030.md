# iter-0030 — Heartbeat partitioning + retention (coupled to the rollup)

## 1. Summary

Bounded the unbounded-growth `heartbeats` table: it is now RANGE-partitioned by `ts` into daily,
UTC-aligned partitions (plus a DEFAULT safety partition), and the scheduler leader pre-creates
upcoming partitions and **drops** those older than `heartbeats.retention_days` (a cheap DDL, not a
large DELETE). Crucially, `retention_days` also bounds the daily-availability rollup's recompute
window, so dropping old raw never wipes the frozen `heartbeats_daily` rows that carry long-range
availability. Introduces **NFR-012**; realizes the reviewer's P2.

## 2. Input artifacts

## 3. What changed (by role)

### Agent A — Implementation
- **Migration `00017_partition_heartbeats.sql`**: converts `heartbeats` in place to
  `PARTITION BY RANGE (ts)` with a `heartbeats_default` partition; a `DO` loop pre-creates a daily
  partition per UTC day present in the old data, then copies rows in (they land in dated partitions,
  not the default). Renames the old index to avoid a name collision. Reversible Down.
- **Store** (`retention.go`): `EnsureHeartbeatPartitions(ahead)` creates `[today, today+ahead]` daily
  partitions (best-effort; the default covers gaps); `PurgeOldHeartbeats(cutoff)` DROPs dated
  partitions whose whole day is `< cutoff` (catalog-driven, regex-validated names) and clears default
  stragglers.
- **Scheduler**: `maintainPartitions` runs on leader-acquire and hourly; **`WithRetentionDays`** sets
  the window, which now also drives the rollup: the leader recomputes only `[today - retention_days,
  today)` so it never touches a dropped day.
- **Config**: `heartbeats.retention_days` (default 30, min 2). **`cli`** wires it into the scheduler.

### Agent B — Tests / verification
- **DB-gated** (`store/retention_internal_test.go`): `EnsureHeartbeatPartitions` creates today's
  partition and a fresh `InsertHeartbeat` lands in it (default stays empty); `PurgeOldHeartbeats`
  drops a 40-day-old partition while keeping a 5-day-old one and its row.
- **Hermetic** (`scheduler_test.go`): the leader runs `Ensure`+`Purge` (`TestSchedulerLeaderMaintainsPartitions`);
  `WithRetentionDays` clamps `<2`. **Config** test: default 30, reject `<2`, override.
- **Suite**: `go build`, `go vet`, `gofmt` clean; `go test ./...` green over Postgres (store 76.5%,
  scheduler 73.1%, config 83.0% — all over the 70% gate); the partitioning migration is exercised by
  every DB-gated store/api/scheduler test that migrates a fresh database.
- **Real-binary e2e** (`--role=all`): migration `00017` applied on boot; the wired scheduler leader
  pre-created `heartbeats_p<today>`, `+1`, `+2` and the `heartbeats_default` partition — proving the
  maintenance path runs end-to-end.

### Agent C — Docs
- `docs/decisions.md` (**D-0037**); `docs/status.md` (**NFR-012 DONE**); `docs/traceability.md`
  (row + summary note); `packaging/config.example.yaml`; this report.

### Agent D — Ops
- Migration additive/reversible; `TruncateAll` still targets `heartbeats` (cascades to partitions).
  The default partition keeps inserts safe if maintenance falls behind; maintenance is idempotent and
  single-active (scheduler leader). Retention reclaims space by DROP (near-instant) rather than DELETE.
  New knob `heartbeats.retention_days`. All build/test/e2e in Docker.

## 4. Requirements advanced

**NFR-012 DONE** — raw heartbeats are bounded and reclaimed cheaply, and long-range availability is
preserved because retention and the rollup window are driven by the same `retention_days`.

## 5. Tests run + results

See §3 Agent B — DB-gated partition-routing + drop test, scheduler maintenance test, config test, full
suite green over Postgres, and the real-binary boot e2e (migration + auto-created partitions). The
riskiest piece (the in-place partitioning migration, insert routing, FK cascade across partitions,
partition pruning) was additionally validated directly against Postgres before wiring.

## 6. Decisions

**D-0037** — daily RANGE partitions + DEFAULT; leader-maintained pre-create and DROP; `retention_days`
bounds both retention and the rollup recompute window so old-raw drop never wipes long-range rollup.

## Role-rule / self-healing / dedup checklist

- Rule residence: partition DDL + drop live in `store` (infra); the maintenance cadence and the
  retention↔rollup coupling live in `scheduler` (application); `config` owns the knob. One
  partition-name convention shared by the migration, `Ensure`, and `Purge`.
- Runtime self-healing: the DEFAULT partition is a deliberate safety net (documented), not a silent
  fix — inserts stay correct if maintenance lags, and `Ensure` is best-effort with the gap purged by
  cutoff. Retention DROPs are logged with a count; nothing is hidden.
- Duplicate checks: retention is one `PurgeOldHeartbeats`; the rollup window and the retention cutoff
  derive from the single `retention_days`, so they cannot drift apart.
- Conclusions transferred to canonical docs before artifact removal: yes.
