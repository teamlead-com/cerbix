# iter-0031 — Scheduler efficiency (snapshot scheduling + batched push-liveness)

## 1. Summary

Removed the two parasitic Postgres load sources in the scheduler leader's hot loop: the **per-second
full `ListEnabledMonitors` scan** and the **per-push `LatestHeartbeat` N+1**. The leader now schedules
active checks from an **in-memory monitor snapshot** refreshed every 15 s, and detects tripped push
(dead-man's-switch) monitors with a **single batched `StalePushMonitors` query** every 5 s. Behavior is
unchanged; the DB work is now independent of monitor count per tick. Realizes the reviewer's P1
scalability item (last of the four).

## 2. Input artifacts

- The reviewer prompt's P1 (scheduler scan every second; push N+1) — confirmed against the code before
  changing anything (the loop did reload the full table each 1 s tick and call `LatestHeartbeat` per
  push monitor); my note that a timing wheel is overkill at current scale, so the cheap wins are: reload
  less often + batch the push query. The `(monitor_id, ts DESC)` heartbeats index (iter-0030 kept it on
  the partitioned table).

## 3. What changed (by role)

### Agent A — Implementation
- **Scheduler** (`scheduler.go`): the leader keeps an in-memory `monitors` snapshot, **reloaded every
  `refreshEvery` (15 s)** via `ListEnabledMonitors`; the 1 s tick publishes due active checks from the
  snapshot using the existing `nextRun` map — no per-tick scan. `pruneNextRun` drops schedule entries
  for monitors gone from the snapshot. `checkStalePush` (every `pushCheckEvery`, 5 s) publishes a down
  result per monitor returned by the batched query, still throttled by `nextRun`. The per-monitor
  `evaluatePush` and the `LatestHeartbeat` dependency are removed.
- **Store** (`monitors.go`): `StalePushMonitors` — one query returning enabled, not-already-down push
  monitors whose `COALESCE(max(heartbeat.ts), created_at) < now() - make_interval(interval_seconds)`,
  using the heartbeats index for the correlated max.

### Agent B — Tests / verification
- **Hermetic** (`scheduler_test.go`): the leader schedules active checks from the snapshot
  (`TestSchedulerLeaderPublishesDueJobs`) and publishes downs for the batched stale set
  (`TestSchedulerPushLiveness`, now driving the fake's `StalePushMonitors`).
- **DB-gated** (`store/pushstale_internal_test.go`): a never-reported-but-old and a last-beat-90s-ago
  push monitor are returned; a freshly-reported, an already-down, and a non-push monitor are excluded.
- **Suite**: `go build`, `go vet`, `gofmt` clean; `go test ./...` green over Postgres (scheduler 73.9%,
  store 76.5% — all over the 70% gate).
- **Real-binary smoke** (`--role=all`): the leader acquires leadership and runs healthily across both
  the 15 s refresh and 5 s push-check cadences with **zero scheduler errors** over the observation window.

### Agent C — Docs
- `docs/decisions.md` (**D-0038**); `docs/status.md` (FR-008 efficiency note); `docs/traceability.md`
  (row + summary note); this report.

### Agent D — Ops
- No schema, migration, or config change. Scheduling load on Postgres is now ~one snapshot query per
  15 s + one batched push query per 5 s, independent of monitor count per tick. New-monitor pickup
  latency is bounded by `refreshEvery` (15 s) — acceptable for interval-based checks. All build/test in
  Docker.

## Role-rule / self-healing / dedup checklist

- Rule residence: the staleness predicate lives in one place — the `StalePushMonitors` SQL (infra); the
  cadence and throttling live in the scheduler (application). The active-scheduling policy is unchanged.
- Runtime self-healing: none. The snapshot is a performance cache, not a correctness fallback; a failed
  reload logs and keeps the previous snapshot until the next refresh (no silent divergence — deleted
  monitors are pruned on the next successful reload).
- Duplicate checks: push-liveness is one query + one publish loop (was N lookups); `nextRun` throttling
  is shared shape with active scheduling; no parallel staleness logic remains.
- Conclusions transferred to canonical docs before artifact removal: yes.
