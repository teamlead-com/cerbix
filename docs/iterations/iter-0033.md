# iter-0033 — Encrypt secrets at rest (webhook & channel credentials)

## 1. Summary

Closed a security gap: notification-channel credentials (SMTP passwords, Telegram bot tokens, incoming
hook URLs) and webhook HMAC signing secrets were stored **plaintext** in Postgres. Added a
`secret.Cipher` (AES-256-GCM) applied at the store's column boundary so `webhooks.secret` and every
`notification_channels.config` value are encrypted on write and transparently decrypted on read.
Enabled by `security.encryption_key`; **off by default**, with un-prefixed legacy rows read as-is so
encryption can be switched on without migrating existing data. Introduces **NFR-013**.

## 2. Input artifacts

- The security-track intent (sec-hardening); the plaintext webhook `secret` column and JSONB channel
  `config`; my iter-0029/0032 notes flagging secret-at-rest encryption as remaining backlog.

## 3. What changed (by role)

### Agent A — Implementation
- **`internal/secret`** (new): `Cipher` over AES-256-GCM. `Encrypt` → `enc:v1:<base64(nonce‖ct)>` (random
  nonce per value; empty string and nil cipher pass through). `Decrypt` → reverses it, **passes
  un-prefixed (legacy plaintext) values through**, and errors on an encrypted value with no key (never
  returns ciphertext silently). `New` validates a 32-byte key.
- **Config**: `security.encryption_key` (base64 of 32 bytes); `EncryptionKeyBytes` decodes/validates
  (fail-fast on malformed/wrong length); empty = disabled.
- **Store**: `WithCipher`; `scanWebhook`/`collectWebhooks` and `scanChannel`/`collectChannels` became
  `*Store` methods that **decrypt** (one place per entity); `CreateWebhook` and
  `CreateNotificationChannel` **encrypt** before insert (config value-by-value). Callers/deliverers
  always see plaintext.
- **`cli`**: builds the cipher from config and attaches it via `store.WithCipher` (fail-fast on a bad
  key), logging `secret_encryption_enabled`.

### Agent B — Tests / verification
- **Hermetic** (`secret/secret_test.go`): round-trip (incl. unicode/empty), legacy-plaintext
  passthrough, **wrong-key GCM failure**, nil-cipher identity + encrypted-value-without-key error,
  key-length validation. Coverage `internal/secret` **83.3%**.
- **DB-gated** (`store/encryption_internal_test.go`): the raw `webhooks.secret` and
  `notification_channels.config` columns are `enc:v1:`-prefixed and **never contain the plaintext**,
  while `Get*` return decrypted plaintext; a legacy plaintext row still reads.
- **Config** test: non-base64 / 16-byte keys rejected, valid 32-byte accepted.
- **Suite**: `go build`, `go vet`, `gofmt` clean; `go test ./...` green over Postgres (store 76.x, all
  packages over the 70% gate).
- **Real-binary e2e** (`--role=all`, encryption on): a webhook created through the API stores
  `enc:v1:…` in the `secret` column while the API **round-trips the plaintext** `whsec_…` — proving
  encryption on write and transparent decryption on read end-to-end.

### Agent C — Docs
- `docs/decisions.md` (**D-0040**); `docs/status.md` (**NFR-013 DONE**); `docs/traceability.md`
  (row + summary note); `packaging/config.example.yaml`; this report.

### Agent D — Ops
- No schema change, no migration. Enabling encryption is a config opt-in with a **zero-migration
  rollout** (legacy rows stay readable; new writes are encrypted). Operational caveat documented:
  losing the key makes encrypted secrets unrecoverable (rotate by re-entering secrets, not covered
  here). API-token hashes and argon2id password hashes were already one-way and are unaffected. All
  build/test/e2e in Docker.

## 4. Requirements advanced

**NFR-013 DONE** — webhook signing secrets and channel credentials are encrypted at rest once a key is
configured, so a database dump no longer leaks live secrets.

## 5. Tests run + results

See §3 Agent B — secret unit tests (83.3%), DB-gated at-rest test, config validation test, full suite
green over Postgres, and the real-binary encryption e2e.

## 6. Decisions

**D-0040** — AES-256-GCM `Cipher` with `enc:v1:` tag and legacy passthrough; store encrypts
`webhooks.secret` and channel config values at the column boundary; `security.encryption_key` opt-in,
validated fail-fast.

## Role-rule / self-healing / dedup checklist

- Rule residence: crypto lives once in `internal/secret`; the store applies it at the column boundary
  (infra); config owns the key. No secret ever encrypted/decrypted outside the store's scan/create
  helpers.
- Runtime self-healing: none. An encrypted value with no key is a hard error, not a silent
  ciphertext-passthrough; enabling/disabling encryption is an explicit config choice, not an inferred
  downgrade. Legacy-plaintext passthrough is a deliberate, documented migration affordance.
- Duplicate checks: one `Cipher`; one decrypt path per entity (the `*Store` scan methods); encryption
  applied symmetrically in the matching `Create*`.
- Conclusions transferred to canonical docs before artifact removal: yes.
