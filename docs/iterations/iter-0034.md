# iter-0034 — Encryption key rotation

## 1. Summary

Completed the at-rest-encryption story from iter-0033: keys can now be rotated with zero downtime and
no data loss. The `secret.Cipher` became a **keyring** — it encrypts with the primary key and decrypts
by trying every key (AES-GCM's authentication tag identifies the right one), so a new primary can be
introduced while old keys still read existing data. A new `cerbix reencrypt` command rewrites all
stored secrets under the current primary. Advances **NFR-013**.

## 2. Input artifacts

- iter-0033 / D-0040 (single-key at-rest encryption, `enc:v1:` format) and its documented follow-up
  (key rotation); a compromised/aged key had no replacement path.

## 3. What changed (by role)

### Agent A — Implementation
- **`internal/secret`**: `New(keys ...[]byte)` builds a keyring (primary = first). `Encrypt` uses the
  primary; `Decrypt` tries each key and returns the first that authenticates, erroring only when none
  can — the `enc:v1:` wire format is **unchanged** (no key id needed; GCM disambiguates).
- **Config**: `security.previous_keys` ([]base64) alongside `encryption_key`; `Keys()` returns the
  ordered validated keyring (previous_keys without a primary is a config error). `serve` builds the
  keyring, so a running service reads under any key and writes under the primary.
- **Store**: `ReencryptSecrets(ctx)` — for every webhook secret and channel-config value: read (decrypt
  via keyring) → write (encrypt under primary); no-op when encryption is off; returns counts.
- **`cli`**: new one-shot `reencrypt` subcommand (load config → keyring → `ReencryptSecrets` → log
  counts). Rotation procedure documented in `config.example.yaml`.

### Agent B — Tests / verification
- **Hermetic** (`secret/secret_test.go`): `TestKeyringRotation` — a value under key A reads via `[B, A]`,
  new writes use B, and A alone can't read them; `TestDecryptFailsWhenNoKeyMatches`; empty-keyring
  rejected. Coverage `internal/secret` **86.1%**.
- **DB-gated** (`store/reencrypt_internal_test.go`): encrypt under A, rotate the store to `[B, A]`,
  `ReencryptSecrets`, then the raw `secret`/`config` columns read under **B alone** and **not under A**.
- **Config** test: `previous_keys` without a primary rejected; primary + valid previous → keyring of 2;
  malformed previous key rejected.
- **Suite**: `go build`, `go vet`, `gofmt` clean; `go test ./...` green over Postgres (all over the 70%
  gate).
- **Real-binary rotation e2e**: a webhook is created under key A (via the API); `cerbix reencrypt` with
  keyring `[B, A]` changes the ciphertext (still `enc:v1:`, count = 1); a **B-only** `reencrypt` then
  **succeeds** (B reads everything) while an **A-only** `reencrypt` **fails** (exit 1) — proving the
  data has moved off A.

### Agent C — Docs
- `docs/decisions.md` (**D-0041**); `docs/status.md` (NFR-013 rotation note); `docs/traceability.md`
  (row + summary note); `packaging/config.example.yaml`; this report.

### Agent D — Ops
- No schema change; `enc:v1:` format and existing data untouched. Rotation is an offline one-shot
  (`cerbix reencrypt`) plus a config edit — no downtime for the running service, which reads under the
  keyring throughout. Try-all decrypt is O(keys) per value; keep `previous_keys` to the few needed
  during a rotation. All build/test/e2e in Docker.

## 4. Requirements advanced

**NFR-013** extended from "secrets encrypted at rest" to "…with a supported rotation path", so a
compromised or aged key can be replaced without data loss or downtime.

## 5. Tests run + results

See §3 Agent B — keyring unit tests (86.1%), DB-gated reencrypt/rotation test, config validation, full
suite green over Postgres, and the real-binary rotation e2e (reencrypt `[B,A]`; B-only ok, A-only fails).

## 6. Decisions

**D-0041** — keyring with try-all decrypt (GCM tag disambiguates, format unchanged); `previous_keys`
config; `cerbix reencrypt` migrates data to the primary.

## Role-rule / self-healing / dedup checklist

- Rule residence: the keyring lives in `internal/secret`; `ReencryptSecrets` in `store` (infra); the
  rotation command in `cli`; config owns the keys. One encrypt path (primary), one decrypt path
  (try-all).
- Runtime self-healing: none. A value no key can decrypt is a hard error (not silent passthrough);
  reencrypt fails loudly if any value can't be read, so a botched rotation is visible, not masked.
- Duplicate checks: `ReencryptSecrets` reuses the same Cipher and the same encrypt/decrypt paths as the
  live store; no parallel crypto. The keyring is the single owner of multi-key logic.
- Conclusions transferred to canonical docs before artifact removal: yes.
