# iter-0039 — Confirm phase: accelerated confirmation of a failure

## 1. Summary

Third iteration of the reliability package (spec `specs/func-confirm-phase.md`). With
confirmations, time-to-alert was `interval × failure_threshold` (60s×3 ≈ 3 minutes of silence). Now
**only the confirmation phase** is accelerated — from the first counted failure to the down verdict
(or the reset): probes run at `confirm_interval_seconds` instead of the main interval.
Deliberately NOT a "flapping mode": constantly speeding up would finish off a degrading service.
Implementation started from the approved SPA mockup (the form field + the "confirming" state).

**E2E result: time-to-down 25s instead of ~180s** (probe→verdict — 11s).

## 2. What was done

- **Migration 00045**: `monitors.confirm_interval_seconds` (default 10; 0 = off).
- **domain**: the field + read-only `consecutive_failures` on Monitor (the column already existed,
  now in the select); `Normalize` clamps to [5s, interval], push/composite → 0;
  `ConfirmConfigured()` / `InConfirmPhase()` / `ConfirmInterval()`.
- **store**: `monitorColumns` + scan + Create/Update; `RecordCheckStatus`, when incrementing
  the counter without a verdict, sends **`pg_notify('monitor_confirm', id)`** in the same transaction
  (delivery on commit; a miss is harmless). `ConfirmNotifier` — a LISTEN hub modeled after
  PullNotifier (one connection, reconnect, buffered fan-out with drop on a slow subscriber).
- **scheduler**: `WithConfirmSignals(ch)`; in the lead loop — `confirmFast` (id → acceleration
  expiry = one main interval after the last signal: recovery stops the
  signals → the acceleration fades out on its own) + a `byID` snapshot. A signal (or the refresh
  fallback via `InConfirmPhase` from a fresh snapshot — for the case of a missed notify) pulls
  `nextRun` toward the confirm interval, **never pushes it back**. The publish loop computes the
  effective interval; **pull jobs in the confirm phase carry a short TTL** (fast probes
  do not pile up at a dead agent). **Cap `confirmCapPerRegion=50`**: on a mass failure a
  region falls back to the normal rhythm (anti-thundering-herd), WARN `confirm_phase_capped`.
- **cli**: ConfirmNotifier is started for the all/scheduler roles (Subscribe without unsubscribe —
  lives with the process).
- **api/openapi**: `confirm_interval_seconds` in create (default 10)/update/Monitor;
  `consecutive_failures` readOnly; regen schema.d.ts.
- **SPA** (per the mockup): the "Confirm interval" field in the Reliability block (disabled+opacity when
  confirmations ≤ 1, a hint with the rules); `StatusPill` got an optional label — in the monitor
  list a "Confirming N/M…" pill in degraded style while confirmation is in progress.

## 3. Verification

- domain `TestConfirmIntervalNormalize` (5s/interval clamp, off, push/composite → 0,
  phase predicates); store `TestRecordCheckStatusConfirmNotify` (real LISTEN: notify on
  fails 1 and 2, silence on the verdict and recovery; `consecutive_failures` in the select);
  scheduler `TestConfirmSignalAcceleratesProbe` (1h interval, signal → probe in ~1s) and
  `TestEnterConfirmCap` (region cap, the neighboring region unaffected).
- `-race` 30 packages; vue-tsc + vite build clean.
- **E2E** (live binary, dev DB): migration 45; a tcp monitor 60s/threshold 3/confirm 5 against a
  dead port → **down in 25s** (3 heartbeats, 1st probe → verdict in 11s; without the feature
  it would have been ~180s).

## 4. Decisions

D-0099. Limitations (recorded): the acceleration can outlive recovery by up to one
main interval (the signals stop, the latch fades out; the refresh clears it earlier);
the cap applies to a whole region at once. Next iteration — iter-0040 (dependency graph),
starting with the mockup.
