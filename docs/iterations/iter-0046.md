# iter-0046 — Live minimum password length

## 1. Summary

Third slice of the audit-gap package, the security-relevant one: Settings →
Authentication → "Minimum password length" saved to the database and changed nothing.
Both password paths compared against the **startup YAML** value (`h.minPasswordLen` in
the api handler, `a.minPasswordLen` in reset-confirm), so an admin raising the minimum
in the UI got a confirmation and zero enforcement. Every other auth-policy field
(session TTL, TOTP requirement, e-mail allowlist) was already live — this was the one
outlier.

## 2. What was done

- `internal/api`: `effectiveMinPasswordLen()` — the live policy from the settings
  service (DB → config-seed → default) when wired, the construction-time config value
  otherwise; `POST /api/v1/me/password` uses it.
- `internal/auth/handlers_reset.go`: reset-confirm reads `authPolicy().MinPasswordLen` —
  the existing fallback chain already returns the config value when no settings service
  is attached, so worker/agent-style constructions are unaffected.
- The YAML `local.min_password_length` keeps its documented role: the seed before the
  first UI save (settings Bootstrap already carried it).

## 3. Verification

- New `TestResetConfirmUsesLivePolicyMinLength`: with a policy source demanding 12,
  a 10-char password (fine per config default) → 400, a 12-char one → 204.
- `-race` auth + api green.
- **Live E2E**: PUT auth-policy `min_password_len=16` → `POST /me/password` with a
  12-char password → 400 "new password too short" (previously passed); policy restored.
