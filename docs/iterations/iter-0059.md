# iter-0059 — Monitor defaults that actually apply

## 1. Summary

Fifth slice of package 2 (mockup approved): Settings → Monitor defaults changed nothing
for UI-created monitors — the form hardcoded its own copy of the defaults and always
posted explicit values, so the server-side "fill omitted fields" logic never fired. A
second bug hid underneath: `retries`/`renotify_seconds` were plain ints in the create
body, so an operator's explicit `0` was indistinguishable from "omitted" and silently
replaced by the instance default.

## 2. What was done

- New authed `GET /api/v1/monitor-defaults` returns the *effective* defaults (DB →
  config seed → built-ins) to any signed-in user; editing them stays on the
  admin-gated settings endpoint.
- `NewMonitorView` prefills a **new** monitor from it (edit mode untouched); the local
  literals remain only as a pre-fetch fallback.
- Create handler: `retries`/`renotify_seconds` become `*int` — absent → instance
  default, explicit `0` → honest zero (0 retries / never re-notify). The update handler
  was already fully pointer-typed.
- OpenAPI path (+ reuse of the MonitorDefaults schema); schema.d.ts regenerated.

## 3. Verification

`-race` api green; vue-tsc green. Live E2E: raised defaults to 120/15/2 → the effective
endpoint returns them; a create with omitted fields lands 120/2; a create with explicit
`retries:0, renotify_seconds:0` keeps zeros; defaults restored, test monitors removed.
