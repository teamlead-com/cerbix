# iter-0067 — E2E-load findings: quiet delete race, honest token cleanup

## 1. Summary

Running the 34-test suite repeatedly surfaced two defects invisible in normal use.

## 2. What was done

- **Product**: a probe result landing after its monitor was deleted (the scheduler
  snapshot keeps probing until the next refresh, ≤15s) hammered the log with
  `insert_heartbeat_failed` FK-violation ERRORs. `InsertHeartbeat` now maps that FK
  violation (23503 on `*monitor_id_fkey`) to `ErrNotFound` and ingest drops the row
  with a single INFO (`heartbeat_for_deleted_monitor`). Migration `00048` renames the
  confusing `heartbeats_new_monitor_id_fkey` (a leftover of the 00043 hypertable swap)
  to `heartbeats_monitor_id_fkey`; the detector matches both names.
- **Suite**: the API-token cleanup read `id` from the wrong level of the create
  response (`{token, api_token}`), producing `DELETE /api/v1/tokens/undefined`
  (a 500 in the logs) and the leftover rows seen earlier; fixed with an assertion.

## 3. Verification

New `TestInsertHeartbeatForDeletedMonitor` (delete → in-flight insert → ErrNotFound);
`-race` store+ingest green; live race forced deterministically (first heartbeat →
delete → 0 ERROR / 2 INFO lines); full E2E 34/34 green.
