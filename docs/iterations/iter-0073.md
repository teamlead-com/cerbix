# iter-0073 — AMQP channel-level resilience

## 1. Summary

Second `func-hardening` slice, and the direct residual of the D-0129 fix: the connection
supervisor only reacts to **connection** loss (`conn.NotifyClose`). A **channel**-level
death with the connection still alive — an operator deleting/recreating a queue,
`basic.cancel`, a 4xx channel exception, an `Ack` error — made `consumeOnce`/`serveTestsOnce`
return and then block on the reconnect signal, which never fires. The worker / results
consumer / test-RPC server parked forever behind a healthy connection. `ServeTests` was
especially exposed: its `checks.tests.<region>` queue is auto-delete, so any consumer gap
deleted it and killed test-connection for the process lifetime.

## 2. What was done

- `consume`/`ServeTests` retry loops gained a `channelRetryBackoff` (2s) leg alongside the
  reconnect-signal wait, so a channel death resubscribes on the same live connection.
- `consumeOnce` now **declares its queue on every session** (durable, matching
  `dialAndSetup`/`declareJobQueue`) instead of trusting the publisher's declare cache —
  a deleted queue is recreated on resubscribe (the cache can't know it vanished). This
  was caught by the new test: recovery from a queue DELETE hung until the declare was
  added.
- `Close()` reads `conn`/`pubCh` under `connMu`/`pubMu` (was a race with `redial`'s swap).
- `NewAMQP` defaults a nil logger to a discard sink (the supervisor logs unconditionally —
  a nil logger would have panicked on the first broker event).

## 3. Verification

New `TestAMQPConsumerSurvivesChannelDeath` (opt-in, live broker): round-trip → delete the
results queue on a separate channel (connection stays up) → the consumer re-declares and
resumes, with no `broker_lost` logged. All three AMQP integration tests green under
`-race`; `-race` dispatch + scheduler green.
