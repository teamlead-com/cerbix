# iter-0076 — Maintenance mutes delivery, not the transition record

## 1. Summary

Fifth `func-hardening` slice. Maintenance suppression was applied at **enqueue**, not at
delivery — the one place in the alert spine that violated "facts always record; only
delivery is muted". The consequence was a silent never-alert:

- A monitor going **down during a maintenance window** had its transition outbox event
  dropped (`if prev != cur && !inMaint`) **and** its `last_notified_at` left NULL (the
  `AND NOT maint.in_maint` guard on the stamp).
- `EnqueueRenotifyReminders` only re-fires down monitors with `last_notified_at IS NOT
  NULL`, so a monitor that went down mid-window and stayed down was **never alerted, even
  after the window closed** — no event, no reminder, no incident.

## 2. What was done

- `store.RecordCheckStatus`: enqueues the transition on **every** real flip (dropped the
  `&& !inMaint`) and stamps `last_notified_at` on a fresh down regardless of maintenance.
  Still returns `inMaint` as the `suppressed` flag, so ingest keeps NOT opening an incident
  during maintenance. Non-maintenance behavior is byte-for-byte unchanged.
- `store.MonitorInMaintenance(ctx, monitorID)`: new — is the monitor inside an active
  window right now (monitor-specific or project-wide), mirroring the `RecordCheckStatus`
  maint CTE. Fail-closed to `false` on error.
- `outbox.Worker`: on a `TopicMonitorTransition` whose `Cur == down`, calls
  `MonitorInMaintenance` and mutes delivery (no-op, marked delivered) when true, logging
  `alert_suppressed_by_maintenance`. Fail-open on lookup error (a DB hiccup never silently
  mutes a real alert). Recovery (`up`) is never muted. Added to the outbox `Store`
  interface (breaks the outbox fake on purpose; api/scheduler fakes don't implement it).

Flow after the fix: down-in-window → event enqueued, first delivery muted by the
maintenance check, `last_notified_at` stamped → renotify re-enqueues reminders on cadence,
each muted while the window is active → the first reminder after the window **delivers**.

## 3. Verification

- `outbox.TestMaintenanceSuppression`: initial down + renotify reminder muted during a
  window (delivered as no-ops), recovery still delivered; after the window the reminder
  delivers; a lookup error fails open.
- `store.TestMaintenanceDownEnqueuesAndStamps`: `MonitorInMaintenance` false→true across
  window creation; a down-in-window flip is `suppressed=true` yet enqueues one transition
  event and stamps `last_notified_at`; the renotify job then finds it eligible.
- Existing `TestRecordCheckStatusConfirmationsAndMaintenance`, `TestRenotifyReminders`
  still green. Full `-race` suite green; `go build`/`vet` clean; image rebuilt; E2E 34/34.
- Delivery-logic + `maintenance_windows` only — no heartbeats/retention storage-mode
  branch touched, so no dual-DB run required.

## 4. Known limitation

A monitor with `renotify_seconds = 0` that goes down mid-window and stays down is not
re-alerted after the window — reminders are the carry-out mechanism and that monitor opted
out of them (recorded in D-0134).
