# iter-0077 — Leadership watchdog + health gauges

## 1. Summary

Sixth `func-hardening` slice — a split-brain hole plus the two health gauges that make
leadership and broker state observable/alertable.

- **Undetected leadership loss.** `TryBecomeLeader` acquires a Postgres session-level
  advisory lock on a connection held from the pool, but `lead()` never re-checked it. If
  that connection dropped (network blip, Postgres restart, PgBouncer/pooler eviction) the
  server released the lock while the old leader kept publishing jobs, running renotify, and
  advancing escalations. Another scheduler could then win the lock → **two active leaders**
  = double dispatch, double reminders, double escalation steps.
- **No leader/broker health signal.** There was no way to alert on "0 leaders" or "2
  leaders", or on broker unreachability, from metrics.

## 2. What was done

- `store.TryBecomeLeader` now also returns `check(ctx) (bool, error)` — a probe that runs
  on the **same held connection** (so it doubles as a liveness check) and queries `pg_locks`
  for an advisory lock still `granted` to `pg_backend_pid()`, reconstructing the original
  bigint key from `(classid, objid)`. Signature grew from 3 to 4 returns (fake in
  `scheduler_test` + the store integration test updated).
- `scheduler.lead` runs `check` every `leaderCheckEvery` (5s, and on the first tick). On a
  false result or any error it logs `scheduler_leadership_lost` / `_check_failed` and steps
  down; `lead` now returns a `lost bool`. `Run` re-contends after a lost lock (vs. exiting
  on a clean context cancel) and drives the leader gauge.
- `metrics.Registry`: `SetSchedulerLeader(bool)` → `cerbix_scheduler_leader` gauge and
  `SetBrokerUp(bool)` → `cerbix_broker_up` gauge, each emitted only once tracked (a process
  that runs no scheduler / no AMQP transport doesn't export a misleading 0).
- `scheduler.WithLeaderState(sink)` wired for the `all` and `scheduler` roles.
- `dispatch.AMQP.WithBrokerState(f)` drives `cerbix_broker_up` off the connection
  supervisor: `false` on `broker_lost`, `true` on `broker_reconnected` (and on initial
  wiring, since the dispatcher exists only after a successful dial). Wired in the CLI where
  the AMQP dispatcher is built. Callback guarded by a mutex (race-free under `-race`).

## 3. Verification

- `scheduler.TestLeadershipWatchdogStepsDown`: with `check` reporting the lock lost, the
  leader flaps — steps down, drives the gauge true→false, and re-contends (elections ≥ 2).
- `metrics.TestSchedulerLeaderGauge` / `TestBrokerUpGauge`: gauges absent until tracked,
  then reflect 0/1.
- `store.TestLeadershipMutualExclusion` extended: `check()` reports held=true while the
  lock is held.
- Full `-race` suite green; `go build`/`vet` clean; image rebuilt; E2E 34/34.
- **Live**: single/all stack `/metrics` shows `cerbix_scheduler_leader 1` (the leader) and
  correctly omits `cerbix_broker_up` (inproc transport, no broker). `cerbix_broker_up` is
  covered by unit test + the AMQP supervisor path validated live in iter-0071 (D-0129).
- Watchdog/gauge logic only — no heartbeats/retention storage-mode branch → no dual-DB run.
