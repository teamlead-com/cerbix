# iter-0078 — Region affinity in the shipped wiring

## 1. Summary

Seventh `func-hardening` slice. Region affinity is "strict by design" (a monitor belongs to
one region; its region's prober is the only one that may probe it — no fallback to core).
Two gaps let that break in the topologies we actually ship, both invisible until a
private/region-specific target quietly returned the wrong result.

- **`--role all` didn't route pull regions.** `all` is the prod (`docker-compose.prod.yml`)
  and single-geo topology. Its scheduler never called `WithPullRegions`, so a monitor in a
  pull region had its job published to the in-process worker and **probed from core**
  instead of enqueued to `pull_jobs` for the region's HTTP-pull agent. `config.dev.yaml`
  even documented this as a known limitation.
- **The distributed/geo CORE worker ran DB-less.** Composite monitors derive their status
  from their children's current statuses read from the database (no network probe). The
  shipped `worker --region core` mounted the DB-less `config.worker.yaml`, so the composite
  prober returned "composite evaluation unavailable" and every composite flapped **down**.

## 2. What was done

- `cli`: the `all` scheduler now wires `WithPullRegions(cfg.Pull.Regions)` +
  `WithPullMetrics(registry)`, so pull-region jobs go to `pull_jobs` (agent-claimed) exactly
  as under `--role scheduler`.
- `cli`: the test-connection router was refactored to layer pull-region routing over
  **either** base tester (AMQP or the inproc local tester), so a pull-region "Test
  connection" reaches the agent (`pull_tests`) even under `--role all` — no silent local
  fallback. Non-pull regions keep the AMQP RPC / local behavior.
- `deploy/config.worker-core.yaml` (new): `config.worker.yaml` + a `database` block
  (service-name DNS `postgres`/`rabbitmq`, which resolves on the central network in both
  composes). Only the core worker needs the DB; remote geo workers stay DB-less.
- `deploy/docker-compose.yml` (distributed) and `deploy/docker-compose.geo.yml`:
  `worker`/`worker-core` now mount `config.worker-core.yaml` and `depends_on` Postgres.
- `deploy/config.dev.yaml`: the stale "all mode doesn't route pull" NOTE replaced with the
  now-correct behavior.

## 3. Verification

Live, on the actual stacks:

- **Pull routing under `--role all`** (single stack): a monitor created in region `pull1`
  produced rows in `pull_jobs` (waiting for an agent) and **0** heartbeats — it was NOT
  probed by the co-located worker. Before the fix the in-process worker probed it from core.
- **Composites on the distributed core worker**: brought up the distributed profile
  (migrate-once → up); the worker logged `database_connected`; a `mode: all` composite over
  an up child and a down child evaluated to `1/2 child monitors up (mode all)` → **down** —
  a real evaluation, not "composite evaluation unavailable".
- `go build`/`vet` clean; full `-race` unit suite green; E2E 34/34 on the single stack
  (composite-quorum and ghost-region tests confirm core composites and non-pull regions are
  unaffected by the routing/tester refactor).

## 4. Out of scope

Region-worker alerting for pull agents under `--role all` (`WithLiveRegions`) is not wired
here — it is alerting completeness, not the affinity bug, and remains a `--role scheduler`
concern. Composites must run in a region whose prober has DB access (i.e. core); a DB-less
region still cannot evaluate them.
