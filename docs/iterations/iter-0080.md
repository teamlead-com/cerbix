# iter-0080 — Escalation / incident lifecycle

## 1. Summary

Ninth `func-hardening` slice — three lifecycle gaps around auto-incidents and the on-call
escalation ladder.

- **Disabled monitor escalates forever.** `AdvanceEscalations` selected any non-resolved
  auto-incident on a monitor with an escalation policy, without checking `enabled`. A
  disabled monitor is no longer probed, so its open incident can never auto-recover to
  resolve — it pages the on-call ladder indefinitely.
- **Auto-incident double-open (TOCTOU).** `ingest.openAutoIncident` checked
  `FindOpenAutoIncidentByMonitor` then created — two concurrent down transitions could both
  pass the check and open two incidents for one monitor.
- **Failed incident-create pages no one.** For an escalation-policy monitor the ladder
  pages OVER the auto-incident and the flat down-notify is suppressed at delivery. If
  `CreateIncident` failed, there was no incident to escalate and no flat notify — the
  outage went entirely unalerted.

## 2. What was done

- `store.AdvanceEscalations`: added `AND m.enabled` to the incident selection. (Deletion is
  already handled — the `JOIN monitors` drops the row.) A re-enabled, still-down monitor
  resumes escalating.
- Migration `00049_one_open_auto_incident.sql`: resolves any pre-existing duplicate open
  auto-incidents (keep earliest per monitor), then adds a partial unique index —
  `(monitor_id) WHERE source='auto' AND status<>'resolved' AND monitor_id IS NOT NULL`.
  `CreateIncident` maps the resulting `23505` on that index to a new sentinel
  `store.ErrAlreadyOpen`; `ingest.openAutoIncident` treats it as a benign race win.
- `ingest.openAutoIncident`: retries a transient `CreateIncident` failure (3 attempts,
  250ms backoff; `ErrAlreadyOpen` is success, not retried), and logs a persistent failure
  at ERROR with an `escalation` flag so log-based alerting catches the (now rare) silent
  case. Rationale for not using a periodic reopener or delivery-time check is recorded in
  D-0138 (manual-resolve regression / incident-creation race respectively).

## 3. Verification

- `store.TestAdvanceEscalationsSkipsDisabledMonitor`: a disabled monitor's incident fires 0
  escalation steps; re-enabling resumes the ladder.
- `store.TestCreateIncidentRejectsSecondOpenAuto`: a second open auto-incident →
  `ErrAlreadyOpen`; a manual incident is unaffected; a fresh auto-incident is allowed after
  the first resolves.
- `ingest.TestAutoIncidentOpenRetries`: two transient `CreateIncident` failures then success
  → the incident opens (3 calls). `ingest.TestAutoIncidentAlreadyOpenIsBenign`:
  `ErrAlreadyOpen` → no retry, no second incident.
- Existing escalation/incident/ingest suites still green; full `-race` suite green.
- **Live**: migration 00049 applied on the dev DB (goose version 49, index
  `incidents_one_open_auto` present); image rebuilt; E2E 34/34.
- Migration touches `incidents` only (not heartbeats/retention), so no dual-DB-mode run.

## 4. Follow-up

A hard delivery guarantee for the escalation-monitor down alert (open the auto-incident in
the same transaction as the status transition, so it can never be lost) is a larger
architectural change, deferred and noted in D-0138.
