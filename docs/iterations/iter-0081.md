# iter-0081 — Auth-surface hardening

## 1. Summary

Tenth `func-hardening` slice — a focused audit of six auth/tenant-isolation concerns.
Two needed no change; four were real and fixed.

**Already handled (no change):**
- **OIDC token verification.** `go-oidc`'s verifier is built with the client id, so it
  enforces audience == client_id plus signature, issuer, and expiry; nonce and
  state/PKCE are checked in the callback. (The client-credentials verifier's
  `SkipClientIDCheck` is intentional and gated on memberships, not the interactive path.)
- **Status-page cross-project linking.** Components are org-scoped (`monitorInOrg`). The
  org is the tenant boundary and cross-**org** linking is already blocked; intra-org
  cross-project is the same customer, so this is by-design aggregation, not a cross-tenant
  leak. Left as-is.

## 2. What was fixed

1. **Login rate-limiter: XFF spoofing + unbounded map** (`internal/auth/ratelimit.go`).
   The key came from a blindly trusted `X-Forwarded-For` first hop, so a per-request
   spoofed XFF gave every attempt a fresh bucket — the brute-force limit was a no-op. And
   the key map was never evicted. Now `clientIP(r, trustedProxies)` ignores XFF when
   `trustedProxies == 0` (keys on the direct peer) and otherwise reads the client
   `trustedProxies` entries from the right of the XFF+peer chain (a spoofed leading XFF
   can't win); `allow` opportunistically sweeps idle keys every 5 min. New config
   `server.trusted_proxy_count` (default 0), wired through the Authenticator, documented
   in `config.example.yaml`.
2. **Cross-tenant escalation references** (`internal/api/tenant_scope.go` + handlers). A
   monitor's `escalation_policy_id`, an escalation policy's step targets, on-call schedule
   participants, and an override's channel id were persisted with no same-project check
   (FKs enforce existence only; targets are FK-less JSONB). New helpers
   (`channelInProject`, `scheduleInProject`, `escalationPolicyInProject`,
   `escalationStepsInProject`, `channelsInProject`) assert same-project ownership in
   `createMonitor`/`updateMonitor`, `create`/`updateEscalationPolicy`,
   `create`/`updateOnCallSchedule`, and `addOverride`.
3. **Password-change session invalidation** (`store.DeleteSessionsByUser`, wired in
   `changePassword`). A change now drops the user's OTHER sessions while keeping the
   caller's current one — the raw session token is threaded via
   `auth.WithSessionToken`/`SessionTokenFrom` from the middleware. The reset path is
   intentionally left non-invalidating (see Non-change below).
4. **Public status-page id leakage** (`domain.Incident.PublicRedacted`,
   `MaintenanceWindow.PublicRedacted`, threaded `public` flag through
   `writeStatusPageRender`/`enrichIncidents`). The public render now strips
   `project_id`/`monitor_id`/`external_key`/`acknowledged_by` from incidents and
   project/monitor ids from maintenance; the authenticated preview keeps full detail.

## 3. Verification

- `auth.TestClientIP` (0 hops ignores XFF; 1–2 hops skip a spoofed leading XFF; short-chain
  clamp), `auth.TestLoginLimiterEvictsIdleKeys` (sweep bounds the map).
- `api.TestCrossTenantEscalationRefsRejected` (foreign channel/participant/policy → 400;
  same-project → allowed).
- `store.TestDeleteSessionsByUser` (keep-current drops the others, blank drops all, other
  users untouched).
- `api.TestPublicRenderRedactsInternalIDs` (public omits internal ids + external_key;
  authed preview retains them).
- Full `-race` suite green; `go build`/`vet` clean; image rebuilt; **E2E 34/34**.

## 4. Regression found and fixed mid-iteration

The first cut invalidated ALL sessions on both change AND reset. That broke the E2E
shared-session model: `mail.spec` resets the admin then restores the password "through the
still-valid admin session", and `settings.spec` changes the password via the shared
session — deleting all sessions logged the suite out mid-run (and left the admin password
stranded at the temp value). Fixed by keeping the caller's current session on change and
not invalidating on reset; verified by restoring the stranded dev password via the (now
session-preserving) change endpoint and a clean 34/34 E2E run.

## 5. Non-change: reset-time global invalidation

Deliberately deferred. The product/E2E contract treats a self-service reset from a
logged-in browser as keeping that session, and the reset flow carries no current-session
token to preserve selectively; global reset-time invalidation is a separate product/UX
decision (recorded in D-0139). The higher-value proactive-change path is covered.
