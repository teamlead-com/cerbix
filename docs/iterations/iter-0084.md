# iter-0084 — Review-driven P0 hardening (round 2): egress policy split + iter-0083 corrections

## 1. Summary

A follow-up review of the iter-0083 consilium pass found that two of its claims were
inaccurate and one fix was mis-wired. This iteration records the corrections and the
first shipped P0 slice from the review's prioritized backlog (egress policy split).
iter-0083 is left as its original historical snapshot; corrections are recorded here
and in the D-0141 decision entry (the living log), not by editing the earlier report.

## 2. Corrections to iter-0083 / D-0141

1. **"OIDC delivery routes through `prober.Guard`" — false.** OIDC discovery/JWKS/token
   use a 15s-bounded `http.Client` (`auth/auth.go`), NOT the SSRF guard. OIDC is an
   operator-trusted path (an internal Keycloak is a supported deployment); it was never
   routed through the guard. D-0141 amended.
2. **The alert-delivery SSRF guard was effectively open.** iter-0083 shipped the guard
   (`prober.Guard.HTTPClient`/`EgressDialContext`) but wired it from
   `cfg.Prober.AllowPrivateIPs`, which defaults **true** (cerbix legitimately probes
   internal apps). So webhook/notify/SMTP delivery still permitted loopback/RFC1918/ULA/
   CGNAT by default — the mechanism was correct, the policy wiring was the defect. Fixed
   below (P0.2).

## 3. What was fixed (P0.2 — egress policy split)

- New **`notification_egress`** config policy, independent of `prober`, defaulting to
  **deny-private** (and deny-metadata). Alert delivery (webhook/Slack/notify HTTP + SMTP)
  now builds its guard from it via `cli.notificationEgressGuard`; probes keep the
  allow-private prober policy. Opt back in per deployment only for genuine internal
  delivery endpoints.
- OIDC left explicitly operator-trusted (not guarded); documented as a deliberate
  contract, not an omission.
- `config.example.yaml` gained the `notification_egress` block and a breaking-upgrade
  note; the SMTP example no longer implies an internal `mail.internal` works by default;
  `runbook.md` documents the breaking upgrade (existing internal webhook/SMTP endpoints
  must opt in).
- `prober.Guard.HTTPClient` doc corrected: the dialer mechanism is shared, the policy is
  the caller's (deny-private for delivery, allow-private for probes).

## 4. Verification

- `TestEgressPolicyDefaults` (config): probe allows private, notification denies private,
  both block metadata, explicit opt-in honored.
- `TestNotificationEgressGuardWiring` (cli composition): with the default policy, delivery
  to a loopback `httptest` server is blocked; with an explicit opt-in it succeeds — this
  catches a regression that rewires the delivery guard back to `cfg.Prober`.
- `go build`/`go vet`/`gofmt` clean; full `-race` suite green. E2E unaffected (the webhook
  E2E targets a public host and asserts CRUD only; probes still use the allow-private
  prober policy).
