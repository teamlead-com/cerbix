# iter-0096 — Monitoring as Code: review refinements to iter-0095 (FR-017, IN_PROGRESS)

## 1. Summary

Four precise follow-ups from the review of iter-0095, all landed and verified. FR-017/NFR-014
stay IN_PROGRESS; the remaining P0/P1 order in iter-0095 §4 is unchanged (with one added
caveat below).

## 2. Changes

1. **Bounded reader (memory-safe byte limit).** `ScanDirectory` no longer does an unbounded
   `os.ReadFile` before checking size. It reads through `io.LimitReader` capped at
   `min(max_file_bytes, max_total_bytes − total) + 1`, so an oversized file (grown between
   stat and read) is NEVER fully loaded — it is rejected at cap+1. The stat size is kept only
   as a cheap early reject; the bounded read is authoritative. This upgrades the earlier
   "post-read violation rejected" to a real resource bound (TOCTOU now fully closed).
2. **Direct tests for the new bounds.** `fileprovider.TestScanTotalBytesBound` (cumulative
   byte budget), `fileprovider.TestScanBoundedReadRejectsOversize` (bounded reader rejects a
   file larger than max_file_bytes), `runtime.TestReconcileRejectsOversizedBundle`
   (`max_monitors_per_bundle` → whole-bundle reject, no apply, no orphan/freeze).
3. **Living-doc contradiction fixed.** `docs/status.md` and `docs/traceability.md` no longer
   claim the committed smoke proves restore/id+token; both now state it proves
   create → orphan-disable → process-alive only (matching the iter-0095 correction). The
   iter-0094 traceability row is marked IN_PROGRESS with its `§19 all met` claim withdrawn.
4. **Spec §11 made normative for polling.** `func-monitoring-as-code.md` §11 now specifies
   poll-based change detection (name+size+mtime signature + debounce) with the mandatory
   periodic resync as the primary correctness path, and states explicitly that a pure `chmod`
   is guaranteed to be observed no later than the next resync (spec outranks D-0147 per AGENTS).

## 3. Caveat recorded for a remaining item

`max_managed_monitors` (iter-0095 §4 P0 item 2) cannot be a plain `COUNT` inside the apply
transaction: two concurrent applies could each read free quota. Its enforcement MUST serialize
provider-wide — a provider/quota row lock, a provider-scoped `pg_advisory_xact_lock`, or an
equivalent CAS — before the count is trusted. This is now noted so the future implementation
doesn't ship a racy check.
