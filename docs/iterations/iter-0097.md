# iter-0097 — Monitoring as Code: deterministic bounded-reader test + wording fixes (FR-017, IN_PROGRESS)

## 1. Summary

Two small review follow-ups to iter-0096. FR-017/NFR-014 stay IN_PROGRESS; the remaining
P0/P1 order (iter-0095 §4) is unchanged.

## 2. Changes

1. **Bounded reader is now proven directly.** The previous `TestScanBoundedReadRejectsOversize`
   used a 4096-byte file against a 64-byte limit, but the cheap `info.Size()` stat early-reject
   fired first — so `io.LimitReader` was never reached and the "stat allowed → file grew →
   bounded read stops at cap+1" scenario was NOT exercised. Fixed:
   - the read is extracted into `readBounded(r io.Reader, capBytes int64) ([]byte, overflow, err)`;
   - `TestReadBounded` drives it on in-memory readers and asserts an oversized source yields
     **exactly cap+1** bytes with `overflow=true` (never the full source), a within-cap source
     yields the exact bytes with no overflow, and `cap 0` overflows on any byte;
   - the old scan test is renamed `TestScanRejectsOversizeFileByStat` to state honestly that it
     covers the stat early-reject, not the bounded reader. `TestScanTotalBytesBound` continues
     to exercise the bounded reader via the remaining-total budget.
2. **Wording corrections.**
   - iter-0096 said a rejected oversized bundle causes "no apply/orphan/freeze"; the accurate
     semantics are **"no apply/orphan; the project remains frozen/present"** (it IS treated as
     present so the disappearance path never orphans it). Recorded here (iter-0096 is immutable).
   - The living `docs/traceability.md` reference to the removed `TestScanBoundedReadRejectsOversize`
     is repointed to `TestReadBounded` + `TestScanRejectsOversizeFileByStat`.
