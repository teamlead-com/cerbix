# iter-0098 — Monitoring as Code: true leadership fencing of the apply (FR-017, IN_PROGRESS)

## 1. Summary

Closes the P0 from the review: the file-provider apply transaction was on a pool connection
while the advisory lock lived on a separate dedicated connection, so a lock loss mid-apply
was not fenced — a former leader could commit after another node became leader (§17
violation). Fixed by running the apply ON the lock-owning connection.

## 2. Change (Agent A/B)

- `store.LeaderSession` (new): holds the advisory lock on a pinned `*pgxpool.Conn` and exposes
  `Check`, `Release`, and `ApplyFileManagedBundle` — the apply runs on that SAME connection.
  `TryBecomeLeaderSession` acquires it. The scheduler's `TryBecomeLeader` is untouched.
- `store.applyBundleTx` extracted: the whole reconcile body on a caller-owned `pgx.Tx`. Two
  wrappers: `(*Store).ApplyFileManagedBundle` (pool, for tests/non-leader) and
  `(*LeaderSession).ApplyFileManagedBundle` (leader connection → fenced). If the lock
  connection dies, Postgres aborts the in-flight tx AND releases the session lock together:
  the former leader's `Commit` fails, so it can never commit after losing leadership.
- `internal/fileprovider/runtime`: the `Applier` interface now yields a `LeaderSession` for
  the mutating apply (read-only lookups stay on the pool — a stale read only feeds a
  destructive decision whose apply is itself fenced). `NewStoreApplier` adapts `*store.Store`
  (Go has no interface return-type covariance). The reconcile loop applies via the session;
  cli wires `NewStoreApplier(st)`.
- **Fencing test** `store.TestLeaderSessionFencing` (real PG): acquire a session, begin a tx on
  its connection, `pg_terminate_backend` it from another connection → (a) a second candidate
  acquires the freed lock (failover) and (b) the former leader's `Commit` errors and its
  `Check` reports not-held. `runtime.TestProviderLeadershipFailover` updated to sessions.
