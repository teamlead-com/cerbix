# iter-0100 — Monitoring as Code: transactional audit + persisted diagnostics (FR-017, IN_PROGRESS)

## 1. Summary

Closes P1 #1 (transactional audit) and most of P1 #2 (persisted per-bundle diagnostics +
honest last_success + error rate-limit). FR-017/NFR-014 stay IN_PROGRESS; the remaining
P1 work is the RUNTIME diagnostics surface (leadership/last-scan/empty providers in the API,
a cross-replica status concern) and the storm/two-replica/full-real-binary test matrix.

## 2. Changes (Agent A/B/D)

1. **Transactional audit (§9 step 10).** A changed apply appends a `file_provider.apply`
   `audit_logs` row IN the apply transaction (org-scoped, actor NULL, bounded target:
   provider/project/generation/plan counts). A no-op apply writes none. Test:
   `store.TestApplyWritesAudit` (real PG: one row on create, none on the no-op re-apply).
2. **Persisted rejection diagnostics (§15).** `store.RecordBundleAttempt(provider, org, proj,
   path, status, lastErr)` upserts the bundle row with `status`/`last_error` (≤500 chars,
   already secret-free)/`attempted_at`, WITHOUT advancing the applied generation/LKG; an
   unresolvable tenant is a no-op. The reconcile loop now persists a rejected/errored attempt
   (`rejected` for a `*fileprovider.BundleError`, else `error`) on the `max_monitors_per_bundle`
   pre-check and on any `ApplyFileManagedBundle` failure, so an invalid bundle finally SHOWS as
   rejected in diagnostics. Tests: `store.TestRecordBundleAttempt` (persist + no-op).
3. **Honest `last_success` (§16).** `last_success_timestamp` advances only on a clean scan
   (`!Degraded && Rejected == 0`) — a scan with any rejection is no longer a "success", so the
   fleet stale-success alert fires while bundles are broken. Test:
   `runtime.TestLastSuccessOnlyOnCleanScan`.
4. **Error rate-limiting (§16).** `warnThrottled` logs a given (message,key) at most once per
   30s, so a persistently broken bundle can't flood the log.
