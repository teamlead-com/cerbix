# iter-0106 — Monitoring as Code: scheduler listens for config changes (FR-017, IN_PROGRESS)

## 1. Summary

Fixes review P1#2. The file apply committed `pg_notify('monitor_config_changed', …)` but nothing
listened, so a committed config/target change was only picked up by the scheduler's slow 15s
snapshot refresh. A `ConfigNotifier` now turns that channel into an in-process wake signal, and
the scheduler forces a snapshot reload on the next tick when it fires (§12).

## 2. Changes

1. **`store.ConfigNotifier` (`internal/store/confignotify.go`).** Mirrors `ConfirmNotifier`: one
   background goroutine holds a single `LISTEN monitor_config_changed` connection and fans out a
   coalesced `struct{}` wake to subscribers; payload discarded (any signal → full reload);
   reconnect with backoff; a dropped signal is harmless (the periodic refresh is the fallback).
2. **Scheduler (`internal/scheduler/scheduler.go`).** New `configCh` + `WithConfigSignals`; the
   `lead` select has a `case <-s.configCh` that zeroes `lastRefresh`, so the next tick's refresh
   guard fires immediately and reloads `ListEnabledMonitors` — the committed change is scheduled
   within a tick instead of up to `refreshEvery` (15s) late.
3. **cli (`internal/cli/cli.go`).** `configSignals()` builds+runs a `ConfigNotifier` and
   subscribes; wired into the scheduler for the `all` and `scheduler` roles alongside the
   confirm signals.

## 3. Tests
- `store.TestConfigNotifierWakesOnConfigChange` (real PG): a `pg_notify` on the channel wakes a
  subscriber promptly (not the max-hold fallback) — mirrors the PullNotifier test.
- `scheduler.TestConfigSignalForcesSnapshotReload`: with no monitors (reload counting only), a
  config signal forces a second `ListEnabledMonitors` within a couple of ticks, far under the
  15s `refreshEvery` fallback.
- `e2e/mac-smoke.sh` extended (real binary, no restart): after create+update, a **target change**
  now asserts `execution_revision` bumps (config committed + NOTIFY) AND a fresh heartbeat lands
  after the change — end-to-end proof the NOTIFY has a listener that reschedules with the new
  config, not just the fallback. (Monitor interval shortened to 10s so propagation is
  observable; the earlier steps re-checked at the new cadence.)
- `-race` store+scheduler+cli green.
