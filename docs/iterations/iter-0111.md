# iter-0111 — Delete a project (FR-018)

## 1. Summary

Adds a first-class, RBAC-guarded, irreversible **delete project** operation
(`DELETE /api/v1/projects/{projectID}`). Projects could be created and read but never
deleted; the Org-Admin role already advertised "create/delete projects", so the
capability was expected but unimplemented. Spec: [`func-project-deletion.md`](../specs/func-project-deletion.md).
Decision: **D-0150**.

## 2. Design (D-0150)

- **Hard delete via DB cascade.** Every FK into `projects` is already `ON DELETE
  CASCADE` (monitors → heartbeats/rollups/incidents/notifications/dependencies, SLA,
  escalation/on-call, notification channels, project-scoped tokens/webhooks/status
  pages, file bundles). So the store does a single `DELETE FROM projects WHERE id AND
  org_id` in one tx — no application-level multi-table deletion, no new migration.
- **Org-admin only** (`ActionOrgManage`) — symmetric with project creation; a
  project-scoped Project Admin cannot delete the project. Global admin passes.
- **Refused `409 managed_by_file`** when the project owns file-provider bundles/monitors
  (a reconcile would recreate it). The ownership check and the delete share one tx so a
  concurrent file apply can't reclaim ownership between them.
- **Confirmation** is type-the-slug in the UI (GitHub-style, irreversible); the API
  guard is RBAC.

## 3. Changes

**Backend**
- `internal/store/projects.go` — `DeleteProject(orgID, projectID)`: one tx, file-owner
  guard (`file_provider_bundles`/`managed_monitors` by `project_id`) → `ErrManagedByFile`,
  `DELETE … WHERE id AND org_id` → `ErrNotFound` on 0 rows.
- `internal/api/handlers.go` — `deleteProject`: resolve project → 404 if invisible →
  403 unless `ActionOrgManage` → map `ErrNotFound`/`ErrManagedByFile` → best-effort
  `project.delete` audit → 204.
- `internal/api/api.go` — `DELETE /api/v1/projects/{projectID}` route + `Store.DeleteProject`.
- `openapi.yaml` — documented `delete` on `/projects/{projectID}`; **drive-by fix**: the
  mislabeled `delete: Remove a member` that had drifted onto `/organizations/{orgID}/projects`
  is moved to its real path `/organizations/{orgID}/members/{membershipID}` (openapi and the
  committed `schema.d.ts` had diverged). TS schema regenerated.

**Frontend**
- `stores/workspace.ts` — `deleteProject(id)` (DELETE, drop from list, switch away,
  friendly `managed_by_file` message).
- `components/settings/DangerZonePanel.vue` — Danger Zone card + type-slug confirm modal.
- `views/SettingsView.vue` — project-scoped **Danger zone** tab, org-admin-gated.

## 4. Verification

- `go build ./...`, `go vet ./...` — clean.
- `store.TestDeleteProject` — **PASS in both storage modes**: timescale hypertable
  (`cerbix_test`) and declarative partitions (throwaway `postgres:16-alpine`). Covers the
  cascade (monitor gone after project delete), tenant scoping (wrong org ⇒ `ErrNotFound`),
  and the file-provider refusal (`ErrManagedByFile`, project survives).
- `api.TestDeleteProjectAuthz` (`-race`) — 204 org/global-admin · 403 project-admin/viewer ·
  404 outsider/unknown · 409 managed.
- Frontend docker `vue-tsc` + `vite build` — green.
- **E2E** `e2e/tests/project-delete.spec.ts` on a live single-profile stack — create
  project + monitor → Settings → Danger Zone → type-slug confirm → delete → redirect to
  dashboard → project and (via cascade) its monitor return 404. **PASS.**

Non-admin UI visibility is covered by the api unit test (the shared E2E admin session
can't cheaply assume a second role — never add per-test logins).

## 5. Follow-ups

- None blocking. Q1 (rely on the 15 s scheduler snapshot rather than a delete-time NOTIFY)
  held; no noisy in-flight FK-failure logs were observed in the E2E.
