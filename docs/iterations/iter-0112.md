# iter-0112 — Delete an organization (FR-019)

## 1. Summary

Adds `DELETE /api/v1/organizations/{orgID}` — a global admin permanently deletes an
organization and everything under it. The org-level analogue of FR-018 (delete project,
iter-0111), reusing the same shape. Spec: [`func-org-deletion.md`](../specs/func-org-deletion.md).
Decision: **D-0151**.

## 2. Design (D-0151)

- **Hard delete via DB cascade.** Every FK into `organizations` is `ON DELETE CASCADE`
  (memberships, projects → their whole subtrees, org-level status pages, org-scoped
  tokens/webhooks, audit_logs), so the store does a single `DELETE FROM organizations
  WHERE id` in one tx — no new migration.
- **Global admin only** (`ActionGlobalManage`) — symmetric with `createOrganization`.
  Checked before any existence lookup, so non-admins get `403` without an existence leak;
  a missing org (for a global admin) is `404`.
- **Refused `409 managed_by_file`** when the org owns file-provider-managed projects. A
  reconcile does **not** recreate a deleted org (it fails tenant resolution,
  `ErrBundleTenantNotFound`, and would error every pass) — refusing keeps the provider out
  of a perpetual error state. Checked in the same tx as the delete.
- **Instance-level audit.** `org.delete` is recorded with `org_id = NULL` (an instance
  action; `audit_logs.org_id` is nullable since migration 00047) precisely so the row
  **survives** the cascade that removes the org's own `audit_logs`.
- **Confirmation** is type-the-org-slug in the UI; the API guard is RBAC.

## 3. Changes

**Backend**
- `internal/store/organizations.go` — `DeleteOrganization(orgID)`: one tx, file-owner
  guard (`file_provider_bundles`/`managed_monitors` by `org_id`) → `ErrManagedByFile`,
  `DELETE … WHERE id` → `ErrNotFound` on 0 rows.
- `internal/api/handlers.go` — `deleteOrganization`: global-admin gate first → 403,
  `GetOrganization` → 404, map `ErrManagedByFile` → 409, instance-level `org.delete` audit,
  204.
- `internal/api/api.go` — `DELETE /api/v1/organizations/{orgID}` route + `Store.DeleteOrganization`.
- `openapi.yaml` — documented `delete` on `/organizations/{orgID}`; TS schema regenerated.

**Frontend**
- `stores/workspace.ts` — `deleteOrg(id)` (DELETE, drop from list, switch to another org +
  reload its projects, friendly `managed_by_file` message).
- `components/settings/OrgDangerZonePanel.vue` — org Danger Zone card + type-slug confirm modal.
- `views/SettingsView.vue` — org-scoped **Danger zone** tab, global-admin-gated (distinct
  from the project-scoped one from FR-018).

## 4. Verification

- `go build ./...`, `go vet ./...` — clean.
- `store.TestDeleteOrganization` — **PASS in both storage modes** (timescale hypertable +
  declarative partitions): two-level cascade (org → project → monitor), unrelated orgs
  survive, unknown ⇒ `ErrNotFound`, file-provider refusal (`ErrManagedByFile`, org survives).
- `api.TestDeleteOrganizationAuthz` (`-race`) — 204 global-admin · 403 org-admin/member/
  outsider · 404 unknown · 409 managed.
- Frontend docker `vue-tsc` + `vite build` — green.
- **E2E** `e2e/tests/org-delete.spec.ts` on a live single-profile stack — global admin
  creates an org + project + monitor, Settings → org Danger Zone → type-slug confirm →
  delete → redirect → org and (via cascade) its project + monitor return 404. **PASS.**
  The FR-018 project-delete spec was re-run green alongside (regression).
