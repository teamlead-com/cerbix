# iter-0113 — Monitoring as Code hardening pass (FR-017 reopened)

## 1. Summary

A third independent review of the Monitoring-as-Code file provider (FR-017, closed at
iter-0110) surfaced **seven** defects — two P0, four P1, two P2 (the two P0/P1 counts overlap;
see the table). All were independently confirmed and fixed on branch `fix/mac-hardening`, each
as its own commit with a regression test, and each verified against **both storage modes**
(TimescaleDB hypertable + declarative daily partitions) where a real database is involved.
Decisions: **D-0152** (target inline-secret scope), **D-0153** (scope-change quarantine).

## 2. Findings and fixes

| # | Sev | Defect | Fix | Commit(s) |
|---|-----|--------|-----|-----------|
| 1 | P0 | File-provider leaders each pin a pool connection for life; with more providers than the pool floor, providers past the floor block forever in `pool.Acquire` and never reconcile — and the winners' reconcile queries also deadlock. | Size `MaxConns` to fit every leader pin + reconcile + pinned-app baseline + query headroom; detect an operator `pool_max_conns` via `pgx.ParseConfig` RuntimeParams and fail fast if it is too small; log the actual cap. | `f1ed288`, `efc0f1a`, `956e7d4` |
| 5 | P1 | A monitor `target` could carry credentials — URL userinfo (`https://u:p@h`) or a secret query key (`?token=…`) — reaching the DB and diagnostics in cleartext. | Reject userinfo, secret query keys (reusing `secretSettingKeys`), and malformed URL-shaped targets; never echo the target/value. D-0152. | `61b1396`, `22aacb0`, `bf88cb4` |
| 3 | P1 | The leader loop sampled the directory fingerprint AFTER reconcile, so a file written *during* a reconcile was absorbed into `lastFP` and not re-reconciled until the periodic resync. | Sample the fingerprint BEFORE each reconcile (initial/resync/debounced) and remember that value; a mid-reconcile write then re-triggers on the next poll. | `54e6b29` |
| 2 | P1 | Absence was trusted for every owned project, so a provider restarting with the same name but a narrower/different scope value orphaned its prior-scope monitors. | `ProviderScopeConfig.Includes` filters the owned set to the current scope before the absence check; out-of-scope rows are quarantined (kept, read-only, logged), never orphaned or adopted. D-0153. | `3786539`, `42a7b92` (docs) |
| 4 | P1→P0 | A tenant-bound invalid bundle suspended orphaning **provider-wide**; the first fix keyed the freeze on the file header, which let a header typo orphan the real prior tenant; the second still tracked rejected paths incompletely (duplicates/over-limit). | Freeze per-project by the **prior LKG path**: an owned project is preserved when its `source_path` is present this scan but did not cleanly apply (duplicate, decode error, over-limit, apply error, or header typo) — tracked as `presentPaths` vs `cleanlyApplied`. Duplicate-by-claim counts bound-invalid declarations; binding runs before policy checks; a non-string tenant header stays unbound. | `7568572`, `4ccf765`, `e19aa47` |
| 6 | P2 | `leaderKeyFor` = base \| FNV-1a-32(name); two names whose 32-bit hash collided shared one advisory key, so one provider never led. | FNV-1a-64 under a distinct namespace byte, plus a startup `AssertDistinctLeaderKeys` guard that refuses to boot on a configured collision — collision-free by construction. | `e8078dc`, `ea0cb85` |
| 7 | P2 | The warn-throttle map was unbounded (keyed by msg+path), growing for the process lifetime under directory churn; a naive LRU then re-logged every scan for a wide working set. | Bounded LRU (memory) **plus** a provider-wide fixed-window emission budget with a single suppressed-count summary (log volume). | `f809524`, `ae85bf2`, `63b6195` |

## 3. Verification

- `go build ./...` and `go vet ./...` clean.
- New/updated regression tests in `internal/{store,config,fileprovider,fileprovider/runtime}`;
  every destructive-case test (pool progress, mid-reconcile absorb, over-suspend, the four
  #4 path-protection scenarios, scope-orphan, leader-key collision) was verified to FAIL when
  its fix is reverted.
- DB-backed suites (`internal/store`, `internal/fileprovider/runtime` leadership) run under
  `-race` against **both** a plain `postgres:16` (declarative partitions) and a
  `timescaledb-pg16` (hypertable) instance.
- Independent per-commit review by the `monitoring-review` agent; findings #1, #2, #3, #5, #6,
  #7 signed off; #4 iterated to the present-path model after two P0 catches.

## 4. Follow-ups

- Keep `secretSettingKeys` the single source for target + settings secret classification as new
  credential aliases appear (access_token/signature/…), per the #5 review note.
- The scope-change quarantine (D-0153) is deliberate; an explicit provider release/migration
  operation remains future work.
- **Rejected-never-applied diagnostics rows** (non-blocking, from the #4 review): a bindable
  invalid bundle at a new tenant/path can insert a generation-0 `file_provider_bundles` row
  (status `rejected`, no `managed_monitors`), which `FileProviderProjects` then counts as owned.
  It is not destructive (the path freeze keeps it out of orphaning while the file is present,
  and it can normalize to an empty applied bundle once the file disappears), but the desired
  retention/lifecycle of rejected-never-applied rows should be made explicit — candidate: prune
  bundle rows that never reached an applied generation once their source path is gone.
