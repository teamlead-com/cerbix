# iter-0113 — Monitoring as Code hardening pass (FR-017 reopened)

## 1. Summary

A third independent review of the Monitoring-as-Code file provider (FR-017, closed at
iter-0110) surfaced seven defects. All were independently confirmed and fixed on branch
`fix/mac-hardening`, each as its own commit with a regression test, each per-commit
re-reviewed, and each verified against **both storage modes** (TimescaleDB hypertable +
declarative daily partitions) where a database is involved. Decisions: **D-0152** (target
inline-secret scope), **D-0153** (scope-change quarantine).

## 2. Iteration plan (7 tasks, ordered P0 → P1 → P2)

| Task | P | Finding |
|------|---|---------|
| T1 | P0 | Pool starvation: file-provider leaders pin pool connections for life; past the pool floor, providers block forever and the winners' reconcile queries deadlock. |
| T2 | P0 | Orphan-safety: a tenant-bound invalid bundle over-suspended provider-wide; a naive per-project freeze then keyed on the file header, letting a header typo / duplicate / over-limit orphan the real prior tenant. |
| T3 | P1 | Target inline secrets: URL userinfo and secret query keys reached the DB/diagnostics in cleartext. |
| T4 | P1 | Mid-reconcile absorb: a write during a reconcile was folded into `lastFP` and not re-reconciled until the periodic resync. |
| T5 | P1 | Scope-change over-orphaning: a same-name provider with a changed scope value orphaned its prior-scope monitors. |
| T6 | P2 | Leader-key collision: FNV-1a-32 advisory key let two names collide so one provider never led. |
| T7 | P2 | Unbounded warn-throttle map; and, once bounded by an LRU, a wide working set re-logged every scan. |

## 7. Follow-ups

- Keep `secretSettingKeys` the single source for target + settings secret classification as new
  credential aliases appear (access_token/signature/…), per the T3 review note.
- The scope-change quarantine (D-0153) is deliberate; an explicit provider release/migration
  operation remains future work.
- **Rejected-never-applied diagnostics rows** (non-blocking, from the T2 review): a bindable
  invalid bundle at a new tenant/path can insert a generation-0 `file_provider_bundles` row
  (status `rejected`, no `managed_monitors`), which `FileProviderProjects` then counts as owned.
  It is not destructive (the path freeze keeps it out of orphaning while the file is present,
  and it can normalize to an empty applied bundle once the file disappears), but the desired
  retention/lifecycle of rejected-never-applied rows should be made explicit — candidate: prune
  bundle rows that never reached an applied generation once their source path is gone.
- Pre-existing repo-wide lint debt (errcheck/forbidigo/staticcheck outside MaC source) is
  tracked separately and out of scope for this pass.
