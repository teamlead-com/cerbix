## 2. The gen3 review round (three P0s, all self-inflicted)

Every one of these shipped inside iter-0119's own slice and passed its full suite.

| # | Defect | Why the suite missed it |
| --- | --- | --- |
| P0 | **The carrier was chosen from the STALE snapshot region.** The scheduler nominated a batch by snapshot region and passed one scalar carrier; the materializer then read the authoritative row, picked the right region and the right keyring, and sealed under the carrier of wherever the monitor used to be. A monitor moved from a capability-2 region to a capability-1 one just before the read got a correct, correctly-keyed job published onto a queue nobody in its new region consumes. | No test moved a monitor between regions of DIFFERENT capability. Region-move regressions existed, but they asserted routing and keys — not the carrier. |

| P0 | **The default single-binary `role=all` never moved past generation 2.** The carrier was raised only from a pull capability-2 heartbeat or an mqadmin v3 consumer; role=all registers its executor in-process, so the execution binding and field-set rules were inert in the most common deployment — while the worker inside the same process could open them perfectly well. | Every generation-3 test used an explicit external executor. Fixes in `8fb164e`: the carrier policy is a per-region map resolved on the authoritative row
(the carrier now comes from the same row as the keyring) and the post-read readiness re-check
tests the capability THIS job's carrier needs; test materialization is generation-aware with
exact 1/2/3 pull routing and a `ServeTestsV3` consumer; a same-process executor's capability
is this binary's by construction; `cerbix_dispatch_transport_failed_total{reason}` is its own
family with a fail→success recovery regression; the down migration FAILS CLOSED with the
pending count; and the carrier→envelope mapping is exact, with anything unknown an error on
both sides.

## 3. The §9 debt, closed

### 3.1 The fail-open lie, demonstrated (not asserted)

Unit tests prove the structural gate refuses a stripped credential before dialling. Only a
real target can show what that refusal prevents. `make secret-smoke` now runs an **auth-less
Redis** — it answers PING to anyone — behind a credentialed monitor, stops the agent so the
enqueued job is still pending, and performs the actual attack: `payload -
'credential_envelope'`. One deleted JSON member. No key, no forgery.

UP is unreachable there by any honest path (Redis rejects AUTH when no password is set), so
an UP result can only mean an anonymous probe ran. Assertions are ordered so a regression
fails saying the monitor **reported UP** — that is the defect; a missing `probe_error` is
only its symptom.

**Verified by mutation on live infrastructure.** Restoring the pre-r7 envelope-absent
short-circuit produces:

```
FAIL: a credential-stripped redis probe reported UP — the gate let an anonymous probe
      through and the monitor now lies
```

That is the whole amendment in one line, reproduced rather than argued.

### 3.2 Generation 3 in a live mixed-capability fleet

The smoke now proves core actually EMITS carrier generation 3 into a region whose agent
declared capability 2 — previously only unit-tested — then claims from that same live queue
as both capabilities: a capability-1 claim is never handed a generation-3 row, a capability-2
claim receives it, and an understated capability on the generation-3 endpoint is refused with
400. A capability-1 client mid-rollout is a legitimate state, not an attack, which is exactly
why the barrier must be one-directional in this shape.

### 3.3 The browser gate, and FR-020 on by default in dev

`e2e/tests/secrets.spec.ts` creates a secret through the PANEL and then exercises the guards
that exist only because something references it: deletion refused with 409 `secret_in_use`;
rename re-points the reference atomically, verified by reading the monitor back; the value
absent from every read surface and from the rendered page; and, once the consumer is gone,
deletion succeeds — the guard was about the reference, not about the secret.

`docker/config.dev.yaml` now enables FR-020 with a per-region dispatch keyring. That is the
point rather than scaffolding: a feature that only ever runs inside a bespoke smoke is a
feature nobody exercises by accident. Two mistakes are recorded because both look configured
and are not — a 43-byte base64 key rejected at startup (fail-fast working), and a keyring
filed under the literal name `default` while monitors live in `core`, which rejected every
dispatch with `no_dispatch_key`.

## 5. Acceptance

**FR-020 and NFR-015 return to `DONE`.** The amended §9 matrix is fully evidenced: the three
audit blockers and the P1, the six findings of the gen3 review, and the three items
iter-0119 §8 named as missing. What makes this different from the iter-0116 acceptance it
replaces is not that more tests pass — it is that the central claim is now demonstrated as a
failure that can be reproduced on demand, rather than inferred from green unit tests.

One thing is outstanding and is stated rather than folded in: the independent reviewer's
round-2 acknowledgement of `8fb164e` had not arrived when this report was written. His
round-1 findings are all addressed above and the two-round contract puts any residual
disagreement to the owner rather than to a third round, so acceptance does not wait on it;
if that acknowledgement contradicts anything here, it gets its own report rather than an
edit to this one.
