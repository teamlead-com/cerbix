# iter-0121 — Secret inventory: the rest of the audit (three P1s and the P2 set)

## 1. Summary

The FR-020 conformance audit produced more than the four findings that gated acceptance.
This iteration closes everything that was left: **three P1s** and **seven P2s**, none of
which were part of the §9 matrix.

**Acceptance is unchanged.** FR-020/NFR-015 were re-declared `DONE` in
[iter-0120](iter-0120.md) on the §9 evidence; nothing here alters that, and nothing here was
withheld from it — these were tracked separately from the start, and are closed now because
"the blockers are fixed" is a poor reason to leave known defects standing.

Two commits: `5062892` (P1s) and `78e77c9` (P2s).

## 2. The three P1s

| Defect | What it actually was | Why nothing caught it |
| --- | --- | --- |
| **MaC apply violated the §4.3 lock order.** | `monitorSecretBindings` locks its secret rows in id order — correct for ONE monitor, but apply called it inside the per-entry loop, so across a bundle the transaction took S1, M1, S2, M2 … A concurrent rotate or rename, which takes all its secret rows first, can hold S2 while waiting for M1. Resolution is now hoisted into `planSecretBindings`: every secret the plan touches is locked in one id-ordered step before any monitor row is written. | The outcome was fail-safe — both sides abort, the bundle keeps its last-known-good, `lock_timeout` bounds the wait — so a deadlock looked like a transient blip rather than a design fault. |
| **A partial PATCH could not preserve the stored credential.** | The API ran every submitted config through exactly-one-of, but the value is write-only: a client that read the monitor back never had it to resend, so changing any OTHER setting required sending `"password": ""` as a placeholder. The store already knew how to preserve, expressing it by stuffing a fake password in and stripping it out — so the two layers disagreed about whether an omitted slot was legal. The rule now lives in the domain as `SurfaceAPIUpdate` and both layers call it. | Both layers had tests. Neither had a test for the case where they disagreed, because each was written from its own side of the boundary. |
| **A dangling `password_ref` rendered a blank field and said nothing.** | The `<select>` binds a value that is absent from its options, so a monitor pointing at a secret the project no longer has looked like a monitor with nothing selected. | The state cannot be produced through the API at all — the guards prevent it — so it only arises from a bundle restore or a project moved between environments. Nothing in the suite creates those. |

## 3. The P2 set

- **Readiness degraded on the FIRST authentication failure**, while the spec degrades on a
  persistent one. Two consecutive failures now degrade; a success clears the streak;
  failures that are unambiguous statements about the executor's own configuration (no key,
  or none matching the id) stay immediate, because repeating them tells nobody anything new.
- **A skipped monitor was counted as a secret-resolution failure.** A row the authoritative
  read finds disabled or deleted is skipped by design (§4.4.3); counting it makes ordinary
  reconcile churn look like broken credentials, and an alert that fires during normal
  operation is an alert people mute.
- **The D-0142 fence SQL existed twice**, hand-copied between `UpdateMonitor` and the
  rotation fence — which an earlier review had specifically required to match character for
  character. One `revisionFenceSetSQL` constant now, so they cannot drift.
- **`resolveProjectSecret` was dead production code** kept alive only by tests, moved into
  the test file. A second decrypt path sitting in the production file invited the assumption
  that it was one of them.
- **The postgres prober's comment described a default it no longer explained** (see §5 —
  the default itself was deliberately left alone).
- **`CLAUDE.md` still described the pre-FR-020 world** — one keyring, `Redacted()` as the
  boundary — on the branch that replaced it.
- **Two secrets-API error codes had no mapping**, so an operator who hit the per-project
  quota was shown the bare string `secret_quota`. The mapping moved into
  `lib/secretErrors.ts`: one place instead of three near-identical ternary chains, which is
  exactly how the gap appeared.

## 4. A test that asserted the right thing and proved nothing

Worth recording because it nearly shipped.

The lock-order regression blocks a secret in another transaction and then checks, with `FOR
UPDATE NOWAIT`, that no monitor row is locked while the apply waits. The first version chose
the blocked secret with `ORDER BY id DESC LIMIT 1` — "the last one". It passed. It also
passed **under the mutation that restores the buggy per-entry order**, which is the only
reason it was caught at all.

The cause: `plan.Entries` is sorted by UID, not by secret id. Blocking a randomly-chosen
secret has a coin-flip chance of blocking the FIRST entry's, in which case the apply stalls
before touching anything and the probe succeeds no matter which code is running. The test
now blocks the second entry's secret by name, and says why in a comment.

The general lesson is not "write better tests" — the assertion was right the first time. It
is that a regression is only evidence once it has been observed to FAIL, and that a mutation
run is what separates a test from a decoration.

## 5. Deliberately not fixed

**The postgres prober still defaults `sslmode` to `prefer`.** Reference-based monitors are
normalized to `require` before they reach it, so the fallback only applies to rows written
before that contract existed. Raising it would silently flip those monitors from
opportunistic to mandatory TLS and start failing every plaintext server they point at.
Changing the transport posture of already-running checks is a migration decision with an
operator-visible cost, not a prober default someone tidies up in a P2 sweep. The comment now
says which rows it applies to and why it stays.
