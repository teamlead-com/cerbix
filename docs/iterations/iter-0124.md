# iter-0124 — FR-021 Service Reliability, phase 1: the declaration, the epoch, and the seal

## 1. Summary

The product had five capabilities that were all *about* something it did not model. A monitor
answers "did this check pass"; nothing answered "was **checkout** available, and who decided
what that means". Phase 1 of FR-021 introduces that object and the machinery under it, and
stops deliberately short of the number.

What ships:

- the pure evaluator (`internal/reliability`) — a piecewise reducer over breakpoints, two
  conserved axes, duration-weighted in microseconds;
- the two-axis storage model — `definition_revision` (what a human declared availability to
  MEAN) and `evaluation_epoch` (what the system was MEASURING), written in one transaction;
- ingest→seal handshake, the contiguity watermark, durable repair ranges, and the maintenance
  mutation contract;
- bundle **format 2**, so a service is declarable as code beside the monitors it names;
- the REST surface and the three SPA screens from the approved mock.

What does **not** ship, and is absent rather than zeroed: availability over a window, the
error budget, the burn rate, coverage. A `0%` a client would render as a number is exactly the
confident falsehood this feature exists to prevent, so `reliability` is a present-and-null key
in the API and there is no percentage anywhere in the UI. An E2E assertion enforces that at the
DOM level: no leaf element whose entire text is a percentage.

Design took **seven adversarial rounds** before implementation began (D-0159, spec r8 APPROVED,
47 acceptance invariants). Implementation took **fifteen slices**, each mutation-tested.

## 3. The decisions that cost the most to get right

**A fact references the EPOCH, never the revision.** Two axes with different owners and
different authority rules cannot share one stream. Every definition-revision transaction
creates a matching epoch unconditionally: a revision with no epoch is not a latency problem,
it is an unsatisfiable reference. The store test that catches a regression here asserts
`revision_count == epoch_count`, not that an epoch exists.

**`effective_at = ceil_to_bucket(created_at)` from the DB clock.** A declaration is
prospective. Applying it to the bucket it was written in would restate a bucket already partly
measured under the previous definition. Only the FIRST revision may be retroactive
(`BackfillFrom`, floored), and what that produces is a *declared reconstruction* evaluated with
today's members — the UI says so in those words rather than presenting it as evidence.

**`sealed_through` is defined by CONTIGUITY.** A hole holds the watermark rather than being
jumped over. This is why the services LIST shows the watermark as its last column and not a
90-tick strip: a strip in a table row draws a plausible picture over a service that stopped
materializing two hours ago, where a lagging timestamp cannot be misread.

**The seal/ingest handshake is gated on ACTUAL insertion.** `service_bucket_ingest` is
upserted in the heartbeat's own transaction, and the seal UPSERTs-then-locks. The obvious
lock-then-upsert order leaves a phantom: a heartbeat committing between the seal's read and
its write is sealed over.

**Repair is a durable RANGE, not "the current job".** Coalescing preserves the union and each
batch carries a maintenance-generation CAS, so a repair that raced a maintenance edit is
discarded rather than writing facts computed under a definition that no longer holds.

## 4. Defects the slices found in their own tests

Mutation testing was applied to every slice, and it repeatedly found defects in the tests as
often as in the code. Three worth recording:

- **Slice 5**: the execution path reused the declaration path's supersede helper, so editing a
  monitor silently marked the service's DECLARATION `superseded_before_effect`. The tests did
  not catch it because they asserted epoch *counts*, and same-boundary supersession displaces
  rather than accumulates. Split into `supersedeEpochsAtBoundary`; tests rewritten to assert
  identity.
- **Slice 7**: the watermark query returned the first broken ROW's start instead of the gap's
  start — a bucket PAST the hole. A `stops` CTE now distinguishes non-sealed from missing.
- **Slice 8**: `SET LOCAL statement_timeout` through a pool is a no-op, and the code carried a
  comment admitting it. Replaced with a dedicated acquired connection and session timeouts.

Slice 14 found one more of the same kind: the API's fake store returned a bare error on a
duplicate slug where the real store returns `ErrConflict`, which would have let a 500 pass
review as a 409.

## 5. Three gaps the API surfaced in the store

Building the REST layer made three store behaviours visible as 500s, all fixed where every
caller passes rather than in a handler:

1. A UI declaration or delete against a **file-owned** service is now `ErrServiceManagedByFile`
   → 409. The file apply reaches `putServiceDeclarationTx` directly, which is exactly the write
   this refuses to let a human make behind the reconcile's back. Ownership persists while
   orphaned — absence from a bundle is not a release.
2. A duplicate slug is `ErrConflict` → 409, not a scan error.
3. A malformed slug is refused at the store. Both callers validate first; the store is the
   choke point every future caller comes through, and the slug is the URL segment **and** the
   bundle reference key.

`domain.ValidServiceSlug` delegates to the monitor rule rather than restating it. The same
reasoning gave `FreshnessPolicy` a JSON codec: the bundle spells the floor `90s` and a bare
`time.Duration` would spell it `90000000000`. One policy field with two spellings is the same
defect as two validators, so JSON now uses the duration string and still reads the integer that
older rows hold.

## 6. UI

Three views implement the approved mock (D-0159, `docs/design/notes.md`), including its three
placement rules:

- **Services sits ABOVE Monitors as a PEER.** Order expresses level of abstraction; nesting
  would express containment, which the model rejects — a monitor may be in several services'
  SLI, or in none, and zero services is a valid state forever.
- **The uptime strip is a CARD element, never a table cell.** The list is numeric and its last
  column is the watermark.
- **The `NEW` badge is a temporary adoption affordance** and must disappear once the project
  has its first service — including one a bundle created, which is why the nav probes the count
  once per project instead of waiting for a visit.

The declaration editor keeps the two lists physically separate with the rule between them.
That rule is the load-bearing element of the screen: without it the ordinary action *"let me
add a Redis check for diagnostics"* silently redefines what availability of checkout means.
Unchecking a context member drops it as an input in the same gesture, and quorum thresholds are
validated against the DECLARED input count, so a policy made unsatisfiable is refused at the
edge rather than becoming a permanent `Bad` nobody can explain.

## 8. Scope explicitly deferred to phase 2

Availability over a window, error budget, burn rate, decidable coverage, the reliability
timeline and the segments/provenance screens. All of them read from **sealed facts only**,
which is why the watermark ships before any of them. The mock's five screens include those
three; they are built when there is something true to put in them.
