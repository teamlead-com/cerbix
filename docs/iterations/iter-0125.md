# iter-0125 — FR-021 phase 1 reopened: twelve P0s, and the one class of test that would have caught all of them

## 1. Summary

iter-0124 closed phase 1 as DONE. An implementation review rejected it, and the
rejection was right: **the subsystem was correct and unreachable.**

Nothing outside a test ever created a `service_materialization` row, and nothing ever asked
for a bucket to be computed. A service declared through the shipped API produced zero facts
forever and `sealed_through` stayed NULL. Every unit test passed because every unit test
called the store directly — and the browser spec recorded the defect *as its expectation*,
asserting "not materialized yet" as a resting state when it was the only state the system
could reach.

Eleven more P0s followed the same pattern in smaller ways: a repair path that refused to
touch the sealed facts it existed to fix, a claim that could not be recovered, an ingest path
outside its own handshake, a linearization point that held for one caller of five, a
retroactive-maintenance contract whose entire implementation was referenced only by its own
tests.

iter-0124's `DONE` is withdrawn. This report is the canonical disposition; iter-0124 stands
as written.

## 2. The class of defect

Every one of the twelve is the same shape: **code that is right, and unreachable, guarded by
tests that reach it directly.** Mutation testing cannot find this — the code under test is
correct, so every mutant dies honestly. Neither can coverage: the lines run.

What finds it is a test forbidden from naming the thing it verifies. The new
`servicereachability_internal_test.go` may use only what the product uses — the declaration
write the HTTP handler calls, the result-recording the ingest pipeline calls, the leader
slice the scheduler calls — and it fails on the shipped code at the first assertion.

The helper that hid it is gone. `startMaterialization` inserted the materialization row and
was the only thing in the codebase that ever created one.

| P0-2 | Repair refused to rewrite sealed facts — the buckets it existed to fix | Two materialization modes; recompute stays sealed; the restatement is audited with both sides |
| P0-3 | Maintenance contract off the product path (legacy INSERT + hard DELETE) | API creates through the checked family, DELETE **archives**, annul is its own endpoint, preview endpoint added |
| P0-4 | Preview token not bound to the mutation it authorized | Token carries monitor + range + kind; confirm verifies all four; stored raw floor used as the monotonic predicate it was documented to be |
| P0-5 | A crashed leader's claim stranded the range forever | Lease on claim; expired lease reclaimable, live one not stealable; lease extended in the cursor's own transaction |
| P0-6 | Historical ingest outside the seal handshake; late data behind the watermark repaired nothing | Backfill in an explicit tx, marks gated on actual insertion; late data queues its own `late_data` repair atomically |
| P0-7 | Epoch bump on `UpdateMonitor` only — MaC and rotation bypassed it | Moved into the shared write contract; the rotation fence opens epochs too (the secret generation is IN the snapshot) |

## 4. Two things worth keeping

**A safeguard that cannot fire is not one.** P0-8 was first fixed twice: the FK drop *and* an
`invalidated_at` flag written on service deletion. The mutant proved the flag never fired —
with the snapshot intact the ordinary set comparison sees the change by itself. The flag and
its column were removed rather than kept behind a softened comment.

**Two of the new tests were wrong first, and wrong in the same way**: they built a situation
that could not exhibit the defect (a window on a non-SLI monitor affects nothing; deleting the
only affected service leaves nothing to gate), so they passed against code that had the hole.
Both were rebuilt to hold the affected set constant so only the property under test can fail.

Migrations 00067–00069 apply in both modes; down paths are reversible except the

## 6. Still open (P1, not claimed as done)

The reviewer's nine P1 findings are not addressed here and are not claimed: composite
`service_id` in the epoch/fact FKs, UI/declaration audit coverage beyond the two events added,
archive semantics for a future window, a tx-scoped coalescer for maintenance invalidation,
`ServiceDetail`'s multi-snapshot assembly, the range deadline over the whole slice, service
fact partition maintenance, the `NO TRANSACTION` migrations and the slug-suffix overflow, and
the service metrics/readiness surface. Config exposure of the caps added in P0-10 (§10.10) is
open with them.
