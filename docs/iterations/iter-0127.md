# iter-0127 — FR-021 round 3: eight P0s, the fixes my fixes needed, and a mutant that survived my first test

## 1. Summary

Review round 1/2 rejected iter-0126 with eight P0s and six P1s. This iteration closes all
eight P0s and five of the six P1s, and — required by the previous round's own findings —
re-applies every fix as a mutant against the iter-0126 code before claiming it.

The pattern held for the third consecutive round: of the eight, at least three were defects
**introduced or half-fixed by my previous pass**. The interval-overlap hole (P0-1) was in the
gate I built; "both axes" (P0-2) was an AC I wrote that my own code did not satisfy; the era
that reset the watermark but not the cursor (P0-6) was masked by a test that wrote the missing
fix into its fixture. This report keeps those, because the class matters more than the list.

It also keeps a governance correction: iter-0126's status rows used a status value the file's
own header does not permit, claimed a dual-mode `-race` run that was single-package on one
mode, and counted a mutant that had no regression. Those claims were retracted in `003c4b8`
**before** any new work began.

## 3. The mutant that survived my first test

The deadlock regression for the batch ordering passed against the unsorted code. Reason: its
rounds reused one PK set, so from round two on `ON CONFLICT DO NOTHING` matched existing rows
and took **no row locks at all** — twenty-four of its twenty-five rounds could not have
deadlocked no matter what order anything ran in. Every round now inserts fresh rows, and the
unsorted mutant dies three out of three runs on fresh databases.

That is the fourth test across three rounds that was wrong before it was right, and all four
failed the same way: the test did not construct the state its assertion needs. The check that
catches this is mechanical — re-apply the shipped behaviour and demand a failure — and it is
now part of how every fix in this feature is claimed.
