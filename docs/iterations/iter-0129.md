# iter-0129 — FR-021 round 5: deadlineTx, the interval-aware affected set, and a PostgreSQL fact I had wrong

## 1. Summary

Round 1/2 rejected iter-0128 with two P0s, four P1s and one P2. All are addressed. The round
also corrected a piece of my PostgreSQL knowledge with a reproducible proof: `SET LOCAL`
issued inside a savepoint SURVIVES its `RELEASE` into the parent transaction — only
`ROLLBACK TO SAVEPOINT` reverts it. Verified on the live PG16 before building on it.

## 2. The mechanism: deadlineTx

Both P0s had one root: bounds were set at phase boundaries while the contract (§10.10,
D-0159) demands them derived from the remainder before every statement. `deadlineTx` wraps a
transaction so that:

- a client-side check refuses to START any statement inside the reserve — the only thing
  that stops accumulation, since many statements each finishing just under a bound set once
  sum to any total;
- the server bounds are re-derived from the shrinking remainder (re-issued when stale beyond
  a drift allowance, so fast statements pay nothing);
- the client context deadline is a NET one scheduling tolerance behind the slice — never the
  mechanism. The +2s cushion is gone. The server always speaks first, which is what keeps the
  leader's lock-owning connection alive through a blocked slice;
- a parent invalidates its view of the session's bounds whenever a child savepoint finishes,
  because of the RELEASE fact above.

The preview budget now covers lock → resolve → gate → project → persist → commit, with a
persist RESERVE the work phases may not touch: an exhausted budget still writes the
approximate answer down instead of dying while trying to say it. The pre-phase 1-second floor
is gone; blocked on the membership lock, a 500ms preview returns a bounded SERVER error, and
the regression rejects `context.DeadlineExceeded` by name — a wait "bounded" by killing the
connection is the mechanism the server-first rule exists to prevent.

## 3. The affected set answers the question asked

`servicesAffectedByWindow` joined any effective revision the service ever had. It is now
interval-aware — a revision governs `[effective_at, next revision's effective_at)` and only
validity overlapping the requested range counts. Three existing tests turned out to encode the
"ever" semantics and were rebuilt: under interval-awareness a service can join a PAST range's
affected set only by first-adoption backfill, which is exactly what the rebuilt tests do.

## 4. Also closed

The projection bound counts TOUCHED buckets (an unaligned range touches one more than
