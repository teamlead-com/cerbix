# iter-0130 — FR-021 round 6: the persistence phase joins its own mechanism

## 1. Summary

Round 2/2 rejected iter-0129 with two P0s that share one diagnosis: for the third round
running, I built a bounding mechanism and then exempted the phase I was standing in.
`deadlineTx` bounded the work phases; persistence — and on the repair path, the claim and
every lifecycle write — ran outside it, on the raw transaction, behind one fixed `SET` that
`statement_timeout`'s per-statement restart makes worthless as a bound on a SUM.

## 2. What changed

**persistPhase(), commit included.** Persistence on all three paths runs through a second
adapter over the same transaction with reserve zero: the held-back time becomes spendable, but
per statement, remainder-derived, and the top-level adapter's `Commit` now runs `ensureBounds`
first — `COMMIT` is a statement the server executes, and it was the last step of every slice
still outside the mechanism. The preview's per-service inserts are gone structurally: one
`unnest` statement, so the phase is two statements and a commit regardless of the affected
count.

**The repair lifecycle envelope.** The claim is bounded by `min(slice remainder, lifecycle
cap)`; release, complete, fail and park each run as one small bounded transaction
(`boundedLifecycleExec`); and a missed release is safe BY DESIGN — the range stays `running`
under its lease, the lease lapses, any claimer resumes at the durable cursor. The regression
proves the whole story: blocked release → bounded return → lease lapse → resume at the exact
cursor.

**Normative thresholds.** Every timing regression asserts
`budget + schedulingTolerance + ciAllowance(150ms, stated separately)`. The previous 3–4×
thresholds would have green-lit exactly the accumulation this round closes.

## 3. Honest limits

- **Two persistence hybrids are not behaviourally killed.** A raw-transaction persist with one
  fixed `SET`, and a commit outside the adapter, diverge from the mechanism only in a
  sub-50ms race between a fixed bound's tail and the client net. No deterministic lock
  construction pins that window without flaking. What is enforced instead is a structural
  tripwire — every slice path persists through `persistPhase()` and never commits the raw
  transaction — labelled in the test as a weak proof and an excellent alarm.
- **A hang is a kill, and the harness now knows it.** The true unbounded-claim mutant HANGS
  the suite; the previous harness read the absence of a FAIL line as a survivor. It now checks
  compilation before counting and reads a test timeout as the defect demonstrated. My first
  claim mutant this round was also wrong (it left the cap in place) — caught by asking why it
  survived instead of recording it.
- Per the governance finding, the "server always speaks first / no slice can exceed" claims in
  iter-0129 §2 and AC-0129-1 were narrowed by THIS iteration's evidence rather than edited in
  place: the statements were true of the work phases and false of persistence and the repair
  lifecycle, which is exactly the scope this round closed.

## 5. Round 1/2 disposition — the patch

Round 1/2 rejected the changeset with one P0 and one P1, both correct, both verified against
the code before a line changed. The P0 is the same diagnosis a fourth time, one layer down:
`boundedLifecycleExec` bounded each lifecycle write and not the slice — a release that runs
after the budget expired MINTED a fresh 100ms on top of the ~250ms already spent, and the
reviewer's repro shape measures ~350ms on a 250ms slice. Reproduced here at 349.4ms.

**The fix.** Lifecycle writes take an ABSOLUTE deadline through the full envelope (client
refusal, remainder-derived bounds, commit included, net one tolerance behind), under an
explicit policy: `leaderLifecycle` fits the write inside `min(slice deadline, now + cap)` and
refuses it once the slice is spent — the lease owns recovery; `standaloneLifecycle` (pool
callers, no cadence on the connection) mints the cap, which the review explicitly permits.
The repair loop budgets batches to end `lifecycleReserve` (40ms) before the slice deadline,
so the closing write normally runs INSIDE the slice rather than being refused at its edge;
and the leader skips a claim with less slice left than the claim's worst case plus that
reserve — a tail-of-slice claim could only park the range under a 60-second lease.

**The P1.** `cadenceLimit` is now the §10.10 number itself — budget + max_scheduling_tolerance
— and what the test environment adds is MEASURED per run (`measuredOverhead`, five probe
round trips, 5ms floor, logged beside the contract), never a fixed 150ms baked into the bound.
The demanded full-slice case exists: `TestAFullSliceBlockedAtTheLifecycleWriteHoldsCadence`
drives a real `RunServiceSlice`, provably parks the work at a lock wait (pg_stat_activity),
locks the queue table mid-flight, releases the work — and the slice slams into the blocked
lifecycle write with the budget nearly spent. Asserted: ≤275ms + measured overhead (observed
250.3ms against 280ms), no `context.DeadlineExceeded`, session at defaults, leadership held,
state still `running`, cursor unmoved, lease-lapse reclaim at the exact cursor.

**Mutants vs the iter-0130 shape.** The composite (fresh mint + no reserve): killed at
349.4ms. Mint-only (reserve kept): killed twice — by the full-slice test and by the
re-tightened release test (a 10ms slice now asserts 35ms + overhead). Honest limits: the
`lifecycleReserve` alone and the tail-of-slice claim floor have no independent behavioural
kill — both are lease-avoidance belt-and-braces whose absence degrades throughput (a parked
range) rather than cadence, and this file says so instead of claiming kills that do not exist.

Per the standing instruction, this patch stays uncommitted until the phase verdict; the
reviewer verifies the working tree.
