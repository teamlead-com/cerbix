# iter-0135 — FR-021: adoption keeps the parent authoritative, and readiness never guesses

## 1. Summary

The final iter-0134 verdict found a P0 my own adoption redesign had introduced — batched
DELETE into an unattached staging table hid sealed facts from every parent read mid-adoption,
and a crash stranded them permanently behind `CREATE TABLE IF NOT EXISTS`'s "already exists,
skipping" success — plus three P1 contracts (row-examined bounds, a leadership fail-open
window, zero-row lifecycle outcomes) and test/doc gaps. This changeset closes all of them,
and its own testing found one MORE latent hole in my first fix (the watermark-swept fence).

## 2. Iteration plan (P0 → P1 → P2)

1. **P0** — copy-authoritative adoption: parent visible at every committed point, resume via
   pg_inherits, fence authoritative by construction.
2. **P1** — per-state partial indexes; the plan pin covers every sampled probe and rejects
   residual state filters.
3. **P1** — UNKNOWN published synchronously before leadership is visible.
4. **P1** — lifecycle outcomes recorded only when a row changed.
5. **P2** — lifecycle tests through the real `Run`/`lead` path; docs reconciled.

## 3. What changed

**P0 (adoption).** The long phase COPIES (keyset-paginated upsert batches) into a standalone
staging table carrying a validated month CHECK — it never deletes from DEFAULT, so every
parent read sees every fact at every committed point, and any error, shutdown or timeout
leaves nothing stranded. `factPartitionStateOf` distinguishes absent/attached/STANDALONE via
`pg_inherits`, and `EnsureServiceFactPartitions` reads the state FIRST — the CREATE-IF-NOT-
EXISTS "skipping" success can no longer masquerade as an attached partition; a standalone
staging is resumed. The fence (parent lock → sweep → ATTACH) is AUTHORITATIVE by
construction: `DELETE … RETURNING` under the lock is the final content of every row still in
DEFAULT, imposed on the staging with a DISTINCT-filtered upsert. My first fix swept the fence
by a `computed_at` watermark — my own reworked test caught it: the column is assigned at the
writer's transaction START, so a write that began before the watermark and committed just
before the fence carried a timestamp the sweep skipped, and the attach kept stale content.
The watermark passes remain as warmers only; correctness never depends on them.

**P1 (indexes).** 00075 adds `…_pending_idx`/`…_running_idx` (state-keyed partials): 00067's
shared claim index carried state only in its predicate, so proving "pending = 0" filtered
every RUNNING row and vice versa — bounded returns, unbounded examination. The plan pin now
covers all three probes and additionally rejects any `Filter: (state …)` residue.

**P1 (fail-open window).** `Run` publishes `SetServiceWedged(true, unknown)` SYNCHRONOUSLY
before `setLeaderState(true)` and before the sampler goroutine exists; the readiness endpoint
can no longer observe leadership without the unknown verdict. Proven through the real `Run`
acquisition path with an ordered recorder (unknown strictly precedes `leader=true`).

**P1 (zero-row outcomes).** `boundedLifecycleExec` returns the affected row count; all four
writers record an outcome only for `rows > 0`. The deterministic cascade-delete race —
range deleted under a claim, zero-row COMPLETE — records nothing.

**P2 (tests through production paths).** Step-down is exercised through the real `lead`
return: a blocked sample, the watchdog deposing the leader, and `leader=false → clear` as
the final events with nothing after (the join). Healthy→error happens in ONE sampler loop
(injectable cadence). The fence-reconcile test commits its concurrent update while the fence
provably waits at the parent lock — the interleave that killed both the unsound watermark
and my first fix.

## 5. Honest limits

- The fence's sweep is O(rows still in DEFAULT for the month) inside a 5s statement bound —
  the long-phase warmers shrink its write set but the DELETE cost is inherent. A month too
  large or too hot to cut in 5s aborts safely forever until an operator intervenes; that is
  the honest trade against invisibility, stated in the runbook.
- The long-phase watermark passes are best-effort warmers by design; no correctness claim
  attaches to them and no mutant is claimed for their absence.
- Epoch/late-arrival aggregates remain sampled at the stats cadence: a counter's freshness
  is one cadence behind the event, which is inherent to the persisted-aggregate design.

## 7. Round 1/2 disposition — the fix pass

Round 1/2 accepted the copy-authoritative direction and rejected on four P1 contracts and
five P2s. All closed:

- **P1-1 (deletion contract).** The staging carries the parent's referential lifecycle from
  its first pass: `ensureStagingLifecycle` sweeps orphans by anti-join FIRST (a ghost row
  would fail the constraint validation and wedge every retry), then installs the services
  CASCADE FK, the deferred epochs FK, and the month CHECK — idempotently, on creation AND on
  every resume. Deleting a service is one transaction that removes its facts everywhere,
  staging included; `TestServiceDeletionCascadesThroughStaging` and
  `TestOrphanedStagingRowsAreSweptOnResume` prove both directions, and the ATTACH converges
  past the ghost. Mutant (lifecycle skipped) dies on "tenant fact rows survived".
- **P1-2 (rollover).** `recoverPastFactMonth` runs on every maintenance pass: the oldest
  standalone month table (catalog probe by regclass, schema-qualified), else the oldest past
  month still holding DEFAULT rows (one probe of the month index). One month per cadence —
  bounded catch-up, nothing rolls out of reach. `TestPastMonthsAreRecoveredAfterRollover`
  covers both shapes under the injected clock; the probe-removal mutant dies on
  "was not recovered".
- **P1-3 (CHECK on resume).** The month CHECK is part of the same idempotent lifecycle —
  ensured and VALIDATED on every pass, so the crash window between CREATE and ALTER cannot
  produce a fence-scanning ATTACH. `TestMonthCheckIsEnsuredOnResume` starts from a bare LIKE
  table; the only-at-creation mutant dies on "missing after resume".
- **P1-4 (rows examined).** Migration 00076 adds the partitioned `(bucket_start, service_id)`
  index — the DEFAULT child inherits it — and the keyset copy now ORDERS BY exactly that key
  with its cursor derived from the ORDERED pick (a CTE), never from RETURNING order. The
  correctness-neutral computed_at delta warmers are REMOVED outright. The plan pin resolves
  the DEFAULT child's index name from the catalog and requires it in both the pick and the
  fenced DELETE plans — "no Seq Scan" alone was the rows-examined trap again, and the
  hardened pin is what killed the dropped-index mutant.
- **Found by this pass's own suite (the discipline working):** the first recovery probe had a
  FUTURE-SHADOW bug — any current/future standalone staging matched the probe first, was
  dismissed as "not past", and the function returned without ever probing DEFAULT: past
  months lost their recovery for as long as the leftover existed. Caught when a test's
  leftover future staging made the rollover regression fail deterministically; fixed by
  scoping the standalone probe to months strictly before the current one (zero-padded YYYYMM
  makes the lexicographic bound exact), and the rollover regression now plants a future
  standalone SHADOW before asserting past recovery — the pre-fix shape fails it 3/3.
- **P2s.** `factPartitionStateOf` resolves by regclass OID, never bare relname; the
  absent→CREATE window re-verifies state after the CREATE (a concurrent creator's skip is
  adopted, not trusted); the fence test's narrative states precisely what it exercises
  (lock_timeout at the parent lock — a row lock cannot reach the DELETE) and what it does
  not (a demonstrated statement_timeout abort); the runbook's recovery procedure names the
  exact signal and the exact operator action; iter-0134 U3 carries its superseded marker;
  traceability counts are exact (28 regressions, sixteen named mutants, migrations
  00074–00076).
