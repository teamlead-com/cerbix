## 2. Failure-mode table (self-adversarial, before code)

| Change | How it could be wrong | Guard |
|---|---|---|
| Raw bound | 100.00004 sneaks in by rounding down | RAW input is rejected at >=100 BEFORE rounding — the bound is on what the caller said, not on what rounding made of it |
| Post-round bound | 99.99995 rounds UP to 100 and passes the raw check | the canonical value is ALSO required <100 after rounding — both fences explicit |
| Schema fence | app rule tightened, DB CHECK still admits 100 via any non-API writer | migration 00079 tightens the CHECK to `> 0 AND < 100`, clamping any pre-existing 100 to 99.9999 first (documented; no released deployment carries a 100) |
| Zero sentinel | BurnRate/ErrorBudget's allowed<=0 → 0 still reachable | unreachable BY CONSTRUCTION once no admitted objective yields allowed=0; the sentinel stays as robustness, stated in D-0165 |
| Monitor scope drift | service rejects 100, monitor store path stores it | the shared CanonicalObjective guards both handlers; the DB CHECK guards every writer; the store regression proves the CHECK by direct INSERT |
| Docs | OpenAPI `maximum: 100` survives | `exclusiveMaximum: 100`; TS regen + SPA build gates |

## 3. Changes

- **`domain.CanonicalObjective`** rejects RAW input at >0/<100 BEFORE rounding (100.00004 is
  rejected as said, never rounded into range), then requires the canonical 4-decimal value
  to stay inside (0,100) too (99.99995 → 100 → rejected). Maximum admissible: 99.9999. One
  rule, both scopes — the burn math's allowed<=0 sentinel is unreachable by construction and
  stays as robustness.
- **Migration 00079** tightens the schema CHECK to `objective > 0 AND objective < 100`
  (clamping the never-released 100 rows to 99.9999 first), so every writer — API or not —
  meets the same fence. numeric(7,4) from 00078 is kept (harmless, avoids schema churn).
- **OpenAPI**: `exclusiveMaximum: 100` + the D-0165 sentence in the request description; TS
  regenerated; SPA build green.
- **D-0165** records the contract and names the deliberately-out-of-scope future: a true
  zero-error-budget objective is a separately specified cross-scope change.
- **[195]'s mechanical P2**: status AC-0141 evidence now lists M1–M7 + the disclosed
  survivor and the 00078/00079/CanonicalObjective chain; traceability names the migrations,
  the domain rule, the added mutants and D-0165.
