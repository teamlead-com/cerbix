## 2. Failure-mode table (self-adversarial, before code)

| Change | How it could be wrong | Guard |
|---|---|---|
| `guarded()` normalizer | the catch masks a rendering bug as a transport error, or the fallback `{error}` shape leaks an ugly message | it wraps ONLY the api call promise (render errors are outside); the fallback error is `{}` so every consumer falls to its own operator prose |
| Boundary ownership | a health/series rejection still reaches the primary error, or vice versa | there is no outer try/catch left in `load` — each await is a `guarded()` call whose failure can only set its own state; rejected-Promise tests per boundary |
| Health pending | the pending state hides a real answer, or the pill flashes unknown before data | the card branches error → pending (`!health`) → pills; the pending test uses a never-resolving promise and asserts NO pill while the report renders |
| Per-segment requests | the segment strip double-fetches or over-fetches on every window | fetched only when the segment cards render (`spansRevisions \|\| segments.length > 1`), one request per segment, ranges bounded by the window (≤90d, inside the API's own cap) |
| Same-epoch parts | a straddling rollup point still lands in both strips | the server filters buckets by `[from,to)` BEFORE grouping — the client never slices; the regression pins exact half-day request ranges and one-rect-per-strip |
| Segment transport | a failed segment fetch silently renders "no strip" | per-segment `null` marks the failure; its own transport-error line (`svc-segment-series-error`), distinct from a legitimately empty strip |
| PUT boundary | a rejected save leaves an unhandled rejection and a stuck Save button | `saveObjective` goes through `guarded()` too; test asserts the editor error, the open editor, and the un-disabled button |
| Serial coupling ([228] P1-1) | a hung health request gates the timeline, or a report failure leaves health "pending" forever | health is an INDEPENDENT generation-gated task launched before the report await; the series/segments start off the report alone; tests: health-never with timeline+strips rendering, report-error with health settling into pills |
| Segment fan-out ([228] P1-2) | N segments become N simultaneous requests; one hung request suppresses every ready strip | unique-epoch segments slice the GLOBAL series (no request; the API splits points at epoch boundaries; provisional excluded; global failure inherited as the strip's failure); only same-epoch reconstruction parts get exact requests, through a 4-worker pool, each result assigned AS IT COMPLETES; explicit per-segment pending/failed/ready states; bound + deferred-one/fast-one tests |
| Repair-mask extent ([228] P1-3) | an exact-request point carries the TRUNCATED step start, so a repair in one half masks the other | segment ticks clip the point interval to `[max(stepStart, seg.from), min(stepStart+step, seg.to))`; regression: repair `[06:00,07:00)` masks only the first half |

## 3. Changes

- **`components/ServiceReliability.vue`** (the only code file):
  - `guarded<T>()` normalizes a REJECTED fetch into the same `{error}` shape an HTTP error
    arrives in, applied at EVERY request boundary: report (sole owner of the primary
    error), health (`healthError`), sealed+tail series (`seriesError`), per-segment series
    (per-segment `null`), and the objective PUT (`objectiveError` — the same defect class
    at the write boundary, disclosed here).
  - The health card renders three states: transport error → explicit prose; NO ANSWER YET →
    "Checking the live signal…" with no product pill (unknown is a real categorical state
    the server computes, never a placeholder); answer → the two pills, now from non-null
    data with no `|| "unknown"` fallback anywhere.
  - `segmentPoints` — a map keyed by `(epoch_id, from, declared_reconstruction)`. The
    client-side epoch+range slicing of the merged series (the [221] defect) is REMOVED for
    the ambiguous case: a SAME-EPOCH reconstruction part is fetched by its OWN exact
    `[from,to)` request through the EXISTING series API, so PostgreSQL filters buckets
    before `date_trunc` grouping and a straddling rollup step physically cannot appear in
    both strips. A UNIQUE-epoch segment needs no request at all ([228] P1-2): the API
    already splits series points at epoch boundaries, so the epoch key alone slices the
    fetched global series exactly (provisional tail excluded — segments are sealed ranges);
    a global-series failure is inherited as those strips' failure. Exact requests run
    through a 4-worker pool with each result assigned AS IT COMPLETES; a segment renders
    explicit pending / transport-failed / ready states.
  - Health is an INDEPENDENT generation-gated task ([228] P1-1): launched before the report
    await, it neither gates the timeline nor waits for the report, and it settles honestly
    even when the report fails; a hung health request leaves the timeline, tail and segment
    requests untouched.
  - Segment ticks CLIP the point interval to `[max(stepStart, seg.from),
    min(stepStart+step, seg.to))` ([228] P1-3): an exact-request point carries the
    truncated rollup start, and without the clip a repair confined to one reconstruction
    half masked the other half too.
