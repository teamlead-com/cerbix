## 1. Normative extract (spec §14.2/§14.4/§14.7, gathered BEFORE code)

- Dedicated edge routes: `GET/PUT …/services/{id}/dependencies`; reads return
  `graph_generation` from ONE SQL snapshot; PUT requires it (409 `graph_generation_stale`,
  first-committer-wins); validation errors are actionable 400s; typed actor attribution.
- Service create additionally accepts `depends_on` — create-with-edges under the same
  validator and lock (an atomic §14.1 lock path, never create-then-replace).
- Impacts are an authenticated-DETAIL enrichment: never a field of `domain.Incident`
  (the public serializer embeds that model — invariant 59), never on the incident LIST
  (invariant 60), never on public/internal status-page projections until phase 4.
- The service detail gains `dependencies` (both directions + neighbour health); neighbour
  health comes from ONE batched snapshot for the whole set — never a per-service loop.
- openapi is the source of truth: bump + regenerated TS schema.

## 7. Fix-pass record (review [288], round 1/2 → FINAL 2/2)

| Finding | Fix |
|---|---|
| P0 file-owned edges UI-mutable | `ReplaceServiceDependencies` calls `assertServiceNotFileManagedTx` (the canonical guard `PutServiceDeclaration` uses) under the graph+row locks — active AND orphaned, since an orphan is still the provider's LKG; the provider track calls `applyServiceDependenciesTx` directly. Real-PG regression over both phases + a UI-owned sibling that still writes; API 409 `managed_by_file` |
| P1-1 non-strict request contract | presence-aware `*[]string` / `*int64`: omitted or null `depends_on` is a 400 (never a silent delete-all), omitted `graph_generation` is a 400 (never a passing zero), `[]` clears legitimately; path id via the established `serviceIDParam`, every body id UUID-checked at transport. 5-case wire regression asserting the set AND token are untouched by every rejection |
| P1-2 N+1 behind a fake-call claim | REAL batching: `serviceNeighbourHealthTx` issues FOUR set-wise reads (scope+epoch via LATERAL, observations, maintenance spans, diagnostics) for any neighbour count, then the SAME pure evaluator per service. Proof: a pgx `QueryTracer` counts statements for 1 vs 30 neighbours and requires equality (and ≤6); a parity regression asserts batched verdicts are byte-identical to `ServiceHealthNow` per service. The reviewer's fan-in arithmetic is adopted in the spec: downstream degree is bounded by the PROJECT service cap, not by 2× the edge cap |
| P1-3 actor label was a uuid | `authz.Principal.AuditLabel` set by the auth layer (session → email, API token → `token:<name>`, client-credentials → its resolved identity) + `AuditActorLabel()`; `graphActor` carries it. HTTP regression captures the store-side `GraphActor` for a human (real uuid, via_token false, email) and a token (NULL uuid, via_token true, `token:` label) |
| P1-4 failed impact read looked like "no impacts" | `impacts: null` + `impacts_unavailable: true` on a degraded read; `[]` stays reserved for the honest "no links". Regression covers both, decoding into fresh values so the omitempty flag cannot leak between assertions |
| P1-5 create-with-edges atomicity unproven | real-PG regression: a foreign parent leaves NO service, no edge, no generation, no audit row (counted before/after), and the success path lands all three in one transaction; the API fake now validates parents BEFORE creating, so a create-then-commit implementation fails it too |
| P2 "one validator/mutator" overstated | `dedupe` + the domain cap moved INTO `applyServiceDependenciesTx`; both callers dropped their copies. Regression: duplicates collapse to one edge, and create-with-edges hits the cap through the shared owner |

## 9. Final-round disposition ([292], owned under the [263] delegation)

FINAL 2/2 verdict: no P0; the file-ownership guard, the four-statement neighbour read with
its tracer proof and single-owner parity, the trusted actor label, the disclosed impacts
degradation, the real transactional create rollback and the shared normalization owner are
all verified closed. ONE residual P1: create-with-edges did not cross the body-UUID transport
fence the PUT added — `POST /services {"depends_on":["not-a-uuid"]}` reached the store's
uuid-typed membership query and would surface as a 500, contradicting both §14.4's "every id
in the path or the body is validated at transport" and the OpenAPI item contract; the API
fake masked it by mapping any unknown string to `ErrServiceGraphForeign`, and the strict
contract regression covered PUT only.

Disposition: implement the reviewer's prescribed narrow fix verbatim — ONE transport helper
(`validDependsOn`) called by BOTH the replace-set PUT and create-with-edges before either
store call. No design change, no contract change. Regression added
(`TestCreateServiceWithDependenciesValidatesBodyUUIDs`): malformed and empty ids are 400s
naming the rule, no service is created by a rejected request, and the valid path still
creates through the same fence.
