# iter-0150 — FR-021 phase 4: the status-page service projection and the composite lifecycle

Spec: `specs/func-service-reliability.md` §15.0 / §15.5 (amendment committed `1b848b5`, design gate
cleared in party message [310], owner-approved mock `design/mock-status-projection.html`).
Decision record: **D-0167**. Predecessor: iter-0146…0149 (phase 3 + the SPA-snapshot fix).

## 1. What this phase makes true

A Service can now be what a status-page line reports. That sentence is small; making it honest was
not, because the shipped status page carried three inherited statements that reported an UNKNOWN as
health, and adding a third component source would have multiplied all three.

**The third source is a discriminator, not a second column.** `components.source ∈ {monitor,
service, manual}` decides what the line renders from; the other binding stays DORMANT so a
conversion can be reverted without the operator re-choosing what it replaced. The shipped renderer
branched on `c.MonitorID != ""`, which after this change would have kept rendering the OLD monitor
of a component that had been converted to a service — and `if c.ManualStatus != ""` would have let a
dormant manual status override a live service. Both now branch on the discriminator alone.

**`no_data` is a public status that is deliberately not a severity.** Measurement absent — nothing
sealed, no `sli[]` declared, a monitor never confirmed, a manual component whose operator has said
nothing. Asking whether "we do not know" is better or worse than declared maintenance is a false
comparison, so the page summary reports **worst-of-MEASURED plus an unmeasured COUNT** instead of
ordering them. An operator can never type it: `components_manual_no_data_chk` refuses it at the
schema, and both write paths refuse it with a reason.

**Three inherited lies removed (§17, the enumerated public-behaviour changes):**

| Was | Now |
| --- | --- |
| a `pending` monitor component published `operational` | `no_data`, reason `monitor_never_confirmed` |
| a manual component with no status published `operational` | `no_data`, reason `no_manual_status` |
| an EMPTY page summarized `operational` — "all systems operational" with no systems | `summary_state: empty`, "No components configured" |

The two unit tests that PINNED the old behaviour were rewritten, not deleted, and each now also
asserts the old answer is gone — so a revert fails loudly rather than silently passing.

**Conversion is explicit, previewed, reversible and CAS-fenced.** The operator sees the line and the
page summary before and after, rendered by the SAME resolver the public page uses, and consents to
that pair. Consent is bound to `components.revision` AND `status_pages.component_generation` — the
latter bumped by ANY component mutation on the page, neighbours included, because the preview showed
the page summary. A mismatch is `409 page_configuration_stale`, first committer wins. Confirming
without the tokens is a `400`: the fence is not optional in practice.

**The composite lifecycle is three separate acts.** Recording a successor changes nothing (it does
not even bump `execution_revision`, so no referencing service re-probes for an annotation).
Retiring is ONE transaction setting `retired_at` **and** `enabled = false`, plus the config fence,
the `state_sequence` advance that makes a queued DOWN stale at delivery, and the `BumpEpochsForMonitor`
fan-out for every service whose SLI names it. Converting a composite builds a service and leaves the
composite running at full strength. Collapsing any two of these into one button is how an operator
stops a monitor they only meant to annotate.

## 2. The decisions this phase had to make, and why

**The service FK is `RESTRICT`, and the refusal is typed.** `SET NULL` would be the automatic
conversion invariant 70 forbids — a customer would watch a page line silently change what it means —
and `CASCADE` would delete a customer-visible row because of an internal decision. So
`DeleteService` returns `ErrServiceRendered` naming the page AND the component. A **dormant** service
binding does not pin anything: it is swept in the same transaction (with the revision and page
generation bumped, so a revert preview cannot be confirmed against a service that is gone), which is
what makes `RESTRICT` mean *rendered* rather than *ever mentioned*.

**The page-scope rule needed a deferred constraint trigger on BOTH sides — and a LOCK.** "A
project-scoped page admits only that project's components" has to read `status_pages`, which a CHECK
cannot do, and the `(status_page_id, org_id)` FK proves only the org. So there are two triggers: one
refuses inserting a foreign component, the other refuses NARROWING a page's scope while it still
holds one. Deferred, so a legitimate multi-statement rearrangement is judged at COMMIT on its final
state — but deferral is NOT serialization, which is the [314] P0-1B correction: each transaction
validates against its own snapshot, so the component side takes the page row `FOR UPDATE` and the
narrowing side row-locks it through its own UPDATE. Exactly one of any two orders survives.

**The composite→service conversion asks, refuses, and never approximates.** The `sli[]` is a REQUIRED
input: §15.5 says explicit confirmation, never a silent "all children", so the store has no default
and the UI ticks every child while making the operator confirm. Every live child joins the
operational CONTEXT regardless — that is what keeping a diagnostic visible must not change. A
composite whose declared children are not ALL live is refused by name, because converting on the
survivors moves the aggregation's meaning without anyone stating it. `all` and `any` map exactly.
`quorum` states its threshold as a DOWN-vote count while a service states it as a minimum GOOD count,
so the arithmetic is `degraded_min = n − M + 1` with `healthy_min` equal to it — the exact binary
mapping, because a composite has two states and a degraded band would report more than it did. And a flat "M of N children" is NOT expressible as the service model's
per-region quorum followed by a region rollup, so a quorum composite whose children span regions is
**refused with a named reason** instead of given thresholds that merely look similar. A conversion
that quietly changes what "down" means for a page a customer reads is worse than no tool at all.

**An unreadable service degrades, it does not report `no_data`.** With `RESTRICT` in place an active
service cannot legitimately be missing from the projection, so absence means a failed read. The
component carries a PUBLIC `unavailable` marker — bytes identical to a calm value were the whole
problem — the authenticated view names the reason (`service_unreadable`), and
`cerbix_status_page_component_unreadable_total` counts it. Publishing the calm statement "no data"
would present a bug as a fact.

**The public render is bounded in rows, not only in statement count.** The unit of work is the PAGE:
`ServicePageProjections` takes `(project_id, service_id)` pairs and evaluates them in ONE report
snapshot with five statements, whatever the page holds — an org page spans projects, so a
per-project batch was neither one snapshot nor a constant count. The monitor half is three set-wise
reads instead of three per component. On top of that: a per-page ceiling persisted as
`max(50, current)` that only SHRINKS — lowered by every removal, never raisable above
`max(50, count)`, so no write creates headroom — an absolute fail-closed public ceiling of 500 above
which the page returns `status_page_over_safe_limit` naming both numbers, and a 5-second render cache
keyed to page + access shape + unlisted token as the RATE bound, because a ceiling bounds one request
and not repetition. The authenticated view still lists everything. Both counters are DB-owned, since
FK actions are part of the contract and a cascade has no application on its path.

**`uptime_90d` comes from the report's own decision function, not a second one.** The §11.2/§11.3
withholding rule — era-short, storage gap, zero decidable, low coverage, spans revisions — was
EXTRACTED into `decideServiceWindow` and is now called by both the authenticated report and the
public page, with the page mirroring the report's branch order for the no-watermark and no-SLI
pre-checks. A test asserts they withhold for the SAME stated reason; it caught my first version
answering `no_sli` where the report answered `storage_gap`.

**The 90-day strip ends at `sealed_through`, never at "now",** and a day with zero decidable time is
ABSENT rather than 0%. `sealed_in_window` — not "any fact exists" — decides whether a strip is drawn
at all, because one ancient fact would otherwise claim a history the strip cannot show. When there is
no history the page says "No history recorded yet." instead of drawing an empty rail under
"90 days ago … today", which reads as a flawless record.

**`RetiredAt` is classified SemanticPresentation, and that is the interesting half.** It DOES
accompany a change in execution — but `enabled` is the field that carries it, and `enabled` is
already `SemanticEvaluation`. Listing `RetiredAt` as evaluation too would put the same fact in the
hash twice, and would let a future path that set only `retired_at` register as a semantic change
while the monitor kept probing — the exact inverse of what §15.5 requires. The exhaustive-field
guard in `execsemantics_test.go` is what forced this to be a decision instead of an omission.

## 3. Surface

**Schema** — migration `00081_status_projection.sql`: `components.org_id` (its own tenant identity —
before this it reached its org only through the page, so a direct writer could hang an org-B service
on an org-A page), `source_project`, `source`, `service_id`, `revision`;
`status_pages.{id,org_id}` UNIQUE, `component_generation`, `component_ceiling`; a total deterministic
backfill (`monitor_id IS NOT NULL ⇒ 'monitor'`, else `'manual'`) that changes no rendered output;
four CHECKs; composite tenant FKs; the two deferred constraint triggers;
`monitors.superseded_by_service_id` (composite FK, `SET NULL`) and `monitors.retired_at`.

**Store** — `ServicePageProjections` (page-scoped, five statements, `uptime_90d` + `withheld_reason`
via the shared `decideServiceWindow`), `MonitorPageProjections` (three set-wise reads),
`PublicComponentStatus` (the total §15.0 precedence in one place: maintenance OUTRANKS absence;
`sealed_in_window` governs the strip, never the status, so a live-healthy service before its first
seal is `operational`), transactional `CreateComponent`/`UpdateComponent`/`DeleteComponent` with
page-first locking, `Preview`/`ConfirmComponentConversion` over ONE shared validator that also
validates every RETAINED dormant binding against the proposed project,
`SetMonitorSuccessor`/`RetireMonitor`/`ReactivateMonitor` (composite-only, with the file-ownership
split), `ConvertCompositeToService` (explicit `sli[]`, partial-loss refusal),
`ListMonitorsSupersededBy`, and the `DeleteService` guard + dormant sweep.

**API** — one resolver (`api/statusprojection.go`) shared by the public render and the preview, with
a 5-second render cache (`api/statuspagecache.go`) keyed to page + access shape + unlisted token;
`PATCH /components/{id}`, `POST /components/{id}/conversion/preview`, `POST
/components/{id}/conversion`; `PUT /monitors/{id}/successor`, `POST /monitors/{id}/retire`,
`POST /monitors/{id}/reactivate`, `POST /monitors/{id}/convert-to-service`; `summary_state` and
`unmeasured_count` on the render; `unavailable` and `withheld_reason` as PUBLIC honesty fields with
`source`/`reason` staying authenticated, and `supersedes` on the service detail. `openapi.yaml` is the source of truth and was updated first;
the TS schema was regenerated from it.

**SPA** — the public page renders "Status unavailable" for a failed read and a stated reason wherever
a number is withheld; the composite conversion dialog makes the operator confirm which children
become reliability inputs; the component row shows its ACTIVE source and labels the dormant binding *as* dormant
("kept for revert"); the add form picks a source; the conversion dialog shows both sides with the
consequences the summaries cannot show, and its Apply control does not exist until a preview does; a
stale 409 DISCARDS the preview rather than leaving dead tokens on screen; the monitor page gets a
Retired badge distinct from Paused, a successor block that says an annotation changes nothing, and a
retire confirmation stating BOTH consequences; the service page gets "Converted from" with a
"still probing" badge.

## 4. Review round 1/2 [314] — REJECTED, and what it found

The first submission was rejected with 2 P0, 7 P1 and 2 P2. Recording the substance here rather
than only in the party log, because two of the findings are defects I introduced and one is a
process failure of mine that a passing test suite actively concealed.

**P0-2, the worst of them: a monitor delete BROKE.** `ON DELETE SET NULL (monitor_id)` cleared the
binding and left `source = 'monitor'`, which the new CHECK then rejected — so deleting any monitor
with a status-page component became a 500. Shipped behaviour is that the component becomes manual.
This was a REGRESSION, not a gap, and not one test I wrote deleted a monitor that backed a
component. The fix has to be in the database (a `BEFORE DELETE` trigger on `monitors`) because the
D-0150 project cascade deletes monitors through FK actions with no application on the path.

**P0-1: the tenant guard had two holes.** (a) A composite FK is MATCH SIMPLE, so
`(monitor_id, source_project)` with a NULL project is not enforced at all, and my CHECK demanded a
project only for a non-manual SOURCE — so `manual` + NULL project + a foreign `monitor_id` was
unconstrained on both sides. The rule now keys on the PRESENCE OF ANY BINDING. (b) I reasoned about
`DEFERRABLE INITIALLY DEFERRED` as if it were a lock. It is not: each transaction validates against
its own snapshot, so an insert and a page-narrowing could both commit a state neither would have
accepted alone. The guard now takes the page row `FOR UPDATE`, which serializes both orders.

**P1-1/P1-2: counters and the ceiling were application habits, not invariants.** A project cascade
deleted components without advancing a surviving org page's generation, so a preview for a different
component stayed confirmable; the ceiling was seeded and then left writable in both directions. Both
are now DB-owned, and the lock order is page-first everywhere.

**P1-3: I argued my way out of a real bound.** I treated the monitor N+1 as pre-existing and out of
scope while AC-0150-4 claimed the unauthenticated render was bounded — amplification left in place
is amplification claimed gone. Worse, the service side was per-PROJECT, and an org page spans
projects, so "one snapshot per page" was false for exactly the page shape the feature adds. And a
service component carried no `uptime_90d` and no withheld reason at all, which invariant 69
requires. Both halves are now batched, and the withholding decision was EXTRACTED from the
authenticated report (`decideServiceWindow`) so there is one owner rather than a second
implementation — a test now asserts the page and the report withhold for the same stated reason.

**P1-5: the spec required explicit `sli[]` confirmation and my implementation accepted no SLI input
at all**, which makes that consent impossible at every caller. It also converted a partially-lost
composite on the survivors, silently redefining `all` over 3 as `all` over 2.

**A test of mine passed against the mutant.** My first regression for the newest-day cap asserted
the right thing about a fixture that could never trigger it: every bucket sat at 06:00, so the
straddle day fell outside the window, only 90 groups ever existed and `LIMIT 90` never truncated.
Re-running the mutation is what exposed it. The corrected test fails with
`newest day = 2026-08-16, want 2026-08-17`.

**One finding I pushed back on, and the disposition** ([315]/[316]): the lifecycle actions are
COMPOSITE-only as asked, and `retire`/`reactivate`/conversion refuse under file ownership. The
`superseded_by_service_id` annotation is PERMITTED for a file-managed composite, because it is not
part of bundle format 2, enters no canonical hash or generation, and no reapply can restate it —
refusing it would remove the only way to annotate a file-managed composite while protecting nothing.
§15.1's "may MUTATE a resource" is narrowed in D-0167 to declaration authority, which is what makes
that split coherent rather than an exception.

**The quorum question** was left as a choice between an exact binary mapping and a previewed
vocabulary change needing owner confirmation. With no owner decision available mid-flight I took the
EXACT mapping (`healthy_min = degraded_min`): a conversion must not change what a customer-facing
page says. A degraded band remains available as a later, previewed owner decision.

## 5. Final review round 2/2 [318] — REJECTED, and the second correction pass

The round-2 tree was rejected with 2 P0 + 3 P1 + P2. There is no third reviewer round; disposition
and closure are mine. Two of the findings are defects in fixes I had just written, and two are tests
of mine that passed against the bug they claimed to cover — the same failure mode as round 1, which
is why both are recorded here rather than only in the party log.

**P0-1: I introduced a cross-project data leak while fixing the batching.** A `MaintenanceSpan` with
an empty `MonitorID` is project-wide and covers EVERY member handed to the evaluator. I collected
each project's spans and appended them all to one slice, so on an org-level page project A's
project-wide window marked project B's service as under maintenance — a false PUBLIC status.
Maintenance is now read in ONE statement tagged by project and each service is evaluated against its
own project's spans. `TestProjectWideMaintenanceDoesNotCrossProjects` fails with the merged-slice
mutant.

**P0-2: my "page-first everywhere" claim was false and the deadlock was still live.**
`UpdateComponent` wrote the component and let the AFTER trigger take the page; `DeleteComponent` did
the same. That is component→page, which cycles against confirm's page→component. My test asserted
only that an update BLOCKS while the page is held — which a component→page path satisfies perfectly,
because it blocks inside the trigger while holding the component tuple. Every structural mutation
now takes the page explicitly first, including the dormant sweep and the monitor-delete trigger, and
`TestComponentMutationsCannotDeadlock` fails with `SQLSTATE 40P01` when the lock is removed.

**P1-1: the constant-statement claim held for half a request.** `maintenanceSpansFor` ran once per
project — and my statement-count test seeded services with no epochs or members, so that branch
never executed and the measured constant proved nothing. The render also looped projects for
incidents and maintenance and then looped incidents for timelines and postmortems. All of it is
batched now (`IncidentsForPage`, `MaintenanceForPage`, `IncidentTimelines`,
`PostmortemsForIncidents`), the fixture declares real members and a window per project, and the
corrected test fails on the old loop with `8 … 13`.

**P1-2: a TTL map is not a rate bound.** Concurrent cold misses all rendered. The cache now
coalesces per key — one render, the rest wait — and refusals are never stored. The three properties
that were asserted nowhere (expiry on the injected clock, coalescing under real concurrency, and
refusals not cached) each have a test.

**P1-3: two schema invariants were weaker than the spec.** The ceiling admitted a raise up to
`max(50, count)`; the justification (reaching the inherited value) was wrong because the backfill
runs BEFORE the trigger exists, so it is now strictly shrink-only and the legacy fixture is built by
disabling the trigger for exactly one statement. And a component MOVED between pages bumped only the
destination, leaving the source page's preview confirmable after the line it summarized had left.

**P1-4: a folded migration leaves stale databases claiming to be current.** Both of the reviewer's
DSNs reported goose 81 with the pre-fold schema, which made the dual-mode claim unreproducible for
anyone but me. `TestSchemaMatchesTheFrozenMigration` now fails loudly, naming the missing object and
telling the reader to recreate the database.
