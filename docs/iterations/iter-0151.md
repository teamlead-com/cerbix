## 1. What this phase makes true

A Service can now be the thing that pages, and its members can stop paging for the same failure —
but only while a replacement for THAT signal is demonstrably able to fire and reach somebody.

The whole phase is one sentence with a very expensive second half. `owns_paging = true` silences
nothing on its own. Suppression is per SIGNAL, per POLARITY, and requires ARMED coverage:

```
LIVE armed  ⟺ owns_paging ∧ a policy that can page the CURRENT state
              ∧ a successful evaluation for the CURRENT (config generation, effective revision)
              ∧ a FRESH DB-clock lease ∧ ROUTABLE right now
BURN armed  ⟺ owns_paging ∧ an enabled target with rules
              ∧ every rule's last verdict QUOTABLE — any HOLD dis-arms
              ∧ CURRENT (config generation, target generation, canonical rule key)
              ∧ FRESH ∧ ROUTABLE
```

Everything ambiguous fails OPEN: the member pages. A page that was not needed is noise; a page that
was owed and never sent is the failure this phase exists to prevent.

## 2. Eighteen defects found in code that had already been reviewed

Each was found by RUNNING something or by reading one artefact AGAINST another — never by re-reading
the same file more carefully. That is the finding worth carrying forward: every one of them had
already passed a careful reading, several of them twice.

### 2.1 The narrowed outbox whitelist (P0, found by the full suite)

`outbox_events.topic` has a CHECK whitelist, and a migration that adds a topic restates the whole
list by hand. 00082 added `service_alert` while silently dropping `region_worker_alert`,
`escalation_step` and `subscriber_confirm`. Nothing failed to build and nothing failed to migrate —
every escalation step, region-worker alert and subscriber confirmation would simply have failed its
INSERT in production.

The phase's own targeted regressions could not see it: they exercise the topic being added. The FULL
`internal/store` suite found it. **Guard added** (`TestOutboxTopicWhitelistMatchesTheBinary`): parity
in both directions between `domain.AllTopics` and the live constraint, plus a behavioural insert per
topic. `domain.AllTopics()` is now the single owner of the list.

### 2.2 The lossy canonical rule key (P0, found before it became persisted identity)

`BurnRule.Key()` formatted its threshold with `%.4f`, so 14.40001 and 14.40002 collapsed to one key —
which the new duplicate guard would reject as identical and which a normalized latch could not tell
apart. `ValidateBurnRules` also accepted NaN and +Inf, both of which pass `threshold > 0`.

Fixed to `strconv.FormatFloat(v, 'g', -1, 64)` (lossless, round-trippable) with non-finite thresholds
rejected BEFORE the duplicate scan. The timing is the point: the key became persisted identity one
commit later.

### 2.3 Target identity collapsed across the whole contract (P0)

00077 keys service SLA targets by `(service_id, window_name)`, so ONE service may legally hold a 7d
and a 30d target whose burn rules share a canonical key — the key spells severity/windows/threshold
and names no window. Three places were keyed by half of the identity:

| Place | Consequence |
|---|---|
| `service_alert_episodes_open_uniq` had no target | the second onset unique-violates; a close binds the wrong episode |
| the `service_alert` payload carried `rule_key` only | two identical pages, no way to tell which budget |
| `ServiceAlertSequence` matched `(service_id, rule_key)` | **two rows matched and `QueryRow` took the first**: one target's onset dropped as "superseded" by the other's sequence — a page never delivered |

The fence now takes the WHOLE payload rather than a few fields, so an under-scoped call cannot be
written. The episode's target identity is a SNAPSHOT (`target_snapshot_id`, no FK) because
`rule_removed` and target deletion close THROUGH that row — an FK would erase the identity exactly
when the close needs it.

§16.4a's promised `ON DELETE SET NULL` was also missing entirely: `service_id` carried no FK at all,
so "the episode survives its service" rested on a dangling reference. It is now the DATABASE's
promise, via Postgres 15's column-list `ON DELETE SET NULL (service_id)` — the same constraint also
refuses a cross-tenant episode on the way in.

### 2.4 "Some rule is quotable" is not "no rule is blind" (P0, mine)

§16.1 says **any HOLD dis-arms BURN coverage**, and `alertdelegation.go`'s own comment said a rule
that cannot fire replaces nothing. The query asked whether SOME rule was quotable, with a `DISTINCT`
collapsing the rest. The two predicates coincide only when a service owns exactly ONE rule — the
shape every existing test had.

`burn_rules` is an array of up to four, and one service may hold several enabled targets. A service
with one FIRING rule and one HELD rule armed coverage, and the member monitor's own burn alert was
suppressed while part of the replacement was structurally unable to speak. Arming is now a
conjunction over the whole service: a replacement must EXIST and NOTHING the service owns may be
blind (an enabled target with no latch row at all included).

### 2.5 A fenced topic enqueued into the legacy claim class (P0, review)

The first lifecycle close used a raw `INSERT INTO outbox_events`, taking the column default.
`service_alert` is a FENCED topic, so the onset was invisible to a pre-fence binary while its CLOSE
was claimable by one — in a rolling fleet the ending of an announcement is exactly the row that gets
attempt-burned and dead-lettered. Routed through `enqueueOutboxTx`; **guard added**
(`TestOnlyTheOutboxOwnerInsertsOutboxRows`) that reads source and fails on any raw insert under
`internal/`.

### 2.6 Leader-GATED is not connection-FENCED (P0, review)

Both evaluators were called only under leadership but ran on POOL connections. A leader passes its
watchdog sample, its pinned lock connection dies, a successor takes over — and the old process
commits an evaluation behind it. The latch CAS does not cover it, because the episode and the outbox
row are written BEFORE the upsert: by the time a CAS could lose, somebody has been paged. The worst
shape is a stale CLOSE, since delivery deliberately never drops closes.

Both entrypoints now live on `LeaderSession` and run their whole transaction on the lock-owning
connection; the scheduler's `Store` no longer exposes a pool-backed evaluator at all, so a regression
fails to compile. The CAS result is no longer discarded either: losing it rolls back the episode and
the alert with the transaction.

### 2.7 A rule with no verdict is not coverage (P0, review round 1)

The coverage conjunction of §2.4 walked the latch rows that EXIST, so a rule declared with no row at
all was invisible to it. Adding a second burn rule to an armed target therefore changed nothing any
arming clause could see — the first rule's verdict was quotable, fresh and generation-matched — and
the member monitor's own burn alert stayed suppressed while half the replacement had never once been
evaluated.

Two mechanisms close it, and they cover different halves. CARDINALITY: a target's latch rows must
number exactly the rules it declares, which catches a rule with no verdict and a row deleted
underneath one. Counting rather than comparing keys is deliberate — recomputing the canonical key in
SQL would create a second owner of that format. The TARGET GENERATION catches what counting cannot:
a rule REPLACED in place, where the counts still match and every row describes a rule nobody
declares. 00082's trigger now bumps on `burn_rules` (monitor rows were already excluded), and the
write path stores the array in canonical key order so a pure reorder is not a change.

### 2.8 Leader-gated evaluations were not linearized against config writes (P0, review round 1)

The evaluators read services and targets from a REPEATABLE READ snapshot without locking them, while
both config writers lock the rows they edit. An operator's edit could commit between the snapshot and
the emission, and the pass would then publish a page for a policy, a target or a rule that no longer
exists — with nothing to close it, because the writer looked for an open episode before the evaluator
opened one. Generation mismatch dis-arms the MEMBERS' delegation afterwards; it does not un-send the
service's own stale page.

Both arms now take the writers' locks in the writers' order (services, then targets, ids sorted)
immediately after the slice and before any evaluation. Under REPEATABLE READ a locking read of a row
changed by a transaction that committed after the snapshot raises a serialization failure, so the
pass aborts whole rather than emitting.

### 2.9 A close stamped before the announcement it ends (P1, review round 1)

Both writers read `now()` in their locking statement, and `now()` is transaction-START time. A writer
that queued behind an evaluation would stamp its close with an instant from before the wait — while
the evaluation it waited for opened the episode during that wait. Both now read
`statement_timestamp()` after every lock they need is held.

### 2.10 A partial PATCH that loses a concurrent partial PATCH (P1, review round 2)

The HTTP layer read the policy, merged in Go, and handed the store a FULL value to write under a
lock taken afterwards. Two edits that each mention one field then lose each other: both read the same
row, and whichever commits second writes its stale copy of the field it never mentioned. The merge
now happens under the row lock, inside the write.

### 2.11 A MaC declaration that depended on history (P1, review round 2)

An absent `alerting:` block meant silence, so a bundle that once declared `owns_paging: true` and
then dropped the block left the service still owning paging — the same file converging to two
different databases, uncorrectable through a UI that refuses file-managed edits with a 409. An absent
block is now the DEFAULT declaration. The precedent I had reasoned from (a format-1 bundle's silence
about `services`) was a whole section absent from a different format, not a field taking its stated
default inside a declared one.

### 2.12 Three metric families missing, and a delivery that reached nobody in silence (P1, round 2)

`DeliverChannels` resolved the enabled channels for a set of ids and never compared what it was asked
to reach with what it reached. A close whose snapshot recipients had since been deleted was marked
delivered with nobody told: no error, no retry, nothing to see. Delivery now reports what it reached;
a missing recipient is COUNTED (§16.4a) and an announcement with nobody left is counted and finished
rather than retried forever. The three delivery-side families of §16.6b's table now exist, including
`delegation_total{signal,state}` counted where delegation is actually decided.

### 2.13 A persistently failing evaluator that never tripped readiness (P1, round 2)

Readiness measured the last reported LAG, which only a pass that read state can report — so an arm
erroring every cadence kept the old lag and read as healthy while every lease it should have
refreshed expired. It now measures the AGE of the last success. See §4: I had recorded this as a
deliberate deviation, and that was wrong twice over.

### 2.14 A write echo that reported a latch it never read (P1, round 2)

The burn PUT echoed its rules as `domain.BurnRule`, which always serializes `firing`. For a service
target that latch is the normalized per-rule row this endpoint does not read, so a client PUTting an
unchanged declaration was told `"firing": false` about a rule that was genuinely firing.

### 2.15 A no-op that still stamped the row (P2, round 2)

Both writers issued their UPDATE even when the canonical declaration was unchanged, moving
`updated_at` and burning an MVCC row version — a service shown as freshly edited by nobody every time
a UI saved an unchanged form. Both now return after the diff comes back empty, compared under the
lock.

### 2.16 A coverage badge frozen at page load (P1, final-residue round)

The panel rendered coverage from the service detail's snapshot and never asked again — so a lease
expiring, an evaluation failing, or the panel's OWN save (which bumps the generation and dis-arms the
service) all left a green badge saying ARMED while delivery had stopped suppressing anything. It is
the same disagreement §16 spends a section on, arriving through the UI instead of the SQL. Coverage
is now re-read on a cadence and immediately after every successful save, through a route of its own,
with generation and unmount guards.

### 2.17 The server's reason, hidden behind a tooltip (P1, final-residue round)

One armed signal made the panel print a single generic sentence and drop the OTHER signal's reason,
which is exactly the mandatory case the design notes name: a green ownership toggle beside a
dis-armed burn signal. `last_error` — the evaluator's own message, which the API surfaces rather than
summarizes — was not rendered at all. Both signals now carry their reason as visible text, the
held-burn warning is its own block, and the badges use the approved grammar (`armed` the UP hue,
`pending` the PENDING hue with a dashed ring, `degraded` the DEGRADED hue) rather than colours I
chose myself.

### 2.18 An approved screen silently not built (P1, final-residue round)

The mock is binding and has five screens; I shipped the service panel and left out the delegated
MONITOR — the screen that answers "this is DOWN and nothing paged me, is that broken?". A monitor
detail now carries a dashed chip naming the owner beside its REAL status pill (a delegated monitor is
never greyed out) and states the two signals apart, because a service commonly covers DOWN
transitions while the monitor still alerts on its own budget. My iteration report had named the
burn-rule editor as a non-goal, which was honest, and then said nothing about this one, which was
not: a non-goal has to be declared, not discovered.

## 4. One deliberate deviation, and one I had to withdraw

**The stalled-evaluator runbook lives in `runbook.md`, not `overview.md`.** §16.6b words it as "one
paragraph in `docs/overview.md`", but `overview.md` itself names `runbook.md` as the operations
document and every comparable operational paragraph is already there. Following the spec's letter
would have put one operational paragraph somewhere no operator looks for one.

**Withdrawn: "an arm that errors every cadence does not trip readiness".** An earlier revision of
this report recorded that as a deliberate deviation, on the reasoning that §16.6b's predicate is LAG
and a pass that rolled back reports none. The review round was right to refuse it, on two counts.
First, a deviation recorded in an iteration report does not amend a spec — invariant 91 says a
stalled evaluator marks the scheduler not-ready, and an arm that never completes is the most stalled
it can be. Second, the reasoning was wrong on its own terms: the arm keeps reporting the LAST
successful pass's lag, so the system reads healthy exactly while every lease it should refresh
expires. Readiness now measures the AGE of the last success, which covers both shapes.

## 5. A harness defect, recorded as a harness defect

A fresh Timescale container's FIRST full run failed in a scatter of 0.00s setup errors. It is
recorded here as a HARNESS READINESS DEFECT and not as product evidence, because the facts say so:
the same container with a freshly recreated database passed the whole suite, which rules out a
migration race in the product.

The cause is that `pg_isready` is not a barrier — the postgres/timescale entrypoints answer "ready"
while still initialising and then RESTART the server, killing every connection a test has just
opened. Every fresh-container gate now goes through a real barrier instead: three consecutive
successful `SELECT 1` a second apart (which an init-phase restart cannot satisfy), then ONE serial
migration pass before the parallel suite touches the schema.

Second harness lesson, from an incident that killed both agent sessions: test containers left running
after a gate exhausted the machine's memory. A test database now lives exactly as long as the run
that needs it, and concurrent runs get their OWN database — two suites sharing one database
truncate each other's fixtures.

## 6. What phase 5 does not ship

Named here rather than left to be discovered:

- **the burn RULE editor.** Service burn rules are declared through
  `PUT …/sla-target/burn-alerting` and through the MaC bundle; the SPA panel covers the paging

  suppression note on a MONITOR's own incident.
