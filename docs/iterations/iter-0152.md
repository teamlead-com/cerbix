## 1. What this arc makes true

One sentence: **the badge may never claim more than the server just said.**

Everything below is a way that sentence was broken while the backend was already correct — a badge
frozen at page load, a reason hidden in a tooltip, an approved screen missing, a failed refresh
keeping the last green, a hung request keeping it forever, a test that could not fail, and a count
that contradicted itself in four documents. None of it was a store defect. All of it would have been
believed by an operator.

## 2. What the rounds after the closure found

### 2.1 A coverage badge frozen at page load (P1, final-residue round)

The panel rendered coverage from the service detail's snapshot and never asked again — so a lease
expiring, an evaluation failing, or the panel's OWN save (which bumps the generation and dis-arms the
service) all left a green badge saying ARMED while delivery had stopped suppressing anything. It is
the same disagreement §16 spends a section on, arriving through the UI instead of the SQL. Coverage
is now re-read on a cadence and immediately after every successful save, through a route of its own,
with generation and unmount guards.

### 2.2 The server's reason, hidden behind a tooltip (P1, final-residue round)

One armed signal made the panel print a single generic sentence and drop the OTHER signal's reason,
which is exactly the mandatory case the design notes name: a green ownership toggle beside a
dis-armed burn signal. `last_error` — the evaluator's own message, which the API surfaces rather than
summarizes — was not rendered at all. Both signals now carry their reason as visible text, the
held-burn warning is its own block, and the badges use the approved grammar (`armed` the UP hue,
`pending` the PENDING hue with a dashed ring, `degraded` the DEGRADED hue) rather than colours I
chose myself.

### 2.3 An approved screen silently not built (P1, final-residue round)

The mock is binding and has five screens; I shipped the service panel and left out the delegated
MONITOR — the screen that answers "this is DOWN and nothing paged me, is that broken?". A monitor
detail now carries a dashed chip naming the owner beside its REAL status pill (a delegated monitor is
never greyed out) and states the two signals apart, because a service commonly covers DOWN
transitions while the monitor still alerts on its own budget. My iteration report had named the
burn-rule editor as a non-goal, which was honest, and then said nothing about this one, which was
not: a non-goal has to be declared, not discovered.

### 2.4 A live E2E that proved the build, not the feature (P1, final-residue round)

The phase closed claiming a browser gate of 42 passing tests. Those were the PRE-EXISTING tests: a
`rg` for `alerting|owns_paging|delegat` across `e2e/tests` returned nothing. Together with the manual
401/metrics probes they proved the image was built, the routes were mounted and the families were
exported — none of which is a feature. `e2e/tests/alerting.spec.ts` now covers the changed scope on a
running stack: the declaration and the coverage answering differently, a paging edit dis-arming until
re-evaluated, a partial PATCH leaving the rest alone, a monitor's page saying why nothing paged it,
and a server-owned field refused on the wire with nothing written. It also found a defect in my own
fixture on its first run — the declaration takes monitor IDs and requires `expected_revision`.

### 2.5 A refresh that failed kept asserting ARMED (P1, final round)

§2.16 made coverage re-readable and then handled only the happy path: a rejected transport, and a
response that resolved carrying an error instead of a body, both left the previous answer on screen.
So a green ARMED badge could outlive the coverage indefinitely on nothing but a broken refresh —
the same §16 disagreement once more, now on the error branch. "We could not ask" is neither armed nor
not-armed, and the panel now says exactly that: `unavailable` is its own presentation state, both
badges read `unknown` while it holds, the last payload is kept only as a signature of what the server
last said, and the next successful answer restores it.

The test that was supposed to cover this was VACUOUS: it queued a rejection and never advanced the
cadence, so the rejection was never consumed — deleting the interval entirely left all eleven tests
green. It now drives the timer and asserts that the cadence fired, which is why removing the interval
fails it by name.

### 2.6 A read that never answered kept the badge green (P1, round five)

§2.19 handled the two SETTLED failures — a transport that threw, and a response carrying an error.
It did not handle the third and nastiest: a read that neither resolves nor rejects. Under a
blackholed network no error branch runs at all, so the last ARMED badge stayed on screen
indefinitely while the cadence stacked another request behind it every fifteen seconds, and unmount
cleared the interval without cancelling anything already in flight.

Every read now carries a DEADLINE shorter than the cadence, each read aborts whatever the previous one
left running, and the context switch and unmount abort too. Against a real transport — browser
`fetch`, which honours `AbortSignal` — that means at most one request is outstanding at a time.

The deadline is a RACE and not merely an abort, and the distinction is worth stating precisely
because an earlier wording of this paragraph overstated it. A transport that IGNORES its signal
cannot be cancelled by anyone, so its underlying promise stays pending however many times it is
aborted; what the race bounds is the UI's TRUTH — the panel stops claiming coverage at the deadline
regardless of whether the transport cooperated. So: at most one non-aborted request against a
cooperative transport, and a bounded answer even against an uncooperative one. The test asserts the
second by hanging a read that deliberately ignores the signal it is handed.

### 2.7 A line no test could fail, and a claim wider than its proof (P2, post-close audit)

Two honesty gaps rather than product defects, and both worth recording because they are the kind that
survives a green suite.

**An unpinned line.** The abort at the TOP of a read — "cancel whatever the previous read left
running" — could be deleted with all fourteen tests still passing. The cadence can never reach it: the
deadline is 10s and the cadence 15s, so a cadence read is always already aborted by the time the next
one starts. The line exists for the OTHER caller — a save refreshes immediately, before that deadline
— and that path had no test. It has one now, and deleting that single line fails it by name.

**A claim wider than its proof.** The report and a test name both said there is never more than one
read in flight *even for a transport that ignores its signal*. The test counts un-aborted signals, and
an ignored abort leaves the underlying promise pending regardless — so the sentence was not what the
test showed. Narrowed to what is true and useful: at most one non-aborted request against a
cooperative transport (browser `fetch` honours `AbortSignal`), and a bounded UI answer even against an
uncooperative one, which is what the race provides and what the hang test actually asserts.

### 2.9 A report that undercounted the rounds it is about (P2, round [403])

This report said "five review rounds" in three places and its plan omitted round [399] entirely — so
the narrative disagreed with `status.md`'s own round list, which was right. The cause is visible in
the omission: I enumerated the rounds from memory while writing, missed the recheck, and then wrote a

## 4. Why the counts kept drifting, and where they live now

Three rounds in a row found the two totals disagreeing. The fault was never arithmetic: four documents
each RESTATED the same pair, and a number restated in four places drifts. Resetting them a third time
would have bought one more round.

The cumulative counters now have exactly one owner, `docs/status.md`, chosen because it is long-lived —
a snapshot cannot own a number that keeps changing, which is the whole of finding §2.8. Iteration
reports state what THEIR OWN arc found and nothing cumulative. `docs/traceability.md` points rather
than counts.

The two totals are also different SETS, which is what let them blur in the first place: reviewer
findings include documentation and counting issues that were never product defects, while the defect
sections of a report include the ones I found myself. They are not a cross-check of each other.
