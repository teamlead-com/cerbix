## 2. What landed

### 2.1 Instance audit — the backend

`RecordAudit` has stored an empty `OrgID` as NULL since the global-admin flag shipped, and the only
listing in the product is `ListAuditByOrg`. So `user.global_admin`, `user.delete`, file-provider and
outbox actions have been written for months and shown to nobody — the installation records its own
history and cannot read it.

- `ListGlobalAudit(ctx, limit)` reads `org_id IS NULL`. It is a **separate query**, not the org
  listing with a widened filter, and that is the substantive design choice: a filter that CAN be
  widened by a parameter is one authz slip away from showing a tenant admin the whole installation.
  The two listings now share `auditListSQL` and `scanAuditEntries` instead of duplicating the join,
  the ordering and the bound — so the org view and the instance view cannot drift apart.
- The scan reads `org_id` as NULLABLE. The previous code scanned it into a plain string, which would
  have failed on exactly the rows this listing exists for.
- `GET /api/v1/admin/audit` behind `requireGlobalAdmin`, `limit` clamped server-side (default 100,
  max 500), documented in `openapi.yaml` (version bumped, `schema.d.ts` regenerated so the CI drift
  check stays green).
- The API's store interface grew, which broke `fakeStore` in `internal/api/api_test.go` — intentional,
  per this repository's convention that interface growth must be seen at compile time.

Tests assert the isolation in BOTH directions, because either one alone leaves a real leak available:
an org listing that swept in instance rows would show one tenant the installation's history, and an
instance listing that swept in org rows would do the reverse. Plus authz (an org admin and a viewer
each get 403) and the limit clamp (a hostile `limit=99999` returns 100, not the table).

**The UI, after the owner approved the mock.** `docs/design/mock-instance-audit.html` was signed off
directly by the owner (the earlier approval had arrived relayed by a party participant, which the
process gate does not accept), and the panel implements it 1:1: a tab in the Administration group,
global-admin only, the org trail's row grammar unchanged, one dashed `instance` chip, a machine actor
rendered as "machine", nothing deletable.

One judgement worth stating because it changed existing code: the row grammar is now **one component**,
`AuditRows.vue`, used by this panel and by the org trail in `MembersPanel.vue`. The mock claims "the
org audit's row grammar, unchanged" — a claim that survives by having one implementation, not by two
agreeing today.

And a correction to myself, made before it cost anything: I described `MembersPanel`'s own tests as the
regression guard for that refactor. **It had none** — the settings panels carry one spec between them
(`SecretsPanel`), and the org audit trail was covered by nothing. So the guard was written rather than
claimed: `MembersPanel.spec.ts` now pins that the org panel reads the ORG endpoint, never
`/admin/audit`, renders its own vocabulary through the shared rows, and marks a removal as destructive.

### 2.2 The discharge map, re-read row by row — 18 of 91 were wrong or thin

Round [425] sampled about five rows of the discharge map and TWO were false: the cited test existed,
passed, and did not prove the clause. That refutes the map by sampling, so patching those two would
have been the worst available answer. Every one of the 91 invariant rows was re-read against the
doc-comment of every test it cites — a comparison the gate cannot make, because the gate checks that a
test EXISTS.

**The class, which explains both of the reviewer's findings: a multi-clause invariant cited by a test
that proves ONE clause.** The spec's invariants are conjunctions ("locked ascending, open-state
rechecked under the lock, links inserted, notes atomic"), and I had mapped each row by finding *a*
test about the subject rather than a test per clause. Where the un-cited clause happened to be the
load-bearing one, the row became a lie that passed the gate.

| Outcome | Rows | Which |
|---|---|---|
| Read and confirmed correct | **73** | the majority: every clause of the invariant has a test that asserts it |
| Citation added — a clause had no test named | **11** | 2, 5, 9, 14, 19, 22, 30, 34, 65, 66, 91 |
| FALSE row — the key clause was proven by nothing on that row | **2** | 53 (under-lock recheck), 82 (at-least-once) — both found by [425] |
| Genuinely unpinned → NEW test written | **2** | 4 (provenance tells ignored from excluded), 6 (validation reads the DECLARED cardinality) |
| Marked PARTIAL with the gap named | **1** | 78 (both tests run over the worker's fake; "byte-identical facts" is not asserted at row level) |
| Reworded — the claim was not a test's job | **2** | 28 ("in both storage modes" is a RUN property: the same tests, twice), 46 (two comment-less pre-FR-021 tests, so the row now says what they cover) |

Two things are worth stating rather than filing away.

**Nothing was broken.** All four properties behind the new tests and both false rows are correctly
implemented; no mutant needed a product fix. What the re-read repaired is the ability to CHECK the
claim — which is exactly what D-0169 closed FR-021 against, so the repair is not cosmetic.

**The gate cannot catch this class, and pretending otherwise would be worse than the gap.** A rule
like "the cited test must name the invariant number in its comment" would have caught row 82 and
NOT row 53 — `TestCorrelateBothInterleavings` says "invariants 52–55" in its own comment, which
includes 53. So the honest mechanism is a per-clause reading at the time a row is written, and the
honest record is this table. The gate keeps citations resolving; a reader keeps them true.

The 24 §16.10 scenario rows were not re-read the same way, and the reason is structural rather than
optimistic: each is ONE line of a matrix written before the code, so the multi-clause failure mode
cannot apply to them. The two with internal sub-cases (#5's three routing failures, #17's six
lifecycle transitions) were re-checked and hold.


### 2.3 Project-level SLO objective — the backend, and why the database refuses paging

`sla_targets` has carried `project_id` as one of three exclusive scopes since migration 00077 and no
code ever wrote it: eleven migrations of dormant schema. `func-audit-gaps-2.md:23` had already ruled on
what that means — "a project-level objective is a real feature, not a gap fix" — and the owner's
decision for this arc is REPORTING ONLY.

- `UpsertProjectSLATarget` / `GetProjectSLATarget`, arbitrating on the partial unique index that has
  existed since 00005 (`WHERE project_id IS NOT NULL`, which an `ON CONFLICT` must name or it will not
  use the index at all).
- `GET|PUT /api/v1/projects/{projectID}/sla-target`, `{window, objective}` and nothing else. The
  objective goes through `domain.CanonicalObjective` — the same one rule as monitors and services
  (D-0165), so 100, 0 and 99.99995 are refused by name.
- The project SLA report now STATES the objective and the budget it produces for a window that has one,
  and says nothing for a window that does not. The burn fields stay ABSENT rather than `false`: an
  omitted field is the honest rendering of "this cannot page", where `burn_alert: false` reads as
  "not yet".

**Migration 00083 adds a CHECK, and that is the substantive decision.** "Reporting only" is a promise
about what an operator's edit cannot cause, and phase 5 taught what it costs to leave such a promise to
the application layer. A service-scoped target was refused AT THE SCHEMA for exactly this reason until
the phase that owned service paging arrived and lifted the constraint deliberately, in a migration, with
a decision behind it (§16.4). A project-level pager will need the same — an arming rule, a routing
answer, close semantics — so until then `sla_targets_project_no_burn_chk` means the row cannot say "page
me", whoever writes it and however. The API's 400 on a burn field and the store's missing burn argument
are the other two layers; all three agree instead of one of them being the only thing between an
operator and an alert nobody designed.

The schema half is asserted with DIRECT SQL rather than through the store, because the store not
offering a burn argument proves what this code does today, while the CHECK proves what any future writer
can do. Mutants, each fatal with the test's own message: dropping the constraint →
"'reporting only' must be a database guarantee, not a convention in the store"; removing the API's
refusal → "a field that looks configurable and is ignored is worse than no field".

Not done: the UI. A project objective editor is a new SPA surface, so it needs a mock approved before
frontend code — the same gate that just governed the instance-audit panel.


### 2.4 A result now says which job it answers, and cannot predate it

`func-result-protocol.md` §9 deferred two things with "with P0b/job correlation, not here" and nobody
came back: end-to-end `job_id` correlation, and a strict `observed_at >= job_issued_at` check.

**Half of the identity already existed, in the wrong place.** A `job_id` was generated per job by the
materializer (`gen_random_uuid()` in the SELECT) and carried only INSIDE the credential envelope — so a
monitor with a secret had a job identity and a monitor without one had none, and neither returned it.
Now the id AND the issue instant come from the database in that same statement and ride every
`CheckJob`; executors copy them onto the result through ONE owner, `dispatch.StampResult`, because
three places publish results (the AMQP worker pool, the pull agent's batch, the probe-error path) and a
stamp applied separately in each would drift the first time one was edited.

The issue instant comes from the DATABASE deliberately. The check compares an executor's `observed_at`
against it, so it has to be the one clock the core trusts; comparing two readings of the same unknown
clock would detect nothing.

**The boundary is the owner's decision, and all three of its parts are pinned separately:**

| Case | Behaviour | Why |
|---|---|---|
| `observed_at` earlier than `job_issued_at` by MORE than `result.allowed_skew` | rejected, reason `observed_before_issue` | the result cannot be about the job it claims to answer |
| earlier, but inside the tolerance | ACCEPTED and counted (`cerbix_result_observed_before_issue_total`) | a region's clock trailing the core's by seconds is ordinary; dropping those results would lose real measurements to fix a bookkeeping detail |
| no job identity carried (zero) | nothing is checked | push results and any executor older than the field keep working; zero means "not carried", never "issued at the epoch" |

**The mutation that mattered found a hole in my own work.** Removing the stamp from the worker left the
ENTIRE suite green — so the correlation this feature exists for was resting on nothing, and I had
written the feature that way in this same arc. `TestPublishedResultCarriesTheJobItAnswers` now fails on
exactly that mutation. Six mutants in total, each fatal with its test's own message: the ordering check
removed; the tolerance removed (rejecting everything early); the counter not bumped; the materializer
not stamping; the worker not stamping.

Deliberately NOT done: persisting `job_id` per heartbeat. That would be a column on the hottest,
partitioned table in the system for a correlation nothing queries yet. The id rides the result, appears
in the rejection's reason path and in the probe-error diagnostics, and a durable per-heartbeat trail is
a separate decision with a separate cost.


### 2.5 The status column was prose in a field the process defines as an enum

Reading my own work back — the habit this arc's predecessors were mostly about — I found that
`AC-0155-3`'s status cell said `IN_PROGRESS (UI pending a mock)`. AGENTS' workflow step 2 names three
statuses and only three; a status plus a parenthetical is prose in an enum, and it is invisible to
anything that counts statuses. The qualifier moved to the evidence cell, where it belongs.

Then the same check over the whole file found the defect was not mine alone:

- four rows carried `DONE (74.7%)`, `DONE (75.7%)`, `DONE (76.0%)` — a coverage percentage appended to
  the status. The number is evidence and now lives in the evidence cell;
- `AC-0007-3` carried an unescaped pipe inside a route list (`/healthz|/readyz|/metrics`), which
  silently shifted every later cell, so that row's STATUS column had held a fragment of its own
  requirement text for however long it has been there. Replaced with an enumeration.

**The gate grew rather than the discipline being reasserted.** `make docs-check` now parses every
requirement row and fails unless the status cell is exactly `TODO`, `IN_PROGRESS` or `DONE`, splitting
on UNESCAPED pipes only — because `\|` inside a cell is a legitimate literal (a shell pipeline in an
evidence cell), and a first version of this check that split on the raw character accused four correct
rows while missing the one that was actually broken. Both defect shapes are mutation-proven: a status
with a parenthetical, and a pipe injected mid-row.


## 3. Decisions this arc needs from the owner

- **Item 3 (`job_id`)**: what happens when `observed_at < job_issued_at`? Rejecting loses real results
  whenever a region's clock drifts; accepting silently keeps the class of bug the check exists to find.
  My recommendation: reject only beyond a configurable tolerance and COUNT the rest, mirroring the
  existing `result.allowed_skew` — but the default value is the owner's call.
- **Item 2 (project objective)**: reporting only, or paging too? Recommendation: reporting only, exactly
  as services were in phase 2. Paging doubles the work and needs its own arming rule.
- **Item 4 (§16.9)**: which of the six is commissioned first, if any. Each needs its own requirement.
