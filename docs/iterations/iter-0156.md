## 1. What this slice makes true

**An incident's subject is unambiguous at the schema, and stays true after the subject is gone.**

## 2. What landed

### 2.1 The schema, and why each shape is a decision rather than a convenience

- **The anchor is EXCLUSIVE and enforced by CHECK**, not by the store: two anchors on one row is not a state
  the application should have to remember to avoid. The constraint says *at most* one, never *exactly* one,
  because a manual project-level incident carries neither today and must keep working — a detail that would
  have broken every manual incident if the spec had said "exactly".
- **The FK is COMPOSITE** against `services (id, project_id)`, because a same-project guarantee living in
  application code is one bug from crossing tenants (FR-021 invariant 48 exists for that), and it uses
  PG15's column-list `ON DELETE SET NULL (service_id)` — a bare `SET NULL` clears EVERY referencing column
  including the NOT NULL `project_id`, the exact trap iter-0125 hit.
- **One OPEN auto-incident per service**, by partial unique index mirroring 00049's per-monitor rule. A
  flapping service must not accumulate incidents, and under concurrent evaluators only the database can
  promise it.
- **A member snapshot table**, because a postmortem is read after the world moved (spec D6).

### 2.2 The store, and a model the code corrected

`OpenServiceIncidentTx` opens inside the CALLER's transaction, which is what lets task 3 satisfy FR-022
invariant 7 (an incident without its announcement, or an announcement without its incident, is
unrepresentable). It returns `created bool` rather than an error when the index refuses a second open: a
concurrent evaluator losing that race has done nothing wrong, and the caller needs the incident that IS
open so it can annotate that one instead of believing it opened a new one.

**The spec was wrong about the snapshot's shape, and the code found it.** I had specified
`[{monitor_id, name, slug, role}]`. But `service_definition_members` stores one row per (monitor, ROLE), and
a member is commonly both operational context and an SLI — so the first implementation snapshotted the same
monitor twice, which reads as a duplicate rather than as a fact. The roles are now aggregated and the
monitor appears once; the spec says so and says why. Two further details the code settled: the snapshot
reads `monitor_name` from the DECLARATION rather than joining `monitors`, because the effective revision is
already a snapshot of the membership and a join would render an empty name for a member deleted since —
which is the very case the table exists for; and a MISSING snapshot is a different answer from an EMPTY one,
so `IncidentMemberSnapshot` returns `(members, present, err)`.

### 2.3 The evaluator opens and resolves — and the spec was missing half of it

The open rides the SAME transaction as the announcement, which is what FR-022 invariant 7 asks for: an
incident without its announcement, or an announcement without its incident, is now unrepresentable. Only the
LIVE evaluator can reach this code, which is the structural form of spec D1's "never on a burn breach".

**Writing it exposed a hole in my own spec.** D1 said "auto-open" and said nothing about closing — and an
incident that opens by machine and closes only by hand is a trap with two edges. The operator reads
"investigating" on a service that recovered hours ago; and because at most one auto-incident may be open per
service, the NEXT outage cannot open one, so the second failure is invisible in the timeline. The monitor
path has always resolved its auto-incident on recovery, so the precedent existed and the spec had simply not
looked at it. **D1b** now states the resolve, invariants 15 and 16 pin it, and the matrix gained three lines
(recovery resolves; a second failure opens a second incident; a human's incident is left alone).

`ResolveServiceIncidentTx` names `source = 'auto'` in its WHERE, and that clause is the whole difference
between a machine that tidies up after itself and one that overwrites a person's conclusion.

### 2.4 The supersession, done in the same change rather than promised

FR-021 invariant 86 said a service alert opens, resolves or annotates NO incident. The moment the evaluator
landed, its test failed with its own safety message — which is exactly what a good test does when the rule
it guards changes. All three obligations from §4 moved in this change:

1. §16.8's invariant 86 carries a SUPERSEDED note, keeps its number (other documents cite it), quotes its
   original text and names what SURVIVES: a service alert still does nothing to a MONITOR's incident;
2. the discharge row for 86 moved to the rewritten test, and so did §16.10's scenario 24, which tested the
   same rule from the matrix side — I had not listed that one in §4 and the gate found it;
3. `TestAServiceAlertNeverTouchesTheIncidentTables` became
   `TestAServiceAlertOpensAndResolvesOnlyItsOwnIncident`, asserting the NEW rule and the surviving half.
   Rewritten, not deleted, so the record that this rule ever changed survives its change.

`make docs-check` could not have caught the supersession itself — the old row cited a test that existed. What
it DID catch was the consequence: three stale references to the renamed test, one of them in a document I had
just written. It also exposed a gap in its own vocabulary, since it treats "renamed" as a legitimate reason
for a citation not to resolve but had never heard of "rewritten"; both words are now in that list.


### 2.5 Correlation over the second anchor — and the invariant that turned out to be structural

FR-022 promises a service incident "with its impact links", so correlation had to stop returning early on
`monitor_id IS NULL`. Three things changed, and one deliberately did not.

**The anchor's own services.** A monitor resolves through `monitors[]` membership; a service anchor is its
own, and exactly one. An incident anchored to NEITHER — a manual project-level record, or a service incident
whose service was deleted between enqueue and delivery — still returns "skipped by design, delivered".

**Both kinds of anchor now WITNESS.** This is the part I would have got wrong by doing less. Counting only
monitor incidents as witnesses looks conservative and is actually a correctness bug: the mirror back-fill
would give a monitor incident its `affected` row when the service incident opened SECOND, and nothing at all
when it opened first. The relation's content would depend on opening order — the exact asymmetry §14.3's
mirror exists to prevent. In a world with no service incidents the new branch matches nothing, which is how
NFR-017 stays true by construction rather than by assertion; the whole pre-FR-022 correlation suite is
unchanged and green, and that IS the regression proof.

**Invariant 9 is held structurally, not by a check, and I did not add a check that could not fire.** I went
looking for the configuration where a service incident names its own service and could not build one: `walk`
skips its own start node, a service anchor's own set is a single service, and the write path refuses cycles
under the graph lock. So the self-link is impossible through every public path, and a guard in the candidate
builder would have been untested dead code claiming to hold a property something else holds.

What I did instead is make the real owner of the property observable. `walk`'s `nb == start` line now says
what it holds, and the property is pinned by three tests whose mutants each fail with their own message:
correlation skipping the service anchor again (no links at all), the witness query losing its service branch
(order-dependent content), and `walk` returning its own start node — which is only reachable if the stored
graph contains a cycle, so that test PLANTS one by direct SQL, the way the tenancy test does. The mutant then
produced exactly the row the invariant forbids, `payments|affected|payments>checkout>payments`, which is the
only evidence I would accept that the line is load-bearing rather than decorative.

**The enqueue lives with the open, not with the evaluator.** `OpenServiceIncidentTx` enqueues the correlation
attempt in the same transaction, on the same fenced topic `CreateIncident` uses. An incident that exists
without its correlation event is precisely the dual-write the outbox exists to make impossible.


### 2.6 The public projection, and a leak I had already shipped into the branch

FR-022 invariant 11 asked for the incident and no impact links on the public page. Checking it found
something worse than a missing feature: `Incident.PublicRedacted` cleared `project_id`, `monitor_id`, the
external key and the ack actor — and NOT the `service_id` I added in slice 1. Every unauthenticated render of
a page with a service incident was shipping the service's internal UUID. Nothing failed, because the
redaction list is a list, and a list does not notice what was added to the struct beside it.

The fix is one line; the test is the part that matters. It checks two promises that fail differently:

- the ANCHOR is an internal id of the same class as `monitor_id` — a page names its components by slug, and
  an unauthenticated viewer has no use for a UUID. Removing the new line makes the test print the whole
  leaked body, so the failure names the actual bytes rather than a boolean;
- the impact LINKS are absent for a different reason: §14.7 makes them a detail-only enrichment, so an
  unbounded public list never multiplies by them.

The same test asserts the AUTHENTICATED render still carries the anchor, which is what makes the redaction
targeted rather than a blanket drop an operator would have to work around.

**One thing is deliberately unchanged and worth naming rather than discovering later.** The 🕸 note lives in
`incident_updates`, and §14.5 approved it rendering "through the existing system-update mechanism,
unchanged" — so it has been publicly visible for monitor incidents since phase 3, and its prose names service
slugs. A service incident inherits exactly that treatment; the test pins the inheritance so nobody reads the
"no impact links" rule as also silencing the note. If the graph's slugs should not be public, that is a
change to §14.5 for BOTH anchors, not something FR-022 gets to decide for one.


## 3. Gates

- `go test -race -count=1 ./internal/store/ ./internal/domain/ ./internal/api/` — green on a database that
  applied all 84 migrations from zero; container removed the moment the run finished.
- `go build`, `go vet`, `gofmt`, `make docs-check` — clean.
- **Five mutants.** Four fail behaviourally with the test's own message: the anchor CHECK dropped ("an
  incident naming BOTH … was accepted"); the composite FK's tenant half (a cross-project anchor accepted);
  the member snapshot not written ("present=false" where a postmortem needs it); and the roles left
  un-aggregated (the monitor listed twice).
- **One mutant is honestly weaker and it is named rather than counted as equal:** dropping the partial
  unique index makes the `ON CONFLICT` clause fail loudly (`no unique or exclusion constraint matching`)
  instead of letting incidents accumulate. That proves the code DEPENDS on its arbiter, not that the count
  stays at one — so the test also asserts the count behaviourally after two opens, and removing the
  `ON CONFLICT` clause instead produces a duplicate-key failure, which is the same coupling from the other
  side. Neither mutation can produce accumulation, because the database refuses it; that is the point of
  putting the rule there.

## 4. What must move WITH task 3, not after it

FR-022 supersedes **FR-021 invariant 86** — "no service alert opens, resolves or annotates an INCIDENT" —
which is true today and held by `TestAServiceAlertNeverTouchesTheIncidentTables`, written three days ago in
iter-0155. When task 3 lands, the invariant gains a SUPERSEDED note keeping its number, its discharge row
moves to the test holding the new rule, and that test is REWRITTEN rather than deleted, exactly as phase 5
rewrote the phase-2 burn-rejection test when it inverted. `make docs-check` will not catch this: the row
would still cite a test that exists. It is a reading obligation, and it is recorded here because the last
three arcs each found a statement left standing after the event it was conditioned on.
