## 1. What this slice makes true

**A service that pages can also escalate, and every predicate that decides whether it may is stated.**

## 2. What landed

### 2.1 A second query, not a wider one

The monitor candidate query is unchanged, character for character. The service candidates come from their
own `SELECT`, which is the same choice FR-022 made when it added the second anchor and for the same reason:
the way to keep "a monitor's ladder is byte-identical" (NFR-018) is to add a path, not to widen the one that
already works.

Every predicate is a service analogue of a monitor predicate, and the mapping is the argument that this is a
translation rather than an invention:

| monitor ladder | service ladder | why |
|---|---|---|
| `m.escalation_policy_id IS NOT NULL` | `s.escalation_policy_id IS NOT NULL` | the column has existed since phase 5, deliberately unread |
| `m.enabled` | `s.owns_paging` | a service that is not the thing that pages escalates nothing |
| `m.status = 'down'` | `st.live_firing` | the LEVEL, not an edge |
| — | `st.lease_until > now()` | no analogue: a monitor's status is a fact it maintains, a service's verdict is one an evaluator must keep refreshing |

**The fail-closed rule is in the JOIN, not in a branch.** No state row means no candidate; a stale lease means
no candidate; a read error fails the pass, which fires nothing. That is the opposite polarity from
delegation's fail-open, and the asymmetry is the point: at delivery time ambiguity means *a page exists*,
while here it would mean *a page multiplies* on a state nobody can currently confirm. Both rules pick the
same thing — a page exists, and it does not multiply on a guess.

**What is deliberately absent: any pause driven by the service graph.** The monitor ladder pauses while a
transitive parent is down, and mirroring that over §14 looks like consistency. §14 states its own position —
the impact graph *annotates and links; never suppresses, merges or hides* — so a graph sold as advisory does
not become a suppression mechanism because this feature found it convenient. The test for that invariant
builds the exact configuration that would pause a monitor and asserts the service ladder fires anyway.

**D8 is enforced by a value rather than a comment.** A service has no renotify knob, so a service candidate
carries `renotifySeconds = 0` — which is precisely what the existing repeat branch requires to be positive.
The non-goal cannot drift, because breaking it would mean writing a number that does not exist.

### 2.2 A payload that names the service without stranding an old worker

`EscalationStepAlert` gained `service_id` and `subject_name`, and `Message()` prefers the subject.

My first answer to the mixed-version hazard was to FENCE `TopicEscalationStep`, and the code refused the idea
in its own words: `domain.FencedTopics`' doc comment says *"the pre-fence topics stay legacy forever because
every deployed owner already dispatches them."* Fencing a pre-fence topic inverts the protection — a
currently-deployed worker claims `status = 'pending'` and would stop seeing escalation steps at all during a
rolling upgrade. The fence stops an old worker mishandling a NEW topic; using it on an OLD one silences a
working delivery path.

So `monitor_name` stays, populated with the SUBJECT's name, documented as a legacy render field. The test
asserts what a pre-FR-023 worker renders by building the payload from that field ALONE — "Checkout is DOWN" —
because the claim is about a binary I cannot run here, and the only honest way to check it is to render
through exactly the data that binary reads.

### 2.3 The one place delegation must NOT reach

The worker suppresses a MONITOR's step while a service owns its paging. A SERVICE's step is the owner's own
page: muting it would leave the outage with nobody told at all. The service branch therefore skips the
delegation path — and the monitor lookup with it, because a service step carries no monitor id, so the lookup
could only fail and the fail-open it logged would be an alarm about a question nobody asked. The test asserts
the ABSENCE of that call, which is why the fake now records its lookups.

### 2.6 The ladder becomes countable, and it never was before

`AdvanceEscalations` returned one integer, and the scheduler logged it. FR-023 would have made that number a
blend of two subjects with different owners and different fixes, so it returns `EscalationPass`
{MonitorSteps, ServiceSteps} and `cerbix_escalation_steps_total{subject}` publishes both. Two notes on the
shape:

- attribution takes the SERVICE ID rather than a boolean, because the anchors are exclusive at the schema —
  the id's emptiness is the same fact the payload branches on, so there is no second flag to keep in sync;
- the ladder had **no metric at all** before this, only a log line. That is worth stating plainly rather than
  presenting the label as the whole improvement: "how much did the on-call ladder fire this week" was not an
  answerable question in this product until now.

The wiring test uses unequal numbers (2 monitor, 5 service) so a wiring that published one total twice cannot
pass, and the mutant that drops the publish fails it.


### 2.7 Sizing the SPA delta found a hole in the product, not in the UI

Before drawing a mock I checked what an operator can do today, and the answer was: nothing. `services` has
carried `escalation_policy_id` since phase 5, but **there is no update endpoint for a service at all** — only
create, get and delete. The field was settable at creation or by a file provider, and a service that already
existed could not be given a policy through the API in any way.

That was harmless while the column was inert. FR-023 made it decide who is woken at 03:00, which moves it
under §16.6a's rule for paging configuration: every change audited, with its actor and what moved, INSIDE the
mutating transaction. So the slice became a backend one, and the mock waits.

`PUT …/services/{id}/escalation-policy` is its own route, for the reason `handlers_servicealerting.go` already
states about the burn declaration: a distinct transaction, a distinct audit action, distinct consequences —
those do not belong behind one merge. The store function follows the declaration write's shape exactly: the
service row locked and tenant-scoped FIRST (one answer for wrong tenant, unknown id and a non-uuid, so
existence never leaks), the file-ownership refusal, then the no-op check, then the policy's own tenancy.

Four decisions in it are worth reading:

- **a no-op writes nothing at all** — no `updated_at`, no audit line. A trail that records a change nobody
  made is worse than one line short, and the declaration path already refuses no-ops for the same reason;
- **the foreign-policy check is explicit even though the composite FK would refuse it.** The mutant that
  removes it proves why: the failure becomes a raw `services_escalation_policy_tenant_fkey` violation, which
  an API can only render as a 500. The check exists so the refusal is legible, not so it is possible;
- **the audit names WHAT MOVED** — `none→id`, `id→none`, `id→id` are three different operational stories, and
  an operator reading the log after a missed page needs to tell them apart;
- **a change does NOT reset a ladder in flight.** A monitor's policy can be swapped mid-outage today and its
  step index is left alone; a service behaves identically, because a second rule to learn is worse than a
  shared footgun. The consequence is stated in the code rather than left to be discovered: swapping to a
  SHORTER ladder can leave the index past its end, which fires nothing further — the conservative direction,
  since rewinding to zero would page everyone again for an edit.

Five API sub-cases and one store test, each refusal asserting that nothing was written; four mutants, all
fatal (audit dropped, no-op written, tenancy unchecked, file ownership unchecked).


### 2.8 The mock's palette was mine, not the product's

The owner's first look at the mock said the colours differ from cerbix. They did: I had written a palette
instead of using the design tokens. The block is now lifted VERBATIM from `frontend/src/style.css` — the same
one every approved mock carries — and verified against it token by token by a script rather than by eye (zero
differences). Lifting it also duplicated the reset and body rules, which I then removed.

The colour DECISION is now stated rather than improvised: FR-023 adds no hue at all. An escalation step is not
a new state, it is the existing DOWN story told again to more people — so a fired step carries the DOWN hue,
the progress pill keeps the degraded hue it already has, and steps not yet due are OUTLINED rather than
tinted, because something that has not happened is not a state.

A mock that puts a colour decision nobody made in front of a reviewer is worse than no mock: it spends their
attention on my invention instead of on the product.

### 2.9 The write path on a live stack, audit included

The unit tests prove the store inserts an audit row; only a live run proves the ACTION NAME reaches the
surface an operator reads. The new e2e attaches a policy to an existing service, checks the service detail

Two fixture errors of mine, both fixed in the fixture: the test used `firstProject` where this spec has its

navigating — those fetch RELATIVE urls from inside the page, so on `about:blank` they fail with "Failed to
parse URL", which also took the spec's own `afterEach` down with it. The suite is 48 passing, 1 known skip.


### 2.10 The SPA delta, and the one placement decision the tests forced

The owner approved the mock, so the control was built exactly as drawn: the policy picker in the paging
panel, with `— none —` clearing it, and its OWN save button. Two writes, two audit actions, two error
lines — one button that half-applies is worse than two buttons, and a shared error line could not say which
half failed.

**The tests moved it out of a branch I had put it in.** My first placement was inside the block that renders
the declaration form, which is `v-else` on "the declaration could not be read". So a failed declaration READ
would have hidden a control that has nothing to do with the declaration — the policy is a different field on
a different route. The unit tests failed on exactly that (six of them, all "unable to get the select"), and
the fix was structural rather than a fixture tweak: the control now sits outside both branches.

Three other decisions are pinned by tests rather than left to reading:

- **the picker trusts the ECHO, not its own draft.** The endpoint answers with what the database holds, which
  for a no-op is the stored value; a component that assumed its draft had won would tell the parent something
  the database does not hold, and the parent owns the service row;
- **a project with no policies says so** instead of rendering a picker with one option — a select that
  silently offers one choice reads as "this installation has one policy", a claim this component cannot make;
- **the declaration is not touched.** The test asserts `PATCH` was never called when the policy is saved.

The e2e goes through the CONTROL, not only the route: select, save, poll the service until the API agrees,
then clear with `— none —` and poll again. A select bound to the wrong field would have passed every unit
test in the component.


### 2.11 A flake, its real cause, and the reason it was worth stopping for

The full-suite run failed in `internal/scheduler`:
`TestErroringServiceAlertArmCountsAnErrorOutcome` reported *"the healthy burn arm published nothing"*.

It reproduced at 2 failures in 30 `-race` runs, and it is **not** caused by anything in FR-023: twenty runs
with my metric calls removed by overlay behaved identically, and with `escalationPass` zero-valued those calls
never execute in that test at all. The cause is the WAIT. `leadUntilMetrics` polls until a predicate holds;
that test waited for the health arm's error series and then asserted a BURN series — so it could return while
the burn arm had not yet run a single pass, and then report that an arm published nothing when it had simply
not been asked.

Fixing it exposed the same defect one test over, in the telemetry test I had extended myself: it waited for
THREE series and asserted sixteen. The repair is not a longer predicate but a single source: the wait is now
built from the very list the assertions use, so the two cannot drift again. Sixty `-race` runs of both tests
are clean, and so is the whole 33-package suite.

**Why not just re-run it.** A test that fails once in fifteen full runs is a test nobody will believe when it
fails for a real reason — and this branch has never run in CI, so its first CI run would have hit it. That is
the third observation-shaped defect in this iteration (§4 records the other two), which is the argument for
treating the harness as product rather than as scaffolding.

## 4. Correction of record, and a mistake of mine in the harness

A `-race` run of `internal/store` failed once. I piped that run through `tail -6`, so the failing test's name
was **discarded before I read it** — the output said only which package failed. Three further runs were green.
What I can state: the failure is not reproducible in three attempts, and it is not visible in the non-race
run either. What I cannot state is which test it was, and that is my fault rather than the suite's — a run
whose failure detail is thrown away costs the whole run.

The habit this earns: **never pipe a test run's output through `tail` while it can still fail.** Save the
whole log, then read the tail of the file.

**A second harness mistake, mine as well.** I then started a three-run repeat batch on the SAME database my
foreground checks were using — two runs of one package against one database, each calling `TruncateAll` under
the other. That is a rule this project already wrote down after paying for it, and I broke it within the hour.
The batch was stopped and its results discarded rather than reported: a green run from a contaminated
database proves nothing, and a red one would have sent me hunting a bug I had created in the harness. The
confirmation run in §3 used a database of its own.

Both mistakes have the same shape — I optimised the OBSERVATION and corrupted it. Worth naming as a pair.
