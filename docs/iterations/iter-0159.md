# iter-0159 — the dependency backlog, merged in two classes

> **Lifecycle: CLOSED on 2026-08-19.** Every dependabot branch is merged and verified, and what stays
> unmerged is named in §6 with the reason. No decision record: nothing here decides anything the project did
> not already decide by running dependabot. From this commit the report is IMMUTABLE.

No requirement. Seven dependabot branches had been open since 2026-08-17 and none of them were stale: `main`
carried the older version in every case. They were merged in **two classes**, because "bump dependencies" is
not one job — three of them are patch/minor and verified by the ordinary gates, four are major and can only be
trusted by running the thing they change.

## 2. The lock conflicted, and it was regenerated rather than hand-merged

`unplugin-auto-import` collided with `main` in `package-lock.json`. A hand-merged lock is a **fiction**: it
describes a dependency tree npm never resolved, and every later `npm ci` would install something nobody
tested. So the conflict was resolved by regenerating the lock from `package.json` and then READING IT BACK to
confirm the pin (`21.1.0`, and `14.4.0` for the second one) rather than trusting the range.

## 3. An experiment worth more than the bump: nothing uses `@vueuse/core`

Before believing the vueuse major, I removed `@vueuse/core` from the auto-import preset in `vite.config.ts`.
Both the type-check and the build stayed green — so no vueuse API is used anywhere in this SPA. The dependency
exists only as a name in an auto-import list.

That means bump 7 is safe **by accident rather than by verification**, and it raises a question this iteration
deliberately does not answer: whether the dependency should exist at all. Dropping a dependency is a decision
about what the auto-import surface should offer, and it belongs to whoever wants that surface — not to a
dependency sweep. Recorded as a question, with the experiment that produced it, so the next person does not
have to rediscover it.

## 4. The snapshot that did not change, and why that is the interesting result

`make spa-snapshot` produced a **zero diff** after all four majors: the emitted bundle is byte-identical. That
is worth stating precisely because the honest expectation was the opposite — a new vite plugin major and a
regenerated tree usually move the output. The check was run rather than reasoned about, which is the only way
that claim is worth anything, and `go build` embeds exactly what is committed there.

## 6. What is left unmerged, and must stay that way

`deps/tailwind-v4` and `deps/ts58-vue-tsconfig-openapi-fetch` (local, from 2026-08-11). Both branch from a
point 154 commits behind and carry OLDER versions than `main` now has — openapi-fetch 0.13.4 against 0.17.0,
`@vue/tsconfig` 0.5.1 against 0.9.1, tailwindcss 3.4.15 against 4.3.3. Merging either would roll dependencies
BACKWARDS. They are candidates for deletion, not for merging, and deletion is the owner's call.

`origin/feat/service-reliability` points at the same commit as `main` and contains nothing unique — also a
deletion candidate. Its PR state was not checked: `gh` is not installed in this environment, so the conclusion
rests on the git graph alone.
