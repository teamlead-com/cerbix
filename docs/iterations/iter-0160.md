# iter-0160 — the public positioning, reviewed against the code

> **Lifecycle: CLOSED on 2026-08-19 (D-0174).** No requirement: this iteration changes what the product SAYS
> about itself, after verifying what it does. From this commit the report is IMMUTABLE.

The owner proposed relabelling cerbix a **Reliability Control Plane** and asked for a critical review rather
than acceptance. The review was done against the code first; one part of the proposal was refused.

## 1. What the code supports, and where the proposal over-reached

Verified, not recalled: versioned reliability definitions (immutable declaration revisions + evaluation
epochs), SLI membership held separately from context members, region-aware and quorum aggregation,
GOOD/BAD/UNKNOWN with reasons, one duration-weighted timeline per Service, service SLO / error budget / burn
rate quoted against a seal watermark with two independent coverage axes (`ServiceWindowReport` carries
`objective`, `budget`, `burn` beside `status`, `reason`, `coverage`, `segments`), incidents on either anchor,
dependency-impact candidates, status pages, on-call ladders, and a reconciler driving all of it from files.
There is also a real control/data-plane split by role: `api`/`scheduler` hold desired state, `worker`/`agent`
execute probes.

**Where "control plane" over-reaches, in three specific ways.** It implies ACTUATION on the user's
infrastructure — deploys, traffic, rollbacks — of which cerbix performs none. It implies sitting IN the request
path, and cerbix is strictly out of band. And it implies authority over all reliability signal, when cerbix
knows only what its own checks observe plus what it pulls through PromQL.

So the term was neither adopted as the primary noun nor banned: the README carries it as a bounded CONCEPT —
a control plane for reliability *definitions* and *operational response* — and the SRE-facing phrase is
**system of record for service reliability**, which claims the definition and the facts without promising
execution.

## 2. What the differentiator actually is

Not monitoring (table stakes), not SLO arithmetic (Nobl9, Pyrra, Sloth, Grafana SLO all do it), not
multi-tenancy alone. The pair that nothing else in this space puts together:

1. **the definition of reliability as a versioned artefact** — you can answer "under which definition was this
   month measured, and what changed on the 14th";
2. **the refusal to state a number it cannot defend** — UNKNOWN as a first-class state with a reason, withheld
   aggregates instead of a confident 100%, two coverage axes, sealed facts, and a window that never ends at
   `now`.

…and the fact that the SAME object drives the response: the service whose budget was computed is the service
that pages, opens the incident and renders the status page.

## 3. "Define what reliable means." — accepted, with a second clause

The line is honest, and unusually so: the code literally versions that definition. It was accepted as the
headline with a second clause added, because on its own it is a philosophy rather than a product —
**"Define what reliable means for a service — then measure it and run the response."**

The README now also states the NON-GOALS publicly, quoted from `func-service-reliability.md` §3 rather than
softened, and adds a "Where it fits" table that says plainly what cerbix does not replace.

## 4. A stale API description, which is a capability claim rather than a wording choice

`ServiceDetail.reliability` said SLO, error budget and burn rate "are phase 2". Phase 2 shipped in iter-0144
and those numbers live on `GET …/services/{serviceID}/reliability` together with the context they require. The
field is still `null` by design — a bare number on the detail object would carry none of the honesty machinery
— and the description now says THAT instead of implying the feature is unbuilt. TS types regenerated;
frontend type-check clean.

## 6. The release, and a gate that was blind where it mattered

Cutting `v0.1.5-beta.1` (the owner's choice of number; `0.1.1`–`0.1.4` never existed, and semver
ordering is still correct after `v0.1.0-beta.5`) exposed that the version story disagreed with itself:
git carried `v0.1.0-beta.1…5` while `CHANGELOG.md` carried `v0.35.0` and `v0.10.0`, which correspond to
no tag in this repository, and its `[Unreleased]` block described work that had been shipping across all
five betas because nobody ever moved it out.

None of it was deleted. The stale block is RELABELLED as what it is — the whole beta train, with a note
saying the per-beta split is not reconstructed because inventing one after the fact would be a worse
claim than admitting the gap. The two foreign version numbers are kept with a note that they are
historical labels, not releases anybody can check out.

**And the gate was blind in a way worth recording.** `CHANGELOG.md` cited
`backend/internal/prober/guard.go` — a tree layout this repository has never had. Adding the file to the
living set did NOT catch it: `PATH_RE` only matches paths inside BACKTICKS, and this one lived in a
markdown link target. So the gate now checks link targets too (absolute urls and anchors excluded), and
that extension was verified the only way worth trusting — by reintroducing the exact broken path and
watching `docs-check` fail on `CHANGELOG.md:120`. A gate extended without that check is a claim, not a
gate.
