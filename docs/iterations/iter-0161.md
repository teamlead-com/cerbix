# iter-0161 — a production upgrade failed on PostgreSQL 14, and two claims were corrected

> **Lifecycle: OPEN.** No requirement. It closes when the corrections below are discharged.

`iter-0160` is closed and immutable, so findings that arrived after its closing commit go here.

## 1. The failure, and what my testing never covered

An upgrade to `v0.1.5-beta.1` on a production host running **PostgreSQL 14** applied migrations
`00061`…`00069` and died on `00070`:

```
ERROR 00070_owner_fk_and_maintenance_provenance.sql: failed to execute SQL query
  "... ON DELETE SET NULL (escalation_policy_id) ..."
  ERROR: syntax error at or near "(" (SQLSTATE 42601)
```

Five migrations (`00070`, `00080`, `00081`, `00082`, `00084`) use the **column-list**
`ON DELETE SET NULL (col)` form, which arrived in PostgreSQL 15. The plain form cannot substitute: on a
composite FK it nulls EVERY referencing column including the NOT NULL `project_id`, which is the exact bug
`00070` exists to fix.

**Reproduced rather than reasoned about.** A throwaway `postgres:14-alpine` (14.24) with the guard removed
fails exactly as production did, on the same file, with the same SQLSTATE. That is what turned a hypothesis
into a diagnosis, and it also proved the failure is SYNTAX rather than data — no cleanup of the operator's
rows was needed.

**Why nothing caught it.** Every test and both CI matrix legs run PostgreSQL 16, every image and document
says 16, and the test helpers always migrate **from zero on an empty database**. The requirement was real
from the day `00070` landed and was never stated where an operator would see it, never checked by the code,
and never exercised against an older server.

## 2. The guard, and a bug in its own first version

`Migrate` now reads `server_version_num` and refuses a server older than 15, naming the version, the
requirement, the five migrations and the fact that nothing was applied. Verified on 14.24: the refusal
arrives with **zero** tables created, `goose_db_version` included.

The first version of that check sat after `pg_advisory_lock` but before the unlock `defer`, so its early
returns left the session lock held and relied on `db.Close()` tearing the backend down. It now runs BEFORE
the lock is taken: reading a GUC needs no lock, so the question disappears instead of being handled.

`TestMigrateRefusesAServerTooOldForItsOwnSchema` pins it against whatever database it is given — a refusal
naming version, requirement and "Nothing has been applied" on an older server, and no refusal at all on
15+, because a guard that blocks a supported server is worse than none.

## 3. A partial upgrade has one sharp edge, and it is documented now

`00070` is transactional and rolled back, so the database sits consistently at `00069`. But `00065` did
apply, and it sets `monitors.slug` NOT NULL with **no default** — while a pre-`00065` binary does not write
that column. A system left in this state on the OLD binary keeps serving, alerting and recording, and
**cannot create a monitor**. The runbook now carries that fact and the one-line relaxation for operators
who must keep creating monitors before the upgrade completes.

## 4. A stale UI claim, found by an operator's screenshot

The service page footer said availability, the error budget and the burn rate "arrive with the next
iteration" (written 2026-08-16, before phase 2). They arrived in iter-0144 and the page already renders
them from the report. What is actually missing on a fresh service is sealed facts and a declared objective —
which the page says elsewhere, correctly, and now says here too.

This is the third stale-claim defect in three iterations (`openapi.yaml`'s `reliability` field, the README's
positioning, this footer). The pattern is the same every time: a sentence written truthfully at one moment
and never revisited when the moment passed. `docs-check` cannot catch these — they are not broken
citations, they are true-then statements.

## 5. A blank dropdown an operator photographed, and the cast that hid it

Creating a status-page component from a Service showed an EMPTY option in the picker. The invisible half
was worse than the visible one: the option carried **no value** either, so the component could not be
created at all.

One cause for both. `GET …/projects/{id}/services` answers `ServiceSummary` — the service WRAPPED with its
rollup counts — and the view read `sv.name` / `sv.id` directly. What kept the compiler quiet was an
`as Service[]` cast on the load, which is a promise to TypeScript that the shape is something it is not. I
hit the same endpoint in `IncidentsView` two iterations ago and got a clean type error there, precisely
because I wrote no cast.

**The test fixture had the same wrong assumption**, answering the flat shape, which is why six passing
tests never saw it. Fixing the fixture to the real shape and asserting the option's value AND label pins
both halves; reverting the read makes it fail with "the dropdown cannot bind a service".

Three of my own fixture mistakes on the way to that test, all mine and all in the test: the picker only
exists once the ADD form's source is Service, the form itself is gated on `canManage`, and I deleted the
`mockLoads()` call while restructuring so nothing rendered at all. Worth recording because the pattern
repeats: when a UI test cannot find an element, the first suspect is the state the test failed to set up.

## 6. Correction of record — a scope error in my own release note

The `v0.1.5-beta.2` tag message ends with an "STILL OPEN" block naming *"the production decision between
upgrading PostgreSQL and a compatibility branch of those five migrations"*. The owner rejected that, and
correctly: whether one operator's database host gets upgraded is **their infrastructure decision**, not an
open item of the software. A release tag describes the software.

Two things went wrong from one confusion:

1. **The tag** carried one deployment's operational state into an artefact meant to describe a version. The
   product-side fact is complete and needs no caveat: the schema requires PostgreSQL 15+, the requirement is
   enforced before the first migration and documented in three places.
2. **`DoD-0161`** made this iteration's Definition of Done depend on an action nobody here controls. The
   iteration's work — the guard, the documentation, the two UI fixes — was finished. The row is now DONE.

What survives as a legitimate PRODUCT question, recorded as a question rather than as a blocker: should
cerbix support PostgreSQL 14? It would mean emulating the column-list `ON DELETE SET NULL` semantics with
triggers across five migrations and carrying that forever, so it needs its own requirement and a decision,
not a footnote in a DoD row.

The tag itself is left as pushed. Rewriting a published tag to improve its prose would be worse than the
prose: anyone who already fetched it would hold a different `v0.1.5-beta.2` than the remote. The record is
corrected here instead, which is what this file is for.

## 7. Documentation described a race the lock had already removed (issue #40)

`teamlead-com/cerbix#40` asked for migrations to stop running automatically for every role, on the
grounds that unexpected migration execution is undesirable. The capability the author wanted already
exists: `cerbix migrate` is a standalone command, and running it before the roles leaves nothing
pending for their startup call to apply.

The premise came from our own text. `docs/overview.md` §2.2 still said:

> Roles auto-apply migrations at startup, and on the first deploy of a new migration, simultaneously
> starting roles race for it (goose does not take a cross-process lock) — one applies it, the others
> fail with `relation already exists`.

`store.Migrate` has held a session `pg_advisory_lock` for the whole goose run since `ed652d0`
(2026-08-08). The paragraph dates from the initial commit three days earlier and was never revisited,
so for seventeen days the documentation warned operators about a failure mode the code had already
closed. Corrected in `75123c2`: the one-off `migrate` stays recommended, now for the reason that
actually applies (keeping a schema change a deliberate act), and `D-0088` carries a superseding note
rather than being rewritten.

What remains open, and was put back to the reporter rather than assumed: whether the requirement is a
runtime database user with **no DDL rights at all**. That is the one thing the recommended workflow
cannot give, since nothing enforces the operator's discipline. Also worth fixing regardless of the
answer: the migrate call keys off `database.dsn` rather than the role, so a `worker` sharing one config
file runs migrations even though `servicesForRole` gives it no database work at all.

## 8. A partly unmeasured hour rendered green

An operator's screenshot of the Reliability card, 24h window: availability `99.967%`, coverage `100%`,
storage contiguous, and one hourly tick painted solid red. `99.967%` of 86400 seconds is about **28
seconds** of bad time, so the tick claims 3600 seconds where 28 exist.

**That part is not a defect, and my first reading of it was wrong.** §9.1 fixes the display rule and
states its rationale in the spec itself: the rule is *deliberately pessimistic — a one-second outage
colours the whole tick — so the picture never hides an outage, while the number underneath stays
exact.* The screenshot is the design working. Recorded here because I called it a bug before reading
the paragraph that governs it.

Reading that paragraph found the real fault. §9.1 orders the tick
`bad > 0 → BAD; else unknown > 0 → UNKNOWN; else good > 0 → GOOD; else EXCLUDED`, and
`ServiceReliability.vue` evaluated `bad → good → excluded → unknown`. Unknown outranking good is the
half that matters: a step holding both measured-good and unmeasured time rendered **green**, which is
the timeline claiming to have watched an hour it only partly watched. The pessimism the spec spends a
paragraph defending was inverted in exactly the case where it earns its keep.

Why the suite missed it: the one fixture exercising an unknown tick carries unknown time **alone**, so
both orders satisfy it. A rule about precedence cannot be pinned by an input with nothing to precede.
The new regression uses mixed durations per step and asserts the sequence `['unknown', 'bad',
'excluded']` — mostly-good-with-a-sliver-unmeasured, bad-plus-unknown, and excluded-with-no-good.

**Mutation evidence:** restoring the previous order fails the regression with
`expected [ 'good', 'bad', 'excluded' ] to deeply equal [ 'unknown', 'bad', 'excluded' ]` — the green
tick, reproduced on demand.

Left alone deliberately: the whole-tick colouring itself. It is spec text with a written rationale, so
replacing it is an amendment and a product decision, not a fix. Recorded as a question for whoever takes
it up: at hourly granularity the rule overstates a 28-second outage by roughly 126×, and a proportional
fill with a minimum visible sliver would keep "never hide an outage" while dropping the overstatement.
The durations needed for it (`GoodUs`, `BadUs`, `UnknownUs`) already reach the component.

## 9. Resolved was terminal only until two writers overlapped

An external review of `27c63f7` found no P0 and six P1s. This is the first of them discharged, and it
is the one the other two service-incident findings rest on.

`addIncidentUpdate` read the incident, refused if `Status.Terminal()`, and then called
`AddIncidentUpdate`, which wrote `UPDATE incidents SET status = $2 ... WHERE id = $1` with no guard
and no row lock. The read and the write are in different transactions, so the interleaving is
ordinary rather than exotic:

1. request B reads `investigating` and is admitted by the pre-check;
2. request A resolves the incident and commits;
3. B's unguarded write lands, and the incident is `investigating` again.

`resolved_at` stays stamped, because the CASE only fills it on the way IN to resolved. The result is a
row no legal sequence produces: an open incident that claims a resolution time. For a service
auto-incident it is worse than untidy — the row re-enters `incidents_service_open_auto_idx`, whose
whole job is to admit one open auto-incident per service, so the NEXT outage's `ON CONFLICT DO
NOTHING` finds a squatter and opens nothing.

The guard now lives in the write itself: `WHERE id = $1 AND status <> 'resolved' RETURNING`, and it
runs BEFORE the timeline insert so a refusal leaves no trace at all — no update row, no lifecycle
event for a change that did not happen. Zero rows is classified rather than collapsed: the incident is
missing (`ErrNotFound`) or it is terminal (`ErrIncidentTerminal`, new), and the handler answers 404 or
400 instead of 500. The pre-check stays, demoted to what it always was — a fast, friendly answer that
does not hold under concurrency.

**Mutation evidence:** removing `AND status <> 'resolved'` fails the regression with
`write against a resolved incident: <nil>, want ErrIncidentTerminal`.

The regression asserts the whole refusal, not just the error: status still resolved, `resolved_at`
unmoved, timeline count unchanged, `incident_event` count unchanged, and a missing incident answered
`ErrNotFound` rather than the same error as a terminal one.

This is step one of the fix order agreed with the reviewer. The primitive is now the guarded write;
what follows is moving the service auto-open and auto-resolve THROUGH it (which also discharges the
missing `incident_event` on the service path), then reason-aware resolution on the lifecycle closes.
The class those three share was already seen once in this phase, on the outbox topic whitelist: a new
path built BESIDE an existing guarantee instead of THROUGH it.
