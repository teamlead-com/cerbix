# iter-0161 — a production upgrade failed on PostgreSQL 14, and two claims were corrected

> **Lifecycle: OPEN.** No requirement. It closes when the corrections below are discharged.

`iter-0160` is closed and immutable, so findings that arrived after its closing commit go here.

## 1. The failure, and what my testing never covered

An upgrade to `v0.1.5-beta.1` on a production host running **PostgreSQL 14** applied migrations
`00061`…`00069` and died on `00070`:

```
ERROR 00070_owner_fk_and_maintenance_provenance.sql: failed to execute SQL query
  "... ON DELETE SET NULL (escalation_policy_id) ..."
  ERROR: syntax error at or near "(" (SQLSTATE 42601)
```

Five migrations (`00070`, `00080`, `00081`, `00082`, `00084`) use the **column-list**
`ON DELETE SET NULL (col)` form, which arrived in PostgreSQL 15. The plain form cannot substitute: on a
composite FK it nulls EVERY referencing column including the NOT NULL `project_id`, which is the exact bug
`00070` exists to fix.

**Reproduced rather than reasoned about.** A throwaway `postgres:14-alpine` (14.24) with the guard removed
fails exactly as production did, on the same file, with the same SQLSTATE. That is what turned a hypothesis
into a diagnosis, and it also proved the failure is SYNTAX rather than data — no cleanup of the operator's
rows was needed.

**Why nothing caught it.** Every test and both CI matrix legs run PostgreSQL 16, every image and document
says 16, and the test helpers always migrate **from zero on an empty database**. The requirement was real
from the day `00070` landed and was never stated where an operator would see it, never checked by the code,
and never exercised against an older server.

## 2. The guard, and a bug in its own first version

`Migrate` now reads `server_version_num` and refuses a server older than 15, naming the version, the
requirement, the five migrations and the fact that nothing was applied. Verified on 14.24: the refusal
arrives with **zero** tables created, `goose_db_version` included.

The first version of that check sat after `pg_advisory_lock` but before the unlock `defer`, so its early
returns left the session lock held and relied on `db.Close()` tearing the backend down. It now runs BEFORE
the lock is taken: reading a GUC needs no lock, so the question disappears instead of being handled.

`TestMigrateRefusesAServerTooOldForItsOwnSchema` pins it against whatever database it is given — a refusal
naming version, requirement and "Nothing has been applied" on an older server, and no refusal at all on
15+, because a guard that blocks a supported server is worse than none.

## 3. A partial upgrade has one sharp edge, and it is documented now

`00070` is transactional and rolled back, so the database sits consistently at `00069`. But `00065` did
apply, and it sets `monitors.slug` NOT NULL with **no default** — while a pre-`00065` binary does not write
that column. A system left in this state on the OLD binary keeps serving, alerting and recording, and
**cannot create a monitor**. The runbook now carries that fact and the one-line relaxation for operators
who must keep creating monitors before the upgrade completes.

## 4. A stale UI claim, found by an operator's screenshot

The service page footer said availability, the error budget and the burn rate "arrive with the next
iteration" (written 2026-08-16, before phase 2). They arrived in iter-0144 and the page already renders
them from the report. What is actually missing on a fresh service is sealed facts and a declared objective —

This is the third stale-claim defect in three iterations (`openapi.yaml`'s `reliability` field, the README's

and never revisited when the moment passed. `docs-check` cannot catch these — they are not broken
citations, they are true-then statements.

## 5. A blank dropdown an operator photographed, and the cast that hid it

Creating a status-page component from a Service showed an EMPTY option in the picker. The invisible half
was worse than the visible one: the option carried **no value** either, so the component could not be
created at all.

One cause for both. `GET …/projects/{id}/services` answers `ServiceSummary` — the service WRAPPED with its
rollup counts — and the view read `sv.name` / `sv.id` directly. What kept the compiler quiet was an
`as Service[]` cast on the load, which is a promise to TypeScript that the shape is something it is not. I
hit the same endpoint in `IncidentsView` two iterations ago and got a clean type error there, precisely
because I wrote no cast.

**The test fixture had the same wrong assumption**, answering the flat shape, which is why six passing
tests never saw it. Fixing the fixture to the real shape and asserting the option's value AND label pins
both halves; reverting the read makes it fail with "the dropdown cannot bind a service".

Three of my own fixture mistakes on the way to that test, all mine and all in the test: the picker only
exists once the ADD form's source is Service, the form itself is gated on `canManage`, and I deleted the
`mockLoads()` call while restructuring so nothing rendered at all. Worth recording because the pattern
repeats: when a UI test cannot find an element, the first suspect is the state the test failed to set up.

## 6. Correction of record — a scope error in my own release note

The `v0.1.5-beta.2` tag message ends with an "STILL OPEN" block naming *"the production decision between
upgrading PostgreSQL and a compatibility branch of those five migrations"*. The owner rejected that, and
correctly: whether one operator's database host gets upgraded is **their infrastructure decision**, not an
open item of the software. A release tag describes the software.

Two things went wrong from one confusion:

1. **The tag** carried one deployment's operational state into an artefact meant to describe a version. The
   product-side fact is complete and needs no caveat: the schema requires PostgreSQL 15+, the requirement is
   enforced before the first migration and documented in three places.
2. **`DoD-0161`** made this iteration's Definition of Done depend on an action nobody here controls. The
   iteration's work — the guard, the documentation, the two UI fixes — was finished. The row is now DONE.

What survives as a legitimate PRODUCT question, recorded as a question rather than as a blocker: should
cerbix support PostgreSQL 14? It would mean emulating the column-list `ON DELETE SET NULL` semantics with
triggers across five migrations and carrying that forever, so it needs its own requirement and a decision,
not a footnote in a DoD row.

The tag itself is left as pushed. Rewriting a published tag to improve its prose would be worse than the
prose: anyone who already fetched it would hold a different `v0.1.5-beta.2` than the remote. The record is
corrected here instead, which is what this file is for.

## 7. Documentation described a race the lock had already removed (issue #40)

`teamlead-com/cerbix#40` asked for migrations to stop running automatically for every role, on the
grounds that unexpected migration execution is undesirable. The capability the author wanted already
exists: `cerbix migrate` is a standalone command, and running it before the roles leaves nothing
pending for their startup call to apply.

The premise came from our own text. `docs/overview.md` §2.2 still said:

> Roles auto-apply migrations at startup, and on the first deploy of a new migration, simultaneously
> starting roles race for it (goose does not take a cross-process lock) — one applies it, the others
> fail with `relation already exists`.

`store.Migrate` has held a session `pg_advisory_lock` for the whole goose run since `ed652d0`
(2026-08-08). The paragraph dates from the initial commit three days earlier and was never revisited,
so for seventeen days the documentation warned operators about a failure mode the code had already
closed. Corrected in `75123c2`: the one-off `migrate` stays recommended, now for the reason that
actually applies (keeping a schema change a deliberate act), and `D-0088` carries a superseding note
rather than being rewritten.

What remains open, and was put back to the reporter rather than assumed: whether the requirement is a
runtime database user with **no DDL rights at all**. That is the one thing the recommended workflow
cannot give, since nothing enforces the operator's discipline. Also worth fixing regardless of the
answer: the migrate call keys off `database.dsn` rather than the role, so a `worker` sharing one config
file runs migrations even though `servicesForRole` gives it no database work at all.

## 8. A partly unmeasured hour rendered green

An operator's screenshot of the Reliability card, 24h window: availability `99.967%`, coverage `100%`,
storage contiguous, and one hourly tick painted solid red. `99.967%` of 86400 seconds is about **28
seconds** of bad time, so the tick claims 3600 seconds where 28 exist.

**That part is not a defect, and my first reading of it was wrong.** §9.1 fixes the display rule and
states its rationale in the spec itself: the rule is *deliberately pessimistic — a one-second outage
colours the whole tick — so the picture never hides an outage, while the number underneath stays
exact.* The screenshot is the design working. Recorded here because I called it a bug before reading
the paragraph that governs it.

Reading that paragraph found the real fault. §9.1 orders the tick
`bad > 0 → BAD; else unknown > 0 → UNKNOWN; else good > 0 → GOOD; else EXCLUDED`, and
`ServiceReliability.vue` evaluated `bad → good → excluded → unknown`. Unknown outranking good is the
half that matters: a step holding both measured-good and unmeasured time rendered **green**, which is
the timeline claiming to have watched an hour it only partly watched. The pessimism the spec spends a
paragraph defending was inverted in exactly the case where it earns its keep.

Why the suite missed it: the one fixture exercising an unknown tick carries unknown time **alone**, so
both orders satisfy it. A rule about precedence cannot be pinned by an input with nothing to precede.
The new regression uses mixed durations per step and asserts the sequence `['unknown', 'bad',
'excluded']` — mostly-good-with-a-sliver-unmeasured, bad-plus-unknown, and excluded-with-no-good.

**Mutation evidence:** restoring the previous order fails the regression with
`expected [ 'good', 'bad', 'excluded' ] to deeply equal [ 'unknown', 'bad', 'excluded' ]` — the green
tick, reproduced on demand.

Left alone deliberately: the whole-tick colouring itself. It is spec text with a written rationale, so
replacing it is an amendment and a product decision, not a fix. Recorded as a question for whoever takes
it up: at hourly granularity the rule overstates a 28-second outage by roughly 126×, and a proportional
fill with a minimum visible sliver would keep "never hide an outage" while dropping the overstatement.
The durations needed for it (`GoodUs`, `BadUs`, `UnknownUs`) already reach the component.

## 9. Resolved was terminal only until two writers overlapped

An external review of `27c63f7` found no P0 and six P1s. This is the first of them discharged, and it
is the one the other two service-incident findings rest on.

`addIncidentUpdate` read the incident, refused if `Status.Terminal()`, and then called
`AddIncidentUpdate`, which wrote `UPDATE incidents SET status = $2 ... WHERE id = $1` with no guard
and no row lock. The read and the write are in different transactions, so the interleaving is
ordinary rather than exotic:

1. request B reads `investigating` and is admitted by the pre-check;
2. request A resolves the incident and commits;
3. B's unguarded write lands, and the incident is `investigating` again.

`resolved_at` stays stamped, because the CASE only fills it on the way IN to resolved. The result is a
row no legal sequence produces: an open incident that claims a resolution time. For a service
auto-incident it is worse than untidy — the row re-enters `incidents_service_open_auto_idx`, whose
whole job is to admit one open auto-incident per service, so the NEXT outage's `ON CONFLICT DO
NOTHING` finds a squatter and opens nothing.

The guard now lives in the write itself: `WHERE id = $1 AND status <> 'resolved' RETURNING`, and it
runs BEFORE the timeline insert so a refusal leaves no trace at all — no update row, no lifecycle
event for a change that did not happen. Zero rows is classified rather than collapsed: the incident is
missing (`ErrNotFound`) or it is terminal (`ErrIncidentTerminal`, new), and the handler answers 404 or
400 instead of 500. The pre-check stays, demoted to what it always was — a fast, friendly answer that
does not hold under concurrency.

**Mutation evidence:** removing `AND status <> 'resolved'` fails the regression with
`write against a resolved incident: <nil>, want ErrIncidentTerminal`.

The regression asserts the whole refusal, not just the error: status still resolved, `resolved_at`
unmoved, timeline count unchanged, `incident_event` count unchanged, and a missing incident answered
`ErrNotFound` rather than the same error as a terminal one.

This is step one of the fix order agreed with the reviewer. The primitive is now the guarded write;
what follows is moving the service auto-open and auto-resolve THROUGH it (which also discharges the
missing `incident_event` on the service path), then reason-aware resolution on the lifecycle closes.
The class those three share was already seen once in this phase, on the outbox topic whitelist: a new
path built BESIDE an existing guarantee instead of THROUGH it.

## 10. The service incident announced itself to nobody

Second of the review's P1s, and the one the first step made cheap.

`incident_event` is the topic that reaches incident webhooks and the confirmed subscribers of every
status page surfacing the project (D-0041, `decisions.md:986`). `OpenServiceIncidentTx` enqueued its
correlation attempt and nothing else; `ResolveServiceIncidentTx` enqueued nothing at all. So a service
outage was visible in the database and in the UI while the people who explicitly asked to be told
heard nothing, in either direction.

The framing that makes it a defect rather than a design choice: it is not manual-versus-automatic.
Monitor auto-incidents are opened by the reconciler through `CreateIncident`
(`ingest/reconciler.go:102` → `incidents.go:117`), which has always enqueued the event. Two AUTOMATIC
paths therefore disagreed about whether an outage is announceable, and which one you got depended on
whether the outage was expressed as a monitor incident or a service incident. The service's own
`service_alert` does not cover the gap: it pages the service's RECIPIENTS, a different audience from a
status page's subscribers.

Both halves now enqueue in the transaction that carries the fact. Two details are load-bearing:

- the opening enqueue sits AFTER the `ON CONFLICT DO NOTHING` branch, so an evaluator that loses the
  open race returns `created == false` and announces nothing. One opening, one announcement;
- the resolve's `UPDATE ... RETURNING` now hands back the whole row and the timeline insert returns
  its own, so the closing payload describes the incident as it IS and carries the update it wrote,
  matching the shape `AddIncidentUpdate` publishes. A second read would have been a second opinion.

**Mutation evidence**, one per half: dropping the open enqueue fails with `after the open, events = [];
want exactly one incident.opened for <id>`; dropping the resolve enqueue fails with `after the resolve,
1 events, want 2`. The regression also pins the two silences that must stay silent — a losing racer and
a no-op second resolve each announce nothing.

## 11. The live occurrence ended in halves, and the incident was the half left behind

Third of the review's P1s, and the largest: it is the one that leaves an operator somewhere they
cannot leave without SQL.

Every lifecycle path that ends a live announcement — ownership switched off, a `page_on` edit that no
longer covers the announced state, the same two through a MaC apply, and deleting the service — closed
the health EPISODE and stopped there. The auto-incident stayed open, and the only thing that resolves
one is `ResolveServiceIncidentTx`, whose single caller was the evaluator's recovery path
(`servicealerteval.go:234`). The evaluator's slice is `WHERE s.owns_paging`, so after ownership is
switched off the service is never looked at again: the incident could not be resolved by ANY code
path, not merely "not until it recovers".

Two consequences, both verified rather than reasoned about:

- delete the service mid-outage and the incident survives with `service_id` nulled by 00084's
  `ON DELETE SET NULL (service_id)`, an open project incident about a service that no longer exists;
- disown a service mid-outage and re-own it later, and the survivor still occupies
  `incidents_service_open_auto_idx` — so the NEXT outage's `ON CONFLICT DO NOTHING` opens nothing and
  the second failure has no incident at all.

The resolution now lives inside `closeServiceEpisodesTx`, the one function all five call sites already
go through, and fires when the close actually ended a HEALTH episode. Putting it there rather than at
the call sites is the whole point: a lifecycle path added later inherits the ending instead of
re-earning it, which is the property this phase has now failed to have three times. BURN closes never
touch the incident — `burn_disabled` and `rule_removed` say nothing about whether the service is down.

The timeline entry names the reason and denies the recovery in words, because `resolved` on a status
page is otherwise read as "it is fine now": *paging ownership was turned off for this service, so
nothing evaluates it any more. This is not a statement that the service recovered.* The ending is
announced through §10's event, so subscribers learn it ended.

**Mutation evidence, both directions of the rule.** Removing the resolution fails with `incident is
"investigating"/resolved_at=<nil> after disowning`. Making EVERY close resolve fails with `incident is
"resolved" after a BURN close; a budget alert is not the outage record`.

**A test defect found by that second mutation, and worth recording as itself.** The burn regression
passed the mutation on its first writing — because the fixture had no open burn episode, so the close
loop never ran and the assertion held for the wrong reason. It is the same vacuity §8 found in the
unknown-tick fixture: a rule about *which* case is excluded cannot be pinned by an input that never
reaches the case. The fixture now opens a real burn episode with its latch and asserts one was closed
before checking what survived.

## 12. The postmortem could name a declaration that had not started governing

Fourth of the review's P1s. `snapshotServiceMembersTx` resolved the declaration itself, with
`state = 'effective' ORDER BY effective_at DESC LIMIT 1` — and no time bound, while the nine other
sites that ask this question all carry `effective_at <= now()`.

The reason those nine carry it: `service_definition_revisions.state` defaults to `'effective'` at
INSERT (00064), so a revision is 'effective' from the moment it is authored and its `effective_at`
sits on the coming bucket boundary. The reviewer framed this as scheduled future revisions, which
understates it — every ORDINARY edit opens the window. An edit at 12:00:30 leaves until 12:01 in which
"the latest effective revision" and "the revision governing now" are different rows, and an incident
opened in that gap took its members from a declaration that was governing nothing, while the outage
that opened it had been computed from the previous one.

The evaluator already resolves the governing revision for the verdict itself (`servicealerteval.go:99`,
`effective_at <= $2` against the snapshot instant). That exact id is now passed down through
`OpenServiceIncidentTx`, and the snapshot resolves nothing on its own. A NULL revision snapshots
NOTHING rather than reaching for the newest one: no declaration governs, so there is no membership to
name, and the fallback would be the same defect one level down.

**Mutation evidence:** restoring the local unbounded resolution fails with `the snapshot named
[checkout-dns] — it took a declaration that governs only from the next boundary`. The fixture asserts
the future revision really is `state = 'effective'` before relying on it, so the test cannot quietly
stop exercising the window it was written for.

## 13. The ladder an incident climbs is now the one it started with

Fifth of the review's P1s, and the only one that needed a schema change.

`AdvanceEscalations` joined `services.escalation_policy_id` LIVE and timed every step from
`incidents.started_at`. Attach a policy to a service whose incident has been open for two hours and
the next pass finds every delay already elapsed, so the whole ladder pages at once — for an outage
nobody had asked it to page for. `func-service-escalation.md` §8 lists exactly that as a NON-GOAL, so
the code was contradicting the spec rather than filling a gap in it.

**Pinning the policy id would not have been enough**, and this is the part the review's plan did not
cover: `escalation_policies` keeps its ladder in a `steps` jsonb column and carries no version. An
in-place edit therefore moves the ladder under every open incident that names it — the same defect
reached by a third route, and the one an operator is least likely to expect. So 00085 snapshots the
STEPS: `incident_escalation_snapshots`, one row per incident, with the policy id kept for the record
and deliberately not a foreign key, exactly as the member snapshot outlives its declaration.

Three behaviours result, and only the middle one is new in kind:

- **attach after the fact** — no snapshot exists, the incident is not selected, nothing pages. The
  non-goal is now enforced by a join rather than by prose;
- **edit or replace the policy mid-incident** — the incident climbs the ladder it froze;
- **detach the policy entirely** — escalation STOPS. The snapshot freezes what the steps ARE; it does
  not make a ladder unstoppable, and detaching is an operator saying "stop paging through this".

That third rule is not a decision I made: an existing regression
(`TestAServiceLadderIgnoresAHumansIncidentAndAPolicylessService`) failed when my first version dropped
the live attachment check, which is the suite doing its job. The live `escalation_policy_id IS NOT
NULL` is back alongside the snapshot join.

`CreateIncident` takes the same snapshot when an incident arrives with a service anchor. No production
caller does that today — the evaluator uses `OpenServiceIncidentTx` — but an incident that reached the
table through the other door would silently never escalate, and "the other door forgot" is the shape
of three defects already fixed in this iteration.

**Mutation evidence, one per half.** Reading the live policy instead of the snapshot fails with `the
open incident paged the REWRITTEN ladder's target; it must climb the one it froze at open`. Making the
snapshot join a LEFT JOIN fails the retroactive-attach regression.

## 14. The successor picker read the wrong object, and a cast is why

Last of the review's P1s, and the cheapest — but the interesting part is how it survived.

`GET /projects/{projectID}/services` answers with SUMMARIES: the service nested under `service`,
beside the revision and coverage fields a picker has no use for. `MonitorDetailView` asserted the
response was `Service[]` and read `sv.id` / `sv.name` off the row, where both are undefined. The
dropdown rendered a list of blank options and would have posted `undefined` as the successor id, and
the "current successor" label beside it was empty for the same reason.

The frontend uses `openapi-fetch` with the generated `paths`, so `res.data` was ALREADY typed
correctly. The only thing standing between this defect and a build failure was the cast:

```ts
services.value = (res.data as components["schemas"]["Service"][] | undefined) ?? [];
```

That makes the fix a class fix rather than a line fix, which matters because this same defect was
repaired once already in this iteration's §5 for the status-page picker. Mapping instead of asserting
puts `vue-tsc` back in charge of a shape the SPA does not own. A sweep found exactly one other cast of
this family on the same screen — `(res.data as { monitor: Monitor }).monitor` — and removing it
immediately produced a real type error: `monitor` is OPTIONAL in `CompositeConversion`, so the cast had
been asserting a guarantee the API does not give. It is a checked access now.

The regression pins the API's real shape in the fixture, not a convenient one: a `ServiceSummary` row
with `service`, `revision`, `context_members`, `sli_members`, `epoch_seq` and `repairing_count`. A
fixture shaped like a bare `Service` would let the defect return invisibly.

**Mutation evidence:** restoring the cast fails with `expected undefined to be 'svc1'` — the blank
option, reproduced.

## 16. The snapshot table shipped without an upgrade path, and without a tenant

An adversarial review of §9–§15 found six P1s. These three are mine, in code committed hours earlier,
and all three were confirmed independently before being fixed.

**The migration had no backfill.** 00085 created `incident_escalation_snapshots` empty while the
selection that reads it INNER JOINs it, so every service auto-incident already open at upgrade time
loses its ladder — permanently, silently, with the service still owning paging and its policy still
attached. An upgrade performed DURING an outage is exactly when that lands. The backfill now runs in
the migration itself, so the table is never observable in the empty-but-required state: after that
transaction, "every open service incident that can escalate has a snapshot" holds for old rows and new
ones alike.

**The table had two independent foreign keys where it needed one composite.** `incident_id →
incidents(id)` and `project_id → projects(id)` written separately make each column individually valid
while the PAIR is not, so direct SQL attaches project B's ladder to project A's incident. The row that
decides who gets paged is the wrong one to leave un-tenanted, and the `(id, project_id)` key this now
points at has existed since 00080 for exactly this purpose.

**§12's fix weakened the member snapshot.** Passing the revision id down (right) also made the query's
only predicate a value from outside (wrong): it filtered on `revision_id` alone and no longer checked
the service and project it was handed. Today's single caller passes correct values, which is an
argument for checking them rather than against. The revision is now joined and scoped.

**A test defect of my own, again caught by a mutation.** The first upgrade regression re-typed 00085's
backfill statement and ran that — so it would have passed unchanged after somebody deleted the
original. It now migrates a throwaway database to 84, opens a service incident there the way a running
installation would have one, migrates to head and requires the snapshot. That is the third time in
this iteration a mutation has exposed a test that passed for the wrong reason (§8's unknown tick,
§11's burn fixture, this one), and the common shape is a fixture that never reaches the case it
claims to cover.

**Mutation evidence.** Deleting the backfill from the migration fails with `the incident carried
across the upgrade has no ladder snapshot, so it will never escalate again: sql: no rows in result
set`. Splitting the composite key back into two fails with `an incident of one project accepted
another project's escalation snapshot`. The second mutation had to be redone: the first attempt left a
dangling comment and died on a SQL syntax error, which is not evidence about behaviour.

## 17. The backfill's mirror image, caught before it shipped

The review's first response to §16 was that a naive backfill trades one upgrade defect for its
opposite, and it was right. Recorded here because the fix arrived within the hour and the reasoning is
the interesting part.

Steps are fired for every offset that has ALREADY elapsed, all of them in one pass
(`escalation.go`'s `for step < len(p.Steps)`), and the offsets were measured from `incidents.started_at`.
So a snapshot backfilled onto a two-hour-old incident would empty its whole ladder into the on-call
rotation on the first pass after the upgrade — the same retroactive paging §13 had just made
impossible for new incidents, reintroduced through the migration.

It cannot be narrowed by looking at the data. WHEN a policy was attached to a service is recorded
nowhere, so an incident that opened with no policy at all is indistinguishable from one that had this
policy from the first second. Any rule that tries to page for the elapsed time is guessing.

The snapshot therefore carries `due_base`, the instant its offsets are measured from: the incident's
own `started_at` for a row written at open time, which is the behaviour the ladder has always had, and
the MIGRATION's instant for a backfilled row. A carried-over ladder starts at the upgrade — its first
step fires on the next pass, its later steps wait their real delays. Monitor incidents set `due_base`
to their start explicitly, so the arm FR-023 promised not to touch keeps measuring exactly where it
did.

**That is an EXCEPTION, and the first draft of this section wrongly called it "the same direction §13
chose".** It is not the same rule: a native attach-after-open never escalates that incident at all,
while a carried-over one does, prospectively. The two are justified differently — §13 refuses because
the operator's intent is knowable and was "not for this incident"; this refuses only for the ELAPSED
time, because intent is unknowable, and prefers continuity to silence for the time that follows. It
applies to exactly one population, the rows the backfill wrote, and cannot recur. Recorded as
**D-0175** rather than left as a sentence in a report.

**Mutation evidence, both statements of the rule.** Making the backfill copy `i.started_at` fails the
column assertion; making the ladder measure from `startedAt` again fails the behavioural one with `the
first pass after the upgrade fired 3 steps, want exactly its first` — the burst itself, reproduced.

## 18. Three follow-ups the review found in the follow-ups

**The upgrade test migrated to HEAD while claiming to be about 00085.** `goose.UpContext` applies

**The scoped member read answered "nothing" when it meant "not yours".** §16 fixed the missing tenant

not a refusal: a postmortem reads it as "the declaration named nobody". Ownership is now established in

ownership failure rather than merely erroring.

**The `due_base` rule is an EXCEPTION and is now recorded as one (D-0175).** The review accepted the

chose", and it is not the same rule. A native attach-after-open never escalates that incident; a
carried-over one escalates prospectively. Both refuse to page for elapsed time, but §13 refuses because
intent is knowable and was "not this incident", while D-0175 refuses because intent is UNKNOWABLE and

## 19. Forward-flowing was written down and enforced at one step only

`docs/decisions.md`'s incident section says the lifecycle is forward-flowing toward Resolved. The
store enforced the LAST step of that — §9 made `resolved` terminal against concurrent writers — and
nothing anywhere enforced the rest. `monitoring → identified` and `identified → investigating` were
accepted through the ordinary API, sequentially, no race required. The public timeline would then read
as though the operators had un-diagnosed the outage.

The race made it worse rather than causing it, and it had its own mechanism. `addIncidentUpdate`
filled an omitted status from the incident it had read a moment earlier — `body.Status =
string(inc.Status)`, in a different transaction — so a plain comment published an opinion about the
lifecycle that was true when the screen loaded. Landing after somebody else's transition, it reverted
it silently. The SPA did the same thing one layer up (`composer.status || incident.value?.status`),
and `openapi.yaml` has said `Omit to keep the current status (a plain comment)` the whole time: the
contract was right and both implementations were materializing around it.

Three rules now, and their ORDER is the invariant:

1. **Lock first.** The incident row is taken `FOR UPDATE` before anything is decided. Every rule below
   is about the row's current status, and a rule evaluated against a value read outside the lock is a
   rule about the past.
2. **Then read the clock.** `now()` is the transaction's START, so a writer that waited on the lock
   stamps its timeline entry with a moment before the update it is following, and
   `ListIncidentUpdates` orders by `created_at` — the record would claim a sequence the database never
   had. One `statement_timestamp()`, in its own statement after the lock, is threaded through the
   incident, the timeline row and the outbox event.
3. **Then write**, with the monotonicity rule applied to the locked row: forward or staying put is
   legal, backward is `ErrStatusRegression` (400). An empty status means "whatever this lands on" and
   is resolved HERE, never by the caller.

`IncidentStatus.CanFollow` owns the ordering in the domain, where the lifecycle is described. The SPA
sends no status for a plain comment.

**Mutation evidence, one per rule.** Allowing backward ranks fails with `monitoring → identified:
<nil>, want ErrStatusRegression`. Resolving an empty status to a constant instead of the locked row
fails the comment regression. Swapping `statement_timestamp()` for `now()` fails the waiter regression
with `the timeline entry is stamped …, before the lock was released at …`. The SPA echoing its loaded
status again fails with `expected { status: 'identified', … } to deeply equal { body: 'adding a
note' }`.

The waiter regression holds the INCIDENT row, not the service row — a distinction the review insisted
on, and correctly: `statement_timestamp()` is the start of the current statement, not a clock that
knows about waiting, so the instant is only post-linearization if every participating lock is already
held when it is read.

**Not fixed here, and named rather than left implied:** delivery ORDER. One instant fixes what the
records say; it does not make the outbox hand `incident.opened` to a worker before `incident.resolved`.
`ClaimDueOutbox` returns `UPDATE … RETURNING` with no `ORDER BY`, and `incident_event` carries no
per-incident sequence the way `service_alert` does. That is a real gap, it predates this arc, and §10's
claim about a paired lifecycle should be read as "both events are enqueued in the transaction that
causes them", never as "they are delivered in that order".

## 20. Finishing §19, including the parts its own tests could not see

The review read §19 while it was being written and named five things it did not cover. All five were
right, and two of them are about the tests rather than the code — which is the more useful half.

**The waiting-writer regression slept instead of waiting.** `time.Sleep(600ms)` proves nothing about
whether the goroutine has begun its transaction: under load it can reach the lock after the release,
and then a `now()` mutant passes because there was no wait to be early about. The package already had
`waitForLockWait`, a `pg_stat_activity` barrier, and the test uses it now — the release instant is read
only once a backend is genuinely blocked.

**The plain-comment regression could not kill the handler's materialization**, because it called the
store directly with an empty status. The defect lived in the handler, so the regression has to go
through it: `internal/api` now posts a body with no status and asserts the handler passed the intent
down untouched. Its mutation — restoring `body.Status = string(inc.Status)` — fails with `the handler
passed status "identified" for a comment that carried none`.

**The refusal was asserted by its outcome only.** A backward transition now also has to leave no trace:
the timeline count and the `incident_event` count are checked after each refused regression, not just
the final status.

**The event was still scheduled on the transaction's clock.** `outbox_events` defaults
`created_at`/`next_attempt_at` to `now()`, and `next_attempt_at` is what the claim orders by — so an
event caused by a later action could come due before the one it followed. `enqueueOutboxAtTx` states
the instant instead, and only the callers that own a post-lock one use it: changing the default would
re-time paths that never take a row lock. This does NOT fix delivery order (§19), it removes a
knowingly inverted schedule.

**`AcknowledgeIncident` had the identical defect one function over.** A single UPDATE looks atomic and
is, but its `now()` is fixed when its transaction began, so an acknowledgement queued behind a timeline
update stamped the incident's `updated_at` before the update it waited for — walking the row's own
modification time backwards. Same contract now: lock, post-lock clock, guarded write, with its own
waiter regression.

**And one new defect, found by the review in the same area.** `CreateIncident` accepts an initial
status of `resolved` — the API and the new-incident form both offer the whole list, so recording a past
outage is a supported act — and did not stamp `resolved_at`. Such an incident falls out of BOTH
status-page lists at once: the active one filters `status <> 'resolved'`, the recent one `resolved_at IS
NOT NULL`. The operator writes it down and it appears nowhere. It is stamped at creation now, and an
open incident still carries no stamp, because the stamp means "reached Resolved" rather than "was
written".

**The UI stopped offering steps the server refuses.** Both screens listed the whole ladder, so from
`monitoring` an operator could press `investigating` and get a 400 — or, in the list view, silence,
since `setStatus` swallowed the error. One shared `forwardStatuses` helper now returns the current
status and the ones after it; resolving stays its own action with its own confirmation.

**Mutations:** the handler materialization (above); `now()` for the acknowledgement's clock; offering
the whole ladder again fails the picker regression.

## 21. A service opened incidents nobody could be told about

Found by the review, outside the commits it was reviewing and inside the FR-022 behaviour they rest
on. FR-022 invariant 5 reads "opens an incident ONLY on a live onset, only while that signal's
coverage is ARMED", and the evaluator checked exactly one of arming's five conditions —
`owns_paging`, which the slice already filters on. Two of the others can be false at the moment a
service decides to speak:

- **no route.** Ownership on, a pageable DOWN, no enabled channel and no populated schedule: the
  announcement reaches nobody, `activeLiveDelegationSQL` says DIS-ARMED through its routable clause,
  and the members are correctly paging for themselves. On top of that the service opened an incident
  — the thing FR-022's own test comment calls worse than opening none;
- **no governing declaration.** Before the first revision takes effect, `revision_id` is NULL, the
  verdict was computed from nothing, and delegation is dis-armed for the same reason.

**The latch made it permanent, and that is the worse half.** Emitting nothing while advancing
`live_firing` and `emitted_state` leaves the service looking announced, so restoring the channel
produces no edge and the outage is never paged at all. The silence outlives its cause.

Onsets are now withheld unless a route resolves and a declaration governs, and a withheld onset does
NOT latch: the next pass sees the same candidate, the same streak, and announces the moment it may.
CLOSES are never withheld — §16's polarity rule — because an announcement already made must be able
to end whatever the route looks like now. Withheld onsets are counted separately as `Unroutable`,
since silence that means "nobody could be told" must not read as "nothing was wrong".

The existing invariant-5 regression only toggled `owns_paging`, which is why four conditions went
unexercised. Two behavioural tests now cover the route and the declaration, and the route one carries
the recovery: take the channel away, watch nothing be announced, give it back, and the SAME outage
opens its incident.

**Mutation evidence.** Dropping the routability gate fails with `an UNROUTABLE service announced
{… Onsets:1 … IncidentsOpened:1 …}`. Withholding the announcement while still latching fails with
`the service latched (firing=true emitted=<nil>) while announcing nothing`.

## 22. Routability was decided by counting array entries

A P0, found by the review while checking §21's route gate, and the sharpest defect in the arc: both
paths could go silent at once.

`oncall_schedules.participants` is a JSON array of CHANNEL IDS
(`api/tenant_scope.go`), and nothing prunes it. `DeleteNotificationChannel` removes the channel row
and leaves its id in every schedule that named it; disabling a channel changes no JSON at all. Two
places then read that array without looking inside it:

- `routablePredicate` armed a service when `jsonb_array_length(participants) > 0`, so the member's own
  alert was SUPPRESSED on the strength of a rotation naming a channel that no longer exists;
- `resolveServiceRecipientsTx` returned `sc.OnCall(at)` unchecked, so the service's own page went to
  that same dead id.

The member is silenced because the service covers it; the service's page reaches nobody. §16.1 exists
to prevent exactly this, and §16.6 already says what should happen instead — "a deleted or empty
target falls back to the project's channels" — a disabled one being the same fact wearing a different
hat.

Both now require the channel to EXIST, be ENABLED and belong to the same project, and the predicate is
deliberately no more permissive than the resolver: it asks for a live participant, the resolver falls
back to project channels, so anything armed has somewhere to land. The channel id is compared as TEXT
rather than cast to `uuid`, because a participant that is not a uuid must resolve to nothing rather
than error the slice — one malformed entry would otherwise stop evaluation for every service in it.

**Four fixtures across three files were inventing participants** (`"ch-first"`, `"ch-live"`,
`{"kind":"email",...}`), which the old predicate accepted because it never looked. One of them,
`TestUnroutableServiceDisarmsBothSignals`, "restored the route" with a participant that resolves to
nobody — it passed only because arming counted entries. They now create real channels. This is the
fourth fixture-shaped finding in this arc, and the pattern is identical each time: a test that never
reaches the case it claims to cover.

**Mutation evidence.** Arming on `jsonb_array_length > 0` again fails with `a schedule whose only
target is DISABLED still armed live coverage`. Returning the rotation's channel unchecked fails with
`the resolver returned [<id>] for a schedule pointing at a disabled channel`.

## 23. The withheld onset, decided rather than assumed

§21 changed a documented behaviour without saying so, and the review caught it. §16.6 said an alert
with no resolvable recipient "is recorded and counted with `cerbix_service_alert_undeliverable_total`
rather than silently dropped"; §21 withholds it entirely. Both cannot be the contract.

The owner chose WITHHOLD, and **D-0176** records why rather than leaving it as a diff. The short
version: recording is not free, because it has to LATCH. A latched announcement nobody received is an
announcement that can never happen — restoring the route produces no edge, while delegation arms and
silences the member who had been paging correctly all along. The rejected alternative (record without
latching or opening an incident) satisfies both documents and writes an undeliverable episode plus an
outbox row on every pass, a few seconds apart, for as long as the route stays broken.

Three things followed from the decision, and the first two were the review's:

- **the counter is real now.** `ServiceAlertEvaluation.Unroutable` was returned and read by nobody, so
  §21's line about keeping silences distinguishable was a claim about observability that did not
  exist. It is wired through the scheduler pass as
  `cerbix_service_alert_evaluations_total{outcome="withheld"}` — a new VALUE on an existing bounded
  label, beside `ok`/`error`/`skipped`, so no new series family appears. `skipped` keeps its meaning:
  the burn arm's HOLDs are verdicts that cannot be QUOTED, which is a different fact from cannot be
  DELIVERED;
- **the burn arm withholds too.** §21 fixed the live signal only, and leaving the sealed one alone
  would have kept exactly the same swallow in the second signal, with a sharper edge: after the route
  returns, `activeBurnDelegationSQL` arms and suppresses the member's own burn alert while the
  service's onset was already spent on an empty route;
- **§16.6 carries a superseding note** naming D-0176, and the runbook documents what a non-zero
  `withheld` rate means — somebody's paging configuration is broken, not that the service is fine.

**Mutation evidence:** removing the burn gate fails with `an unroutable burn FIRE announced
{… Onsets:1 … Withheld:0}`.

Also approved by the owner in the same round: **D-0175**'s legacy escalation semantics, and building
the outbox ordering fence now rather than deferring it (§24).

## 24. The ordering fence, built rather than deferred

The review would not accept narrowing §19's claim about the paired lifecycle, and was right not to:
a subscriber really can be told an incident resolved and then, from a retried older row, that it
opened. The owner chose to build the fence now. **D-0177** records it.

Two independent causes. Within one claim, `UPDATE … RETURNING` has no defined row order — the
`ORDER BY` in its sub-select picks which rows are claimed, not the order they come back — so a batch
holding an opening and its resolution could hand them over either way round. Across claims and
workers there is no order at all: a retry lands minutes later, beside another worker mid-delivery.

`incidents.event_seq` (00086) is advanced by every path that enqueues a lifecycle event, in the
transaction that writes the fact, and stamped into the payload; delivery drops a superseded ONSET and
never a RESOLUTION, exactly as §16.5's gate never drops a close. A payload without a sequence predates
the fence and is delivered rather than guessed about. `ClaimDueOutbox` sorts its batch by
(`next_attempt_at`, `created_at`, `id`), which handles the in-batch half.

What it does not claim is stated in the decision rather than left to a reader: the gate makes a wrong
order unobservable by dropping the stale half of the pair; it does not serialize two workers. That is
the same guarantee `service_alert` has carried since §16.5, and it is enough for the failure that
motivated it.

**Mutation evidence:** removing the gate delivers the superseded opening; letting it apply to
resolutions drops an ending.

## 25. Coverage follows the state, the onset, and a route that is really a route

Three findings closed together, because they are one question asked at three depths: what does it
take before a service may silence its members?

**The policy must cover the state the service is IN.** `activeLiveDelegationSQL` asked whether the
policy pages SOMETHING — `cardinality(page_on) > 0 OR page_on_unknown` — while §16.1 asks whether it
can page the CURRENT state. A service at DEGRADED with `page_on = {down}` announces nothing and
suppressed its member's DOWN anyway. Both clauses are now separate and both are required: "pages
nothing" and "does not page THIS" have different fixes and now have different reasons.

**The announcement must be COMMITTED, not merely possible.** This one my own §21 created. A withheld
onset leaves a service pageable-in-principle and silent in fact, so restoring the route armed coverage
in the instant before the next evaluation announced anything: the member fell silent first and the
service spoke second. Coverage for a pageable state now requires `live_firing` with `emitted_state`
equal to what is observed; `healthy`/`excluded` need neither, since there is nothing to replace.

**A participant must be a channel.** §22 fixed the read side; the write side still accepted anything.
The check that matters is not the SHAPE but the TENANCY, and only the write path can make it: a
participant must be a notification channel OF THIS PROJECT. At read time the two failures are
indistinguishable — a value naming nothing looks exactly like a channel deleted since — and they have
opposite correct answers, because §16.6 falls back for a deletion while a typo must be fixed by a
person rather than papered over forever. So the evaluator keeps the crude half (`domain.IsChannelID`)
and treats corruption as an evaluation error, which collapses the lease, dis-arms, and puts the reason
where an operator reads it.

**A design correction along the way.** The first version of the write-path rule lived in
`domain.OnCallSchedule.Validate` as a uuid-shape check, and it failed the API tests immediately —
their fake channels are named `nc1`. That was the rule telling me it was in the wrong place: the
domain cannot know what a channel id looks like in a store it has never seen, while the store can
simply ask whether the channel exists. The shape helper survives only where the cheap answer is the
only one available.

**Mutations, one per rule.** Reverting to "pages anything" fails with `a DEGRADED service with
page_on={down} silenced its member`; arming without a committed onset fails with `coverage armed for a
DOWN service that has announced nothing`; dropping the write-path check accepts `ops-team`; letting
the resolver fall back for a corrupt participant fails with `a corrupt participant resolved silently`.

**And a fifth fixture-shaped finding.** The state test first passed its own mutation, because it
cleared the latch along with the state and disarmed through the OTHER clause. It now leaves the latch
committed and matching, so it exercises the clause it names. Five times in one arc, always the same
shape: a fixture that never reaches the case the test claims to cover.

## 26. The same window in the second signal, and two claims that outran the code

**The burn arm armed on a verdict rather than on an announcement.** §25 closed this for the live
signal and I reported it as closed; `activeBurnDelegationSQL` still read `last_verdict IN ('fire',
'clear')`. A withheld FIRE leaves the verdict at `fire` with `firing` false, so restoring the route
armed burn coverage in the instant before the next evaluation — the member's own burn alert falls
silent for an onset that was never sent. A CLEAR covers by itself (the rule looked and had nothing to
say); a FIRE covers only with `firing` set and a sequence issued. The regression now asserts the
dis-armed state BETWEEN re-enabling the route and the next evaluation, which is the half that was
missing, and that nothing was WRITTEN on the withheld pass — zero episodes, zero outbox rows — rather
than only that counters were zero.

**Two claims in §23 were wider than the code.** Both were caught by the review reading the diff
rather than the prose:

- `withheld` was added as a fourth value on the evaluations `outcome` label, but `ok` still counted
  every service evaluated, so the two OVERLAPPED and the label stopped partitioning anything. Worse,
  the burn pass never forwarded its count at all, so half the telemetry the section claimed was
  structurally zero. It is its own bounded family now, `cerbix_service_alert_withheld_total{signal}`,

- D-0176 stated that `cerbix_service_alert_undeliverable_total` "is not implemented". It is, in the

**Mutation evidence:** arming burn on the verdict alone fails with `burn coverage armed on a restored

## 27. A counter that named the wrong cause, and a contract that was true only of its comment

**The withheld counter reported a missing declaration as a broken route.** §23 introduced it and §26

## 28. Ordering that survives a mixed fleet

§24 built the fence and the review found two ways it was still only half a guarantee. Both were right.

**The claim released both ends of a lifecycle at once.** Dropping a superseded onset at DELIVERY keeps
a subscriber from being told an outage began after it ended; it does not keep the two events in order,
and one batch holding an opening and its resolution could hand them over either way round — or two
workers could take one each. The claim now refuses an event while an earlier event of the same
incident is undelivered. A DEAD predecessor blocks as well, deliberately: releasing past it delivers a
resolution whose opening was parked for an operator. Migration 00087 indexes the question so the poll
does not scan the outbox to ask it.

**A pre-fence worker bypassed the whole thing.** The ordering lives in the claim, and an old binary
runs the old claim — so in a mixed fleet the new rows were still delivered out of order, and the fix
was correct only after full convergence. `incident_event` is a FENCED topic now: an old worker does
not list it, so its capable claim cannot match, and the rows wait for a worker that can order them.
That is the fenced class's standing trade — a delay rather than a wrong order — and it is why the
class exists. Rows enqueued before the upgrade keep the legacy class and the old behaviour, since they
carry no sequence and the gate never turns a missing number into a missing page.

The topic-parity gate earned its keep here: adding the topic to the fenced set failed
`TestFencedTopicsAreDispatchable` immediately, which is the check that a fenced topic no worker
dispatches would wait forever.

**Mutation evidence:** dropping the causal predicate fails with `2 lifecycle events claimed at once`;
letting a dead predecessor release its successor fails with `the resolution was released past a DEAD
opening`; unfencing the topic fails with `fenced incident_event rows = 0, want 1`.
