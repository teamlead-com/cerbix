## 1. What landed

### 1.1 The gate ledger's `state` filter is the server's (task 2, Agent A)

`GET /api/v1/projects/{p}/gate/decisions` accepts `state` as a repeatable query parameter — a set, OR —
over the five states; any other value (including lower case and the empty string) is 400
`state_invalid: "<value>"`, refused before a permit is taken. The store's one statement gains
`AND state = ANY($n::text[])` beside the `service_id` clause; `LIMIT limit + 1` and the keyset cursor are
unchanged, so a page of 50 is 50 matching rows and the cursor continues within the filtered set. The
`Store` interface grew (`ListGateDecisions(…, states []domain.GateState, …)`), which broke the API fake
on purpose. The SPA's decision history sends `state: [picked]` on the first page and on every
`Show 50 more`, filters nothing itself, and its "client-side" hint is gone; an empty filtered page names
the state it asked for.

Tests: store `TestGateLedgerListingStateFilter` (12 rows cycling BLOCK/ALLOW/WARN so every match is
flanked by non-matches, plus a second service: one state → only it; `limit 3` over four BLOCKs → three
BLOCKs with the cursor from the last returned MATCH, the next page the fourth, the concatenation equal to
the filtered newest-first timeline; BLOCK|WARN across three pages; composition with `service_id`; an
unknown value → an empty non-nil page). API `TestGateDecisionListValidation` (+4 refusals, none reaching
the store) and `TestGateDecisionListStateFilter` (nil when absent, dedupe in first-seen order, all four
query parts landing in the store). SPA `GateDecisionsView.spec.ts`: the filter travels as a one-element
array on both pages and a WARN row served on a filtered page is NOT dropped client-side; the empty page
names its state. Vitest 26 files / 262 tests. `docs/overview.md`: the route row and the SPA paragraph.
`make spa-snapshot` regenerated `internal/web/dist`.

### 1.2 The alerting panel's draft survives a late prop (task 1, Agent B)

The intermittent `alerting.spec.ts:36` was a product defect with two halves, both proven before the fix.
The mechanism: `frontend/src/components/ServiceAlerting.vue` rebuilt its whole draft on every new
`alerting` prop object, so a prop landing after the operator typed and before Save discarded the typed
value — `dirty` went false, Save disabled itself. The source and its timing: on a cold load `ws.projectId`
is empty until `ws.init()` — awaited inside `ServiceDetailView.load()` — selects the project; that set
fires the view's own `[route.params.id, ws.projectId]` watcher, whose flush runs BEFORE `init()` marks
`loaded`, so a second full `load()` runs (two more workspace GETs). At `9793758`, with no generation
guard, load #1 handed the panel the declaration, the operator typed, and load #2 handed it a second,
value-identical object two round trips later — the late prop. From `e78f4f7` (the P1 [90] guard) load #1
is superseded before it reads, so the E2E-visible trigger was already gone; the component's weakness was
not. Both halves have a test that fails on the unfixed file: `ServiceAlerting.spec.ts` "a late alerting
prop does not discard an unsaved edit" and "an untouched field's server-side change flows into a dirty
draft" (fail on the unfixed component with `expected '0' to be '900'`); `ServiceDetailView.spec.ts` "cold
load › hands the panel ONE declaration although ws.init() re-triggers load()" (fails on the `9793758`
view with "only the surviving load reads the service: expected 2 to be 1").

The fix: `diffAlerting(before, now)` extracted as the single definition of "changed" (used by
`changedFields()` unchanged in semantics, and by the watcher); on a new prop with a dirty draft the
watcher keeps the touched fields and takes the server's value for every untouched one; nothing touched →
re-initialise as before; a `[projectId, serviceId]` change discards the draft (service A's edits never
merge into service B's prop); a successful save adopts the server's echo before emitting, so the form is
clean whatever the server canonicalised. Five vitest cases in the new describe "keeps unsaved edits across
a prop update", one in the view spec; vitest 26 files / 268 tests. The E2E waits for the stored value to
be present after `page.reload()` before filling and waits for the PATCH response before reading back
(the second, structural race in the spec — `toBeDisabled()` passed while the PATCH was still in flight).
`alerting.spec.ts` 3 × 3 passed and the full suite 54 passed / 1 skipped against Agent B's SPA served by
vite dev over the live :8080 backend (`scratchpad/e2e-full-0164b.log`); `make spa-snapshot` regenerated.

Named, not fixed, for the owner: every cold load of a view runs `ws.init()` twice (four workspace GETs
instead of two) because the `projectId` watcher fires before `loaded` is set — an in-flight promise in
`init()` would close it; a separate decision.
