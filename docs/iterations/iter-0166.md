## 0. Where this came from

Not a feature request. An operator asked whether a synthetic monitor could carry a bearer token, and the
answer turned out to be "yes, in cleartext, to everyone": stored plaintext in `monitors.config`,
returned to every principal who may READ the monitor, skipped by key rotation, and echoed into
`heartbeat.msg` with the whole request URL whenever a step's transport failed.
`func-oncall-synthetic-pull.md` FR-SYN-1 and its §217 already promised encryption and rotation coverage;
D-0090 promised the message "never echoes bodies/headers". None of the three was true of the tree. So
this is a **spec-versus-code defect** of the same class as FR-022's invariant 14 — and the SYN
requirements had NO rows in `docs/status.md`, which is how a false promise survived unnoticed.

## 1. What landed

**Stage 0** replaces `Msg: err.Error()` with a bounded class plus the host, composed in one place
(`internal/prober/failure.go`) and applied to `http`, `promql`, `synthetic` and the RabbitMQ management
probe. Type-wide rather than synthetic-only, because the leak reproduced on an ordinary `http` monitor:
`net/http` embeds the request URL in every error it returns. Safe to change because `heartbeat.msg` is
never parsed for a decision — verified before the change, not assumed.

**Stage 1** turns one secret set into three classifications by MEANING and the reader into a MODE named
by what it decrypts. A viewer receives no scenario; a writer does, through a store call chosen AFTER the
authorization decision, not by redacting a decrypted document.

**Stage 2** makes a declared credential a named binding: `{{secret:<binding>}}` in the document, the
inventory secret's NAME in a flat config key `scenario_secret_<binding>_ref`. The flat key is the whole
design — it is where `repointSecretRefs` already looks — and the executor substitutes the value into the
scenario after the structural gate, leaving no copy beside it.

## 2. What the tests disproved, and what the review caught

Three claims of mine were wrong, and each is recorded where it can be found again.

1. **The materializer reads through the same boundary as a display list.** Adding `scenario` to the
   encrypted set stripped it from every job, so every synthetic probe would have run with no scenario —
   a security fix causing a monitoring outage. The reviewer predicted the shape of it; the test caught
   it on the first run.
2. **"The digest already covers the scenario."** It covers the keys of a credential SCHEMA, and
   synthetic has none — so an attacker holding a valid envelope could rewrite a step's URL and have the
   credential delivered to a target of their choosing. Fixed by making the scenario and its ref keys
   EXECUTION BINDING KEYS. That exposed the next one: only `EnvelopeV2` binds the body, so a binding
   REQUIRES a body-bound envelope and an older carrier gets `carrier_too_old` per monitor.
3. **The type gate that was not there (review round 5, P0).** Every helper matched the
   `scenario_secret_` prefix and none asked the monitor TYPE, so an http monitor could be saved with a
   binding — writing a `monitor_secret_refs` row, adding an expected envelope field, joining the
   execution digest and raising the carrier generation the dispatch gate demanded, until the executor
   refused a scenario that does not exist. No credential escaped: every step fails closed. What broke
   is AVAILABILITY, at dispatch, for a config the write surface had ACCEPTED — the failure shape the
   owner's blast-radius ruling exists to prevent. The rule is now decided once at the write boundary and
   gated in three further places (D6b).

The review also refused two claims the documents were making. **D7** may not say a scenario cannot
contain a literal: a literal is not detectable by shape, so the enforceable rule is the header-NAME one,
and the residual — a credential in an unlisted header or a body — is now written down in the spec, the
status row and D-0216. **D10** promised authoritative materialization for an unsaved test; the code
refuses instead ("save the monitor before testing it"), and the spec follows the code.

## 3. Gates

`go build ./...`, `go vet ./...`, `gofmt -l` clean; `make docs-check` green; the full suite under
`-race -count=1 -timeout 40m` against a hypertable `cerbix_test`. The `-timeout 40m` is not padding:

wrong bug.

for the machine, and 12 of 12 clean when the machine was idle, including at `b3c99b6` in a separate
worktree with none of this iteration's changes — so it is load-dependent and older than this arc. FR-028
touches nothing in gate maintenance. Not chased here; named for whoever picks up FR-024's tail.

Live E2E on the single stack (`make dev-build && make dev-up && make dev-test`) is the gate for the
whole arc and its result is recorded in §5 when it runs — this report does not claim it in advance.

## 4. Not done, named rather than implied

- The SPA cannot declare a binding. Stage 2 is reachable through the API and not through the editor,
  and `openapi.yaml` documents the key so that is a usable statement rather than a hidden one.
- A synthetic monitor still cannot live in a Monitoring-as-Code bundle (D9): the flat
  `settings map[string]string` cannot carry a nested scenario. Stage 2 removed the REASON for the
  exclusion (a scenario need no longer contain a secret) and not the exclusion.
- Two breaking changes owed to the next release's notes, already recorded in `docs/roadmap.md`: URL
  userinfo refused on every write surface, and a synthetic monitor whose `authorization`-class header
  holds a literal failing validation on its next write. Both keep probing; nothing re-validates on read.
