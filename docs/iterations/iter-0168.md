## 1. What landed

**The door split, not an argument** (`internal/store/incidentaudit.go`, `incidents.go`). Revision 1 of
the design passed an actor into one shared writer and read `nil` as "machine". D3 replaced that with two
doors — `…ByPrincipal` requires an actor in its signature, `…BySystem` takes none — so a handler that
forgets the actor does not compile. The audit row is one INSERT inside the caller's transaction, with the
organization resolved from the project in the statement itself (D6), which is what makes it work for an
incident whose service was deleted and for one that never had an anchor.

`AuditActor.valid()` refuses two shapes: nothing at all, and a bare LABEL with no user id and no token
flag — an attribution that names nobody. The three legal shapes are the three principals that exist: a
session user, a Cerbix token (NULL id, `via_token`), and an OIDC client-credentials principal (a real id
AND `via_token`), which is why neither "NULL means token" nor "via_token means NULL" would have been a
correct rule.

**The exemption that hid the defect.** The first version of guard 1 excused `handlers_alertmanager.go`
by name, reasoning that the receiver is "a machine writer that happens to arrive over HTTP". It is not:
D1 audits the receiver's create and its resolve, because Alertmanager posts with a project-write token
and a token is a principal. The receiver had been wired to the SYSTEM doors and audited nothing, and the
exemption is exactly what stopped the guard from saying so. There is no exemption now, and both guards
are additionally driven by fixtures that DO contain the violation — a guard nobody has watched fail is a
guard nobody knows works.

**D8a and D8b, the two corrections FR-026 carries** because its own invariant depends on them.
- D8a: a repeated acknowledgement used to rewrite `updated_at` on every retry. FR-026 may not claim "an
  idempotent no-op audits nothing" while the write underneath is not idempotent, so the guard moved into
  the statement (`updated_at = CASE WHEN acknowledged_at IS NULL THEN $3 ELSE updated_at END`, with
  `(acknowledged_at = $3) AS first_ack` deciding the audit row). It stays a statement rather than a Go
  branch so a concurrent second acknowledgement loses the same way under the row lock. The property D8a
  must not break — an acknowledgement that WAITED behind a timeline update still stamps forward — has
  its own test.
- D8b: two simultaneous firings of one fingerprint both miss the "already open" read, and the loser
  violated `incidents_external_key_open_idx`, which was not mapped — so the receiver answered 500 where
  the sequential retry a millisecond later answered 200 and "ignored". The index is now mapped to the
  same benign `ErrAlreadyOpen` as the auto-incident index, and the resolve half maps `ErrIncidentTerminal`
  to "ignored" IN THE RECEIVER ONLY: the human route still tells an operator the incident is already
  resolved.

**D2a, and what its test can actually see.** The postmortem writer gained a transaction in the design and
a row lock here: it resolves the incident FIRST (`SELECT project_id … FOR UPDATE`), so an unknown incident
is `ErrNotFound` from that read rather than a foreign-key error from the upsert, and `created` vs `updated`
(`xmax = 0`) is decided with the row held. The first test written for it asserted that a competing lock
holder makes the postmortem WAIT — and that assertion cannot distinguish the change, because
`postmortems.incident_id` is a foreign key and the insert takes a KEY SHARE lock on the same row either
way. The test now names which half distinguishes what, and the mutation that IS caught is moving the
tenant read back after the upsert.

## 2. The mutation sweep

Eight mutations, applied to the product and reverted:

| Mutation | Result |
| --- | --- |
| the create writes no audit row | CAUGHT |
| an audit INSERT failure is swallowed instead of aborting | CAUGHT |
| the repeated acknowledgement audits again (`firstAck` guard dropped) | CAUGHT |
| D8a reverted (`updated_at = $3` unconditionally) | CAUGHT |
| `incidents_external_key_open_idx` unmapped | CAUGHT |
| the receiver's resolve routed back through the system door | CAUGHT |
| the note target carries the body | CAUGHT |
| a bare label accepted as an attribution | CAUGHT |
| the postmortem's tenant read moved back after the upsert | CAUGHT |

Two mutations SURVIVED and were not left as passing claims. Removing `FOR UPDATE` from the postmortem's
tenant read survives, for the foreign-key reason above — the test was renamed and its limits written into
it. Reading `upd.Status` instead of `next` in the audit branch survives because `upd.Status` is assigned
`next` twenty lines earlier; the code now reads `next` anyway, so a future edit that moves that assignment
cannot turn every plain note into a transition to the empty string, but nothing here is claimed as a fix.

Two tests failed to reach their own mechanism before being corrected, which is the defect class this
repository has hit most often. The body-leak test drove only STATUS changes and never the NOTE branch, so
a mutation that appended the body to the note target survived it; it now drives a status change, an
explicit keep-current note and an omitted-status note. And the postmortem lock test named a keyword it
could not observe.

## 4. What did NOT change

No migration, no new route, no new read: FR-026 adds rows of an existing shape to an existing table from
write paths that already own a transaction. The organization's audit listing shows them under the rule it
already had; the instance listing shows none, because they carry an organization. Machine writes stay
unaudited by decision, and their record stays the incident's own timeline.
