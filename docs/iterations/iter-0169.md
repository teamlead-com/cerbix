## 1. What landed

**Phase B — the contract is a type, not a convention** (`internal/domain/canary.go`,
`canarycanonical.go`, `canaryexec.go`). Closed unions, ten frozen credential-bearing header names, a
body algebra whose only credential-carrying node is `{secret_ref: <binding>}`, two restricted grammars
(a JSON path and an RFC 7230 header token), and bounds with a number each. Two decisions were made by
reading the tree rather than by preference:

- `monitors.config` is `map[string]string`, and `repointSecretRefs` decodes it as one — so the whole
  workflow is persisted as ONE canonical JSON string under `config["workflow"]` (D3e). A nested
  structure would have been silently mangled by a function that already exists.
- `canonicalHash` already hashes `password_ref` by NAME, so a canary binding hashes by name too (D3g).
  Rotating a project secret does not move a canary's execution revision; changing a URL does.

`workflow.secrets` is INPUT-ONLY: it is validated and then projected into flat
`canary_secret_<binding>_ref` keys, which are the sole persisted identity. The stored document keeps
the `secret_ref` markers and no project-secret name at all, so a rename touches one row and the stored
document cannot go stale behind it.

**Phase C — the executor owns the rules `net/http` does not** (`internal/prober/canary.go`). Five
stages, its own `NewGuard(false, false)` with no configuration path into it, and its own
`CheckRedirect` that drops EVERY binding-backed header on a host-or-port change — `net/http` strips
`Authorization` and has never heard of `x-api-key`. The correlation id is bounded and percent-encoded
into exactly one path segment. Every failure is a stage plus a bounded class, and nothing else.

**Phase D — one run per monitor, four per region** (migration 00095). The in-flight row is the
per-monitor lease and the per-region count is the cap. The first version of the change claimed the slot
only in the credential-dispatch branch — and a canary with no bindings never goes there, so it would
have had NO duplicate-submit protection at all. The claim is now on both paths, and the mutation that
removes either one is caught. A refused run writes ONE ordinary DOWN with a bounded reason
(`region_saturated`, `already_in_flight`) and the monitor's own `failure_threshold` decides the flip,
so the sample counts as unavailable in the standard SLI exactly as the brief requires.

**Phase E — and a defect older than the canary.** The per-job pull claim lease (migration 00096) exists
because the agent endpoint hardcoded 30 s: ANY pull monitor with a timeout past 30 seconds was
re-claimable mid-probe. That is not a canary bug; the canary is what made it visible. Also here: SSE
with a pinned content type, no reconnect in v1 and line/event/total bounds; the embedded `small_wav_v1`
whose SHA-256 is verified before a byte is uploaded; admission to `fileSupportedTypes` with a recursive
inline-secret guard that walks every position; two low-cardinality `cerbix_canary_*` metrics carrying
no monitor id, URL or correlation id; and the runbook section, which states what is NOT protected as
plainly as what is.

**The DB constraint the Go suite could not see.** Every Go test passed while the real `monitors` table
refused `async_canary`, because no store test writes to it — the E2E found it on a live stack.
Migration 00097 extends `monitors_type_check`, and `TestEveryValidMonitorTypeIsAcceptedByTheDatabase`
now asserts the vocabulary against the database itself, so the next type cannot repeat it.

## 2. What is NOT built, named rather than implied

- **Capability announcement, its dispatch filter and `no_capable_runner`** (invariant 6). Until it
  lands, nothing filters a canary job away from an older executor binary: that binary answers
  `unsupported monitor type "async_canary"` — an ordinary DOWN, per monitor, self-healing the moment
  the region runs a current binary. The runbook now states the fleet order (upgrade the region, then
  declare the canary) rather than leaving it to be discovered.
- **Phase F, the typed UI form.** `docs/design/mock-async-canary.html` exists — four screens, no JSON
  editor anywhere by contract — and awaits the owner's visual approval, which is the standing gate for
  every SPA surface in this repo (D-0207, iter-0167). A canary is declared in a bundle or through the
  API today.
- **The per-workflow-kind AMQP queue.** The kind rides the existing per-region queue.
- **The audit-trail half of invariant 13.** `cleanup.kind: none` with `acknowledged: true` is visible in
  the API payload because it is part of the stored document; it is not in an audit trail, because a
  MONITOR write leaves no audit row today for any type. FR-026 audits INCIDENT writes. A monitor-write
  trail is in no requirement yet, and the discharge row says so rather than citing a test for it.

## 2a. What the review found: internal provenance on the wire (P0, D-0222)

The redirect policy has to know WHICH headers a binding produced, because the schema knows that and
the transport does not. The first version carried that provenance in an `X-Cerbix-Binding-Backed`
request header and deleted it after `client.Do` returned — which is after the request is sent. So the
initial target AND every redirect hop received an undeclared internal header naming exactly which of
the request's headers hold credentials. That is worse than the marker looks: it hands an untrusted
endpoint a map of what to attack.

It is now a **context value** (`canaryWithBindingBacked`), which reaches `CheckRedirect` through
`req.Context()` on every hop and reaches no socket at all. No wire header is set or deleted anywhere.

The reason it survived phase C's own six mutations is worth stating: every redirect test asserted what
the target must NOT keep (`authorization`, `x-api-key`) and what it must keep (`x-tenant`) — nothing
asserted what the target must never RECEIVE in the first place. `TestCanaryProvenanceNeverReachesEitherTargetOnTheWire`
closes that by asserting on both hops with a `x-cerbix-` PREFIX rather than the one name, so a future
marker with a different spelling cannot slip past it. Mutation: reinstating the wire header — CAUGHT on
both hops.

## 2b. What the full review found: invariant 8 did not hold (P0-2, P0-3, D-0223)

Two more from the reviewer's complete pass, both against §6 invariant 8 — "the scheduler never has two
in-flight executions of one monitor" — which the implementation claimed and did not keep.

**P0-2, a claim without a delivery leaked the slot.** The claim happened BEFORE the publish, the pull
enqueue, the marshal and the credential-path publish, and no failure branch released it. Four transient
faults consumed a region's whole cap until `timeout + 60s`, and every canary there then reported
`region_saturated` — a bounded reason naming a cause that had not occurred. A broker blip became a
fleet of false outages, which is worse than a missing guarantee: it is a guarantee that lies.

**P0-3, a stale result released a newer run's slot.** The row stored `run_key`; the release deleted by
`monitor_id` alone and the heartbeat carried no run identity. Run 1 claims → lease lapses → run 2
claims → run 1's late result deletes run 2's row → run 3 starts beside run 2. The exact concurrency the
lease exists to forbid, reached through the one door the lease did not cover.

**And a third, uncovered while fixing them.** The run key was written inline in the credential
materializer, which the PLAIN path never reaches — so a canary with no bindings claimed with an EMPTY
run key. That slot could never be released by key: it would have parked its own monitor for the whole
TTL on every run. The formula has one owner now (`domain.CanaryRunKeyAt`), both paths stamp through it
onto a COPY of the config, and the claim refuses an empty key loudly.

**Why phase D's own mutation testing missed all three.** Phase D mutated the CLAIM — remove it from one
path, remove it from the other — and both were caught. Nothing mutated the RELEASE, because there was
no test that made a dispatch fail after claiming, and no test that let a lease lapse and then delivered
a stale result. The claim is the half that is easy to imagine; the release is the half where the
concurrency actually escapes. Four mutations are killed now, one per branch of the two fixes.
