## 2. What the rule could not anticipate: two majors that are one decision

`vue-router@5` declares `peerOptional vite@"^7.3.0 || ^8.0.0"`. On Vite 6 the install fails outright
with `ERESOLVE`. So "each major alone" is not available here: **vue-router 5 and Vite 8 are one
decision**, and the honest sequence is Vite alone first (verified: 38/418 and a clean build), then
vue-router on top of it (verified again). That is what was done, and it is written here rather than
presented as two independent verifications that never happened.

## 3. Declined, with the reason

**TypeScript 5.9.3 → 7.0.2 — NOT taken.** TypeScript 7 is the native compiler port, and `vue-tsc`
3.3.11 cannot drive it: `npm run type-check` dies in `vue-tsc/index.js` resolving the tsc entry point
with `ERR_PACKAGE_PATH_NOT_EXPORTED`, before type-checking a single file. This is a toolchain
incompatibility upstream of anything in this repository, so there is nothing here to fix and nothing to
work around that would not amount to dropping the type-check from the build. The bump waits for a
`vue-tsc` that supports TypeScript 7. The dependabot branch stays open on purpose; closing it would
lose the reason.

## 6. What CI caught that no local run could: a test that measured the machine

`Backend (declarative partitions)` went RED on the release commit and green on the one before it, so
this arc broke it. It was **not** `internal/store`, **not** a storage-mode defect, and **not** the 40 m
timeout (the test step ran 2347 s against a 2400 s limit — a detail worth checking before assuming, as
the first reading of this failure did assume). It was:

```
--- FAIL: TestLeaderLoopEventStormBounded (0.45s)
    provider_test.go:791: storm too weak to be meaningful: only 61 writes
```

The test proves a real §17 invariant — a storm of directory changes coalesces into a small constant
number of reconciles, because the watch is a single dirty bit plus debounce and not an event queue.
Its bug was in how it set the storm up: it wrote for a fixed **300 ms wall-clock window** and then
asserted it had managed **at least 100 writes**. That is an assertion about the MACHINE. On a runner
where `internal/store` took 2278 s (against 605 s locally) the storm goroutine got 61 writes, and the
test failed for a reason that has nothing to do with the invariant it exists to defend.

The storm is now bounded by a **count**: it writes until it has produced 150 changes, with a 20-second
deadline that still fails loudly — a machine that cannot produce a storm in twenty seconds proves
nothing, and the message says so instead of quietly passing. The property under test is unchanged, and
a slow machine now makes the test slower rather than red.

**Verified rather than argued.** The failure would not reproduce locally, even pinned to one core under
eight CPU hogs — this machine is simply too fast. So the slow runner was emulated instead, by raising
the storm's per-write sleep from 1 ms to 5 ms: under the OLD wall-clock shape that produces **58
writes** and the exact CI message, and under the new count-driven shape it passes. That is the
before-and-after the fix rests on.

The general shape is worth keeping: **a precondition guard that measures throughput turns every busy
machine into a red build.** Guard the strength of a stimulus by counting it, not by timing it.

## 6a. The fix for the fix: a red job now explains itself (D-0225)

§6 above was diagnosed only because a human pasted the job log by hand. That is not a process — it is
a dependency on somebody else's admin rights for every red build, and it cost a release cycle: the
storm failure took one paste to solve, and the one after it (`Backend (timescaledb hypertables)`, red

so a pipe would have reported `tee`'s status and silently turned the gate off), and the extraction was
run against a real failing `go test` rather than reasoned about.

## 7. A note on the test database, because it cost an hour

The full `-race` suite failed 43 tests with `TruncateAll` deadlocks and org-slug conflicts, and none of
it was the code. Another agent was running its own verification against the SAME `cerbix_test` database
at the same time — visible directly in `pg_stat_activity` as a `DROP DATABASE IF EXISTS
cerbix_test_utcprobe_…` issued from a connection to `cerbix_test`. Two suites truncating one database
deadlock, and the loser then finds every fixture's organization already present.

The fix is per-run isolation, not coordination: `CERBIX_TEST_DATABASE_DSN` pointed at a private
`cerbix_test_v019`. Note that the database NAME must contain `test` — `TruncateAll` refuses anything
else, which is a guard worth knowing about before naming a scratch database.
