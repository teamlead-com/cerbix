# iter-0171 — the canary's capability announcement (FR-029 phase C, invariant 6)

> **Lifecycle: CLOSED, 2026-09-03.** The last unbuilt half of FR-029, and the one iter-0169 named in
> its own rows rather than implying: an executor receives a canary ONLY if it announced the workflow
> kind and version. FR-029 and NFR-024 move to `DONE` with this iteration, against the discharge map
> with its residuals named. Decision record: **D-0231**.

## 0. What was missing, and why it was not a small thing

Invariant 6 says a canary reaches an executor that announced it can run one, that a region with none
produces `no_capable_runner`, that a version skew produces `capability_mismatch`, and that both are
bounded per-monitor DOWNs rather than an indefinite pending. None of that existed. A canary in a region
whose binaries predate the type answered `unsupported monitor type` — an ordinary DOWN with the wrong
reason — and `docs/runbook.md` §FR-029 told operators to upgrade a region's executors BEFORE declaring
a canary there. That instruction is now unnecessary, and it is removed rather than left as advice
nobody needs.

The reason it is not small: the announcement crosses THREE wires that do not import each other — a pull
agent's heartbeat JSONB, an AMQP queue name, and an in-process registration — and a spelling that
drifts on any one of them fails SILENTLY. The region simply looks incapable forever.

## 1. The shape: a set of tokens, generalized from the envelope generation

`<kind>@<version>`, matched exactly in both directions (`internal/domain/canarycapability.go`). §D1 of
the spec pointed at this: the credential path already answers "is this region ready for what I am about
to emit", generationally, because capability-1 is not evidence for a region core is about to emit
generation 2 into. The version is in the token for the same reason — a future `async_transaction_v2`
must not land on a v1 runner, and a NEWER runner must not silently accept an older contract it may have
stopped honouring.

The required token comes from the DOCUMENT, not from core's constant: a workflow of a kind this core
does not run asks for a runner announcing that kind, and is refused rather than dispatched hopefully.

## 2. Three sources, one merge, and two reasons that stay distinct

`Scheduler.canaryAnnouncements` merges exactly the three sources readiness already uses:

| Transport | The announcement | Read by |
| --- | --- | --- |
| pull | `agent_heartbeats.capabilities->'workflow_kinds'`, from `runner.Supports` | `store.LiveCanaryAgentCapabilities` (union over LIVE agents, 45 s) |
| AMQP | a consumer on `checks.canary.[v3.]<token>.<region>` | `mqadmin.LiveCanaryJobRegions` |
| in-process (`--role=all`) | `WithLocalCanaryRegions`, also from `runner.Supports` | itself |

The sources return the announced SET, not a boolean, because a boolean cannot tell the two failures
apart: a region with no runner needs one started, a region announcing another version needs an upgrade
finished, and the operator reads a different sentence for each. A lookup that FAILS contributes nothing
and the run is refused — not evidence of capability, and dispatching into a region core could not
verify is the one outcome the invariant forbids.

The pull and AMQP sources are NOT crossed: an agent heartbeat says nothing about a region served over
AMQP, exactly as the credential readiness split already treats it.

The resolver runs at most once per tick and only when a canary is actually due. An instance with no
canaries pays for no management call and no query, which a test asserts and a mutation (making the
resolver eager) kills.

## 3. The barrier itself: a queue on AMQP, the claim on pull

D-0160 settled the general argument: **a capability CHECK does not stop a consumer from consuming.** The
scheduler's refusal to dispatch is necessary and not sufficient — in a mixed fleet the region DOES
announce, via its new executor, and the old one takes the job first.

**AMQP.** A canary rides its own queue, `checks.canary.<token>.<region>` (generation 1) and
`checks.canary.v3.<token>.<region>` (generation 3), bound only by a worker whose runner has the type.
Two carriers because `secrets.enabled: false` must keep a secretless canary working on a worker that
can open no envelope, and that worker must stay physically unable to receive one. Both queues announce
the same capability; whether the region can also take an envelope is the credential readiness question,
already answered elsewhere, and asking it twice would give two answers that can disagree. The
publisher's envelope rule on that carrier is exact — an envelope is required precisely when the
workflow binds a secret — so it refuses a stripped envelope AND an envelope on the plain queue.

**Pull.** Every agent claims from one table, so `pull_jobs` carries the capability the job REQUIRES
(migration 00098; NULL for everything any agent may run), the claim declares what it can run in
`X-Cerbix-Workflow-Kinds` — per request, exactly as `X-Cerbix-Credential-Envelope` is — and the claim
query filters. An agent that declares nothing still claims every ordinary job: a barrier that starved
the ordinary path would be the worse bug, and that is precisely the D-0160 defect where a capable claim
returned only its own generation and left every ordinary monitor's row to expire by TTL.

The header is bounded and grammar-checked by the SAME constant and regexp the heartbeat's announcement
is checked against — it reaches a SQL parameter, and one spelling of the rule is one place for it to be
wrong.

## 4. role=all announces from its runner

The in-process executor's capability is this binary's. The credential path paid for forgetting that
once: until D-0160's local wiring existed, the default single-binary deployment never moved past
generation 2 and the whole amendment was inert in the commonest deployment. So both the AMQP worker's
declaration and `WithLocalCanaryRegions` are derived from ONE check,
`runner.Supports(domain.MonitorAsyncCanary)`, so the two paths cannot drift into announcing different
things.

## 6. One rule, one place

The required token is derived at three call sites — the scheduler's dispatch filter, the pull job's
required capability, and the AMQP queue a job is published to. The first version of this change wrote
the derivation three times. Three spellings of one rule disagree exactly for the documents that matter
(the ones of an unfamiliar kind), which is the drift `canarycapability.go` exists to prevent, so it is
now `domain.CanaryCapabilityRequiredByConfig` and nothing else derives it.

## 7. Two things the tests found, written down rather than smoothed over

**The management reader counted one capability twice.** Two carriers per capability means two queues,
and the first version of `LiveCanaryJobRegions` returned the token once per queue. A caller would have
had to know that to count announcements. Found by the test that asserts "exactly once", not by review.

**A comment of mine outran its test again.** `declaredKinds` normalizes nil to an empty array, and the
comment claimed a nil slice would make `= ANY(...)` NULL "rather than false" and leave every ordinary
job unclaimable. A mutation proved it false: pgx sends nil as NULL, `= ANY(NULL)` is NULL, and a WHERE
treats NULL as not-true — the same answer. The helper stays for explicitness; the comment now says
exactly that, and no more. Fourth instance in this arc of the defect D-0228 named.
