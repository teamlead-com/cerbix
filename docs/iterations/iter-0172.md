## 1. A monitor write says who wrote it (D-0233)

FR-026's rules, applied to the three monitor writers the API reaches and to nothing else:
`CreateMonitorByPrincipal`, `UpdateMonitorByPrincipal`, `DeleteMonitorByPrincipal` take the validated
`AuditActor` and write one row inside the mutating transaction through the same `insertProjectAudit`
the incident doors now share. The bare writers are unexported; the tests reach them through
`export_test.go`, so the product has no exported unaudited monitor writer and a forgotten actor is a
compile error. No `…BySystem` door: the file provider is D1's machine writer with its own INSERT.

Three closed words — `monitor.create`, `monitor.update`, `monitor.delete`. The target names the
document and never its contents (`monitor <id> · <slug> · <type> · region=<r>`, `· enabled true→false`
on a pause, `· deleted`), and for a canary with an acknowledged `cleanup.kind: none` it carries
`cleanup=none acknowledged` — FR-029 invariant 13's clause, made true in the trail.

What is asserted: `TestAMonitorWriteLeavesOneAuditRowInItsTransaction` (one row per door, the update's
`enabled` flip taken from the LOCKED row, the delete's row and the row's absence),
`TestAMonitorAuditTargetNamesTheDocumentAndNotItsContents` (a password, a URL and a body key planted
and searched; the canary clause on create and again on update),
`TestAZeroValuedActorRefusesAMonitorWriteBeforeAnyStatement` (three doors, two illegal actor shapes, no
monitor and no row), `TestTheFileProviderWritesNoMonitorAuditRow` (create, update, remove through a
bundle — zero `monitor.%` rows). In `internal/api`: `TestTheStoreExportsNoUnauditedMonitorWriter` with
`TestTheMonitorWriterGuardFailsOnAFixtureThatViolatesIt`, and the fake records the actor per door so a
handler test sees a dropped principal. Live: `async-canary.spec.ts` reads the organization's audit
listing after creating a canary through the API and finds `monitor.create … cleanup=none acknowledged`
with no URL, body key or field name in the target.

### What the review corrected here

Two findings on this range (party [112]), both accepted and both about a claim being weaker than it
read. **P1:** the delete door took a whole monitor from the caller, so the audited region could be stale
after a concurrent update and a caller could file the row under another project's organization. The door
now takes an id and the row is read in the `FOR UPDATE` statement; the update hook takes the `RETURNING`
row. `TestTheDeleteAuditNamesTheLockedRowNotTheCallersCopy` (two organizations, a region moved after the
read) and `TestTheUpdateAuditNamesTheStoredSlug`; both mutations killed. **P2:** the new bounds
enumeration parsed a hand-written file list — the hand count in another form. It globs the directory now,
proven by `TestTheBoundEnumerationSeesAnUnlistedCanaryFile` against a copy carrying a file the list never
had.
