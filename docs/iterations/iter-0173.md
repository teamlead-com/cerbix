# iter-0173 — a monitor says what it is for (FR-030)

> **Lifecycle: CLOSED, 2026-09-03.** The owner's request in one paragraph: a stranger who opens the product
> cannot tell a monitor's purpose from its name, so a monitor gets an optional description with a
> character limit, shown where monitors are listed, and nothing about existing monitors may break. Mock
> first (`docs/design/mock-monitor-description.html`), approved with two answers — the limit is 200 and
> search does not match on it. Specification `docs/specs/func-monitor-description.md`; decision D-0234.

## 1. What landed

One optional field, `monitors.description`, `NOT NULL DEFAULT ''` (migration 00099). The domain bounds it
at `MaxMonitorDescriptionRunes = 200`, counted as Unicode code points and trimmed in `Normalize`, and
classifies it as presentation — it never moves the execution snapshot
(`TestMonitorFieldsAreExhaustivelyClassified` demanded the classification, which is the kind of guard
that makes a new field impossible to half-add). The store appends the column at the END of
`monitorColumns` and the scan, as every column before it did, and the create and update statements carry
it; the file provider accepts an optional `description` key and folds it into the canonical hash; the API
accepts it on create and update (omitted on update = unchanged, `""` = cleared) and answers 400 naming
the field past the limit; `openapi.yaml` and the regenerated TS schema carry it.

The SPA, to the approved mock: a textarea under Name with a live `n / 200` count that turns `--down`
past the limit, a message that says what to do, and Create/Save disabled while it stands; one line under
the name on `/monitors` with the full text as tooltip; the beginning of the description on a dashboard
panel, cut by the panel's own width in CSS so the grid keeps its shape; the whole text on the monitor
page. Every surface is a `v-if`: a monitor without a description renders exactly as before.

## 2. One count, two sides

The bound is published from the server (`TestMonitorBoundsArePublishedForTheClient` writes
`internal/domain/testdata/monitor_bounds.json`) and mirrored by the form (`monitorBounds.spec.ts`
asserts equality and that the count is by code points: a 200-emoji description is 400 UTF-16 units and
must be legal). The same mechanism the canary form ended up needing after three review rounds
(D-0227…D-0230), built in from the start this time.

## 3. What the tests found

- **The first draft of D5 described a scenario the product cannot produce.** "Re-applying a bundle
  without the key over a UI-set description clears it" — but a file-managed monitor refuses UI and API
  writes (`ErrManagedByFile`), so there is no UI-set description to clear. The store test hit the refusal;
  the spec, D-0234 and the test now say what is true: the bundle is the only writer of a managed monitor's
  description — adding the key sets it, a description-only change IS a change (the hash covers it),
  dropping the key clears it.
- **The canary form's "no JSON editor" guard counted textareas.** A description textarea is prose, not a
  document; the guard now admits exactly the `monitor-description` field and still fails on any other
  textarea — the mechanism kept, the exception named.

## 3a. What the review found: a height contract that was never true

Reviewer P1 [122]. The spec said the dashboard panel "keeps its height and its grid". It does not: the
description is a flex child of a `flex flex-col gap-[13px]` card, so a described card is one line —
about 23px — taller, and `truncate` only prevents a SECOND line. Measured before answering:
`MonitorCardDescription.spec.ts` mounts the card both ways and asserts exactly one more flex child.

Two facts decided how to fix it. The approved mock renders exactly what the code renders, so the false
thing was my prose, not the appearance. And this card's height has always depended on content — a
`push` monitor has no latency column and no error-budget meter, so it is already shorter than an `http`
monitor beside it, which the same test asserts. "The panel keeps its height" was never true of this
component for any field.

The owner chose to keep the second line and state the real contract: a described card is one line
taller; inside a grid row the items stretch, so no card is taller than its neighbour and the ROW grows
by that line, an undescribed card gaining trailing space. Reserving the line on every card was declined
— it would change every existing dashboard for people who never write a description. The correction is
in the spec, the mock's own note, `docs/design/notes.md` and D-0234, and the geometry is now asserted
structurally rather than promised in a sentence.

## 5. One thing this iteration cost that it did not have to

`make spa-snapshot` failed with `EACCES: permission denied, unlink '/app/dist/assets/…'` — because an
earlier frontend build in this session used the command from `CLAUDE.md`
(`docker run --rm -v "$PWD":/app -w /app node:22-alpine sh -c "npm run build"`) which, unlike the
Makefile target, does NOT pass `--user`. It wrote `frontend/dist` as root, and the target's own `npm ci`
then could not delete what root had written. The Makefile comment predicted this exactly and named the
cleanup, which is what fixed it:

```
docker run --rm -v "$PWD/frontend":/app alpine sh -c 'chown -R 1000:1000 /app/dist'
```

Worth recording rather than quietly repairing: the documented ad-hoc build command and the documented
snapshot target disagreed about `--user`, and the disagreement is invisible until the second one runs.
`CLAUDE.md` now passes `--user` (with `npm_config_cache`, which a non-root uid needs because it has no
writable HOME in this image) on both commands, and carries the cleanup for a tree already built as root.

The cleanup is written with the ids expanding on the HOST, and that detail is the point: the first
version of this fix put them inside `sh -c '...'`, where `id -u` is 0 and the chown would have handed
the tree back to root — the opposite of the repair. Both forms were run to see which is which
(`in-container: 0:0` vs `host: 1000:1000`), and the command as documented was then proven end to end
against a deliberately root-owned file planted in `frontend/dist`.

## 6. And one gate result that was not about the code

The first full `-race` on this tree came back with 108 `internal/store` failures. Every one was
access-conflict shaped — `notification_channels_project_id_fkey` violations, `deadlock detected
(40P01)`, `store: conflict` — one package, and that package passes in isolation. Two processes were
truncating and seeding one database.

The second process was mine, and the mechanism is worth writing down because it will happen again to
whoever stops a run the way I did. `pkill -f "go test -race -count=1 -timeout 40m"` does not stop a
`go test`: the child that actually runs and holds the connections has its own command line
(`/tmp/go-build<N>/b001/<pkg>.test -test.paniconexit0 …`), which that pattern never matches — and the
pattern DOES match the invoking shell, so the pkill kills the shell that issued it and hides what it
reaped. Measured, not inferred: a sleeping probe test survived the parent's death and had to be killed
by PID. A surviving `store.test` from the stopped chain was still working the same DSN when the next
chain's `store.test` started.

Stop a gate chain by killing the test BINARY (`pkill -f 'go-build.*\.test'`) or by PID, and give each
run a database of its own. The suite was re-run on `cerbix_fr030_test` with nothing else alive.
