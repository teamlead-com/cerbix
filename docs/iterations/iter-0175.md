## 3. B1's entry gate, corrected twice before any B1 code

passes, while the operator is left with `check constraint ... is violated by some row` and no
procedure. The weaker assertion admits the weaker code, which is the same lesson as asserting the

Specifying this one gate has now caught three invariants contradicting the tree — 13a's four bump

## 4b. Revision 25 — a drain rule that named one of two surfaces

*Recorded while this iteration is OPEN, in the form the reviewer approved at [358] for revision 24.
Written while revision 25 was under review; it was approved at [410] and committed as `6f698d5`.* This one differs in kind from 23 and 24: it amends **approved
design content**, so it needs a design disposition rather than a docs/process one.

I raised §13.0's "Rollback and drain" paragraph as a possible defect at [377] while explicitly
declining to judge it — after being wrong twice that afternoon about drain wording, my own judgement
on drain precision was the least reliable thing available. The reviewer assessed it and ruled at
[387] that **revision 25 is required**: the paragraph called `pull_jobs` TTL expiry the drain
mechanism and then generalized that job-shaped sentence to all "in-flight V4 work", while
V4-capable `pull_tests` rows exist too and each surface has TWO terminal paths.

The corrected rule states both surfaces with both paths each — `AckPullJobs` or
`PurgeExpiredPullJobs`; `GetPullTestResult` or `PurgeExpiredPullTests` — and says plainly that **TTL
is the bounded fallback for unconsumed work, not the drain**. On `pull_tests` that has teeth: a row
whose probe has finished holds an answer nobody has read yet, so calling expiry the drain describes
discarding it as routine.

**The phase boundary, because the old paragraph had none.** The rule becomes live in **B2**, the
first phase that can produce a V4 row; B1 selects nothing, so a B1-era rollback drains nothing and
the paragraph is vacuous there. What protects B1 is invariant 10j's migration guard, which is
boundary safety, not drain. Conflating the two is how a rollback story gets written for a phase that
cannot exercise it — the same shape as 10i and 10k's struck claim, for the third time in this
iteration.

**`check_fr032_drain_surfaces` derives the SET from the tree** rather than checking two hardcoded
names: the surfaces are the tables whose EFFECTIVE CHECK admits generation 4, read from each
migration's Up half, and the terminal paths are the store functions that DELETE from one.

**The first version of that derivation was wrong, and so was the mutation I offered as its proof.**
It took every table carrying a `*_protocol_version_check` constraint — but carrying one is not the
same as being able to hold a V4 row, so a future pull table capped at 1..3 would have forced
irrelevant text into §13.0. Worse, the mutation I presented as showing the derivation was real added
a surface with `IN (1)` and called it V4-capable: **the evidence rested on the same false premise it
was meant to disprove** (reviewer P0 at [390]). A negative fixture now pins it — a surface capped
below 4 must NOT be demanded — beside the positive one that must.

Three further details decide correctness. Migrations are ordered by **parsed numeric version**, not
by path: five-digit padding makes lexical and numeric order agree today, and the guard must not rest
on a future filename keeping that formatting (reviewer [402]) — with versions 9 and 10 the two
disagree, and lexical order would let the older definition win. I had noted that dependency at [397]
and proposed a filename-style ratchet instead; the reviewer's answer is better, because ordering
correctly is one line while policing filenames forever is a rule someone must keep. Only each
migration's **Up half** counts: `00101`'s own Down narrows both CHECKs back to `IN (1, 2, 3)`, so
reading Downs empties the derived set, and an empty set passes on ANY wording — which is why the
emptiness is itself reported. And a later Up dropping the COLUMN removes a surface, while one
dropping the constraint alone does not, since an unconstrained column accepts 4.

Two of the kills are worth distinguishing: dropping a table's ROW from the rule was caught by its
uncited FUNCTIONS, not by the surface-name check, because the table name still appeared in the
surrounding prose. The function citation is the load-bearing half.

**One path is excluded by an ALLOWLIST, not by a pattern that happens to miss it.** `TruncateAll`
(`internal/store/store.go`) truncates both surfaces. Documenting that exclusion in prose was my
first answer, and the reviewer refused it at [392]: `TRUNCATE` is now scanned too, and the sole
exclusion is the exact `(*Store).TruncateAll` — receiver AND function, not the file. Anything else
truncating an effective V4 surface is reported, because it is either a terminal path §13.0 must
describe or operational code discarding V4 work. Six fixtures pin the boundary: the helper stays
silent; a truncate in another file is reported; **another function in `store.go` is reported**; the
same helper NAME on a different receiver is reported; and a truncate of a table that cannot hold a
V4 row is ignored.

**The allowlist's own path test was the last defect, and I found it by probing my own fix.** It
compared with `endswith`, so `other/internal/store/store.go` carrying the same receiver and the same
function was allowlisted — an allowlist that admits any prefix is not an allowlist. It is now
NORMALIZED repo-relative equality, with fixtures for the suffix collision, for the traversal path,
and for `./internal/store/store.go` still resolving as the same file (reviewer P0s at [401] and
[407]).

**And my first exact-equality fix carried a bypass of its own.** I normalized with
`os.path.normpath(path).replace(os.sep, '/').lstrip('./')` — but `lstrip` strips a CHARACTER SET,
not a prefix, so `../internal/store/store.go` collapsed to the allowlisted literal and walked
straight past the check. `normpath` already folds `./` away, so the `lstrip` bought nothing and
cost the exactness it was meant to add. Four passes for one exclusion: prose, a mechanism, a
mechanism that narrows to the file it names, and a normalizer that does not undo the narrowing.

The general lesson, and it is the third form of it this iteration: *documented* is not *guarded*.
A decision written in a docstring survives exactly as long as the next person reads the docstring.

## 4f. B2 — the payload and the ledger, together, and four defects the design could not have shown

*Recorded while this iteration is OPEN.* The owner directed the remaining phases to be implemented
without stopping, with ONE review submission covering all of them. §17.7 of the spec states plainly
what that costs and what is offered instead, and this section records the four findings, because
each is a defect in a design that had been approved and re-read a dozen times.

**What landed.** Migration `00102`: `monitor_schedule` (one row per participating monitor) and
`expected_runs` (one immutable row per due window, range-partitioned by `due_at` with a DEFAULT
partition). §7.1's primitive as ONE statement, with the gap-and-fence CTEs shared by TEXT with
§10's segment close — two statements are unavoidable there, so the [229] lesson is honoured by
giving them one expression rather than by pretending one statement can do both. `DueAt` on
`CheckJob` and `Heartbeat`, copied by `StampResult` alone. `dispatch.CarrierFor` as the one owner of
the carrier decision. The terminal fill and the refusal statement inside the ingest transaction,
behind the same gate as the heartbeat. `syncMonitorScheduleTx` at the same FIVE generation-creating
sites phase A's timeline write already covers, with a source scan holding the pairing. The gate ON:
`ledger.carrier_enabled` is now an admissible input, and the two retention bounds are validated in
`config` and applied in `store` from constants that live in `domain`, which is the only package
both may import.

**Finding 1 — a configuration write restamped a lateness threshold, and the error pointed at
over-claiming.** §6.2 defines `interval_in_force` as *the interval that produced `next_due_at`*.
§10 step 3 had the configuration write overwrite it with the NEW interval while deliberately
leaving `next_due_at` alone. So after a 60s→300s edit the standing window was stamped with a
300-second lateness threshold although it had been spaced at 60, and a run answering it four
minutes late read `covered` — which licenses a stroke and counts in the coverage numerator. Every
other trade in this design points the residual at withholding; §14.2 already records that a
direction violation is not excused by a small magnitude. The fix makes `next_due_at`,
`interval_in_force` and `confirm_phase` one write: three columns describing one instant, so they
cannot come to describe different ones. It also removes rule 5's statement entirely, which was
producing the same mis-description from the other direction — it ran before any advance had made
the instant it claimed to describe.

Found by a test asserting §10's own table and getting 300 where 60 was specified. One column asked
to describe two facts, maintained by two writers, is the shape six of this design's eight P0s had.

**Finding 2 — the orphan carrier's source does not exist on the path that needs it.** §8.3 says the
orphan insert takes `carrier_generation` from `dispatch.DeliveredJob.CarrierGeneration`, the
transport adapter's observation. That value lives in the EXECUTOR's process; the result comes back
as a `domain.Heartbeat`, so reaching it would mean putting the carrier in the payload — the exact
source the design forbids and the P0 that killed revision 6, one generation later and on the other
half of the same field. The implementable source needs no wire field: `DueAt` reaches an executor
only on generation 4, because the leader caps a monitor with no standing expectation below the
carrier for precisely that reason, so a result that CORRELATES proves the carrier. The payload's own
`ProtocolVersion` is never read.

**Finding 3 — `MIN(interval, confirm_interval)` is zero for most monitors.** §14.2's conservative
orphan threshold, read literally, is 0 whenever confirm acceleration is disabled — and a
zero-second threshold makes every orphan window `covered_late` however promptly it was answered.
The direction was safe and the result was useless. `LEAST(interval, NULLIF(confirm, 0))` takes the
minimum over the intervals that could actually have spaced the window, which is what "its two
legitimate values" meant.

**Finding 4 — B1 shipped one of the two admission rules §13.0 demands.** That section says
generation 4 needs both rules "at the same place: resolve time", and quotes the two V3 failures
`scheduler.go` records in its own comments. B1's block carried only the first — a region is raised
when its AMQP workers consume the v4 queue or its agents declare the capability — and had no rule
for the IN-PROCESS executor. A pure `role=all` deployment has neither an AMQP management client nor
a pull agent, so nothing could ever raise it: the ledger would have been inert in the most common
deployment, which is the second failure exactly, against a requirement whose whole subject is
knowing that a run was expected. B1 could not observe it, because its config refused the flag that
reaches the block at all. `WithLocalLedgerRegions` follows the ROLE and takes no capability
argument, which is the same fix B1 applied to the worker's declaration at the other end of the same
wire.

The map is now RAISED and never assigned, too. With the ledger answer resolved before the dispatch
loop — which B2 needs, because the plain path asks the question as well — an assignment in the
credential branch would have silently pushed an announced generation 4 back down to 3. A value
decided by branch order is what "so neither builder order nor configuration can restore it" rules
out.

**Two mutations survived the first pass, and both were killed by an assertion that had to be
added.** `GREATEST(existing, new)` on the fence replaced by the new value alone left every test
green, because each of them writes a fence exactly once — the erasure case needed a tick that
truncated NOTHING. And adding §8.1's no-job disjunct to the refusal's guard survived until a case
presented it with an existing never-issued row. Both are the same shape as B1's mutation 17: every
earlier test had exercised a mechanism that had never yet succeeded.

**One declared exception to invariant 1**, which is the owner's headline property. The effective
interval was computed at two sites and the two did NOT agree: the plain path accelerated while the
confirm TTL was in the future, the credentialed path additionally required `InConfirmPhase()`.
Invariant 20d requires one owner, and unifying them moves one of the two instants whichever rule
wins. The stricter rule wins, so a non-credentialed monitor that has just reached its verdict
returns to its base interval immediately instead of up to one interval later. The confirm phase is
by construction the state in which a monitor is probed FASTER than its configuration asks, so the
change can only move a probe later, never earlier — and keeping two rules leaves §7.3 unable to say
which interval spaced a window for half the monitors. It is declared rather than absorbed because
invariant 1 says "no monitor's probe instant changes", and this one does.

**One cross-phase consequence.** B1's `TestAV3ConsumerCannotReceiveAGenerationFourDelivery`
published a generation-4 job carrying no identity — the field did not exist — and B2's consumer now
dead-letters such a delivery. The fixture stopped being a v4 job and became the poison message the
new live test is about, so it gains the identity a real one carries. What 10g asserts did not
change; what changed is that a v4 delivery now has a contract to violate.

**Two defects only the FULL store suite could find, and both are worth recording because my own
phase tests could not have.** The first: `MaterializeExecutionConfigs` needed the standing
expectation, and I added it as a `LEFT JOIN monitor_schedule`. `monitorColumns` is a shared const
whose column names are UNQUALIFIED, so a second table in that query's FROM makes `project_id`
ambiguous and EVERY materialization fails with SQLSTATE 42702 — every credentialed monitor in every
region, immediately. None of this phase's tests call the materializer, so eight materializer tests
in the full suite were the only thing that saw it. CLAUDE.md warns that the const is shared when
APPENDING to it; the adjacent hazard is that USING it constrains the query's shape, and the
`depends_on` aggregate inside the const is a correlated scalar subquery for the same reason the fix
is one.

The second: `TestMaterializeSealsTheEnvelopeItsCarrierCarries` asserted that carrier 4 maps to NO
envelope, which was true in B1 and is finding 4's sibling — the missing `envelopeForCarrier(4)`
case. The test now pins `4 → envelope v2` and keeps its "an unknown carrier is a wiring bug"
property against generations that really are unknown.

**One behaviour change worth naming, gated behind the carrier.** A plain (secretless) monitor's
job now carries `JobID` and `IssuedAt` as well as `DueAt`, and only on generation 4. So step 4b's
clock test — *a result cannot have been observed before the job that asked for it was issued* —
starts applying to non-credentialed monitors in a region emitted at generation 4. It has applied to
credentialed ones since iter-0155, the allowance is `result.allowed_skew` (5 minutes by default),
and `dispatch.go`'s own comment already says the field exists "because every job needs the
identity, not only the ones with a secret". The consequence to plan for is that enabling the ledger
in a region whose executors' clocks trail the core's by more than the allowance turns silently
accepted results into counted rejections — visible in `cerbix_result_observed_before_issue_total`,
which already exists.

**And one phase-boundary correction.** §16 assigned the `expected_runs` partitions and the DEFAULT
partition to phase D. B2's own inserts have nowhere to land without them, and a table left
DEFAULT-only cannot acquire daily partitions afterwards, because the default already holds rows in
their ranges. Invariants 16a and 23a therefore move to B2 with the code, by the same rule that
moved §10's segment close out of phase A.

## 4g. C, D and E — the claim, the ledger's reads, and the stroke's rule

*Recorded while this iteration is OPEN.* The owner directed every remaining phase implemented
without stopping, with one review submission at the end. What follows is what each phase decided,
and what implementing it found.

**C — the claim event, and the `Dispatcher` that did not grow.** §16 said "`Dispatcher` grows a
typed claim message". It does not, and §4a is why: `worker` and `agent` must stay DB-less executors
returning idempotent events over the EXISTING transport. So the claim is a typed MEMBER of
`domain.Heartbeat` — `Claim *RunClaim`, exactly as `ProbeError` is — riding the results queue. No
new method, no new queue, no new endpoint: the pull agent posts to `/api/v1/agent/results`, whose
handler already feeds the same sink AMQP does, and `ingest.Consumer.handle` branches once for both
transports. Invariant 11's five-method set survives the phase most likely to break it, and §18's
open item about the wire shape is closed by the answer §8.4 already implied.

The two executors differ, and it is the transport's asymmetry rather than a divergence: the AMQP
worker claims one job at a time because that is how it takes them; the agent claims a BATCH in one
request before probing any of it. §8.4's "one genuinely new per-run round trip" is an upper bound
and pull comes in under it.

**A defect B1 shipped, found by putting a real generation-4 batch through the agent.**
`resolveStampedGenerations` bounded the server's stamp by the ENVELOPE-derived generation, which
caps at 3, while the agent polls `/v4/jobs`. The first generation-4 row a core stamped made it
reject the WHOLE claim response and claim nothing — **a pull region on the ledger carrier would have
stopped executing entirely.** B1 could not see it: nothing stamped 4, and its own tests omitted
`protocol_versions` and took the legacy fallback. The ceiling is now the endpoint actually called.

**Two senses of "late", and my assertion was the wrong one.** §8.6's "completed late" describes the
ROW — a window written as unfinished is completed rather than replaced; §14.1's `covered_late` is
`issued_at - due_at` above the interval that spaced the window. A run issued on time and merely slow
is `covered`. I asserted `covered_late` for it first, and the code was right. Conflating them would
have been an over-claim in the WITHHOLDING direction — safe, and still wrong: every slow probe would
forfeit its stroke.

**D — retention, `ledger_from`, the read API, the measurement.** Retention drops a dated partition
only once its whole range is past the cutoff AND deletes what leaked into the DEFAULT partition,
which the gate ledger's retention never has to do and this one must, because the default exists
precisely so an insert is never lost. `ledger_from` is computed from four inputs and never stored;
the mutation that proves it is the one that makes the bound ignore the partition floor, because
that is exactly how a stored bound behaves. The cursor is VERSIONED, which the gate ledger's is
not — a change to its shape there could only be found by a caller getting wrong pages.

**E — the stroke's rule, and the render that is deliberately not written.** §14's gate is
`strokeSegments`: every window in a span plain `covered`, the whole span at or after `ledger_from`,
a span with no windows drawing nothing, and `interval_assumed` never consulted. It returns SEGMENTS
rather than a boolean, because a monitor with one unanswerable hour still has defensible strokes on
either side and refusing the whole series would understate what the ledger proves.

The RENDER is not built, and that is this project's rule rather than my judgement: `CLAUDE.md`
requires an approved UI mock before frontend code for any SPA surface, and how the line LOOKS —
what happens where a segment ends, whether the observation ruler stays, what a partially-strokable
series reads as — is exactly what a mock decides. "Implement without stopping" removes review
pauses, not the process the owner set. §17.10 states what the mock has to answer.

**One guard corrected, and the correction is the lesson.** The scheduler's ledger-read scan fired on
`purge_expected_runs_failed` — a LOG KEY that names the table without reading it. A guard that
miscounts its own subject fails on a correct tree and gets deleted by whoever is unblocking CI, so
it now looks for SQL keywords beside the name, and carries its own negative fixture in both
directions.

**And one harness failure that cost two false readings.** My mutation script restored the file on
its last line under `set -e`, so a FAILING test — the expected outcome of a mutation — exited before
the restore and left the mutation in the tree; the next run then read as three unrelated failures.
Worse, one restore used `git checkout <file>` on an uncommitted tree and discarded this arc's work
in two files, which had to be rewritten from the diff. The harness now restores from a `trap`,
never from git, and refuses to run without `CERBIX_TEST_DATABASE_DSN` — because the store package
SKIPS without it and a skip prints `ok`, which reads exactly like a surviving mutation.

## 6b. The one test this slice broke, and why the fix is a decision already made here

`TestGateMigrationDownRemovesEverythingItCreated` failed on THREE consecutive clean runs of this
tree and passed on TWO clean runs of a parked baseline on the same host, always the same way: `drop
probe database …: context deadline exceeded` at 47.5 seconds against a 45-second budget. I did not
report it as a flake, because a baseline that passes twice is not a flake, and B1's reviewer set the
standard for this exact situation by reproducing a failure from a parked baseline before accepting
that it was not a delta. Here the parking showed the opposite.

**What it actually waits on, measured rather than guessed.** Polling `pg_stat_activity` through a
failing run showed the drop parked on `IPC/CheckpointDone`, its duration climbing past 45 seconds in
two-second samples. `DROP DATABASE` forces a checkpoint and blocks until it completes, so on a
server that is mid-checkpoint it inherits however long that one takes. Requesting an explicit
`CHECKPOINT` first does NOT help — that statement waits for the in-flight checkpoint too, and spends
the same budget — which is why the first fix I tried was reverted rather than shipped.

**The decisive observation was in the same run's log.** The `tzprobe` probe database's drop waited
**47.8 seconds** and its test PASSED. Its cleanup uses a three-minute budget and carries a comment
that reached this conclusion first: *"`DROP DATABASE` queues behind the catalog work of every other
package creating and migrating databases during a full `-race ./...`, and a 30-second budget failed
the test for a reason that says nothing about the code under test."* So the same operation was
already tolerated at one site and not at its twin: one helper had been fixed and the other kept 45
seconds. B2 adds about five percent to this package's work — roughly fifty new tests, each with its
own migrate-open-truncate — and that was enough to turn the untouched site into a reproducible
failure.

The fix is to apply the ruling this repository already made, at the site that was missed. It is not
a widened tolerance for a real defect: the drop is still MANDATORY and a leaked probe database still
fails the test, because a leak must be visible. What changed is that a cleanup no longer fails a
migration test for the state of the server's checkpointer.
