## 3. B1's entry gate, corrected twice before any B1 code

**[342] P0-a — invariant 10i was assigned to a phase that cannot prove it.** 10i requires that a V4
delivery missing its defining payload is dead-lettered rather than probed. But a V4 delivery is
*defined* by `DueAt`, and `dispatch.CheckJob` carries `JobID` and `IssuedAt` today and gains no
`DueAt` until B2. So in B1 there is no field whose absence is detectable, nothing publishes V4 at all
while `ledger.carrier_enabled` is false, and the test would have to hand-craft a publish that
production cannot make. The gate named a proof its own phase cannot produce. Expanding B1 to meet it
would smuggle B2's payload into a deliberately inert carrier phase, so 10i moved to B2 — where §16
already puts the payload and the ledger atomically — with **both its mutations kept named** in §17.4
so B2's gate inherits the analysis.

**[342] P0-b — the carrier migration had no rollback guard, and no invariant asked for one.** B1
widens `pull_jobs_protocol_version_check` and its `pull_tests` twin to `IN (1, 2, 3, 4)`, so its DOWN
narrows them again while generation-4 rows may still be pending. None of the previous 66 invariants
said anything about rolling back. Invariant **10j** now does, and 00063 had already written down what
goes wrong: its own first draft "said 'drain first' and then unconditionally DELETEd them, which is a
destructive write-off wearing the words of a safe rollback".

Its second claim is the one worth keeping. Deleting the guarded `DO`-block and letting
`ADD CONSTRAINT` fail on its own **still fails closed** — so an assertion of "the DOWN errored"
passes, while the operator is left with `check constraint ... is violated by some row` and no
procedure. The weaker assertion admits the weaker code, which is the same lesson as asserting the
`Dispatcher` interface's exact method SET rather than "contains no method called `Ack`".

Specifying this one gate has now caught three invariants contradicting the tree — 13a's four bump
sites, 11's "no ack concept" clause (`internal/agent/agent.go:290` and `:329` hold a lease-ack that
predates this requirement), and 10i's phase. That is the argument for gating at ENTRY rather than at
close: at close, the code would already exist and the test would be shaped to fit it.

**The third transport was missing from the rollout plan.** *Recorded while this iteration is OPEN,
after the commit that closed §1–§3's tasks; the reviewer's [353] admission was superseded by [356]
because of it.*

§13.0 enumerated the surfaces a V4 carrier has to grow — AMQP queues, pull rows, pull claim,
scheduler admission, enqueue — and asserted that "isolation is physical, not a filter, and that
distinction is the acceptance test". Both are true of the two transports that HAVE a wire, and I had
stated the claim generally, including to the reviewer. **In-process has no wire:** `CarrierGeneration`
is the job's own `ProtocolVersion` (`internal/dispatch/inproc.go:34`, and `internal/cli/cli.go:255`,
whose comment already said it — "no wire between the materializer and this runner, so the job's own
protocol version IS the carrier generation"). Inertness there rests on the flag, never on isolation.

`role=all` is also a PRODUCTION topology — `docker/docker-compose.prod.yml` line 1, "single-process
(--role all)" — and this project has already made **both** possible mistakes at exactly that
admission site, each recorded in `internal/scheduler/scheduler.go`'s own comments: a generation
raised "on the strength of a runner that will never see the job", leaving a pull region's monitor
with "no outcome at all until the row's TTL"; and, without the converse same-process rule, a
`role=all` that "never moved past generation 2", so the amendment was "inert in the most common
deployment". A ledger inert under `role=all` would be inert for most installations.

Two invariants follow. **10k (B1)** asserts the flag's inertness at the SOURCE rather than once per
transport, because all three transports read what the producer stamped and three sink-side assertions
would still miss the producer. The assertion sits on **`lead()`'s resolved map** — the three
`carrierGeneration[region]` branches at `scheduler.go:1514`, `:1529` and `:1552` all write one map
built at `:1500` in that function — so the gate reads its OUTPUT, never a branch. **10l (B2)** owns
the raising rules, where the flag is true; its two mutations are the two V3 failures above, verbatim.

10k's first draft carried a second claim, "the flag is read at resolve time, not at build time",
struck on reviewer P0-2 at [361]. Proving it means flipping the flag and watching the second resolve
change — which needs the flag ON, and B1 is defined by its being off. **That is the same defect as
10i**, which this iteration had diagnosed two revisions earlier and which I then reproduced: a gate
naming a proof its own phase cannot produce. The pattern is worth stating once, since it has now cost
two rejections — when a phase is defined by a capability being OFF, every assertion about that phase
must be provable with it off, and any claim of the form "flipping it changes something" belongs to
the phase that flips it.

Also corrected while checking every line citation in §13.0, since `make docs-check` validates paths
and `Test*` names but never line NUMBERS: `jobsQueueForGeneration` was cited at `:127` and is at
`:152`. The other four hold — including `agentJobsV3` at `:119`, which I nearly "corrected" to `:41`
before noticing that `:119` is its doc comment and `:41` the route registration.

## 4a. B1-M, the first code of phase B1

*Recorded while this iteration is OPEN.* The reviewer admitted B1 at [366] but **sequenced the
migration first**, because 10j is the only row in the phase with an irreversible failure mode: a
rollback that discards pending work cannot be undone by fixing the rollback afterwards. Landed at
`2fcf2b9`, reviewed at [369].

`00101_pull_carrier_generation_4.sql` widens `pull_jobs_protocol_version_check` and its `pull_tests`
twin to `IN (1, 2, 3, 4)` — widened rather than dropped, for 00063's stated reason: the claim
predicate selects by `protocol_version <= capability`, so a row carrying a generation nobody declares
is invisible to every agent. The DOWN refuses while generation-4 rows exist and deletes nothing.

**The migration says what its guard is NOT**, which is the part worth keeping: narrowing the `CHECK`
would fail on its own, because `ADD CONSTRAINT` validates the rows already there. The `DO`-block's
contribution is a message an operator can act on — without it the failure reads "check constraint …
is violated by some row", naming no count, no table and no procedure. The count is reported per
table because it LOCATES the pending rows for an operator — which of the two surfaces holds them.
The reviewer kept that as operational truth at [369], and at [371], [374] and [376] removed drain
mechanics from this narrative three times: first a claim of mine that was false, then a true one that
was still the wrong KIND of claim here. Correcting a statement's truth value is not the same as
correcting its class, and the runbook owed at B1 close is where procedure belongs.

Five tests, 8 mutations killed, all in §17.5. **The eighth is the one that changed a test.** Mutation
2 — "drain first", `DELETE` then narrow — was killed by the *"the Down succeeded"* assertion, which
meant the row-survival assertion had proved nothing: it was never reached. So the shape where only it
can catch was built and run — `-- +goose NO TRANSACTION` plus a `DELETE` before the guard, so the Down
still refuses and the rows are gone anyway. It reports `pull_jobs holds 0 generation-4 row(s) after
the refusal, want 1: the Down discarded work`. **An assertion earns its place by killing something no
other assertion in its test kills**, and the only way to find out is to try.

Two rulings from this slice worth carrying forward. **A test in an uncommitted tree has not
discharged an invariant** ([368]) — which is why 10j's audit row moved to `DISCHARGED` only after
`2fcf2b9` existed, in a separately reviewed docs update rather than inside the code commit. And the
discharge guard is now **parameterized over (section, test file, row)** rather than copied for the
second case: a guard that gets copied per case is a guard that drifts per case. Closing that also
closed a hole it had inherited — a missing section returned silently, so deleting §17.3 or §17.5
wholesale would have left the row still advertising its counts with nothing checking them.
