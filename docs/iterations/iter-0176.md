## 1. What was measured, before anything was written

Six `advance_expectations_failed` errors in seven minutes of ordinary browser-suite load on a live
`role=all` stack, every one of them `deadlock detected (SQLSTATE 40P01)`. Postgres named both
participants and they are this ledger's own two writers: §7.1's advance and §8.3's fill.

On that instance **every window claiming `expected_never_issued` was false** — two of two, each
contradicted by a heartbeat inside its own window, on enabled monitors that were up. `make dev-test`
passed **68 tests and skipped 1** — the idle file-provider case — while both facts sat in the table.

## 2. The chain, which is longer than the deadlock

1. The advance fails. `monitor_schedule.next_due_at` stays where it was, and `lead()` logs the error
   and DISCARDS the batch's payload — including the identity of jobs it had already published.
2. The next tick calls `LoadDueExpectations`, which reads `next_due_at` FRESH every tick, and mints
   the job's `DueAt` from the value that never moved. The job is published carrying a window that
   has already been answered.
3. Its result reaches §8.3, whose target row already carries a different `job_id`, so
   `expectedRunAdmissibleSQL` refuses it — correctly — and zero rows affected is a documented normal
   outcome. **The run correlates to nothing and leaves no trace**, not even a refusal.
4. The next successful advance computes `first_expected` from the stale instant and materializes the
   window the run actually answered as a GAP.

One failed advance therefore produces TWO wrong outcomes: a real result that reaches no window, and
a fabricated absence at the instant it answered. `lead()`'s own comment said "the residual points at
withholding"; the mechanism beside it asserted that no run happened, which is the opposite.

## 4. What phase F is

**The tick becomes RESERVE → PUBLISH → CONFIRM.** §7.1's statement moves AHEAD of the dispatch: it
writes the window with its minted identity in the `reserved` state, moves `next_due_at`, materializes
the gaps that move passes over, and writes the fence — one statement, as before. An instant is now
either recorded or the schedule never passed it, so **a gap cannot cover an instant a job was
published for, because the publish cannot precede the row.**

`issued_at` is written by the CONFIRM and by nothing else. §8.3's fill may not write it on a row
carrying `reserved_at`, so an early terminal — ordinary on the in-process transport — leaves it NULL
and reads `covered`, which is honest: the run happened and completed.

**The state the model did not have.** A reserved window may read neither absence verdict:
`expected_never_issued` asserts that no run happened, which is the opposite of what is known, and
`issued_never_claimed` asserts that a job was PUBLISHED, which is exactly what it cannot say. Hence
`reserved_at`, `withheld_reason`, and the verdict `reserved` — no stroke, excluded from the coverage
numerator, counted in its denominator.

**One materialization, one identity.** The `CheckJob` is materialized once, by the reserve, and the
wire carries `reserved_at` as its `JobIssuedAt` — so an executor echoes an instant the core already
made durable, which is invariant 20e held structurally rather than by a merge expression. No publish,
confirm, retry or handover may mint a second `job_id` for a reserved window; a new leader does not
republish one, at the accepted cost of one lost probe per reserved window across a handover.

**The batch is not the unit — the window is.** `ReserveExpectations` returns the windows it wrote,
not a count, and a dispatch leaves the process only if its own `(monitor, due_at)` is in that set.
An ERROR leaves the payload held unchanged, because commit status is unknown; a SHORT result drops
the fenced payload, because it was written nowhere and the revision it names is stale.

## 5. What implementing it found in the design

**Advance rule 2 cannot survive the reordering.** It said a failed dispatch records nothing, which is
unreachable once the window is written first. Worse, it left `nextRun` untouched so the next tick
retried at once — correct while nothing was recorded, and a defect generator afterwards: the
expectation has already moved, so the monitor would be due every tick and would reserve a window per
tick for the whole of an outage. The in-memory instant now follows the durable one, and the stated
cost is that a failed publish costs one interval instead of one tick.

## 6. What the panel had been doing since phase E

Drawing the mock for `reserved` found that `expectationCells` mapped three verdicts and sent
EVERYTHING ELSE to the `--down` outline that means "a run was due here and nothing ran" — so
`unknown`, `issued_never_claimed` and `claimed_never_finished` were all drawn as missed runs. The
phase-E mock's own verdict table had assigned `unknown` the HATCH, so the implementation had diverged
from the drawing it was approved against, in the direction of over-claiming.

**On the shipped default the consequence is total**: with `ledger.carrier_enabled` off every window
reads `unknown`, so the expectation ruler drew a full row of missed runs on an instance where nothing
was missed.

One full `-race` run came back FAILED — **108 failures, every one in `internal/store`, all with the
signature `org: store: conflict`**: a unique-constraint conflict creating a fixture organization.

**It is invalid rather than green and it is not a product finding**, and it stays in this record
rather than being replaced silently (reviewer at [46]). What replaces it is a run whose preconditions

zero connections to the test database, and a fresh database so nothing survives from the collision.
`pgrep -af` plus the database's own connection count is the check that works; `pgrep -c` with a
pattern that does not match returns zero and reads exactly like "nothing is running".
