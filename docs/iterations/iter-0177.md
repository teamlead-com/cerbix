Reviewing it would be reading code that is gone.

What was asked for instead, and accepted by the reviewer at [62] as a fresh audit rather than a
retroactive disposition: **read the ledger's write path and read path as they stand, as code that
will run in production.** Store statements and both migrations, the ingest claim and terminal fill,

## 4a. The count drifted three times, so it is derived now

`iter-0177`'s finding count went wrong three times in one evening, each time in a document rather
than in code. The line that opened this iteration said three; the line that closed it said four and
left the opening clause standing, so one sentence carried both; and `docs/traceability.md`'s head
said three — written at the moment the fourth finding was being fixed, which is the fourth finding.

`make docs-check` was green over every one of them, and that is not a failure of the guard: a
citation check validates that what IS written resolves, and cannot see a number that has stopped
agreeing with its own table.

So the number is derived rather than repeated. `check_iteration_finding_counts` reads the findings
table above and fails the build when any document naming this iteration states a different count —
the same treatment §17.2's totals were given after they drifted, for the same reason: **a total
written beside its own table is the one number nobody re-derives.** Proven by putting the stale
count back, which fails with the document, the stated number and the derived one.
