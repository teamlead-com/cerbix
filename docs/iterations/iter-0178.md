## 1. The defect: two halves of one topology disagreeing about credential envelopes

`make dev-test-distributed` failed on the tree that had just passed every other gate:

```
  1 failed
    [chromium] › probers.spec.ts:49:7 › probers against the stack itself ›
      test-connection probes postgres/tcp instantly; unknown region → 502
  1 skipped
  10 passed (1.3m)
```

The API answered `no worker queue for region "core" (AMQP 312 NO_ROUTE)` for a test-connection
against a region whose worker was up, healthy and consuming.

**It had nothing to do with the code being tested.** The distributed topology mounts
`config.dev.yaml` in `api` and `scheduler`, and `config.worker-core.yaml` in `worker`. The first
carries `secrets.dispatch_envelope: "enforced"`; the second carried no `secrets` block at all. So
the API published a credentialed test onto the v2/v3 carrier — `EnvelopeEnforced()` decides which
prefix a publish takes — while the worker, with the same predicate reading false, had started only
the v1 consumers. Nothing was bound to the queue the publish named, and RabbitMQ said so.

**The generalisable part, and the reason this is written down rather than just fixed:** a
capability whose two halves live in two configuration files is not covered by any test that reads
one file. Both sides had tests. The *agreement between them* had none — the same wiring-boundary
shape D-0239 recorded earlier in this arc — a builder defined, documented, and never called.
Both ends proven; the wire proven by nothing.

The second-order fact is worse than the failure: **FR-020's credentialed dispatch was exercised
only by the single-process stack.** In the topology that most resembles production it had been
broken for as long as `config.dev.yaml` has enforced envelopes, and nothing said so, because the
one gate that would have noticed is not part of `make dev-test`.

## 2. The fix, and the boundary it does not cross

`docker/config.worker-core.yaml` gains two blocks:

- `secrets: {enabled: true, dispatch_envelope: "enforced"}` — the executor now starts the v2/v3
  consumers, so it serves the carrier the API actually publishes on.
- `security.dispatch.regions.core.primary` — the same fixed, public, DEVELOPMENT-ONLY key id
  `dev-2026a` that `config.dev.yaml` seals with. A keyring that does not match is worse than none:
  it accepts the delivery and fails to open it, later and less legibly.

It does **not** gain `security.encryption_key`. The at-rest master never leaves core; an executor
holds only its own region's dispatch keys, so a leaked executor exposes at most that region's
payloads. `ValidateSecretsForRole` already refuses a worker config carrying the master or
`previous_keys` — the regression below pins that it stays refused, because the easy wrong fix for
this defect is to copy the whole `security:` block across.

**Geo is deliberately unchanged.** The reviewer's scope grant named the geo worker too, on the
assumption that it had the same split. It does not: `config.geo.yaml` (the geo central role),
`config.worker.yaml` and `config.agent.yaml` carry no `secrets` block at all, so that topology
publishes generation-1 carriers and its executors have nothing to open. "Matching the API" there
means changing nothing. Handing the geo worker a keyring would start consumers nobody publishes to
— configuration that looks configured and does nothing.

**Recorded as an open coverage gap rather than a passed gate** (reviewer, party [113]): FR-020's
credentialed dispatch is not exercised by the geo topology at all. That is pre-existing, it is not
a regression, and it is not closed here.

## 3. The regression, and the four mutations that prove it reaches its mechanism

`TestDevRoleConfigsKeepAtRestMasterOutOfWorker` in `internal/cli/compose_wiring_test.go` loads both
real files through the real `config.Load` and asserts in both directions: the two sides agree on
whether envelopes are enforced, and when they do enforce, the executor holds the API's core key and
does not hold the master.

Each mutation reverts exactly one property of the fix. All four were planted and killed:

| # | Mutation | The assertion that failed |
| --- | --- | --- |
| M1 | remove the executor's keyring (the shipped state) | `secrets.dispatch_envelope: "enforced" requires at least one security.dispatch keyring` |
| M2 | executor stops enforcing, so the two sides disagree | `secrets.dispatch_envelope must be empty or "enforced": "off"` |
| M3 | keyring present, but not the id the API publishes with | `the executor's core key "dev-other" is not the one the API publishes with ("dev-2026a")` |
| M4 | executor handed the at-rest master | `worker config must not carry the at-rest master keyring` |

M3 is why the assertion is not "a keyring is present". M1 and M2 fail inside `config.Load` rather
than in the test body, which is worth naming honestly: for those two the *validator* is the guard
and the test's contribution is that it loads the file at all. M3 and M4 are the test's own.

## 4. What the fix uncovered: the generation-3 test carrier accepted nothing

The rerun was red again, and differently. The routing was repaired — the queue existed and had a
consumer — but nothing answered:

```
POST /api/v1/projects/…/monitors/test  →  502  {"error":"no worker responded in region \"core\""}
dur_ms = 10008
```

`serveEnvelopeTestsOnce` in `internal/dispatch/amqp.go` serves BOTH envelope test carriers —
`serveTestsGeneration(&d.testsV2Once, …, ProtocolV2, …)` and `(&d.testsV3Once, …, ProtocolV3, …)` —
and its admission check compared the delivery's own field against a hardcoded constant:

```go
if err := json.Unmarshal(msg.Body, &job); err != nil || job.ProtocolVersion != ProtocolV2 || job.CredentialEnvelope == nil {
    d.deadLetter("tests.v2", msg.Body)
    _ = msg.Nack(false, false)
```

So **every generation-3 Test Connection was dead-lettered by the consumer bound to its own queue.**
The caller is answered only on success, so it waited out its timeout and reported the region as
having no worker — the same sentence an operator gets when the region really is empty.

Not inferred. `checks.dead` held exactly one message, read through the management API:

```
header x-cerbix-source: "tests.v2"
"protocol_version": 3,
"credential_envelope": {"v":2,"region":"core","key_id":"dev-2026a", …}
```

The dead-letter label was hardcoded too, so the header named a carrier the message had not come
from.

**Why it survived, which is the same geometry as §1.** The v2 carrier has a test
(`amqp_test.go:135`) and it passes, because the hardcoded constant happens to be its generation.
The v3 carrier had none. The inproc dev stack never takes this path. The one gate that does is
`make dev-test-distributed`, and it was red for §1's reason, which masked this one. The comment the
wiring's own author left at `cli.go:1211` reads: *"A published generation with no consumer is a
queue that fills until TTL, which is how 'generation 3 for jobs only' would have silently broken
Test Connection."* The consumer was wired. It admitted nothing.

## 5. The dispatch fix and its regression

The body is no longer asked about its generation at all — **the queue is the generation**, exactly
as the jobs path already states in its own comment (§4.7, D-0160: *"the body's own ProtocolVersion
is attacker-editable … the payload's claim is never consulted here"*). The test path was the one
place that contradicted it, and it was wrong in both ways at once: it trusted a field it should not
have, and it compared that field to the wrong value. What remains is the single property a
generation ≥ 2 test carrier is DEFINED by — it carries a credential envelope. The dead-letter label
is derived from the generation by `deadLetterSourceForTests`.

`internal/dispatch/amqptestcarrier_test.go`:

- `TestEveryTestCarrierAnswersOnItsOwnQueue` — a table over EVERY test carrier (v1 plain, v2 with
  envelope v1, v3 with envelope v2), one runner behind all three exactly as `cli.go` wires them.
  A reply proves the delivery was admitted; the `CarrierGeneration` stamp proves the right consumer
  admitted it. Live broker, opt-in on `CERBIX_TEST_RABBITMQ_URL` like its neighbour.
- `TestTheTestCarrierTableCoversEveryServeEntryPoint` — a `go/ast` scan of `amqp.go` for every
  exported `ServeTests…` method, requiring a row in the table. **The set, not the count**: a fourth
  test carrier cannot be added and left unreachable the way the third was. Runs with no broker.

| # | Mutation | The assertion that failed |
| --- | --- | --- |
| M5 | the hardcoded `ProtocolV2` admission check restored | `v3_envelope_v2: test RPC on carrier 3: no worker responded in region "testcarrier"` — the production symptom, word for word |
| M6 | the v3 row dropped from the table | `test carriers with no row in testCarrierTable: [ServeTestsV3]` |

**Stated rather than left unsaid**, two things this does not do:

- The dead-letter LABEL is diagnostic text and no test asserts it. It is correct now; it is not
  guarded.
- **A refusal is still silence.** The consumer answers only on success, so any future
  dead-lettered test still reaches the operator as `no worker responded in region …`, which is
  indistinguishable from an empty region — and that indistinguishability is what cost this arc a
  debugging cycle rather than a glance. Changing it means replying with a `ProbeError` heartbeat,
  which is a change in wire behaviour, outside the scope granted for this iteration, and is
  recorded here as an open item rather than done quietly.

## 6. NFR-025c: the hand-rolled date surface, and three claims about it that were false

The requirement's last open half. `func-truthful-rendering.md` §9 had it enumerated — 46 matches
on 26 lines across 13 product files, bounded by a per-file ratchet with a reason each — and the
enumeration is where the interesting part turned out to be. **The decisions are in §9's table;
what belongs here is what the enumeration got wrong.**

1. **"day-grid MAP KEYS … never rendered" was false for all three strips.** Each 90-day strip
   wrote `label: key`, and that label is a tooltip: `2026-06-08 · no data`. The key and the
   rendering were the same string, so exempting the key exempted a rendering. Split now —
   `utcDayKey` for the lookup, `utcDayLabel` for what a reader sees — and pinned by a surface
   assertion in `MonitorDetailView.spec.ts`, because no source guard can catch this one:
   `utcDayKey` is a legitimate call.

2. **"already honest in its own words (` Z`)" pointed at dead code.** `clockSecondsLabel` was
   exported from `lib/changes.ts`, documented as the honest one, and called by nothing in the
   repository. Deleted rather than moved.

3. **A site was missing from the enumeration entirely, and the ratchet is the reason.** Its idiom
   required the slice to be CHAINED onto the call, so this, in `lib/changesTimeline.ts`:

   ```ts
   const s = d.toISOString();
   const clock = s.slice(11, 16);          // "16:40" — rendered to an operator, no zone at all
   ```

   was never counted. **It was found by reading, not by the guard whose purpose is to make reading
   unnecessary.** That is the finding worth keeping out of this whole half: a bound expressed as a
   count over an idiom is only as good as the idiom, and an allow-list of thirteen entries reads
   as thoroughness while the hole sits outside it.

So the ratchet is **replaced by an absolute guard**: outside `lib/wallclock.ts` (renderings) and
the new `lib/datekeys.ts` (keys, wire values, control values), no product file calls `toISOString`
or pulls a field off a `Date`. Nothing to enumerate, no list to rot, and an indirection cannot
walk past it because the CALL is banned rather than the shape. Closing it cost ~20 mechanical
substitutions to `isoInstant` at request-body sites, which is the price of the guard being
absolute.

Four guards sit beside it, each answering a way the first one could be green while wrong: every
export has a real caller; every zone-less renderer pins the literal `"UTC"`, selected by
SIGNATURE and not by name (`utcCellExtentLabel` takes a `zone` and is local by contract — a
name-based scan flagged it, which is how that selector was found to be wrong); both owner modules
are asserted to exist AND to contain the banned idiom, so the exemption is load-bearing rather
than a typo; and the three strips are held to the key/label split.

| # | Mutation | The assertion that failed |
| --- | --- | --- |
| N1 | `phaseInstantLabel` back to slicing a `toISOString` held in a variable — **the case the old ratchet missed** | the absolute guard, naming the file and the call |
| N2 | one panel back to a bare UTC date | the absolute guard |
| N3 | a zone-less renderer drops its pinned `"UTC"` | `a zone-less renderer that does not pin UTC renders in whatever zone the viewer has` |
| N4 | an export loses its only CALL, keeping its import | `utcMillisLabel is exported and nothing calls it` |
| N5 | a strip tooltip shows its lookup key again | the key/label split guard AND the surface assertion |

**N4 survived its first version and that is recorded rather than tidied:** the caller check matched
the bare name, and an unused `import` line satisfied it — which is precisely the state a removed
call site leaves behind. Import statements are stripped before the check now.

**Zone-independence is evidence, not a claim:** the whole frontend suite runs green at `TZ=UTC`
and again at `TZ=Asia/Yekaterinburg` — 653 tests over 52 files, both times.

### 6a. A fourth false claim, in this iteration's own prose — reviewer finding on `0a1557c..d0a8fed`

`wallclock.ts`, §9 of the specification, `status.md` and `traceability.md` all said **"ONE SUFFIX,
decided once: every human-facing UTC rendering ends in ` UTC`"**, carving out `utcInstantLabel`
alone as the canonical `Z` form. `utcSecondsLabel` and `utcMillisLabel` were added beside it in
this same iteration and return `2026-08-28 14:03:02Z` and `2026-08-28 14:03:02.417Z` — the carve-out
did not follow them, and the tests expected exactly what the sentence denied.

**Not a zone leak:** `Z` designates UTC unambiguously and those four exist so an engineer can paste
the value into a log query. The mechanism is right; the sentence about it was false. That is the
defect class this arc keeps producing — prose promising what the code beside it does not do — and
it survived a mutation-verified guard suite because no guard was pointed at the claim.

The rule is a TEST now: `wallclock.spec.ts` CALLS every zone-less renderer and requires each to end
in ` UTC` (a phrase) or in `Z` (a canonical instant), with the two buckets checked against the
module's own exports in **both** directions — so a new renderer cannot be added until somebody
decides which form it is in, and a rename cannot leave a stale entry behind. Three further
mutations, all killed:

| # | Mutation | The assertion that failed |
| --- | --- | --- |
| N6 | `utcSecondsLabel` moved into the phrase bucket — **the claim exactly as it was written** | `utcSecondsLabel -> 2026-08-28 14:03:02Z: expected … to match / UTC$/` |
| N7 | a renderer added to the module and to neither bucket | the export list AND the bucket set, both by name |
| N8 | a phrase renderer drops its suffix | `utcClockLabel -> 14:03: expected '14:03' to match / UTC$/` |

**The generalisable part:** this is the same shape as the zone-argument guard at party [199], whose
hand-written list stopped covering two exports added later. A claim about a SET, written as prose,
outlives the set. Every one of those should be a derivation.
