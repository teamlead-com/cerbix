## 1. What this package is

A two-axis review of `v0.1.8..main` — 133 commits, ~34,700 added lines outside `internal/web/dist`
— found 52 defects that no single arc could see, because each lives at a seam between two arcs
built separately. Three are P0: a canary's project secret surviving an `https`→`http` redirect, a
canary whose region has no capable executor never going DOWN, and a carrier stamp one producer
branch never applies.

The common shape is not carelessness. Each arc built a correct mechanism and then relied on a
SENTENCE to connect it to the arc beside it — a docstring, an interface comment, a test name, an
allow-list idiom. The clusters below each replace one sentence with something the compiler, the
schema or a test enforces.

## 2. The three P0s, and what makes each one closed

**A1 — an unstamped job is now unconstructible.** `internal/store/materialize.go` had three exits
and stamped the carrier on two. A type credentialed BY SCHEMA that yields no envelope field —
`promql` with `auth_mode: none`, `rabbitmq` with `mode: amqp`, both `CredentialForbidden` variants
— took neither the no-envelope exit nor the sealed one and left carrying protocol version 1 with
the window field still populated. The core then correlated it and the window recorded
`carrier_generation = 4` for a run that rode generation 1.

The fix is not a third call. The loop body became `materializeRow`, whose success type is
`stampedJob` — an unexported field with one constructor, `stampJob`, which is the only place
`dispatch.WithCarrier` is called in that file. A branch that returns without choosing a carrier does
not compile.

**B1 — every redirect hop is re-validated.** `canaryOrigin` normalised host and port, ignored the
scheme, and defaulted an absent port to 443 for both schemes, so `https://x` and `http://x` were the
SAME origin. `https` was enforced once, at write time, and never again. The hop predicate —
`domain.CanaryHopViolation`: scheme is `https`, a host is named, no userinfo — is now the write
validator's address-independent, non-template subset, stated once and enforced at both surfaces. A
failing hop is REFUSED, so the request is never made and no header leaves the process; the origin
comparison gained the scheme independently.

**B2 — a shortage is an ordinary result.** The dispatch-shortage path wrote through the bare
heartbeat insert, which touches no status, no confirmation counter, no transition outbox and no
service bucket. Its own docstring promised the opposite. Ruled by the owner on 2026-09-06: route it
through `RecordScheduledResult`. `InsertHeartbeat` was REMOVED from the scheduler's store interface,
so the old path cannot be restored by accident — it does not compile.

## 3. The two decisions that did not survive contact with the tree

Both are recorded in the spec's own item bodies, not only here.

**A2.** Its decision names `DeliveredJob` as the carrier source at three sites. At two of them —
`terminalCarrierGeneration` and `correlateExpectedRun` — no `DeliveredJob` exists: they run in the
CORE and receive a `domain.Heartbeat` from another process. The comment above
`terminalCarrierGeneration` already argues why carrying the executor's observation back would mean
putting it in the payload, "precisely the source the design forbids and the P0 that killed revision
6". Implementing the decision verbatim would have reversed a deliberate ruling.

What was built is its implementable content, in two halves: the PRODUCER stops reading its own
choice back off the body (`MaterializedExecution` reports the generation beside the job it stamped),
and the CONSUMER half is A3, at the one place a `DeliveredJob` exists. After A1 the residual
inference — a result that correlates proves generation 4 — is sound by construction rather than by
convention, which is exactly what it was not before.

**C4.** Its decision was "re-measure, then restate", and the measurement inverted the fact the retry
bound was sized from. Measured on the `role=all` dev instance over a full day: **20052** issued
windows at `carrier_generation = 4`, **20050** of them holding a `claimed_at` — 99.99%, against the
1.6% ("one claim across sixty-two windows") the old note recorded. The two without were never
reserved (`reserved_at IS NULL`): §8.3 ADOPTIONS, with no row for any retry to have matched.

The concession that had to be written down: under phase F's ordering a re-offer CANNOT convert an
unmatched claim into a matched one, because the window is committed before the job leaves the
process. The mechanism is kept and both comments now say so; removing it is a behaviour change, not
a re-measurement, and belongs to its own decision.
