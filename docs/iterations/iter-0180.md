## 1. The defect

An `async_canary` that declares a credential binding **could not run at all**. Every dispatch was
refused at the executor gate, and the monitor reported nothing but that refusal.

The chain, in the order it fails:

1. The scheduler nominates a monitor for credential materialization on
   `s.credentialEnvelopes && domain.CredentialedType(m.Type)`.
2. `CredentialedType` answers whether the TYPE carries a static FR-020 credential SCHEMA. An
   `async_canary` has none — its bindings are declared inside the workflow document — so it reads
   **false** even when the monitor has declared one.
3. The canary therefore takes the plain branch and is stamped with a generation that carries no
   envelope.
4. `ExpectedCredentialFields` nevertheless names `canary_secret_<binding>` for that monitor, so
   `dispatch.ValidateAndMaterialize` refuses the job for a missing field — **correctly**, and for a
   field the producer was never asked to supply.

Measured rather than reasoned, on the released tree:

    CredentialedType(async_canary)                              = false
    ExpectedCredentialFields(async_canary, canary_secret_*_ref) = [canary_secret_upload]

Two halves of one product disagreeing about the same monitor: one says it needs an envelope field,
the other says it needs no envelope.

## 2. Why no gate caught it

Nothing was broken by it. Every existing test passes on the defective tree, because no test dispatches
a canary that declares a binding: the canary suites use bindingless workflows, and the credential
suites use schema types. The live browser suite (70 passed) and the geo suite (14 passed) both ran
green over it. It is invisible to a green gate by construction — which is the arc's own subject, and
the reason the independent review was worth its cost.

## 3. The fix, and the one it deliberately is not

`domain.RequiresExecutionEnvelope(m Monitor)` is a new predicate at the MONITOR level, and the
nomination asks it instead.

**`CredentialedType` is not widened.** It routes by schema and every other caller — validation,
normalization, the expected-field set — depends on that meaning. Widening it would make a schema
router answer a dispatch question for a type that has no schema to route by, which is the same
substitution that produced the defect.

**A union, not a re-derivation, and the reason is a measurement.** The tempting definition is
"expects at least one envelope field", derived from `ExpectedCredentialFields`. It is wrong:

    promql   CredentialedType=true   ExpectedCredentialFields=[]   err=<nil>

`promql` has a schema and no required field, so that definition would have silently stopped
nominating it — repairing one type by breaking another. The schema half is therefore left exactly as
it was, and only the canary half is added.

The canary half is DERIVED from `canaryExpectedFields`, the same function that decides which canary
fields the envelope must contain, so the nomination and the envelope's contents cannot drift apart
about whether a binding was declared. A blank reference is not a declaration on either side, because
it is the same non-blank test.

## 4. The regression

`internal/scheduler/canaryenvelope_test.go`, three cases through the scheduler's own loop: a declared
binding is nominated, no binding is not, and a blank reference is not. The negative cases wait out a
window in which the positive one answers, so they prove a rule rather than a race.

**The killing mutation** is the defect itself: restore the nomination to `CredentialedType`. It fails
the positive case by name and leaves the two negatives passing, which is what makes it the mutation
for THIS rule rather than for canary dispatch in general.

**What this test does NOT assert, stated because the reviewer asked for it and it is not here.** He
asked for the seam through to publication — generation 3 with an `EnvelopeV2` and a successful
execution. This asserts the nomination only. The reason is measured: the credential capability is
resolved AFTER the loop that nominates, so at nomination time the carrier policy handed to the
materializer is still empty, and an assertion on it would have been about the harness. What
generation an announced region receives was, at the time this section was written, held only by
`ledgercarrier_test.go` and not for a canary; §4c below closes that half with
`TestACanaryBindingIsPublishedOnTheGenerationItsAgentAnnounced`, which derives generation 3 from a
live agent's announcement and asserts the enqueue. This sentence is corrected here rather than left
to read as an open gap it no longer describes — found by re-reading the report whole, which is what
five consecutive documentation findings had shown patching sentences does not achieve.

What remains open after §4c is stated there and not here: no single process holds all the segments
at once, and no live canary run demonstrates success.

## 4a. The sibling, found by asking where else the same substitution happens

The first repair is not worth much if the question it answers is asked in only one place, so every
product call site of `CredentialedType` was read against what it decides. Eighteen sites: fifteen are
schema decisions and correct. Two more were already unions — `materialize.go` and the executor gate
both name scenario and canary bindings beside the schema check, which is why the gate refused
correctly rather than letting a placeholder through.

**One was the same defect.** `MaterializeTestExecutionConfig` returns a generation-1 job — no
envelope — for any type `CredentialedType` reports false for, and `async_canary` is one. The API's
test-connection path had the matching fail-closed rule for a SCENARIO binding (FR-028 D10, "save the
monitor before testing it") and **none for a canary binding**, while refusing only `push` and
`composite` by type. So Test Connection on a canary that declared a binding went to a prober with
nothing to resolve it, and the operator met a message about a missing envelope field from the far
side of the dispatch instead of the one that says what to do.

The canary arm of that refusal now exists, worded like its scenario twin and naming the binding
rather than the secret it references. Its regression carries a real workflow document, because a
canary without one is refused by ordinary validation long before the rule under test — a fixture
that fails earlier would have proved nothing. The killing mutation is deleting the arm.

## 4b. The third defect, which the demanded test found and the first two repairs did not cover

The independent reviewer refused the regression in §4 and held the release (party [394]): it asserts
the nomination against a fake materializer, not the causal chain he had specified —
scheduler → materializer → publish, generation 3 with an `EnvelopeV2` and a successful execution.
He was right, and about more than rigour: **building the test he demanded found a third defect that
both repairs above leave untouched.**

Against the real materializer and the real store, a canary with a declared binding still failed —
`decrypt_failed` — and the cause was one level below the nomination:

    dispatch: execution binding: settings: monitor type "async_canary" has no credential settings schema

`ExecutionBindingKeys` knows about canaries: it names `workflow`, `canary_run` and every
`canary_secret_*_ref`. `CanonicalSettingValue`, which the digest builder then calls FOR EACH of those
keys, did not: it has explicit arms for the synthetic scenario key and scenario ref keys and none for
the canary's, so every key fell through to the schema resolver, which refuses a type that has no
schema. The digest could not be computed, `Seal` failed, and the monitor was refused with a reason
that names decryption — pointing an operator at a key problem that does not exist.

**So `v0.1.9.1` would have shipped the feature still broken**, with the nomination fixed and the
envelope unbuildable, and the §4 regression green over it. That is the exact failure the reviewer's
AC exists to prevent, demonstrated on the iteration that was arguing it could be deferred.

The canary arms are added, mirroring the scenario ones and for the stated reason: these keys have no
schema field and no canonical default, so the value is what the operator wrote, byte for byte, which
is what the digest must bind. Two killing mutations, one per arm.

**The MATERIALIZATION-AND-GATE SEGMENT is proved** by
`TestACanaryBindingIsSealedIntoAGenerationThreeEnvelope` (`internal/store`), against the real
materializer and the real executor gate: the job comes out on generation 3 carrying an `EnvelopeV2`,
and `dispatch.ValidateAndMaterialize` opens it and reports the credential as USED. That segment and
no more — this test neither publishes nor probes, which §4c states of it and an earlier version of
this paragraph contradicted by calling it end to end (reviewer P1, party [409]).

## 4c. The last link, and the one the product's own policy puts out of reach

The reviewer held the release again (party [396]): the scheduler test and the store test are
disjoint, the store test does not publish, and opening an envelope is not executing a workflow. All
three are true.

**The last link is now closed** by `TestASealedCanaryBindingIsOpenedByTheGateAndReachesTheTarget` in
`internal/prober`. The binding's value is DELETED from the monitor's config and exists only inside an
envelope sealed by a real keyring; the monitor handed to the prober is the one
`dispatch.ValidateAndMaterialize` produces; the real prober then runs the whole journey against
controlled servers, and the assertion is that the TARGET received the secret. Its mutation — probe
the pre-gate monitor instead of the materialized one — fails it, so the test depends on the gate's
output rather than on a value someone put in the config.

**The remaining gap is a property of the design, not an omission, and it is stated rather than
argued.** A single process spanning scheduler, store and prober is not reachable without a
product-level test seam that lets a canary dial a private address — and such a flag is the URL
policy's own bypass, which FR-029 refuses in v1 and as a hidden option. The evidence that this is
the product's standing position and not this iteration's convenience: the live canary E2E fixtures target `https://example.invalid/…` and
`https://canary-uncovered.internal.invalid/…` — RFC 2606 names that never resolve — and the live
suites assert the STAGE a journey fails at. **What that proves is narrow and is stated narrowly** (reviewer P1,
party [404]/[405]): the live cases that exist today do not demonstrate a successful canary run.
An earlier version of this paragraph said no canary has EVER executed successfully here, which
the fixtures do not establish — it is a claim about the repository's whole history made from a
snapshot of its current tests.

**And the link that was still taken on trust is now asserted too (reviewer, party [398]).** He
rejected the dichotomy above as false — correctly: an injected dialer is already a test-only seam, so
"either the production policy or no test" was an overstatement, and it is withdrawn. What was
genuinely missing was narrower and reachable: nowhere did the SCHEDULER derive generation 3 from an
announced capability. The store test handed it a policy and the prober test sealed a job by hand.

`TestACanaryBindingIsPublishedOnTheGenerationItsAgentAnnounced` closes it. Nothing is handed to the
scheduler: a pull region's live agent announces envelope v2 and the canary kind it can run, and the
two facts previously assumed are asserted — the carrier POLICY the materializer is called with, and
the generation the job is actually enqueued on. Two killing mutations: announce envelope v1 instead,
or restore the nomination to `CredentialedType`.

**Its first fixture described a monitor that cannot exist, and the reviewer caught that too (party
[400]).** The workflow was the stub `{"kind":…}`, which `CanaryCapabilityRequiredByConfig` accepts
while the write boundary rejects it — so the seam was proved for a permissive snapshot rather than
for the released monitor class. The fixture is a full canonical document now, with the binding used
in a header, and `Validate` is asserted BEFORE scheduling so it cannot drift back: restoring the
stub fails that assertion by name (`submit: unknown kind ""`) rather than passing quietly. The
distinction he drew is worth keeping — `workflow.secrets` is deliberately not persisted and the
binding lives in the flat reference key, so an absent `secrets` map is not itself the defect; the
defect was a document no prober could execute.

So the chain is four tests whose JOINTS are production types — the monitor, the job, the envelope,
the materialized monitor — while each test observes its segment through what that segment allows.
Said exactly, because "no fakes" appeared here and was false (reviewer P1, party [409]):

- nomination and capability-derived publication — `internal/scheduler`, observed through a
  `fakeStore`, which is what makes the announcement and the enqueue observable at all;
- materialisation through sealing and the gate — `internal/store`, with a REAL database, the real
  materializer and the real `dispatch.ValidateAndMaterialize`; no fake in this one;
- gate output through execution to the target — `internal/prober`, with the real prober and an
  INJECTED DIALER at the existing test-only seam, which is how any canary is tested here.

What is NOT covered is one process holding all of them at once, and a live successful canary run —
the latter being the same absence B1 already carries, for the same reason.
