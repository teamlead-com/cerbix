## 1. The defect

`POST /api/v1/status-pages/{pageID}/components` refused every service-backed component. **Creating
one was impossible through the API and through the SPA** — the only way a component could end up
bound to a service was to create it as something else and then CONVERT it.

Four places describe this feature and three of them agreed:

| Where | Says |
| --- | --- |
| `openapi.yaml`, `CreateComponent` | `service_id` is a property, and the description says "a service binding wins over a leftover monitor one" |
| `frontend/src/views/StatusPagesView.vue` | sends `body.service_id` when the chosen source is `service` |
| `domain.Component` | carries `ServiceID`, and `store.CreateComponent` INSERTs it |
| `internal/api/handlers_statuspage.go` | **did not name the field at all** |

`decodeJSON` calls `DisallowUnknownFields()`, so the request did not lose the field quietly — it
failed in the decoder, and the handler answered `invalid JSON body`. Reproduced by executing the
decode rather than by reading it:

    service_id  -> err=json: unknown field "service_id"
    monitor_id  -> err=<nil>

**The message is the second half of the defect.** The JSON was valid; an unsupported FIELD is not a
malformed body, and telling an operator otherwise sends them to look at their own payload. Nothing
in the response named `service_id`.

## 2. What no test could see

`fakeStore.CreateComponent` in `internal/api` already derived the service source, under the comment
"the source is DERIVED, never taken from the caller, and a service binding wins over a leftover
monitor one". The test double implemented the contract the handler did not — so every test in that
package agreed with the specification while the product disagreed with it, and none of them could
fail. The store half was likewise correct and simply unreachable.

This is the arc's own defect class from a new side: not prose promising more than the mechanism, but
a DOUBLE implementing more than the original.

## 3. The repair, and the hole it would have opened

`service_id` is accepted and passed to `domain.Component`. That alone would have been wrong.

`componentSourceOf` — the store's resolver for the ACTIVE binding — looked a binding up **by id
alone**. Tenancy of a create therefore rested entirely on the caller above it: the API checked a
monitor with `monitorInOrg`, and nothing checked a service, because no service binding could arrive.
Accepting the field without changing that is precisely the P0 §15.0 records: a direct writer binding
another organization's service to a component.

The resolver now scopes through `bindingProjectTx` — the SAME helper the conversion path uses, which
joins `projects` and filters on `org_id`. The two ways a component can acquire a binding now answer
the tenancy question identically instead of nearly so, and the monitor half gains in the store the
scope it previously had only by way of the API.

A binding outside the organization answers exactly as one that does not exist, for the reason
`monitorInOrg` has stated since FR-021: the difference between them is a cross-tenant existence
oracle. The flat `could not create component` is replaced by `binding not found`, which names the
class of problem without naming which id resolved.

### 3a. Two corrections from the review, made before this went anywhere

**A failed lookup is not an absent binding.** The first version of the resolver mapped EVERY error
from `bindingProjectTx` onto `ErrNotFound`. A connection failure would then have reached the
operator as `400 binding not found` — an answer that is not merely unhelpful but false, sending them
to look for a deleted service while the database was unreachable, and hiding the outage from the
error rate the API reports. `bindingLookupError` now translates only the refusal
`bindingProjectTx` OWNS (`ErrComponentConversionTarget`, its "no row for this organization") and
WRAPS everything else with its cause intact; the handler's switch ends in `h.serverError`, which
logs the cause and answers 500 without echoing it. This is the same defect shape §2 describes with
the sides exchanged: a classification that was right for the case the tests produced and wrong for
the case only production produces.

**Create and conversion now ask the same questions, in the same order.** Conversion asserts three
things about a new binding — that it is in the page's organization, that it is inside the page's
PROJECT when the page has one, and that the retained bindings can still share one `source_project`.
Create asserted the first and left the other two to the deferred constraint trigger, so an
out-of-project create failed at COMMIT with the trigger's own text rather than at the assertion with
a sentence naming the rule. `CreateComponent` now calls `assertBindingInPageScope` and
`assertRetainedBindingsSameProjectTx` itself. The page-scope call is guarded on a non-empty binding
project: a manual component has none, and asserting unconditionally refused every manual create on
a project-scoped page — caught by three existing conversion tests, which is what they are for.

## 4. Regressions

- `TestAServiceBackedComponentCanBeCreated` (`internal/api`) — the reported symptom, asserted at the
  surface: the create returns 201, the source is derived as `service`, and the binding survives the
  round trip. It fails explicitly on `invalid JSON body` so a regression reads as itself rather than
  as a status-code mismatch.
- `TestAComponentCanBeCreatedBoundToAServiceInItsOwnOrg` (`internal/store`, real database) — the
  store half that had never been exercised for a service.
- `TestACreateRefusesABindingOutsideThePagesOrg` (`internal/store`) — a foreign-org service, a
  service that exists nowhere, and a foreign-org MONITOR, all answering
  `ErrComponentBindingNotFound` identically.
- `TestACreateRefusesABindingOutsideThePagesProject` (`internal/store`) — a same-org service in
  ANOTHER project refused at the assertion with a message naming the scope, an org-level page
  accepting the same binding, and a manual component still creating on a project-scoped page.
- `TestALookupFailureIsNotAnAbsentBinding` (`internal/store`, no database) — the classification
  itself: a wrapped `ErrComponentConversionTarget` becomes `ErrComponentBindingNotFound`, an
  arbitrary error does NOT and keeps its cause. No DB test could ever cover this, because the DB
  tests only produce the absent case; that is exactly why the first version's mistake was invisible.
- `TestAnInfrastructureFailureIsNotABadRequest` (`internal/api`) — the same distinction at the
  surface: a store error that is no sentinel answers 500, and the response does not echo the cause.
- `TestComponentBindingIDsAreValidatedAtTheTransport` (`internal/api`) — malformed monitor and
  service ids each answer a field-specific 400 before a PostgreSQL UUID comparison can fail.
- `TestTheStoreOwnsMonitorBindingScopeValidation` (`internal/api`) — a valid monitor UUID reaches
  `CreateComponent` without the handler's former `GetMonitor` + `GetProject` preflight.
- `TestAnUnavailableBindingIsABadRequest` and `TestAPageDeletedDuringCreateRemainsNotFound`
  (`internal/api`) — the dedicated binding sentinel maps to 400 while repository `ErrNotFound`
  remains a page-level 404.
- `TestACreateWithBothBindingsRefusesAMismatchedPair` (`internal/store`) — a create carrying BOTH a
  service and a monitor, whose projects disagree, refused with a sentence; the control, both in one
  project, creates, the service wins the source, and the monitor is RETAINED rather than dropped.
  The SPA sends one binding, but the API is not the only caller and the row has one
  `source_project` column for both.

**Killing mutations — six, each applied to the product, run, and restored.** Each patch asserts its
own anchor matched before writing, because a mutation that never applied is indistinguishable from a
weak test.

## 4a. The guard caught the author

The first version of the API regression used the customer name from the bug report as its fixture
name, straight off the screenshot. `make docs-check` refused it by name:

    internal/api/componentservicebinding_test.go:27  [name]  a real customer/project name in
    example data — use a placeholder

That rule exists because a real project name once reached a spec, a mock and fixtures, and the guard
was added across the whole tree in response. It worked on the person who added it, which is the only
evidence that a guard is real rather than decorative. The fixture uses a placeholder.

## 4b. The repair broke an existing test's route to the mechanism

`TestComponentTenancyBySchema` case (b) — invariant 62 AT THE SCHEMA — reached the deferred trigger
`component_project_outside_page_scope` by calling `CreateComponent` with a cross-project service.
Giving create the assertion conversion already had means the application now refuses first, so the
full `-race` run turned red on a test that was asserting something my change did not alter:

    foreign component on a project-scoped page = store: invalid conversion target for this
    component: the page is scoped to one project and this binding belongs to another,
    want the page-scope guard

Left alone it would have made the Go assertion the thing under test, which is the opposite of that
test's name. Case (b) now INSERTs directly, like cases (a) and (d) beside it, so the trigger is
proven against the only caller it exists for — a direct writer — while
`TestACreateRefusesABindingOutsideThePagesProject` owns the application half. **Nothing was weakened
to make a test pass**: both layers still refuse, and each is now asserted where it lives.

## 8. Follow-up review corrections

A second review pass found four release-relevant edges and they are repaired on the same branch:

1. malformed `monitor_id`/`service_id` values reached PostgreSQL UUID comparisons and could surface
   as 500; transport now validates both with the package's strict UUID pattern;
2. repository `ErrNotFound` represented both a disappeared page and a refused binding, so a
   page-deletion race was mislabeled `400 binding not found`; the store now has
   `ErrComponentBindingNotFound`, leaving page absence as 404;
3. `monitorInOrg` duplicated the transaction's authoritative binding scope validation and added an
   asymmetric monitor-only preflight; it is removed, with transport owning format and store owning
   existence and tenant scope;
4. the live E2E created its service before entering `try`, so a page-create or decode failure leaked
   the fixture; cleanup now begins immediately after service creation and deletes the page only when
   it exists.

into D-0249, traceability, status and this report.
