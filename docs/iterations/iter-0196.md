## 1. Problem

At the base commit, one public CLI was split across a manual top-level switch, command-local standard-library
`flag.FlagSet` parsers, manual `gate`/`change` dispatchers, and duplicated usage strings. Root help was a flat
synopsis. `help <command>` ignored the requested command, most leaf help paths exited `2`, `gate --help` and
`change --help` were unknown subcommands, and `version --help` executed the version encoder. Required flags,
defaults, environment contracts, exit classes, and examples had no one command-tree owner.

The migration had to improve discoverability without changing the application contracts that pipelines and
operators use: documented paths, canonical long flags, types, defaults, requiredness, environment variables,
stdout/stderr behavior, and semantic exit codes. The approved exception is explicit: six leaves that silently
ignored positional tokens now reject them with usage exit `2` before side effects.

## 2. Approved design and architecture

The owner approved [`cross-cli-command-tree.md`](../specs/cross-cli-command-tree.md) on 2026-10-02 before
production code changed. D-0265 records the implementation boundary:

- Cobra owns the root, groups, leaves, lookup, arguments, flags, required metadata, and help;
- `Main(args []string) int` remains public and `cmd/cerbix/main.go` remains the only `os.Exit` site;
- typed options separate parsing from parse-independent executors;
- `ExitError` keeps exit mapping application-owned;
- root uses `SilenceUsage`, `SilenceErrors`, explicit output/error writers, and disabled suggestions;
- the public completion command and implicit version flag are disabled;
- `internal/config` remains the YAML/config owner; no persistent pre-run or global registry exists;
- Viper is excluded;
- gate/change credentials remain `CERBIX_URL`, `CERBIX_TOKEN`, and optional `CERBIX_CA_FILE`, environment
  only, with no credential flag, remote-server `--url`, insecure mode, redirect following, retry, or TLS
  bypass.

The resulting hierarchy is:

```text
cerbix
├── serve
├── migrate
├── reencrypt
├── adopt-fact-month
├── enqueue-service-repair
├── gate
│   └── check
├── change
│   └── record
└── version
```

`root.go` derives the grouped catalogue from this Cobra tree. `help.go` renders leaf/group sections from
command and registered flag metadata. One registration helper records order, placeholder, and required
annotation; synopsis, validation, and help consume it, while defaults come from the registered Cobra flag
value rather than a second usage list.

### Phase F — corrective parser-boundary hardening

Later verification invalidated the then-current clean-review and closure claims. Six defect classes were
confirmed against the committed Cobra tree:

1. Cobra `Find` stripped flags while locating commands, so root flags before a top-level command and leaf
   flags before `gate check` / `change record` reached executors instead of preserving the canonical raw
   command position.
2. Parsed `help=false` fell through to side-effect commands.
3. Cobra v1.10.2's Windows pre-execute mousetrap could call dependency-owned `os.Exit(1)` before
   `Main(args) int` returned.
4. `CompletionOptions.DisableDefaultCmd` did not disable hidden `__complete` / `__completeNoDesc` protocol
   commands created by `ExecuteC`.
5. The manual help pre-parser returned a generic flag error before `version`'s `FlagErrorFunc`, breaking the
   measured unknown-flag plus false-help JSON compatibility seam.
6. `SetHelpCommand` stored the custom help command but did not add it to the searchable tree until
   `ExecuteC.InitDefaultHelpCmd`; the earlier preflight `Find` therefore rejected compound help.

The common cause was split ownership around Cobra's runtime initialization: cerbix called `Find` and
`ParseFlags` before `ExecuteC` initialized help/completion, then Cobra repeated lookup and parsing with
slightly different state and precedence. The corrective RED suite proved command-position executor calls,
config-loader diagnostics, HTTP requests, completion protocol bytes, false-help execution, version
compatibility drift, compound-help failure, late help registration, and non-empty mousetrap configuration.
Existing characterization for unknown flag plus true help remained GREEN and was preserved.

The corrective implementation adds one narrow parser-boundary contract before `Execute`:

- walk only exact, available public command names in raw canonical position;
- reject root/group flags before command names and hidden completion protocol command positions before Cobra
  can initialize them;
- scan help using the selected command's registered flag arity, so help-looking string values remain values;
- retain independent `sawTrue`/`sawFalse`/`sawInvalid` facts: any parsed false-help assignment wins for
  root/groups/side-effect leaves/help regardless of repeated flag order, while only `version` keeps the
  false-help no-op and order-independent true-help compatibility exception;
- route preflight parse errors through the selected command's Cobra `FlagErrorFunc`;
- register the custom help command in the searchable tree during root construction and share one exact-path
  renderer between direct and compound help;
- disable `cobra.MousetrapHelpText` through one intentional process-global package-initialization assignment
  before Cobra's Windows `preExecHook`; this is distinct from per-command state and does not mutate
  `cobra.EnableCommandSorting`.

`parser_boundary_test.go` is table-driven and includes canonical/non-canonical positions, all required help
boolean forms, help/completion-looking string values, version executor counts, compound help and rejecting
writers, completion protocol output suppression, config diagnostics, counting localhost HTTP requests,
searchability before `Execute`, and the mousetrap guard. The focused corrective suite, complete
`internal/cli` suite, full repository/build/vet/Windows/race/docs/module/diff gates, and rebuilt-binary matrix
were GREEN before independent review.

That corrective high-effort review returned **CHANGES REQUIRED** with one Important and one Minor finding:

1. the classifier overwrote one enum value per help token, creating undocumented last-value semantics in
   which a later true-help erased an earlier false-help;
2. one spec sentence broadly denied any global Cobra mutation despite the intentional process-global
   `cobra.MousetrapHelpText = ""` assignment.

New tests first reproduced false→true success-help on root, leaves, groups, nested leaves, and compound help,
plus `version --help --help=false` incorrectly producing JSON. The classifier now retains independent true,
false, and invalid facts. Ordinary commands use any-false-wins; `version` treats false-help as a no-op, any
parseable true-help as order-independent help, unknown+true-help as usage failure, and every positional as
higher priority than help/JSON. String values remain excluded by registered flag arity. The documentation
now names the mousetrap assignment as intentional process-global package configuration before the Windows
hook and narrows the ordering claim to `cobra.EnableCommandSorting`.

The targeted re-review confirmed both findings fixed, then returned **CHANGES REQUIRED** for one remaining
Important version seam: non-unknown parse errors returned before `firstVersionPositional`, so
`version --help=invalid extra` emitted an invalid-boolean diagnostic instead of the positional diagnostic.
A dedicated permanent matrix first reproduced long/shorthand invalid values, both false/invalid orders,
unknown+invalid, end-of-options, help-looking post-dash, and literal `-` positionals with encoder calls fixed
at zero. `version.FlagErrorFunc` now checks raw positional input before classifying any parse error; invalid
forms without positionals keep their original diagnostics, unknown+true remains an unknown-flag error, and
unknown+false retains JSON compatibility. Final targeted re-review and separate owner sign-off remain
pending.
