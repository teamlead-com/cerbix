## Source

`BUG-0198-7` (TODO from iter-0198): monitor SLA windows longer than raw heartbeat retention report a
partial-history number as the window. Exploration at `46a76c7` found four readers of such windows —
`GET /monitors/{id}/sla`, `GET /projects/{id}/sla`, the status page's monitor-component
`uptime_90d` (`monitorpageprojection.go`, public) and the weekly SLA report (`projectSLI`, 7d/30d,
which a retention below 30 days also truncates) — and that `heartbeats_daily` is never purged, so
the frozen days needed to answer correctly exist.

## Review round 1 — CHANGES REQUIRED (Critical 0, Important 3, Minor 1)

All four findings were checked against the code and accepted.

| # | Sev. | Finding | Disposition |
|---|---|---|---|
| R1 | Important | The rule used the earliest raw heartbeat as a retention boundary: a young monitor with a raw DOWN yesterday, not yet rolled up, and an UP today read 1/1 (100 %) instead of 1/2 — on `MonitorSLI`, `ProjectSLI` and the status-page projection, with no purge involved. | **Fixed** — rule rewritten: the raw part is every raw heartbeat in the window, and the rollup adds only the whole days before the UTC day of the earliest raw heartbeat (purging is day-aligned in both modes — one-day chunks, daily partitions / midnight DEFAULT delete — so that day is whole whenever older data was purged). |
| R2 | Important | A rollup row for the window's START day was accepted as proof of older data: a monitor first seen after `S` on `S`'s own day was reported complete (no `data_from` / `uptime_since`), and its first-day heartbeat was dropped. | **Fixed** — completeness needs a rollup day strictly before `utc_day(S)` (or raw at/before `S`); the first-day heartbeat is raw and counts. The spec states the conservative consequence (a monitor created on `S`'s day before `S` and later purged reads as incomplete from that day — *wording wrong, corrected in re-review 1, RR1-2: `data_from` is the next counted day*). |
| R3 | Important | The monitor burn-rate long window (up to 7 d against a 2-day minimum retention) stayed raw-only — a reader missed by the inventory; reproduced paging on raw counts the full window never reached. Pre-existing. | **Fixed in scope** (same defect class, small change): `EvaluateBurnAlerts`' long window adds the rollup part; spec readers list, D-0268, status and traceability updated. |
| m4 | Minor | Comments still claimed THREE statements for the monitor projection. | **Fixed** in `monitorpageprojection.go` and `statusprojection.go`. |

## Re-review 2 — APPROVED (Critical 0, Important 0, Minor 0)

RR1-1..RR1-4 resolved, each verified by running and reading. The reviewer counted statements with a
pgx tracer (MonitorSLI and ProjectSLI one per window, burn one per window, the projection three in
all, one of them computing availability), showed the permanent purge-race test fails on both modes
when the round-1 split is restored by overlay, and probed the CTEs (empty project, no raw and no
rollup, raw only before the window, rollup-only monitor, mixed project, midnight boundaries, a
23:30 UTC heartbeat in a non-UTC session, poisoned rollup).

**Cost — my parity claim does not generalise, and is corrected here.** The figures I recorded above
(parity at 50 monitors) hold for that shape only. The reviewer's measurements, store readers only,
three runs:

| Shape | Mode | Base | Candidate |
|---|---|---|---|
| 50 monitors, 144 000 raw rows, four project windows | TimescaleDB | 197–208 ms | 199–209 ms |
| same | plain PostgreSQL | 140–171 ms | 186–245 ms |
| 500 monitors, 1 440 000 raw rows, four project windows | TimescaleDB | 1.99–2.02 s | 2.00–2.07 s |
| same | plain PostgreSQL | 1.06–1.13 s | **2.07–2.49 s** |
| status-page projection, 500 monitors | TimescaleDB | 0.76–0.81 s | 0.79–0.86 s |
| same | plain PostgreSQL | 2.14–2.20 s | 2.41–2.53 s |

EXPLAIN: the per-monitor `min(ts)` probe in `rs` touches every daily partition's index plus DEFAULT on
plain PostgreSQL (not one seek), while `cov`'s EXISTS and the rollup read do not execute for a
raw-covered window. So large projects on plain PostgreSQL pay roughly twice for the project SLA
read. Not a production latency measurement; recorded as a known cost in D-0268, not fixed here.
