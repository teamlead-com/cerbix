  So not a hole: the forward pass itself stopped.

  restart at 19:44:08 CEST the only one (142 in four minutes), is `service_slice_failed … store:
  compute sealed_through: canceling statement due to statement timeout (SQLSTATE 57014)`. The
  journal does not reach 2026-09-24, so the first failure itself was not seen.

  (51 820 buckets since era start), 63 ms for another (33 255) — sequential, whole-era, window-function sort. The

- During the session the v0.3.6 rollout was in progress (scheduler and worker stopped 19:35:45, api
  started 19:37:58, scheduler restarted 19:44:08); that is the operator's rollout, not part of the

- History: the only related change, `dc6246d` (in v0.3.5), bounded the carry-in lookup — another
  statement of the same slice. No other branch carried a fix.

## Invariant audit (before changing the computation)

Starting at the watermark is equivalent to starting at the era only if nothing behind the watermark
can become missing or unsealed without the watermark moving back. Every writer was read:

| Path | Effect behind the watermark |
|---|---|
| `materializeBucketTx` (forward, repair, recompute) | Writes sealed: `seal := now ≥ end + LateArrivalGrace`, and a bucket behind the watermark ends before `now − grace`. |
| Retroactive maintenance (`servicemaintenance.go`, "Rewind the watermark") | Sets `sealed_through = LEAST(…, rangeStart)` and records `retracted_at/retracted_to` in the same transaction that queues the repair. |
| New era (`services.go`) | Sets `sealed_through = NULL`; the walk restarts at the new era start. |
| DEFAULT-partition adoption (`retention.go`) | Moves rows into the new partition in one transaction (`DELETE … RETURNING` + `INSERT`) — no row disappears. |
| Fact partition drop / detach | None exists for `service_reliability_buckets` (only the gate ledger detaches partitions). |
| `UPDATE service_reliability_buckets` | None. |

## RED

`TestForwardAdvanceKeepsUpWithALongEra` before the code change — FAIL on both storage modes with the
instance's own error: "slice 0 failed: store: compute sealed_through: ERROR: canceling statement due
to statement timeout (SQLSTATE 57014)". Its first version (cursor 30 minutes behind) failed on
TimescaleDB but PASSED on plain PostgreSQL: the work loop finished early and the recompute got most
of the slice, not the reserve. The fixture now adopts three days back and puts the cursor two days
behind, so the work loop runs to the reserve as it does on the instance — only that version is RED
evidence. `TestIncrementalWatermarkStillStopsAtAHoleAhead` passes on the old code (a guard).

## GREEN

Both tests pass on TimescaleDB and plain PostgreSQL 16.

**One existing test changed meaning, recorded rather than patched over.** The service regression
set (materialization, watermark, repair, maintenance, annul, era, backfill, late data, burn, gate,
report, slice, declaration) on both storage modes failed exactly one test: `TestSealedThroughStopsAtAHole`
— "sealed_through = …21:34, want the hole at …17:31 — the watermark jumped a gap". It deleted a sealed
bucket BEHIND the watermark with raw SQL and expected the recompute to move the watermark back to it.
No product path deletes or unseals a fact behind the watermark (audit above), and a backwards move
without a recorded retraction is what invariant 17 forbids — the test pinned the old full walk's side
effect, not a product behaviour. It now leaves a slot unwritten AHEAD of the watermark through
`MaterializeServiceRange` and asserts the watermark stops there; it keeps its name because invariant
17's traceability row cites it. It passes on the old code too (a guard for the hole case, not RED
evidence). D-0269 states what is given up.
