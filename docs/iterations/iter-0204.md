## Evidence (read-only, on the pilot, 2026-10-08)

Every PostgreSQL session ran with `default_transaction_read_only=on` and a 60 s statement timeout;
only `SELECT` and `EXPLAIN ANALYZE` of `SELECT` were run; the API journal was read with `sudo
journalctl`; nothing on the host was changed or restarted. Plain PostgreSQL 15.19, migration 110,
965 028 heartbeats (30-day raw retention reached), 13 monitors, one maintenance window in total.

| Request (API journal, last 7 days) | p50 | p95 |
|---|---|---|
| `GET /status-pages/{id}/render` | ~1 600 ms (200s only) | 2 038 ms max |
| `GET /projects/{id}/sla` | 869 ms | 984 ms |
| `GET /monitors/{id}/sla` | 138 ms | 231 ms |

Not a v0.3.8 regression: the render was 1.5–1.7 s on 2026-10-07 too (v0.3.8 cut its size from
330 KB to 37 KB, not its time), and the project SLA was ~870 ms all week. On 2026-10-07 the render
rose from 0.4 s to 1.6 s within nine minutes, while v0.3.7's materialization catch-up ran.

`EXPLAIN ANALYZE` of the statements, rebuilt from the code with the pilot's ids ("buffer" counts are
shared buffer accesses — hits plus reads — not reads from disk):

- **Status page monitor projection** (6 monitors, 90 days, 521 396 heartbeats): 1 500 ms, 1 574 271
  shared buffer accesses, of which 1 564 188 in a Bitmap Heap Scan of `maintenance_windows` looped 521 396
  times — one probe per heartbeat.
- **Project SLI, 30d** (686 885 heartbeats): 488 ms, 1 384 860 shared buffer accesses, 1 373 772 of them in an
  Index Scan of `maintenance_windows` looped 686 885 times. The four windows of one request: 26 + 95
  + 440 + 443 ≈ 1 000 ms, matching the journal.
- Hypothesis, measured the same way on hand-written prototypes of the shape (not the shipped
  statements, not an endpoint benchmark): windows of the scope pre-selected into a MATERIALIZED set —
  the projection 440 ms with ~10 k shared buffer accesses; the project 30d window 266 ms. The effect
  on the pilot's endpoints is to be measured after deployment.

## Tests

**Store** (`internal/store/maintexclusion_internal_test.go`, both storage modes):

- `TestMaintenanceExclusionIsTheSameRuleForEveryReader` — the rule, for all eight readers: start
  inclusive, end exclusive, a cancelled window ending at its cancellation, a project window applying
  to both monitors of its project and to no other project, a monitor window applying to no other
  monitor. Passed on the old SQL (it is an equivalence guard) and on the new.
- `TestMaintenanceWindowsAreReadOncePerStatementNotPerHeartbeat` — `EXPLAIN ANALYZE` of each of the
  eight statements (as revised in review round 1, below: at 1 000 and again at 3 000 heartbeats per
  monitor; the reads may not grow and may not exceed one per monitor in the database).
  **Its first run passed against the unfixed SQL**: on a small test table the planner preferred one
  materialized seq scan, hiding the problem. The test now runs under `enable_material = off` and
  `enable_seqscan = off`, which reproduce the plan the pilot's planner chose on its own; the fixed
  statements must hold whatever the planner prefers. **RED:** all eight read the table once per
  heartbeat (3 000 or 6 000 times). GREEN after the fix.
- Mutations of the shared fragment, each killed: project windows dropped; project windows not bound
  to the monitor's project; cancellation ignored; end inclusive; start exclusive (all by the
  equivalence test); `MATERIALIZED` removed (by the read-count test).

**API** (`internal/api/api_slawindow_test.go`): absent, single, comma-separated, repeated and
duplicated `window` on both endpoints — windows returned in standard order and exactly that many
SLI computations; `1y`, `30d,bogus`, empty and `30D` refused with `invalid_window` and no computation.
RED: all named-window cases returned four windows with four computations.

**Frontend** (vitest, `DashboardOnboarding.spec.ts`): the dashboard's two SLA requests carry
`window: ["30d"]`; the mutation dropping it from the monitor request is killed.

## Review round 1 — CHANGES REQUIRED (P1 1, P2 1, P3 1)

| # | Sev | Finding | Disposition |
|---|---|---|---|
| R1-1 | P1 | The three "today from raw" readers filtered heartbeats with `h.ts >= (now() AT TIME ZONE 'UTC')::date` — a DATE, which PostgreSQL turns into midnight in the **session's** `TimeZone` — while the new window pruning used the UTC boundary. On a session east of UTC a maintenance window just before UTC midnight was pruned although the heartbeat filter still read heartbeats inside it (reviewer: 1/1 → 1/2 under Asia/Tokyo). | **Fixed:** the heartbeat filter of `monitorTodaySQL`, `projectTodaySQL` and `monitorPageDailySQL` uses `todayStartUTC`, the same expression as the pruning. This also fixes a **pre-existing** defect, now BUG-0204-3: the filter has always been session-zone dependent, and the pilot's PostgreSQL runs in `Europe/Moscow` (the application does not pin `TimeZone`), so its live "today" has counted 21:00–24:00Z of the previous day — already in that day's rollup row — and a negative zone loses today's first hours. CHANGELOG "Fixed" entry. |
| R1-2 | P2 | `newMaintFixture` slept up to five minutes after UTC midnight, longer than the test's 60 s context. | **Fixed:** no waiting. The fixture anchors every timestamp on the start of the current UTC day (`dayStart + offsets`); heartbeats may lie in the future shortly after midnight, which no reader bounds. The rollup runs over `[dayStart, dayStart + 24 h)`. The read-count test inserts at `dayStart + g s`, measures at 1 000 and 3 000 heartbeats per monitor, and asserts the reads neither grow nor exceed the monitors in the database (3) — a bound explained by the scope instead of a bare 5. Residual: a run that straddles UTC midnight inside the ~1 s of one test can still see two different "todays"; nothing waits for it. |
| R1-3 | P3 | CHANGELOG, this report and D-0271 said "read once per request", called buffer accesses "reads", and presented prototype timings as the fix's effect. | **Fixed:** "materialized once per SQL statement; the reads of `maintenance_windows` no longer grow with the heartbeats"; "shared buffer accesses"; prototype timings labelled as such, not an endpoint benchmark; the effect on the pilot is to be measured after deployment. D-0271 also corrects the project 30d window's old timing (488 ms in the EXPLAIN, not 440). |
| — | note | The reviewer, like this iteration's own full run, saw `TestGateMaintCrashAfterEveryRemovalStatementConverges/after_drop.gate` fail on TimescaleDB. | Recorded as **FLAKE-0204** in `status.md`: in isolation at `-race -count=10`, 2 of 10 on this branch and 1 of 10 on `f5240f5` (v0.3.8, a `git archive` export) — pre-existing, in gate-maintenance code this iteration does not touch. |
