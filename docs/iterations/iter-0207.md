## Why

The tests that write decisions run before them, so on a retained test database idle for more than a week, today's partition does not exist. The calendar removes it, not a test. | Found and reproduced by the iter-0206 reviewer (drop today's partition → the `Decision` subset fails with this exact message; one maintenance test restores it). | FLAKE-0201 | `TestAuditRetentionPostgreSQLMatrix` (probe `DROP DATABASE … WITH (FORCE)` timed out at 15 s) | `DROP DATABASE` waits for an immediate checkpoint; the checkpointer was in `IO/DataFileSync`. | FLAKE-0203 | `TestGateMaintADropIsDeferredWhileAnOlderTransactionIsOpen` ("dropped 0 day(s) after the older transaction ended") | The drop gate (D-0225) defers while ANY other backend of the database holds a transaction older than the detach. The shared test database always has other backends whose transactions can be older than that: **autovacuum workers vacuuming `pg_catalog`** (`pg_attribute`, `pg_constraint`, `pg_class` — the test databases' catalogs are bloated by the suite's DDL churn; `pg_class` is 632 MB on the TimescaleDB container) and, under IO load, **a probe's `DROP DATABASE` waiting for its checkpoint**. | Round 1 of the review: one convergence waited ≥ 25 s on autovacuum of `pg_class`/`pg_attribute`. The `DROP DATABASE` holder was caught only by this iteration's own IO-load loop (the audit-retention probe looping against the same server, 4–8 failures of 25); in a full run `internal/cli`'s probes finish within the first seconds and were never seen holding the gate. |
| FLAKE-0204 | `TestGateMaintCrashAfterEveryRemovalStatementConverges/after_drop.gate` (and its sibling `after_drop.commit`, the roadmap's flake) | The same drop gate, in two places: the crash-injection loop (20 × 250 ms) and the converging pass after the crash, both on a detach stamped a moment ago. | Reproduced under the IO-load loop: `after_drop.gate` 4 of 25 at first; after fixing only the converging pass, `after_drop.commit` failed at 5.45 s — the 5 s injection bound. |

What backdating does NOT do: it does not weaken the deferral contract. The deferral is still pinned
deterministically — the test's own open transaction closes the gate (0 dropped), and now the test also
proves that backend is one the gate reads. What the backdated second halves prove is "no backend older
than the detach → the pass drops", not that the test's own commit is what opened the gate; with other
sessions on a shared database that narrower statement is the one a test can make reliably. A backend
holding a transaction for 25 hours on a test database fails the test loudly, with the holder logged.
