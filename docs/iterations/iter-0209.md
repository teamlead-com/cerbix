## Origin

[`sec-hardening-2.md`](../specs/sec-hardening-2.md) revision 7, approved by the owner on 2026-11-13, §5 row 1, covers three findings:
- **H-1 (P0).** A realm JWT minted for any client authenticated as the human whose `sub` it carried.
- **H-5 (P1).** A password reset kept the account's sessions alive.
- **H-6 (P1).** Unbounded bodies and passwords reached Argon2id, and `reset/confirm` had no limiter.

Iterations 2–4 are untouched. The implementation plan is
[`plan-sec-hardening-2-iter1.md`](../design/plan-sec-hardening-2-iter1.md).

   `mail.spec.ts` to reset "a dedicated `e2e-` user", but cerbix has no product path that creates a

3. **No subagents** after the mock. The owner asked the controller to implement inline.
4. **The mock** [`mock-machine-clients.html`](../design/mock-machine-clients.html) was approved as

## Changes

- **H-1.**
  - Migration `00112` adds `users.kind` (`human`|`machine`) with the spec's narrow backfill, and
    `oidc_settings.machine_clients`.
  - `UpsertUserByOIDCIdentity` is replaced by `UpsertMachineUserByOIDCIdentity`, which refuses a
    human row and rolls back, and `UpsertHumanUserByOIDCIdentity`, which uses `FOR UPDATE` plus
    `ON CONFLICT DO NOTHING` and retries the locked branch. The human upsert flips a machine row to
    human, deletes its grants, clears `is_global_admin`, and writes the audit rows.
  - `machine_clients` is wired through the YAML, DB, settings API and runtime. One normalization
    applies everywhere, and the interactive `client_id` is refused.
  - `principalFromJWT` moved to `internal/auth/machine.go` and enforces the client claim, the
    delegated markers and the machine-only subject. It re-reads `kind` after the memberships.
  - The refusal log `oidc_bearer_refused` and the metric `cerbix_oidc_bearer_refused_total{reason}`
    are added. The callback logs `oidc_machine_became_human`.
  - `PATCH /admin/users` refuses the global-admin flag for a machine.
  - The SPA gains the Machine clients field and the `machine` badge.
- **H-5.** `ResetPasswordWithToken` deletes every session in its transaction. `store.ChangePassword`
  sets the hash and revokes the other sessions in one transaction, and `changePassword` answers 500
  on a failure instead of swallowing it. `mail.spec.ts` resets the seeded user and asserts that a
  second reset ends the session the first one opened.
- **H-6.**
  - `MaxPasswordBytes = 1024` is enforced in `HashPassword`/`VerifyPassword`.
  - `/auth/local/*` reads at most 4 KiB, and `APIRouter` caps API bodies at 1 MiB.
  - Three limiters (`authLimiters`): per IP before the body is read, per (IP, email), and per email
    counting failures only. `reset/confirm` is now limited.
- **Docs.**
  - OpenAPI with regenerated `schema.d.ts`; `docker/config.example.yaml`; runbook (machine clients,
    refusal table, limiters); `sec-authn-authz.md`; overview; CHANGELOG; traceability.
  - Spec status line, and five line citations in the spec that this iteration's edits moved. Three
    belong to iterations 2–4 and now point at the code's current lines. Two are historical H-1
    citations; they now name the code's new home.

## Client-credentials token shapes, per provider (spec H-1 fix 3)

This table was taken from each provider's documentation on 2026-11-13. No live token was inspected,
so the next operator to list a client should confirm it against a decoded token.

| Provider | Client claim | `sub` | `nonce` / `sid` | `scp` | A delegated token from the same client | Fit with the S1 rules |
| --- | --- | --- | --- | --- | --- | --- |
| Keycloak (≥ 12, default) | `azp` = client id; recent versions also `client_id` (same value) | UUID of the client's service-account user | absent: the grant creates no user session, and `session_state` was removed from all tokens in 25.0 | `scope` (string), no `scp` | auth-code tokens carry `sid`, with the human's `sub` | Accepted. **Caveat:** with the legacy "Use refresh tokens for client credentials grant" switch on, the grant opens a user session and its tokens carry `sid`, so they are refused as `delegated_sid`. The runbook says to keep it off. |
| Okta, custom authorization server | `cid` = client id (no `azp`) | the client id by default (configurable) | absent | `scp` (array) | `cid` = client, `sub` = the user's login → `delegated_cid_sub` | Accepted while `sub` keeps its default; a custom `sub` expression makes `cid ≠ sub`, so the token is refused. The runbook says to keep the default. |
| Okta, org authorization server | `cid` | client id | absent | `scp` | as above | Okta documents org-server access tokens as not meant for third-party validation; use a custom server. |
| Entra ID v1.0 access token | `appid` | object id of the service principal | absent | none; app permissions arrive in `roles` | `scp`, the user's `sub`/`oid`, no `nonce`/`sid` by default | Accepted (`appid`). |
| Entra ID v2.0 access token | `azp` | object id of the service principal | absent | none (`roles`) | as v1, with `azp` | Accepted (`azp`). **Residual:** the markers do not catch a delegated Entra token, so a dual-purpose listed client relies on rule 5 (a human `sub` gets 401) and on the runbook rule that a listed client is service-only. See "Found on the way". |
| Google (service account) | no client-credentials grant; a service account presents an ID token from `generateIdToken`, or a self-signed JWT, with `azp` = the account's unique id | the account's unique id (= `azp`) | absent | none | n/a | Accepted when the unique id is listed. With `includeEmail`, `email` is the account's real address. That is the documented mis-filing: a pre-existing row is filed `human` by the narrow backfill and refused `subject_is_human` until the operator deletes it (CHANGELOG upgrade note). |

Whether `scp` appears differs by provider (Okta yes; Keycloak and Entra app tokens no), which
confirms the spec's refusal to make `scp` a rule.

Sources:
- Keycloak release notes 25.0 and upgrading guide: `session_state` removal, no user session for
  client credentials.
- keycloak/keycloak#53682: a client-credentials token has no `sid` unless the refresh-token switch
  is on.
- developer.okta.com OAuth claims reference (`cid`), and Okta developer-forum answers (`sub` = client
  id for client credentials).
- learn.microsoft.com access-token claims reference: `appid` in v1, `azp` in v2, `idtyp`, `roles` vs
  `scp`.
- docs.cloud.google.com, token types and `generateIdToken`: `azp` = `sub` = the unique id,
  `includeEmail`.

## Found on the way, left alone (not in H-1/H-5/H-6)

- `docs/status.md` (FR-004 and #12 rows) still names `UpsertUserByOIDCIdentity`, which this
  iteration replaced. The rows are historical status, and the docs check does not flag symbol names.
  They are left for the next status sweep.
- `/auth/local/login` answers a malformed body with `http.Error` (`text/plain` carrying a JSON
  string), unlike its siblings' `writeJSONError`. This predates the iteration and is not changed.
- **Entra ID delegated access tokens** carry no `nonce` or `sid` by default, so the delegated
  markers do not catch a dual-purpose listed Entra client. Rule 5 (a human `sub` gets 401) and the
  runbook's "service-only client" rule close it. `idtyp=app` would be a precise marker but is
  optional by default. It is noted as a candidate for a later spec, not adopted here.
