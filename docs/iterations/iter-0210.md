## Review finding: a percent-encoded RabbitMQ path was encoded twice (fixed)

The owner's review of the branch found a regression of this iteration's `rabbitMgmtURL`. It built
the URL from the **decoded** path only, so `url.URL` re-encoded it:
- `/api/aliveness-test/%2F` (RabbitMQ's default vhost) went out as `%252F`;
- `/api/queues/my%20vhost/q` went out as `my%2520vhost`;
- a URL target's encoded base path (`/pre%2Ffix`) was decoded to `/pre/fix`.

On `main` these reached the server as configured, and such monitors would have gone DOWN after the
merge.

**Fix** (`f987216`, now `780bfec`; test first; all four tests were RED):
- `domain.ParseRabbitMgmtPath` parses the path as a URL reference. It refuses a parse failure, an
  invalid percent sequence in the path or in the query (`%zz`, `%2`), and a reference naming a
  scheme, host or userinfo. `ValidateRabbitMgmtPath` applies it, so the write surfaces refuse
  `%zz` too, and no error echoes the input.
- `rabbitMgmtURL` builds the URL with `Path` and `RawPath`: the escaped base path without its
  trailing `/`, plus the escaped reference path. `RawQuery` comes from the reference.
- It is still a `url.URL` and never concatenation, so the S2 guard against an authority swap holds.

**Tests:**
- `TestRabbitMgmtURLKeepsPercentEncoding`: host, `host:port`, a URL with a base path (the proxy
  prefix kept) and an encoded base path, with and without a query.
- `TestRabbitMgmtPathReachesTheWireByteForByte`: an `httptest` server compares `r.RequestURI` and
  `r.URL.EscapedPath()`.
- `TestRabbitMgmtInvalidEscapeRefused` (prober) and `TestValidateRabbitMgmtPathPercentEncoding`
  (domain).

In the same round: `gofmt` of `internal/auth/fakestore_test.go` (`bf9d81c`, now `91fe5f5`), and the

**P1-1 — two parsers for one RabbitMQ management target** (`e3896ce`).

**P1-1 — the 00113 → 00115 chain broke websocket targets with a leading tab, LF or CR**
(`f974cb6`).
- The cause: `btrim(target)` with one argument trims only spaces, so the first 00113 took
  `"\nwss://chat/ws"` for a scheme-less target. It became `ws://\nwss://chat/ws` without
  `tls_skip_verify`, and the first 00115 turned that into `ws://wss://chat/ws`: unparseable and
  DOWN. Reproduced: RED on every such row.
- The fix, in place (the branch is unmerged):
  - 00113 trims `E' \t\n\x0b\f\r'` in both conditions and in the assignment.
  - **VT is `\x0b`, not `\v`.** In a Postgres string literal `\v` is the letter v. The review's
    suggested `E' \t\n\v\f\r'` would have trimmed a trailing v too: checked on Postgres,
    `btrim('v/dev'||chr(11), E' \t\n\v\f\r')` = `/dev`. The regular expressions in 00115 keep
    `\v`, where it is the regex engine's vertical tab (also checked).
- 00115 now repairs a database that ran the first 00113:
  - `^ws://[whitespace]*((ws|wss|http|https)://)` collapses to the scheme the operator wrote;
  - a wss/https row gets `tls_skip_verify: "true"` unless it carries the key.
- **A deliberate narrowing of the review's wording.** The review asked for the key on every
  `^(wss|https)://` row without it. 00115 gives it only to the rows the first 00113 damaged. A
  wss monitor saved after that migration without the key chose verification. Turning
  verification off for it silently would be a downgrade, so it is left alone, and the test pins
  that.
- `TestWebSocketMigrationChain` covers two starting points:
  - **The fixed chain:** 00113 → 00114 → 00115 in order, twice, on `\nwss://…`, `\tws://…`,
    `"  \nhttps://…"`, `\rHTTPS://…\r\n`, a scheme-less target with a leading LF, and two
    targets ending in v (the VT trap).
  - **After the first 00113:** rows in the state the first 00113 and 00115 left, then only the
    new 00115.

  Every result parses with `ParseWebSocketTarget`, and every wss/https row carries the key. It
