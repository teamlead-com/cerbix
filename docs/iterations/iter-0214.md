## Changes

- **Schema** (migrations `00117_monitor_recovery_threshold.sql` and `00118_monitor_recovery_run_guard.sql`).
  - **Columns** (00117). `recovery_threshold integer NOT NULL DEFAULT 1`, `consecutive_successes integer NOT NULL
    DEFAULT 0`, `recovery_started_at timestamptz NULL`.
  - **CHECKs.** `monitors_recovery_threshold_range` (1..10); `monitors_recovery_threshold_type` (exactly 1
    for push and composite); `monitors_recovery_run_state` (no run, or `down` with a run and a stamp).
  - **Reads and writes.** `monitorColumns` and `scanMonitorAs` read the three columns at the end. Create and
    update write `recovery_threshold` only; the other two are server-owned.
  - **Guard** (00118, revision 7, I13a). A `BEFORE UPDATE` trigger on `monitors`,
    `monitors_recovery_run_guard_trg` (function `monitors_recovery_run_guard()`), clears
    `consecutive_successes` and `recovery_started_at` whenever the new status is not `down`, before the
    CHECK is evaluated. It exists for writers this code does not control; every writer here still resets
    the run itself. Down drops the trigger and the function.
- **Domain.**
  - **Rule.** `Monitor.Validate` holds it; `Normalize` does not clamp.
  - **Field classes.** `RecoveryThreshold` is `SemanticDelivery`; `ConsecutiveSuccesses` and
    `RecoveryStartedAt` are `SemanticRuntime` (`internal/domain/execsemantics.go`).
  - **Snapshot.** `internal/domain/recovery.go`: `RecoverySnapshot`, `MonitorTransition.Recovery`, and
    `Sentence`, the one rendering.
- **Store** (`internal/store/monitors.go`).
  - **The run.** `recordCheckStatusTx` applies the §4.1 table in its single UPDATE:
    - a success that does not complete the run keeps `down`, increments `consecutive_successes`, stamps
      `recovery_started_at` once with `statement_timestamp()`, and keeps `last_notified_at`;
    - the completing success returns the snapshot. It goes on the transition event only for a run longer
      than one, so a threshold-1 payload is unchanged.
  - **The wrapper.** `RecordCheckStatus` keeps its signature, drops the snapshot and gains its own
    `SELECT … FOR UPDATE`.
  - **Pauses.** `EnqueueRenotifyReminders`, and the monitor-incident query of `AdvanceEscalations`
    (`internal/store/escalation.go`), gain `consecutive_successes = 0`. The service-incident query is not
    changed.
  - **Resets.** The re-enable in `updateMonitorTxPrepared`, `RetireMonitor`, `ReactivateMonitor` and
    `SetMonitorStatus` (off `down`) reset the run in the same statement.
- **Ingest, notify, outbox.**
  - **Ingest.** `Reconciler.Reconcile` takes the snapshot from `ResultOutcome`, and `resolveAutoIncident`
    appends the sentence to the resolving update.
  - **Notify.** `notify.Dispatcher.Deliver` takes the snapshot and appends the sentence to every channel's
    text. The email Subject and the webhook keys are unchanged.
  - **Outbox.** The worker passes `MonitorTransition.Recovery()` to `Deliver`. A legacy event has no
    snapshot and renders today's text.
- **API** (`internal/api/handlers_monitors.go`).
  - **Create and update.** `createMonitor` resolves an absent value to 1, `updateMonitor` to the stored
    value, and both copy an explicit one verbatim for `Validate`.
  - **Test-connection.** `testMonitor` builds its probe monitor at 1, and `TestMonitorSpec` is not extended.
  - **`openapi.yaml`.** It gains the three fields; the TS schema is regenerated.
- **File provider.**
  - **Decoding.** `recovery_threshold` joins the common monitor fields in every bundle format.
    `applyCommonMonitorFields` resolves absent to 1.
  - **Canonical form.** `canonicalMonitor` carries the field `omitempty`, populated by
    `hashedRecoveryThreshold` only above 1.
- **SPA.**
  - **Shared module.** `frontend/src/lib/monitorRun.ts` holds `confirmingLabel` (moved unchanged from
    `MonitorsView.vue`), `recoveringLabel` and its tooltip, `soakWarning` (at 600 s),
    `dependencyHintShown` and `hasRecoveryThreshold`.
  - **Form** (`NewMonitorView.vue`). The field sits under Confirmations, with the warning and the hint.
    Push and composite get no field and no key on create, on edit and after a type switch. In the
    multi-region set the children carry the value and the composite parent none.
  - **List** (`MonitorsView.vue`). The `recovering N/M` chip sits beside the Down pill.
  - **Page** (`MonitorDetailView.vue`).
    - **Header.** Both labels.
    - **Live status event.** It zeroes `consecutive_successes`, and on a move into `up` also
      `consecutive_failures`.
    - **Configuration.** A Recovery threshold row after Failure threshold, absent for push and composite.
- **Existing tests moved.**
  - **Fixtures.** The in-process monitor fixtures in `internal/store`, `internal/domain` and `internal/api`
    set `RecoveryThreshold: 1` on the literal. No fake store defaults it.
  - **`TestEveryDeclaredTypeCarriesEveryCommonField`** branches by type: push carries 1 and refuses 3
    separately.

### Stage-1 tails: the regression harness

Two points the stage-1 report left open, taken up in stage 2 (`b35c214`).

**`expected_runs.issued_at` — the premise was wrong, the gap was real.** The stage-1 note that `issued_at`
stays NULL in the harness was a misreading: `Store.ConfirmExpectations` (`confirmExpectationsSQL`, the only
writer) runs after the tick's publishes in `Scheduler.publishPending`, and the harness replaced a present
value with a marker (`time.Unix(0,0)`) that its failure dump printed as a zero time. On the tree every filled
window had it on both sides (16 of 16). A scripted result recorded before the confirm is harmless:
`fillExpectedRunTerminalSQL` leaves `issued_at` alone on a reserved row, and role=all is wired the same way.
No production defect. The real gap: the comparison was by presence only, so NULL on both sides passed — the
committed test stayed green with `ConfirmExpectations` stubbed to a no-op while 16 of 16 windows were NULL.
The test now requires `issued_at` on every window a scripted result filled, at or after its `reserved_at`
and before the side's next reservation. One more divergence from production was closed: the scripted
executor never sent the run claim (`dispatch.ClaimHeartbeat` → `Store.RecordRunClaim`, which
`Consumer.handleClaim` makes in production), so `claimed_at` was NULL on both sides; it now sends it, and
`claimed_at` is required and compared by presence.

### Revision 7: writers that do not know about the run

The stage-2 report raised that a binary without FR-043 writes `status` and never the run columns, so for
a monitor in a run the run-state CHECK refused its status write and the heartbeat in the same transaction.
The owner rejected the documents-only mitigation (2026-11-16); migration
`00118_monitor_recovery_run_guard.sql` adds a `BEFORE UPDATE` trigger that clears the run whenever the new
status is not `down` (spec revision 7, §5, I13a, §11). The CHECKs are unchanged and every writer of this
release still resets the run itself.

**The status writers of b823aca**, found by reading every `UPDATE monitors` in the non-test code at that
commit: `recordCheckStatusTx` (success → `up`, failure → `down` or unchanged; reached by
`RecordScheduledResult`, `RecordPushResult`, `RecordDeadmanResult` and `RecordCheckStatus`), the re-enable
in `updateMonitorTxRow` (→ `pending`; API update and Monitoring-as-Code apply/restore), `RetireMonitor`
and `ReactivateMonitor` (→ `pending`), and `SetMonitorStatus` (any status; no production caller).
Disabling a monitor and a maintenance window write no status. The other `UPDATE monitors` statements
(`superseded_by_service_id`, `last_result_ts`, the probe error, `state_sequence`, `last_notified_at`,
