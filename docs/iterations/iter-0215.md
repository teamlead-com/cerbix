## Changes

- **Schema** (migration `00119_incident_impact.sql`). Three columns, each with a closed CHECK wrapped in
  `COALESCE(…, false)` and guarded by `CASE` (a CHECK that evaluates to NULL passes, and `AND` has no
  promised order):
  - `services.impact_by_state jsonb NULL` — NULL is the D6 defaults; an object has exactly the keys
    `degraded`, `down`, `unknown`, each an impact word (`services_impact_by_state_chk`). Not in the
    `service_alert_config_bump` trigger (D9).
  - `projects.default_incident_impact text NOT NULL DEFAULT 'major'` (`projects_default_incident_impact_chk`).
  - `incidents.impact_basis jsonb NULL` — the two shapes of D8, closed (`incidents_impact_basis_chk`).
    NULL for every incident that predates the migration; nothing is backfilled.
  - Down drops the three columns and their CHECKs. `heartbeats` is not touched; the three tables are
    ordinary tables in both storage modes.
- **Domain** (`internal/domain/incidentimpact.go`). `IncidentImpact.Rank`, `ImpactMapping`
  (`DefaultImpactMapping`, `Resolved`, `Validate`, `For`), `ImpactBasis` and its sources,
  `ImpactRaise`, `ImpactRaisedMarker`, `ImpactRaisedNote`, `ServiceIncidentOpeningNote`.
  `Incident.Validate` allows an empty impact only for a monitor-anchored `auto` incident (R1).
  `IncidentEvent` gains the optional `impact_raised`. `domain.Incident` has no basis field (D15).
- **Store.**
  - **Mapping** (`impactmapping.go`, `servicealertpolicy.go`). Read resolves NULL to the defaults; a
    write stores NULL for the defaults (R3); `alertPolicyDiff` adds one `impact_by_state:` segment, last

  - **Monitoring-as-Code** (`fileapply_alerting.go`). The mapping joins the three column lists: the
    unlocked pre-filter `alertPolicyMatchesTx`, the locked re-read and the UPDATE.
  - **Opening** (`serviceincidents.go`, `incidents.go`). `OpenServiceIncidentTx` takes the state and the

### The controller's rulings

- **The project-default write keeps `FOR UPDATE`, as §4.4 says.** The final branch review suggested
  `FOR NO KEY UPDATE`, which would not block the `FOR KEY SHARE` lock that a child-row insert (an
  incident, monitor or service of that project) takes for its foreign key. The ruling keeps the spec's
  wording; `TestTheProjectDefaultWriteLocksTheRowBeforeReadingIt` pins the lock. Cost if wrong: while a
  project PATCH is in its (short) transaction, inserts of that project's child rows wait for it. (The
  rise step's `FOR UPDATE` is not a ruling: §4.3 prescribes it.)
- **The NFR-035 reader scan works per function and per rule, not per file** (`468e420`). The plan
  allowed whole files; an allowed file such as `store/statuspagecontext.go` also holds the gate's
  incident lookup, so a predicate on impact added there would have passed. Each allowed entry is now a
  scope (function, method expression or package-level identifier) and a rule (`selector`,
  `sql-literal`, `incidentColumns`), and a `+` chain of literals is judged as one statement. Cost if
  wrong: a renamed function in an allowed file fails the guard until its entry is renamed — loud, and
  in the safe direction.
- **Citation upkeep in `sec-hardening-3.md:907`** (`4b66783`). Task 1 moved `domain.ServiceAlert.Message`
  from `servicealert.go:355` to `:368`; the citation was repointed in this branch rather than left for a
  later sweep. Cost if wrong: none to the code; a stale line would mislead a reader of that spec.
- **The third round of the P2-1 answer (`c3f485a`) is the reviewer's own proposed rule, applied as
  written and not re-reviewed.** Cost if wrong: a regex in a test file that no second reader checked; a
  wrong rule fails a guard loudly or misses a read the other rules still see.

- **The Incidents card with no project says "Select a project to manage its incident settings."**
  (confirming pass, P2-2), mirroring `SecretsPanel`'s empty state; the mock draws no such state. Cost if
  wrong: one sentence in one card.

## Known limits

- **The guard scans are heuristics** (the "Known limits" comment in
  `internal/store/impactguard_internal_test.go`):
  - SQL assembled any other way than a `+` chain of literals — `+=` on a variable, `fmt.Sprintf`,
    `strings.Join`, a `strings.Builder` — is judged only as its separate literals, so a statement whose
    verb and `impact` land in different literals is not seen;
  - `SELECT *` (or `x.*`) from incidents, and a column list in a constant not named `incidentColumns*`,
    read impact without naming it;
  - a serialized incident (`json.Marshal` of a `domain.Incident`, a template) carries impact to code
    that never writes `.Impact`;
  - a column with a bare alias and only a comma or a keyword before it (`SELECT id, impact sev FROM
    incidents`) reads as prose and is missed; `impact AS sev` is seen;
  - a set, pattern or range test on the column is seen in any text with a keyword, a shapeless
    fragment such as ` AND impact IN ('major')`, ` AND impact NOT IN ($1)`, ` OR impact LIKE 'crit%'`,
    ` AND impact ILIKE $2` or ` AND impact BETWEEN $1 AND $2` included, only when the operator is
    followed by SQL-shaped material: `IN (`; `[I]LIKE` and a quoted literal, `$n` or `?`; `BETWEEN x
    AND` with x a quoted literal, `$n`, `?` or a number. In a fragment with no statement shape, a test
    whose operand is anything else is missed: `IN ` with its parenthesis in another constant (`IN (` +
    list + `)` is seen, `IN ` + list is not), `impact LIKE prefix || '%'`, `impact BETWEEN lo AND hi`,
    `impact SIMILAR TO …`. With a statement shape, `IN`, `[I]LIKE` and `BETWEEN` after a keyword are
    seen whatever follows;
  - known false positives: prose that puts the column next to an operator, an `IS` test, or a set,
    pattern or range test with SQL-shaped material after it ("and the impact in (most) cases", "and
    impact between 2 and 3 hours") is reported when the text has a keyword; prose with only commas or
    keywords around the column is reported only when the text also has a statement shape, so "when
    impact is in doubt" is not; an UPDATE of incidents with `impact = …` in its WHERE is counted as a
    write. Each fails loudly, the safe direction.
- **The behavioural regression is the second line.** What the scans cannot see, the NFR-035 regression
  compares on outputs: two services identical but for the mapping, driven through the same outage,
  produce the same reliability, alerting, gate, delegation, suppression and escalation outputs, and
  differ only in the incident's impact.
